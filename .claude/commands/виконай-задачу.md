# Execute a task

**Required argument: the task file path** (`$ARGUMENTS`; @-mention or plain
path). If it is missing — **STOP** and ask the owner (in Ukrainian): «Вкажи файл
задачі (шлях або @-mention)». If it is a plain path, read the file with Read.

Task file:

$ARGUMENTS

## Role

You are the **orchestrator and validator**. You hand the working steps to
Workflow agents, but **you make the decisions yourself**: what to do, in what
order, and what to do when the plan has diverged from the code. You orient and
check the plan **before** writing the script — otherwise the workflow shape is
fixed blind and no finding inside it can change it any more.

Talk to the owner in Ukrainian. Everything the agents produce follows the
language rule in `AGENTS.md`: code comments in Ukrainian and explain WHY;
consumer-facing text (README, public API, JSDoc, package skills, CLI messages)
in English; internal docs (specs, plans, BRD, roadmap) in Ukrainian; commit
descriptions in Ukrainian after a Conventional Commits prefix, no
`Co-Authored-By` / `Generated with` trailers.

---

## Step 0 — check the plan against the code (YOU do it, before any Workflow)

The procedure is the **`codebase-research`** skill; only what is specific to
starting a task is here. Cheap and mechanical, without pulling files into your
context:

```bash
.agents/skills/codebase-research/scripts/orient --plan <task file>     # plan anchors: paths, symbols
.agents/skills/codebase-research/scripts/orient <Symbol1> <Symbol2> …  # blast radius
```

Call `orient` by its literal repo path, as above: the permission allow-list in
`.claude/settings.json` matches the command prefix, so a shell variable in its
place prompts on every call.

Read **only** the files where `orient` showed `✗`/`⚠`, or where the plan relies
on **behavioural claims** (the exact shape of a Zod schema, what SQL a
generator emits, serializer round-trip guarantees, what a test mocks) — the
graph does not know these, and that is exactly where plans go wrong most often.

If `orient --plan` reports a mismatch (path missing, symbol not found), that is
drift of the PLAN against the code, not a tool failure: record it explicitly
and decide at the gate below (the degradation protocol is in the
`codebase-research` skill).

**Prototype check.** The current packages are a prototype; the target is the
tier layout of the platform spec
(`docs/superpowers/specs/2026-09-24-simetra-platform-design.md`), and each
prototype package's fate is set by that spec's section on what is taken from
the prototype. If the task invests in a package slated for removal, or pulls
consumer-specific semantics into the platform, that is a gate question, not an
implementation detail.

## Decision gate (also yours)

- **Anchors clean, no behavioural assumptions** → go straight to the
  implementation workflow **without an orientation phase**. Put this line in the
  `COMMON` preamble: "plan anchors checked at `<sha>`; if the code disagrees,
  trust the code and record it in the report".
- **Minor mismatches** (moved code, renamed file) → do not spawn recon, just pass
  **delta notes** (200-400 tokens: "the plan cites a line range → search for the
  quoted code text instead, not the line number").
- **A mismatch that changes scope** (the plan deletes something that is alive; a
  type lacks a field; one test contradicts another; the task targets a package
  the platform spec retires) → **`AskUserQuestion`**. That is the owner's
  decision, not a silent "trust the code" inside an executor.
- **Large unfamiliar area** → 2-3 parallel `Agent(subagent_type:
  "codebase-research")` calls (not a Workflow — this is read-only recon). The
  delta contract and report format are already baked in by the skill, so the
  prompt carries **only the questions**. Synthesise yourself — do not hire an
  agent for it.

## Workflow 1 — implementation

Invoked **after** the gate. Phases:

1. **Do ALL checklist items.** Disciplines: `[TS]` — code directly; `[TEST]` —
   the `vitest` skill; CLI work — the `simetra-cli` skill. Generated SQL is
   verified through the generator's own tests and fixtures, never by applying
   it to a live database from an agent.
2. **Legacy cleanup** — leave no dead code or backward-compat shims of the old
   mechanism wherever that is genuinely possible (no half-migration, no dual code
   paths).
3. **Docs/skills sync** — `AGENTS.md`, `CLAUDE.md`, `.agents/skills/*`, package
   READMEs: old approach → new, so the canon does not drift. If the code
   contradicts the platform spec, do not edit the spec silently — raise it to
   the owner.

Mandatory rules for agent prompts:

- **Model tiering.** Every `agent()` gets an explicit `model` + `effort`:
  mechanics (rename, sed, descriptors, tests after a ready pattern, recon) →
  **Sonnet**; architecturally ambiguous work, synthesis, verification →
  **Opus**. Never leave the default (inheriting the orchestrator's model).
- **Executors do not need the code layer.** Put in the prompt: "the map below
  was built by orientation; do NOT spend turns on the code layer/orient; read the
  given paths directly". An executor greps and reads freely during
  implementation — that is fine.
- **Do not paste recon dumps into every prompt.** Delta notes only: the agent
  re-reads the files anyway, and a dump multiplies by the number of agents.
- **Git-committing agents on a shared branch run SEQUENTIALLY** (`for`-`await`),
  never in parallel: index races and clobbered barrels. If an agent must not
  commit, say so explicitly — otherwise it will commit and even push.
- **`schema` is minimal:** exactly one key in `required`, **no** `maxLength`
  (the retry cap of 5 kills the whole workflow after the work is done). Ask for
  brevity in the prompt instead. For reporting agents, plain text output is more
  reliable.
- **Public repo.** No private details of any consumer (schemas, IDs, tenant
  names, secrets) in code, fixtures, docs or commit messages.

## Workflow 2 — verification (a SEPARATE call)

Do not mix it with implementation: between the two you must read the result and
have a chance to intervene.

- The procedure is the **`code-review`** skill: the applicability gate, the
  `blocker/major/minor` × confidence scale with the 80 threshold, lens selection
  by what the diff touches.
- Fan-out: `Agent(subagent_type: "code-review")` — **one lens per call**, in
  parallel and independent (lenses must not see each other's conclusions).
- Then, **mandatory**, `Agent(subagent_type: "code-review-verifier")` for every
  finding — a large share of findings do not survive an attempt at refutation.
  You write the synthesis and **verify whatever you added yourself**.
- A reviewer may run `orient <Symbol>` — but only to check **coverage
  completeness** (a forgotten consumer), not to search.
- **Fix the findings and CLOSE THE LOOP.** A fix is code too and brings its own
  defects, so:
  1. fixes — in a separate workflow (if many) or pointwise;
  2. **re-review only what the fixes changed** (`git diff <sha-before-fixes>...HEAD`),
     not the whole diff again — otherwise round two costs as much as round one;
  3. round-two lenses — only those relevant to the fixes (typically
     `correctness` + the lens that found the original problem);
  4. **limit: 2 rounds.** If a `blocker` survives round two — stop and take the
     decision to the owner: it is no longer "polish", it is an open
     architectural choice.
- Final gates, all green:
  `pnpm format:check && pnpm lint && pnpm typecheck && pnpm test`
  (`pnpm format:fix` repairs formatting; `pnpm --filter <package> test` for a
  quick loop on one package).

## Final step — ticks and status

Mark `[X]` in the task file **only for what is really done** (a live smoke test
that agents cannot run stays `[ ]` as debt), and update related tasks and the
roadmap status where the task moved them.

---

## Validation and success criterion

- At most 2 retries on a lint/typecheck failure inside an agent; after that —
  deeper recon (`orient`, `Agent(subagent_type: "codebase-research")`), not blind
  repeats.
- **Done when:** every item is done and ticked `[X]`, legacy of the old mechanism
  is removed, docs/skills are in sync, every code-review finding is closed, all
  gates are green, related tasks are updated. Report to the owner in Ukrainian.
