# Review an implementation

$ARGUMENTS

**Two modes — chosen by whether an argument is present:**

- **With a task file** (`docs/tasks/*.md` or `docs/superpowers/{specs,plans}/*.md`,
  via `@`-mention or plain path; optionally a phase: "Phase 2" / "Фаза 2" or a
  range "Phase 1-3") → you check **checklist conformance** as well as the code.
- **Without an argument** → a plain review of the current branch: the boundary is
  `git diff main...HEAD` (or `git merge-base` with the base branch). Skip the
  phase steps; the rest of the flow is the same. Do not ask for a task file if
  none was given.

Here Claude Code is the **orchestrator + final validator**: it makes the
diagnosis itself rather than relaying subagent output — "trust but verify" for
every delegated fragment. Report to the owner in Ukrainian.

## Step 1 — parse the task and the scope

**Task mode:**

1. Read the task file in full.
2. Find phases by "Phase N" / "Фаза N" labels. If there are none, treat the task
   as a single phase.
3. Set the review scope: a specific phase → only it; a range → sequentially; none
   given → **all phases** sequentially.

**No-task mode:** scope = the whole branch diff; instead of "phases" work in
logical change groups (by commit or by package), so the report stays readable.

## Step 2 — orientation

- `git log` / `git diff <base>...HEAD` (or the relevant commit range) — to see the
  files actually changed, not only what the task document claims.
- `.agents/skills/codebase-research/scripts/orient <changed symbol> …` shows the
  ripple (who else the change touches) — specifically to check **coverage
  completeness**: a consumer forgotten because it is only visible through a
  barrel or a re-export.
- If the context is insufficient (unfamiliar area, cross-package scope) — delegate
  to `Agent(subagent_type: "codebase-research")`. Skip this when the scope is
  already clear.

## Step 3 — review (loop over phases / change groups)

For **each phase** in scope, sequentially (without a task file — one logical
change group at a time, and skip item 1):

1. **Conformance — the part unique to this command.** Match the phase checklist
   against `git diff`: items ticked `[X]` with no or incomplete code; unticked
   items that are actually done; contradictions between adjacent phases. For large
   phases delegate `Agent(subagent_type: "code-review")` with the **`drift`** lens,
   passing the checklist items and the diff boundary.
2. **Code review — per the `code-review` skill** (it defines lens selection, the
   `blocker/major/minor` × confidence scale with the 80 threshold, the report
   format and the anti-patterns): `Agent(subagent_type: "code-review")`, one lens
   per call, in parallel → then `Agent(subagent_type: "code-review-verifier")` on
   **every** finding. For sensitive code — generated DDL, RLS templates, grants,
   schema plans, the metamodel's public contracts, tier boundaries — add the
   `data-layer` and `history` lenses and two independent skeptics per `blocker`.
3. Record the phase findings before moving on to the next phase.

## Step 4 — consolidated report

One report right in the chat (do not create a file), **in the report format of
the `code-review` skill**. Two differences from the default format:

- in the summary add a **Task conformance** line — what is ticked `[X]` without
  code, what was done beyond the checklist;
- group findings by phase if there is more than one, and add a short
  **Cross-cutting** block — contradictions between phases and duplicated
  patterns.

If you are then asked to fix what was found — after the fixes **re-check only
what the fixes changed** (`git diff <sha-before-fixes>...HEAD`), limit 2 rounds;
after that a surviving `blocker` goes to the owner as a decision, not as polish.
