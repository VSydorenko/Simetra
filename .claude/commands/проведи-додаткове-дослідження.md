# Additional research and a complete solution

The context for this prompt is **every earlier message in the chat that concerns
the open issue** — a code review, an analysis of clarifying questions, or the
current discussion. Ignore unrelated messages about other topics. No attached
files are needed. If the context is incomplete or the open issues are not
identified — ask the owner for clarification (in Ukrainian).

## Task

Run **deep research** on every open issue identified earlier in the
conversation and propose a **complete solution** for each.

## Research sources

> **Tool priority:** 1) the code graph → 2) the repo docs → 3) library docs →
> 4) the web → 5) the platform spec as the arbiter of direction. Use only the
> sources relevant to the question at hand.

### Code (the code graph)

- **Orientation first:** start with the `codebase-research` skill — its
  `.agents/skills/codebase-research/scripts/orient <Symbol1> <Symbol2> …` shows
  where a symbol lives and who **actually calls** it (without transitive
  barrels), through the code layer (`codebase-memory-mcp`); without the graph
  `orient` reports the degradation honestly instead of substituting grep for an
  answer. That is cheaper and broader than reading files blind.
- For an unfamiliar area or a cross-package inventory — delegate to
  `Agent(subagent_type: "codebase-research")`: it works by the same skill,
  returns a delta and anchors, and keeps the main context small. For several
  independent questions — fan out several parallel Agent calls in one message,
  one question each.
- **Behaviour beats reading.** When the question is "what does it actually do"
  (generated SQL, serializer output, CLI result), run the relevant tests or the
  CLI (`pnpm --filter <package> test`) rather than inferring
  from source.

### Repo docs

- `orient --map "<topic>"` — BM25 search over the docs corpus by a
  natural-language topic; it finds the relevant spec section, skill or research
  note without reading the whole corpus.
- `docs/research/*` — the background studies behind the decisions (1C metadata
  model, Frappe DocType, schema introspection and DDL, PostgREST, licensing).

### Library and external-tool documentation

- **Context7 MCP** — **always** for the documentation of any library or external
  tool (Zod, Vitest, TanStack, PostgREST, Postgres, Vite, turbo, pnpm, etc.).
  Never rely on training data — APIs change.

### The web

- **WebSearch** (and WebFetch for a specific page) — for precedents and external
  designs the question depends on (how 1C, Frappe, pgroll or similar systems
  solve the same problem), issue trackers of the libraries involved, and
  anything newer than the library docs. Cite the source.

### The platform spec

- `docs/superpowers/specs/2026-09-24-simetra-platform-design.md` and the
  detailed specs next to it decide the **direction**: check every proposed
  solution against the recorded decisions, the tier layout T0–T6 (imports only
  downward) and the platform/product boundary. The current packages are a
  prototype: a solution that only patches a package the spec retires is not a
  solution.

## Model tiering in fan-out

If there are several independent questions — delegate the recon for each to a
separate agent on `model: "sonnet"` in parallel (one message, several Agent tool
calls). Do synthesis, comparison of alternatives and the final decision yourself,
or through `Agent(model: "opus")` when the question is architecturally ambiguous
and deserves a second opinion. Claude Code is the orchestrator and validator
here: do not relay a subagent's conclusion as fact without checking the key
claims yourself.

## Principles for forming solutions

> These principles are mandatory for every solution.

- **A complete solution in one pass.** No half-solutions and no "we'll fix it
  later". The goal is to settle every ambiguity, exception and clarification
  fully, now, in this pass.
- **Report deviations from the norm, do not resolve them silently.** If the code
  has non-standard behaviour or exceptions to a pattern that need a
  standardisation decision — say so explicitly and give a recommendation. Do not
  make the decision for the owner, and do not try to cover **absolutely** every
  deviation — single out those that really affect maintainability.
- **Maximum standardisation.** Always choose the solution that gives **one
  shared pattern** for all components of the area, so it can be maintained,
  extended and improved in one place when that is actually needed.
- **No new abstractions on top of abstractions.** No new wrappers over existing
  ones for a temporary gain. Every solution should work natively through the
  existing mechanisms — especially when the current abstractions are already
  obsolete.
- **Platform, not product.** A solution must not push one consumer's semantics
  (tenants, product vocabulary, product rules) into the platform; the platform
  exposes an extension point, the consumer fills it.
- **Public repo.** Research may touch a private consumer's code or data for
  context, but its details (schemas, names, IDs) do not go into this repo's
  files or into the proposed text meant to land here.

## Response format

Answer in Ukrainian. For **each** identified issue:

### [Назва проблеми]

**Поточний стан** (what exactly the problem is, confirmed by research)
**Першопричина** (why it happens)
**Запропоноване рішення** (concrete steps, code examples if needed)
**Ризики та альтернативи** (if there are several solutions — compare them)
**Джерела** (which tools/sources confirmed the conclusion)
