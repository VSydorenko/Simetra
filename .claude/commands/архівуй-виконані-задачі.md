# Archive a finished block of tasks

Argument (optional): the block name or a list of tasks — `$ARGUMENTS`.
If there is none, identify the block yourself from the statuses in the task and
plan files and confirm it with the owner.

**The goal is not "delete files" but removing from the repo everything that lies
about the current state.** A finished task is harmful not because it takes space
but because an agent reads it as an instruction and lands a cancelled decision.
Broken references and "was → became" narrative do the same.

Talk to the owner in Ukrainian. Internal docs you touch stay in Ukrainian;
`AGENTS.md`, `CLAUDE.md`, skill/agent/command bodies and the README stay in
English (the language rule in `AGENTS.md`).

> **This command changes the canon.** Step 0 is mandatory: without the owner's
> answers the remaining steps produce materially different work.

---

## Step 0 — the owner's decision gate (DO NOT skip)

First take inventory (`docs/tasks/*.md`, `docs/superpowers/{specs,plans}/*.md`,
read the status in each header), then ask **exactly three** questions via
`AskUserQuestion`:

1. **Where does the live debt go?** Closed tasks almost always keep unfinished
   items (phase debt, unrun smoke tests, deferred decisions). Options: a separate
   backlog task (usually best) / a section in a canon doc / delete together with
   the tasks.
2. **What scope?** Only the task files, or also the block's specs and plans in
   `docs/superpowers/{specs,plans}`. Plans without tasks are orphans, so they are
   usually deleted together. The platform spec and other living specs that still
   describe the target are **not** archived with a block.
3. **What about "removed — do not look for it in the code" lists?** These are two
   different layers: history narrative ("phase 3 merged in PR #N", "reversed on
   date X") and lists of tokens/props that no longer exist. Narrative goes
   always; the lists — the owner decides (they save agents from hunting ghosts,
   but can be rephrased as present-tense prohibitions).

Ask the questions in **one call**, not one at a time.

---

## Step 1 — collect the live debt BEFORE deleting

The most expensive mistake: deleting a task that still had unticked items. After
deletion they cannot be recovered from memory.

Read every file of the block **in full** (not only the header) and extract:

- `[ ]` items in the DoD and in phase checklists;
- sections on debt, carried-over debt, known pitfalls, "what the smoke test did
  not cover";
- deferred owner decisions ("fate of X", "reformulate criterion Y");
- measurement pitfalls — they are valuable and have no place in canon docs.

Write them into the target from Step 0 (typically
`docs/tasks/backlog/<block>-residual-debt.md`), **self-contained**: no references
to the tasks that are about to disappear, and no private details of any consumer
(this repo is public).

## Step 2 — delete

`git rm` the block's files. Together with them — measurement/baseline artefacts
that no longer gate anything (check whether they still have a live consumer).

## Step 3 — references to FILES

First the guard — it covers the canon (`AGENTS.md`, `CLAUDE.md`,
`.agents/skills`, `.claude`) and, besides paths, checks `§` pointers of the form
"doc § section" and "skill § section":

```bash
./scripts/check-doc-anchors.py
```

Then references to tasks and specs across the **whole** repo, which the guard
does not see:

```bash
rg -o --no-filename -e 'docs/[A-Za-z0-9._/-]+\.(md|json)' \
  -g '!node_modules' -g '!.git' . | sort -u | while read f; do [ -f "$f" ] || echo "DEAD: $f"; done
```

Run it over the **whole repo**, not only what you just changed: earlier cleanups
leave broken references, and they are in scope too. Tell apart:

- **broken** — the file was deleted → rephrase or drop the mention;
- **future** — a doc a living task plans to create → keep;
- **in code** (comments, doc blocks) — fix them too.

## Step 4 — § notation in code COMMENTS

**The step that is easy to skip entirely.** A grep for file names does NOT see
it: code refers not to a file but to an item — `§6.4`, a decision id, "Фаза 3",
"Етап 4", "Task 7", "PR #N", a commit SHA. Once the document is deleted, that is
navigation to nowhere.

```bash
rg -n -g '!node_modules' -g '!*.md' \
  -e '§[0-9]' -e 'Фаз[аиуіо][а-яі]* [0-9]' -e 'Етап [0-9]' -e 'Phase [0-9]' \
  -e 'Task [0-9]' -e 'PR #[0-9]' packages apps scripts
```

Filter the noise: UUID v4, cache-key suffixes, "phase" in the domain sense
(expand/contract schema phases are platform vocabulary), references **naming a
living document** — a pointer into the platform spec, or a decision id from it,
stays valid while the spec lives.

Replacement: a § item of a deleted document → the section of the current canon
doc or spec; a stage label → the same wording without the number. **Keep the
substance of the explanation** — remove the navigation label, not the reason
why it is done this way. Code comments stay in Ukrainian.

When the volume is large, this is the case for a `Workflow`: clusters of files
that **do not overlap** (by directory), fix agents on Sonnet + a separate phase of
adversarial verifiers on Opus. The agent prompt must forbid touching code,
string literals and behaviour, and must carry a mapping table "old label →
current canon".

**Do not forbid agents to fix test names blindly.** First check whether anything
filters by test name (`-t`, `--testNamePattern` in CI workflows or package
scripts). If nothing does, renaming is safe — and `describe()`/`it()` titles are
where broken references most often survive.

## Step 5 — the canon: from narrative to state

Go through `AGENTS.md`, `CLAUDE.md`, `.agents/skills/*/SKILL.md`,
`.claude/{agents,commands}/*.md`, `README.md` and the roadmap (docs/ROADMAP.md):

| Remove | Replace with |
| --- | --- |
| "phase 3 merged (PR #N) — the model changed" | a description of the model itself, in the present tense |
| "cancelled by the reversal of date X", "the first draft read it inverted" | "the inverse of this is a typical misreading" |
| "removed in vN: `tokenA`, `propB`…" | "there is no utility for X and there must not be — here is why" |
| a changelog of the document's versions | nothing (history lives in git) |
| "Version / Date" in the header | nothing; `Status` stays |

The roadmap is the one place where a block's status belongs: mark the
subproject's status there as a state, without narrative.

Three checks that catch real defects here:

1. **Canon against the CODE.** Transitional edits leave drift: a doc may describe
   a recipe the code no longer has.
2. **Internal contradictions.** One section describes the state, another a
   cancelled decision.
3. **Stale content in a changelog.** Read it before deleting: it sometimes holds
   descriptions of the *current* state that must survive (check whether another
   doc has them) — and outright falsehoods.

If the canon contradicts the platform spec, do not rewrite the spec here — raise
it to the owner.

**Line numbers in references (`file.ts:148-149`) are fragile** — they shift with
any edit above. Replace them with a description ("the file header and both
`<name>` blocks").

## Step 6 — memory

Memory is local to Claude Code; cloud sessions and other agents do NOT see it.

- Delete journals of closed initiatives entirely (they grow into hundreds of
  lines of intermediate states: branches, PRs, phase debt).
- Rewrite living process lessons **without tying them to phase or PR numbers**.
- Technical knowledge from a deleted journal that other agents need **moves into
  the git-tracked canon** (a skill, `AGENTS.md`, a spec) rather than staying in
  memory.
- Update the memory index and the links between memory files.

## Step 7 — adversarial verification

**Mandatory**, even if you did everything yourself. Two independent agents on
Opus:

1. **Diff safety.** The goal is to REFUTE "the edits are safe": was anything
   changed outside comments; was technical substance lost; were valid references
   removed; are the new § anchors real (grep the headings).
2. **Completeness.** Re-run the Step 3–4 scans + `ls` every mentioned path.

**Never bump "last verified" / "checked on <date>" in files you only
rephrased.** That turns a style edit into a false claim of verification.

**Do not run a bulk mechanical regex replacement over prose.** It produces
mangled text. Edits are pointwise, via `Edit`.

**Agents that rewrite docs invent APIs.** A shortening agent may add a section
about a contract the code does not have and cite functions with non-existent
names — in a confident, canonical tone. The verifier must **spot-grep the
riskiest claims** (symbol names, props, counts of inputs), not only read the
diff.

## Step 8 — gates and commit

```bash
./scripts/check-doc-anchors.py
pnpm format:check && pnpm lint && pnpm typecheck && pnpm test
```

Branch from the **current working branch**, not from `main`. Commit as the
owner: Conventional Commits prefix, description in Ukrainian, no
`Co-Authored-By` / `Generated with` trailers. Push and open a PR only when the
owner explicitly asks.

---

## Definition of Done

- [ ] Step 0: three questions asked, answers applied
- [ ] Live debt moved and self-contained (no reference to anything deleted)
- [ ] Step 3 guard and `rg` scan clean (except deliberately future docs)
- [ ] Step 4 `rg` scan clean (except valid noise, listed in the report)
- [ ] The canon describes state, not history; checked against the code
- [ ] Memory cleaned, index updated, knowledge moved into git
- [ ] Verification passed, defects found are fixed
- [ ] Gates green, branch created, commit made

## Report to the owner

In Ukrainian, briefly, without retelling the steps: what was deleted (how many
files/lines), where the debt went, which **defects were found along the way**
(canon drift, pre-existing broken references, stale content), what was
deliberately kept and why, the gate results.
