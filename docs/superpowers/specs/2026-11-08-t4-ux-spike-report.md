# Звіт спайку 2 рушія T4: стан у UI, оракул мерехтіння й SSR-гідратація

> **Статус:** звіт спайку для архітекторки П4-B. Гілка `spike/t4-ux` у `main`
> не зливається. Код полігона: `spikes/t4-ux/`. Ядро — спайк 1
> (`spike/t4-core` до `ac447962`, злито в гілку). Сценарії сигналів — спайк 3
> (`spike/t4-realtime@6498b629`, звіт, розділ «Сценарії для оракула спайку 2»).

## Підсумок

1. **Мерехтіння, моргання й «пропало-з'явилось» усунено.** Є гідратаційних
   стрибків теж немає. Робоча зв'язка така:
   - React 19 і `useSyncExternalStore` над незмінними знімками ядра;
   - `getServerSnapshot` збігається з `getSnapshot`;
   - ядро гідрується в `router.options.hydrate`, до першого рендера.

   Жодного Suspense на даних, `useOptimistic` чи `useTransition` для
   сховища. Доказ — оракул і 88 тестів. Вони зелені в Chromium і WebKit, у
   dev- і production-збірці.
2. **Модель станів оптимістики:**
   - один словник стану рядка (`synced`, `pending`, `failed`, `conflict`,
     `stale`, `removed`, `unknown`);
   - стан вибірки (`loading`, `ready`, `refreshing`, `hasNewRows`,
     `needsRefresh`);
   - одна зарезервована комірка стану: вміст змінюється, розмітка — ні.

   Таблиця «стан → показ → дії» — у розділі 3.
3. **TanStack Start підходить без обходів.** Потрібні лише штатні опції
   роутера і власний серверний entry на 15 рядків для заголовків кешу.
   Перелік — у розділі 5.
4. **Оракул — головний актив.** Він ловить 9 типів заборонених кадрів на
   навмисно зламаних реалізаціях в обох браузерах. Готовий стати гейтом
   платформи.

## 1. Прецеденти (крок 0)

- **`useSyncExternalStore`.** Під час гідратації React бере
  `getServerSnapshot()`. Якщо потім `getSnapshot()` відрізняється, React
  робить синхронний примусовий перерендер (`forceStoreRerender`, SyncLane) —
  це видимий другий кадр. Тому знімок для гідратації — той самий, з якого
  рендерився HTML. Джерело: `ReactFiberHooks.js`, react.dev.
- **Мутація сховища під час transition** перезапускає оновлення як
  блокувальне. Suspense на значенні сховища показує fallback поверх уже
  показаних даних. Звідси правило: дані сховища ніколи не суспендять.
- **`useOptimistic`** живе лише поки триває Action. Відмова повертає старе
  значення, а `failed`/`conflict` губиться. Тому оптимістичний шар — у
  ядрі, не в React.
- **TanStack Router/Start.** `router-core` `load-client.js` чекає
  `options.hydrate(dehydratedData)` до `matchRoutes`. `StartClient` чекає
  `hydrateStart()` через `Await`. Отже ядро гідрується до першого рендера
  без обходу. Перевірено в коді `@tanstack/router-core@1.171.39`.
- **Інтеграція Query у Start.** Сховище створюється у фабриці роутера, тобто
  на запит. Частина `initial` гідрується синхронно, потокова — фоном. Ми
  робимо так само.
- **Візуальні патерни.** Linear, Notion, Figma й 1С показують `pending` тонкою
  ознакою. `failed` і `conflict` — стійкий маркер із діями. Ніхто не робить
  `pending`-рядок сірим чи порожнім.
- **Вимір мерехтіння.** Пакованого детектора немає. Практика —
  `MutationObserver` у `addInitScript` плюс Layout Instability API
  (`layout-shift`, лише Chromium) плюс React Profiler.

### Сценарії

Усі сценарії зелені в Chromium і WebKit, на ядрі спайку 1, у dev- і
production-збірці.

- **1. SSR-вхід:** HTML = перший кадр, скелета немає.
- **2. Список → картка → список:** картка показує рядок сховища одразу, ліниві
  поля доливаються у зарезервоване місце. Повернення — без запиту.
- **3. Правка поля:** значення одразу; підтвердження змінює лише позначку.
- **4. Відмова:** значення лишається з `failed`; «скасувати» повертає старе
  одним кадром.
- **5. Створення:** рядок з'являється один раз зверху. Ключ — клієнтський
  UUID, після підтвердження рядок не стрибає.
- **6. Фонове перечитування:**
  - змінений рядок оновлюється на місці;
  - зниклий — `removed` на місці;
  - новий — лише банер `hasNewRows`;
  - склад змінює лише `showNew()`.
- **6б. Змінене поле сортування:** рядок на місці з новим значенням.
- **7. Прокрутка:** підвантаження сторінки без стрибка прокрутки.
- **8 і 8б. Зміна суб'єкта:** старі дані не видно жодного кадру. Те саме,
  коли відповідь старого суб'єкта ще в дорозі.
- **9. StrictMode:** «туди й назад» ×5 без запиту й без порожнього кадру.
- **Спайк 3, р1–р9:** сигнал раніше `run`, чужа зміна під `pending`, сплеск
  1000 сигналів, розрив і 50 пропущених змін, видалення при відкритій картці,
  власне видалення, дубль і перестановка сигналів, відставання репліки,
  втрачена відповідь `run`. Файл: `tests/e2e/realtime.spec.ts`, фейковий
  канал — `tests/e2e/signals.ts`.
- **Режими React/Start (`tests/e2e/react-modes.spec.ts`):**
  - потоковий SSR: рядки в першому кадрі, лінивий `count` доходить потоком
    у своєму слоті;
  - запис осідає під час навігації (transition) без проміжного кадру;
  - повторне монтування після `releaseDelayMs`: одне перечитування, без
    скелета.

## 3. Візуальна модель станів (пропозиція для спеки)

Правило розмітки:
- кожен рядок має одну комірку стану фіксованої ширини й висоти;
- слот дії «видалити» теж фіксований;
- маркер стану — внутрішня тінь лівого краю (`box-shadow: inset`), не рамка, тому не змінює геометрію;
- банери вибірки живуть у слоті панелі фіксованої ширини;
- ліниві поля мають місце, зарезервоване на рівні поля.

| Стан | Показ | Дії |
| --- | --- | --- |
| `synced` | без позначки | «×» (видалити) |
| `pending` (зміна) | змінені поля курсивом приглушено; «Зберігається…» | — (кнопки рядка вимкнено) |
| `pending` (видалення) | рядок на місці, закреслений, напівпрозорий; «Видаляється…» | — |
| `unknown` | синьо-сіра смуга зліва; «Перевіряємо результат…»; значення користувача | — (ядро саме розв'язує в `synced`/`failed`/`conflict`) |
| `failed` | червона смуга, світло-червоне тло; «Не збережено» (код у підказці); значення користувача | «Повторити», «Скасувати» |
| `conflict` | бурштинова смуга й тло; «Змінено іншим»; значення користувача | «Взяти серверну», «Перезаписати» |
| `stale` | сіра смуга; «Може бути застарілим»; значення видно | — |
| `removed` | сіре тло, закреслено; «Видалено іншим» | «Прибрати» (оновлення складу — дія користувача) |
| вибірка `refreshing` | «Оновлення…» у слоті панелі; рядки видно | — |
| вибірка `hasNewRows` | банер «Є нові рядки — показати» | `showNew()` |
| вибірка `needsRefresh` | банер «Список змінився — оновити» | `refresh()` |
| виняток безпеки | дані зникають негайно; рядок причини «Доступ змінився — дані приховано» у зарезервованому слоті | оновити сторінку |

Скриншоти:
- `screenshots/list-states.png` — усі стани рядка одночасно;
- `screenshots/card-lazy-loading.png` — картка з рядка сховища з
  зарезервованим лінивим полем;
- `screenshots/card-failed.png`;
- `screenshots/policy-predict-pending.png`, `screenshots/policy-await-pending.png`.

**Форма картки — чернетка поза ядром.** Чернетка тримається до успішного
осідання запису. За `await` сховище показує старе значення до відповіді, і
без чернетки поле блимнуло б старим значенням. Після відмови чернетка лишається
з `failed`. «Скасувати» знімає мутацію, і поле одним кадром показує значення
сервера. Код: `src/routes/items.$id.tsx`, `Field`.

## 4. SSR-гідратація даних

- **Ядро на запит.** `getRouter()` створює `RuntimeHolder`. Root `beforeLoad`
  на сервері бере сесію з cookie через серверну функцію і створює ядро
  суб'єкта. Loader-и роблять `core.preload(spec)`. `dehydrate` віддає
  `{ meta, snap: core.dehydrate() }`. На рівні модуля сервера ядра немає.
- **Клієнт.** `hydrate` створює ядро суб'єкта знімка і викликає
  `core.hydrate(snap)` до першого рендера. Ефект кореня кличе
  `core.endHydration()` один раз (StrictMode повторює ефект, звірка — ні).
- **Тотожність знімка.** `meta` = `subject`, `catalogHash`, `rightsVersion`,
  `issuedAt`, `ttlMs`. Знімок гідрується завжди, інакше HTML і перший рендер
  розійдуться. Після гідратації йде один запит контракту `version`. Якщо
  `rightsVersion` чи суб'єкт інші, діє виняток безпеки:
  `Writer.purge` усіх ключів знімка й причина в UI. Тест «права змінились між
  SSR і гідратацією» зелений. Прострочений знімок чи інший каталог позначено
  як `expired`/`catalog-changed`; дія для них — фонове перечитування. Її
  **не перевірено** окремим тестом.
- **Сесія.** Непрозорий cookie → серверна сесія (форма Better Auth). Специфіки
  Supabase немає.
- **Кеш.** Серверний entry ставить на HTML `cache-control: private, no-store` і
  `vary: Cookie` (`src/server.ts`).
- **Потоковий SSR.** Рядки йдуть у першому фрагменті. Лінивий `count` іде
  потоком через `Suspense` + `Await` у слоті `data-stream-slot`
  фіксованої ширини. Swap потоку Start прибирає `<template>` уже після
  розбору HTML. Оракул вважає це доливанням у слот, а не розбіжністю
  гідратації.
- **Commit-и після гідратації (prod, обидва браузери):**
  - рядки — 0;
  - зона списку загалом — 3: межа потоку лічильника і внутрішні оновлення
    роутера; DOM рядків не змінюється;
  - оболонка роутера — 3 commit-и без змін DOM.

  Зона даних гідрується окремим, пізнішим commit-ом: це селективна
  гідратація code-split маршруту, DOM при ньому не змінюється. Тому вимір
  рахує commit-и після mount зони, а не після першого commit-у застосунку.

## 5. TanStack Start: висновок

**Підходить без обходів.** Усе нижче — штатні опції або звичайна гігієна:

| Що | Навіщо | Оцінка |
| --- | --- | --- |
| `createRouter({ dehydrate, hydrate, Wrap })` | гідратація ядра до першого рендера | штатний API |
| `defaultStaleReloadMode: 'blocking'` | інакше збережений match показується до loader-а (stale-while-revalidate), а звільнений вигляд дає скелет. Оракул це зловив | штатна опція |
| `defaultPendingMs` великий, `defaultPendingMinMs: 0` | без pending-кадру роутера; loader над ядром миттєвий, коли дані є | штатні опції |
| маршрути з даними — `ssr: true` (типово) | `data-only`/`false` гарантують pending-кадр | правило |
| власний `src/server.ts` (15 рядків) | заголовки кешу для персонального знімка | штатна точка; альтернатива — глобальний middleware Start |
| власний `src/client.tsx` | лише вимір (Profiler, `onRecoverableError`) | у платформі — лише `onRecoverableError` у журнал |
| одноразові ефекти після гідратації | StrictMode повторює ефекти | гігієна React |

Версії: Start 1.169.4, Router 1.170.46, router-core 1.171.39, Vite 8.3.5,
Rolldown 1.2.16, React 19.3.1 (як у звіті П0 (а)). Production-збірка
запускається `scripts/serve-prod.mjs`.

## 6. Політики дії `predict` / `await`

Затримку мережі задає сервер (`control latency`). CDP-throttling є лише в
Chromium, тож серверна затримка однакова для обох браузерів. Нижче — медіана
з 5 кліків, production-збірка, перемикач статусу в рядку списку. Оракул
зелений для обох політик: індикатор не зсуває розмітку, значення не блимає, за
`await` результат з'являється одним кадром.

| Затримка | `predict`: значення видно | `predict`: підтверджено | `await`: значення видно = підтверджено |
| --- | --- | --- | --- |
| 50 мс | 9–15 мс | 65–72 мс | 67–69 мс |
| 150 мс | 10–12 мс | 165–167 мс | 165–167 мс |
| 400 мс | 11–15 мс | 412–415 мс | 413–414 мс |

Вимір спайку 3: шлях «сигнал + перечитування» ≈ 2×RTT + 50 мс. Відповідь
`run` — 1 RTT. Тож «чекати realtime» замість `await` гірше ще на RTT + 50 мс.

**Оцінка, де `await` сприймається гірше:**
- **Перемикачі, прапорці, правка значення в рядку.** Відклик ~70 мс на
  локальній мережі ще прийнятний. Від 150 мс уже помітна «в'язкість», від
  400 мс клік здається пропущеним, і користувач клікає вдруге. Тут типова
  політика — `predict`.
- **Створення й видалення рядка.** `predict` дає рядок одразу на визначеному
  місці. `await` дає кадр «нічого не сталося». Тут теж `predict`.
- **Проведення, нумерація, підсумки, усе, що рахує сервер.** Передбачення
  неточне, і `predict` показав би значення, яке потім зміниться. Тут
  `await`.

Форма картки — чернетка, тож для поля картки різниці немає: користувач
бачить своє значення одразу за обох політик.

**Рекомендація:** типова політика — `predict` для точних передбачень
(встановити поле, перемкнути, видалити, створити з клієнтським UUID),
`await` — явно для серверних обчислень. Зараз ядро спайку 1 має типову
`await`. Це розвилка для архітекторки.

## 7. Продуктивність `full` 5000

Вимір: від `core.commit(writer.patch)` до кінця commit-у React зони
(`Profiler onRender`), 60 змін, production-збірка з профілювальним
react-dom.

| Браузер | Зміна значення: ядро p95 / разом p95 | Зміна ключа сортування: ядро p95 / разом p95 |
| --- | --- | --- |
| Chromium | 1.3 / 1.7 мс | 1.7 / 2.0 мс |
| WebKit | 4 / 5 мс | 4 / 4 мс |

У WebKit таймер має крок 1 мс. Dev-збірка: Chromium ≤7.3 мс, WebKit ≤12 мс.
Рендер віртуалізований (видимі ≈30 рядків).

## 8. Оракул як гейт платформи

- **Записувач** (`tests/oracle/recorder.js`, `addInitScript`). Знімає стан
  кожної зони `[data-region]` у таких точках:
  - після кожної пачки мутацій DOM — це суворіше за кадр: стан після кожної
    задачі;
  - на кожну прокрутку;
  - на кожному rAF.

  У знімку — ключ, геометрія (top, висота), значення `[data-field]`, стан.
  Також записує `layout-shift` з джерелом (вузол і прямокутники) і мутації
  `#app` після розбору HTML.
- **Правила** (`tests/oracle/rules.ts`, чиста функція над журналом).
  Сегмент — проміжок між позначками дії користувача (`__oracleMark`). Дія
  дозволяє лише перелічене в `allow`: `clear`, `reorder`, `shift`,
  `shift-once`, `scroll`, `aba`. Заборони:
  - порожня зона чи скелет після даних;
  - ABA присутності й значень у сегменті;
  - інверсія порядку;
  - зсув і зміна висоти рядка;
  - стрибок прокрутки;
  - `layout-shift`;
  - заборонений текст після позначки (зміна суб'єкта);
  - мутації чи помилки гідратації.
- **Уточнення, знайдені в роботі:**
  - стан frame 0, змінений ще до першого кадру, — проміжний стан розбору HTML
    (WebKit), а не кадр;
  - атрибут, записаний тим самим значенням (React гідратує `value`), — не
    зміна;
  - явні слоти потоку виключено з правила гідратації.
- **Межі.**
  - `layout-shift` є лише в Chromium; у WebKit його закриває правило
    геометрії.
  - Покадрових скриншотів на кожному переході **немає**. Є геометрія на
    кожному rAF і trace Playwright при падінні. Скриншоти — лише для
    моделі станів.
  - Unit-тестів правил на синтетичних журналах **немає**. Правила
    перевіряються самотестом на мутаціях у браузері.
- **Дефекти полігона, які оракул зловив сам:**
  - слот «Завантаження…» в кінці вікна переїжджав (CLS 0.038) — тепер ключ
    слота за позицією;
  - кнопка «Вийти» з'їжджала від банера (CLS 0.0001);
  - кнопка «×» зсувала комірку стану;
  - скелет при поверненні після `releaseDelayMs` (SWR роутера).

## 9. Знахідки для ядра (спайк 1)

1. **Вирішено в `ac447962`.** Вигляд `card` бере рядок зі сховища одразу
   (раніше — лише після власного читання).
2. **Злиття на рівні полів при конфлікті версії.** Сценарій: чужа зміна
   іншого поля, тоді власний `update`. Ядро перечитує ключ і пересилає
   зміну — замість `conflict` виходить `synced`. Зміна того самого поля дає
   `conflict` (р2). Це розумно, але не описано в спеці П4-B §7.3 («conflict →
   перечитати, автоповтору немає»). Потрібне рішення.
3. **`refresh()` змінює склад, `refetchKeys` — ні.** Фонове перечитування в UI
   — це `refetchKeys(видимі ключі)`. Нові рядки йдуть лише сигналом
   (`markViews`). Словник спільних правил це вже фіксує. Імена в API варто
   зробити очевидними: `refresh` — дія користувача.
4. **`releaseDelayMs` (1000) і роутер.** Без `defaultStaleReloadMode:
   'blocking'` звільнений вигляд дає кадр скелета. З ним повернення робить
   одне перечитування без скелета.

## 10. Відкриті розвилки й рекомендації

1. **Типова політика дії.** Рекомендація: `predict` для точних передбачень,
   `await` — явно (розділ 6).
2. **Злиття полів при конфлікті** (розділ 9, п. 2). Рекомендація: лишити
   злиття для різних полів і явно описати в §7.3.
3. **Контракт `version` після гідратації.** Чи вважати його «0 запитів»?
   Рекомендація: так. Це звірка тотожності знімка без даних, і вона
   обов'язкова для винятку безпеки.
4. **Оракул як гейт.** Рекомендація: перенести `recorder.js` + `rules.ts` +
   обв'язку в шаблон хоста П4-D. Женеться в CI у Chromium і WebKit.
   Додати unit-тести правил і покадрові скриншоти ключових переходів.
5. **Віртуалізація.** Полігон має власну (фіксована висота рядка), а не
   TanStack Virtual. Скоріш за все, TanStack Virtual потребує `initialRect`
   для SSR і має свій commit вимірювання — **не перевірено**. Перевірити під
   оракулом у П4-D.
6. **Вивантаження далеких сторінок вікна** (≈(видимі+2)×100) **не
   перевірено**. Полігон тримає завантажене. Для вивантаження потрібне
   правило, щоб не було скелета для вже бачених рядків.

## 11. Що змінюється в спеці П4-B

- **§1 «Мета й межі»:** SSR-гідратація даних T4 входить у межі (зараз її
  немає).
- **§6.1, §6.3:**
  - рантайм на сервері — на запит (у фабриці роутера);
  - `dehydrate`/`hydrate`/`endHydration`;
  - `releaseDelayMs`, `preload` для loader-а;
  - власність підмножини — через `subscribe` хендла (вимога React);
  - `view()` — чистий.
- **§6.4 «Публічний API читання»:**
  - хуки над `useSyncExternalStore` з `getServerSnapshot === getSnapshot`;
  - словник станів рядка й вибірки (розділ 3);
  - `card` зі сховища одразу;
  - правило стабільності списку;
  - `refresh` / `showNew` — дії користувача.
- **§7.1:**
  - політика дії `predict`/`await` і її типове значення;
  - форма картки — чернетка до осідання;
  - `create` з клієнтським UUID — стабільний ключ.
- **§7.3:** `unknown` замість мовчазного відкату для
  `unavailable`/`timeout`; злиття полів при конфлікті.
- **§10 «Контракт сесії»:**
  - тотожність SSR-знімка (`subject`, `catalogHash`, `rightsVersion`,
    `issuedAt`, `ttlMs`);
  - звірка `version` після гідратації;
  - виняток безпеки через `purge`;
  - `cache-control: private, no-store` + `Vary: Cookie`.
- **§11 «Інваріанти»:** інваріант «без заборонених кадрів» (перелік з
  розділу 2) з оракулом як доказом.
- **§12 «Тести»:** замість «Браузерні тести не потрібні» — оракул у Chromium і
  WebKit як гейт для T4/T5. Мутаційний самотест оракула — обов'язковий.
- **Додаток А:** шаблон хоста П4-D отримує:
  - `defaultStaleReloadMode: 'blocking'`;
  - pending-налаштування роутера;
  - серверний entry із заголовками кешу;
  - `onRecoverableError` у журнал.
