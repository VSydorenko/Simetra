## 1. Принцип і межа

**Схема `simetra` тримає лише стан і механізми платформи; дані застосунку,
зокрема користувачі й учасники тенантів, живуть у схемах застосунку як
об'єкти метамоделі.** Так само поділено в провайдерах автентифікації:
закрита системна частина (зв'язок «провайдер + ідентифікатор → користувач»)
окремо від профілю, яким володіє застосунок.

Користувачі — за моделлю 1С: автентифікацію дає провайдер (у 1С — список
користувачів інформаційної бази), користувач — довідник, який розширює
застосунок (у БСП — `Справочник.Пользователи`), а учасник тенанта — окремий
рівень застосунку. Три рівні «обліковий запис → користувач платформи →
учасник тенанта» відповідають моделі 1С:Фреш, де користувач сервісу працює
від імені кількох абонентів, а кожна область даних має власний список
користувачів.

**Чому.** Ключ користувача в різних провайдерів має різний тип і різне місце:
uuid у тій самій базі, рядок у тій самій базі або рядок поза базою взагалі
(зовнішні IdP). FK бізнес-таблиць на таблицю провайдера тому непереносний за
побудовою. Зрілі метадані-платформи розв'язують це однаково: власна таблиця
користувачів, на яку посилаються дані, і окремий зв'язок з обліковим записом;
користувача не видаляють, а роблять недійсним.

## 2. Ухвалені рішення

| № | Рішення | Чому |
| --- | --- | --- |
| С1 | Схема `simetra` тримає лише стан і механізми платформи: marker і ledger застосованої конфігурації (П3), `identities`, лічильники нумерації, outbox-таблицю (коли немає `pgmq`), журнал DDL, функції сесії. Даних тенанта в ній немає; власник — роль мігратора; ролі застосунку не мають грантів на її таблиці, лише `EXECUTE` на службові функції; PostgREST її не бачить; компілятор резервує ім'я схеми | одне місце для всього, що платформа зараз розкладає «десь», без RLS-шаблонів у закритій схемі (§3) |
| С2 | Модель користувачів: закрита `simetra.identities` з `PRIMARY KEY (provider, subject)` і `UNIQUE (user_id, provider)`; **системний довідник «Користувачі»**, який оголошує платформа в схемі застосунку, а застосунок розширює власними реквізитами (як БСП `Пользователи`). Платформні реквізити (`userKind` — людина чи агент, `invalid`) пише лише платформа — колонковими грантами й тригером, як `predefined_name`. Стабільний ключ — провайдер + subject, ніколи email | закритою має бути лише унікальність і прив'язка; користувач — дані, на які посилаються інші дані, тож він — об'єкт метамоделі з RLS, embed і реквізитами (§4) |
| С3 | Провізія — одна ідемпотентна функція `simetra.provision_user`: вставка ідентичності `ON CONFLICT DO NOTHING`, відкладений FK на довідник. Її викликає тригер на таблиці користувачів провайдера в тій самій транзакції (Supabase, Better Auth, Auth.js) або JIT при першій перевіреній сесії (зовнішні IdP). На Supabase `id` користувача = id облікового запису. Інтерфейс адаптера провайдера ідентичності: тип ключа, хук провізії, `verifySession`, мапінг claims | тригер — єдиний спосіб атомарно з реєстрацією; PK `identities` дає унікальність під конкуренцією (§5) |
| С4 | Видалення облікового запису робить користувача `invalid`; FK на таблицю провайдера немає; знеособлення — явна команда для реквізитів із новою властивістю `personalData`; фізичне видалення — лише рядка, на який ніщо не посилається | провайдер видаляє облікові записи без блокування, а сліди роботи живуть (§6) |
| С5 | `simetra.current_user_id()` (`SECURITY DEFINER`, `STABLE`, над claims запиту) заміняє `auth.uid()` у контракті платформи; для недійсного користувача повертає `NULL`. Агенти й act-as: ефективний користувач — у `sub`, агент — у claim `act` (RFC 8693) і в журналі | контракт сесії не залежить від провайдера (§7) |
| С6 | Членство в тенанті — декларативна властивість `membership` на скоупленому довіднику застосунку: платформа виводить `UNIQUE (скоуп, користувач)`, функцію «мій учасник у скоупі» і типову функцію множини. Профіль у тенанті, запрошення й ролі — застосунок. Авторство (`createdBy`/`updatedBy` за прапорцем `trackAuthor`) посилається на «Користувачі» з restrict | учасник — об'єкт обліку з реквізитами тенанта, тож таблицею платформи бути не може; механізм членства кожен застосунок інакше пише заново (§8) |
| С7 | RLS Supabase спирається на claims JWT, а не на таблиці `auth`: сервіси (PostgREST, GraphQL, Storage, Realtime) на кожен запит ставлять роль і `request.jwt.claims`, а `auth.uid()` / `auth.jwt()` лише читають цей параметр. Тому `simetra.current_user_id()` працює всюди, де працює `auth.uid()` | жодна функція й політика Storage чи Realtime не читає таблиць `auth`; сам Supabase позначає `auth.uid()` застарілою (§7.1) |
| С8 | Інваріант адаптера Supabase: `id` рядка «Користувачі» = `auth.users.id`; FK на `auth.users` немає | тоді для дійсного користувача `current_user_id()` = `auth.uid()`, а `owner_id` у Storage = id користувача; FK блокує видалення облікового запису в Auth (§7.1) |
| С9 | Кожна політика, яку генерує платформа (дані, Storage, Realtime), кличе функцію лише в обгортці `(select simetra.current_user_id())`; голий виклик платформа відхиляє | без обгортки функція рахується на кожен рядок; лінтер Supabase цієї функції не знає (§7.1) |
| С10 | Тригер провізії на таблиці провайдера — `SECURITY DEFINER` і мінімальний; це **платформний виняток** із правила Р21 «запис лише командами»: він пише «Користувачі» поза командами за задумом, як і підписки на таблицях провайдера | реєстрацію виконує сервіс провайдера, а не команда платформи; помилка тригера скасовує реєстрацію (§5) |
## 3. Системна схема `simetra`: вміст і безпека

**Вміст.** Те, що одне на інстанс, належить механізму платформи й не
читається ролями API напряму:

| Об'єкт | Призначення |
| --- | --- |
| marker, ledger, очікувані звуження | стан застосованої конфігурації (платформна спека §6.1); записи промоції (спека промоції Пр2, Пр5) |
| `identities` | зв'язок «провайдер + subject → користувач» (§4) |
| лічильники нумерації | одна таблиця на всі об'єкти; ключ виду — мітка виду (спека промоції §9.11), скоуп, період (платформна спека Р25) |
| outbox-таблиця | транспорт подій, коли профіль провайдера не має `pgmq` (платформна спека §6.12) |
| журнал DDL поза платформою | сигнал дрейфу (платформна спека §6.12) |
| функції сесії й адаптера | `current_user_id()`, провізія, недійсність ідентичності, тригерні функції адаптера, функція тригера подій DDL |

Скоуплені дані тенанта (дати закриття періодів, історія версій об'єктів),
довідник «Користувачі» й довідники учасників — у схемах застосунку: їх читають
PostgREST, RLS-шаблони й embed.

**Безпека.**

- Власник схеми й усіх її об'єктів — роль мігратора (та, що застосовує плани).
- `REVOKE ALL` на схему від `PUBLIC`; `USAGE` — лише ролям, яким потрібні
  функції сесії. Жодного гранту на таблиці `simetra` ролям застосунку:
  таблиці читають і пишуть лише `SECURITY DEFINER`-функції платформи з
  `SET search_path = ''` (платформна спека §6.7). `EXECUTE` — явний на кожну
  службову функцію.
- PostgREST схему не експонує.
- Компілятор резервує ім'я: метадані застосунку з PG-схемою `simetra` —
  помилка.

## 4. Користувачі: `identities` і системний довідник

**`simetra.identities`** — закрита таблиця зв'язку:

- `provider` — ключ провайдера з пресету (для OIDC містить видавця `iss`, бо
  `sub` унікальний лише в межах видавця); `subject` — ідентифікатор у
  провайдера як рядок; `user_id` — ключ рядка «Користувачі»;
- `PRIMARY KEY (provider, subject)` — одна зовнішня ідентичність дає рівно
  одного користувача;
- `UNIQUE (user_id, provider)` — один обліковий запис провайдера на
  користувача; кілька провайдерів на користувача дозволено (зміна провайдера
  — новий рядок, потім видалення старого);
- FK на «Користувачі» — `DEFERRABLE INITIALLY DEFERRED`, щоб провізія могла
  вставити ідентичність першою;
- жодних персональних даних — лише ключ.

**Системний довідник «Користувачі».** Довідник без скоупу, один на проєкт;
його оголошує платформа в схемі застосунку, а шаблон застосунку постачає
готовим. Стандартні реквізити ролі «користувачі» виводить реєстр видів:

| Реквізит | Хто пише | Сенс |
| --- | --- | --- |
| ключ `id` | платформа | на нього посилаються дані; не перевикористовується |
| найменування | платформа при провізії, далі застосунок | відображуване ім'я з метаданих провайдера |
| `userKind` (людина, агент) | лише платформа | агенти MCP і службові дії — теж користувачі |
| `invalid` | лише платформа | 1С `Недействителен`: вхід заборонено, посилання живі |
| позначка видалення, версія, службові дати | як у довідника | спека П2 §5 |
| власні реквізити | застосунок | контакти, мова, аватар — те, що зазвичай лежить у профілі |

Платформні реквізити захищено двічі, як `predefined_name` (платформна спека
Р24): ролі команд мають `UPDATE` лише на колонки застосунку (колонкові гранти
Postgres), а тригер відхиляє зміну платформних колонок і фізичне видалення
рядка поза платформною командою. Email — не ключ і не стандартний реквізит:
провайдери допускають дублікати й порожні значення, тож контакт — реквізит
застосунку.

## 5. Провізія й адаптер провайдера

**Одна функція.** Усі шляхи сходяться в `simetra.provision_user`: вона
вставляє ідентичність з `ON CONFLICT DO NOTHING`; якщо ідентичність уже є —
повертає наявного користувача; інакше вставляє рядок «Користувачі». Друга
паралельна вставка чекає першу транзакцію й отримує `DO NOTHING`, тож другого
користувача не з'являється. Функція не викликає логіки застосунку: на
Supabase вона виконується в транзакції реєстрації, і будь-яка помилка зламала
б вхід. Реакції застосунку на нового користувача — підписка на створення
рядка «Користувачі» (спека промоції §9.3) або команда при першому вході.

| Адаптер | Виклик провізії | Атомарність | Недійсність |
| --- | --- | --- | --- |
| Локальна таблиця провайдера (Supabase, Better Auth, Auth.js) | `AFTER INSERT` тригер на таблиці провайдера (дозволена поверхня платформної спеки §6.9); на Supabase `id` = id облікового запису | у транзакції реєстрації | тригери видалення й м'якого видалення облікового запису |
| Зовнішній IdP без рядка в базі (Clerk, WorkOS тощо) | JIT: T3 після перевірки сесії, до першого запиту даних | окрема коротка транзакція | вебхук IdP → платформна команда |

**Інтерфейс адаптера:** тип ключа провайдера, хук провізії (тригер чи JIT),
`verifySession` → claims для `runCommand`, мапінг claims (subject, видавець,
ролі). Схема провайдера лишається поза гейтом за пресетом (платформна спека
§6.9).

**Чому на Supabase `id` = id облікового запису.** Тоді
`current_user_id()` збігається з `auth.uid()`, а наявні дані, що посилаються на
обліковий запис, переходять на «Користувачі» без переписування значень —
лише заміною FK (§10).

**Тригер провізії.** Функції тригера й провізії — `SECURITY DEFINER` з
`SET search_path = ''` у схемі `simetra`: тригер на таблиці провайдера
спрацьовує від ролі сервісу автентифікації, яка не має прав на `simetra` і
схеми застосунку; у варіанті `SECURITY INVOKER` реєстрація падає з відмовою в
доступі. Тригер мінімальний: помилка всередині провізії скасовує й вставку
облікового запису, тобто блокує реєстрацію (перевірено на імітації таблиці
провайдера). Цей тригер — платформний виняток із правила Р21 «запис лише
командами»: він пише «Користувачі» поза командами за задумом, бо реєстрацію
виконує сервіс провайдера, — той самий клас, що й підписки на таблицях
провайдера (спека промоції §9.3). Шляхом запису застосунку він не є.

## 6. Життєвий цикл

| Подія | Що робить платформа | Чого не робить |
| --- | --- | --- |
| Обліковий запис видалено в провайдера (фізично чи м'яко), вебхук IdP | видаляє рядок `identities`, ставить `invalid` | не видаляє «Користувачі»: посилання авторства й «виконавця» лишаються, а FK на таблицю провайдера немає, тож провайдер видаляє свій рядок без блокування |
| Застосунок блокує людину | платформна команда ставить `invalid` | обліковий запис у провайдера не чіпає |
| Запит на знеособлення | явна платформна команда очищає найменування й реквізити з `personalData` у «Користувачі» й у довідниках учасників, що на нього посилаються; особисті записи стирає `onRootDelete` виду скоупу `user` | рядок не видаляє: id лишається як «знеособлений користувач» |
| Фізичне видалення | лише платформна команда очистки, коли на рядок ніщо не посилається (FK це гарантує) | застосунок і ролі API — ніколи |

`personalData` — нова декларативна властивість реквізиту: застосунок каже,
що особисте, а платформа знає, як знеособити (рамка спеки промоції §1).

## 7. Поточний користувач і act-as

- `simetra.current_user_id()` — `SECURITY DEFINER`, `STABLE`,
  `SET search_path = ''`: шукає ідентичність за провайдером і `sub` з
  `request.jwt.claims` і повертає `user_id`, лише коли користувач не
  `invalid`. Недійсний користувач із чинним токеном отримує `NULL`: RLS нічого
  не показує, команди відхиляються.
- Шаблони RLS і функції множини кличуть її в некорельованій формі
  `(SELECT simetra.current_user_id())` — один раз на запит (платформна спека
  §6.8).
- Контракт сесії — `request.jwt.claims` + `simetra.current_user_id()`;
  `auth.uid()` — деталь адаптера Supabase (§11).
- **Act-as.** Ефективний користувач — у `sub`; агент, що діє від його імені,
  — у claim `act` (RFC 8693) і в журналі. Права перевіряються за ефективним
  користувачем.

### 7.1 Supabase: RLS тримається на claims

**Як влаштовано.** PostgREST перевіряє JWT і робить `SET LOCAL ROLE` за claim
`role`, а claims кладе в `request.jwt.claims`; Storage і Realtime ставлять ту
саму роль і той самий параметр у своїй транзакції (Postgres Changes — на кожну
подію WAL для кожного підписника); GraphQL іде як RPC PostgREST.
`auth.uid()` і `auth.jwt()` — прості SQL-функції над цим параметром, без
жодного звернення до таблиць. Жодна функція схем Storage, Realtime і GraphQL
не згадує `auth`, а FK на `auth.users` мають лише таблиці самої схеми `auth`;
FK власника об'єктів Storage на `auth.users` знято міграцією Storage, тож
застереження документації про блокування видалення власника файлів
неактуальне. Supabase офіційно приймає JWT сторонніх провайдерів, для яких
рядків у `auth.users` немає взагалі. Отже `simetra.current_user_id()`, що
читає той самий `request.jwt.claims`, працює всюди, де працює `auth.uid()`
(С7). Функції платформи лежать у `simetra`: створювати функції в `auth`,
`storage` і `realtime` провайдер забороняє, а політики й тригери на їхніх
таблицях — дозволяє.

**Інваріант адаптера (С8).** `id` рядка «Користувачі» дорівнює
`auth.users.id` (провізія передає id облікового запису). Тоді для дійсного
користувача `current_user_id()` = `auth.uid()`, а `owner_id` об'єкта Storage
(рядок `sub`) — id користувача. FK з «Користувачі» на `auth.users` немає:
перевірено, що такий FK змушує видалення облікового запису в Auth падати, а з
`CASCADE` — знищує користувача разом зі слідами роботи.

**Обгортка обов'язкова (С9).** Генератор політик — і для таблиць
застосунку, і для `storage.objects`, і для `realtime.messages` — кличе функцію
лише як `(select simetra.current_user_id())`: некорельований підзапит
рахується один раз на запит. Платформа відхиляє голий виклик сама, бо лінтер
Supabase шукає лише `auth.*` і `current_setting`. Виміри на ста тисячах
рядків без індексу: голий пошук в `identities` — 861 мс, голий `auth.uid()` —
73 мс; в обгортці всі варіанти — 3–4 мс; з індексом на колонці власника —
менше 0,2 мс. `SECURITY DEFINER` забороняє планувальнику інлайнити функцію,
але в обгортці це на час не впливає; `STABLE` зберігається, тож функція
придатна й для умови індексу.

**Поведінка (перевірено тими самими налаштуваннями сесії, що їх ставлять
сервіси):**

| Ситуація | `simetra.current_user_id()` | Для порівняння |
| --- | --- | --- |
| дійсний користувач | id користувача | `auth.uid()` — той самий id |
| недійсний користувач із чинним токеном | `NULL` — RLS нічого не показує | `auth.uid()` досі повертає id |
| сторонній IdP із `sub`, що не є UUID | `NULL` без помилки (з рядком `identities` — користувач) | `auth.uid()` валить увесь запит помилкою приведення до uuid |
| `anon` без `sub` | `NULL` | `NULL` |
| `service_role` | `NULL` | обходить RLS атрибутом ролі, незалежно від функції |

Платформні дії від службового користувача тому не спираються на `NULL`, а
ставлять явні claims чи виконуються як команда з явним виконавцем.

## 8. Членство в тенанті й авторство

**Членство — властивість, а не таблиця платформи й не вид.** Учасник
тенанта — повноцінний об'єкт обліку: на нього посилаються авторство,
виконавці, виміри регістрів, і в кожному тенанті він має власні реквізити.
Тому це довідник застосунку зі скоупом виду тенанта, а платформа додає
декларативну властивість `membership`, що називає реквізит-посилання на
«Користувачі». Платформа виводить:

- `UNIQUE (носій скоупу, користувач)` — один учасник на користувача в тенанті;
  посилання nullable (запрошений без облікового запису);
- функцію «мій учасник у скоупі»;
- типову функцію множини виду скоупу за членством, яку проєкт обирає замість
  дослівного SQL.

Профіль у тенанті (ім'я, посада, ставки), запрошення й правила їх прийняття,
ролі й адміністратори — реквізити й об'єкти застосунку. Доступ до кількох
тенантів — кілька рядків членства одного користувача; активний тенант —
питання маршруту, а не схеми.

**Корінь виду скоупу `user`** — довідник «Користувачі», а не таблиця
провайдера (§10).

**Авторство.** Прапорець виду `trackAuthor` дає стандартні реквізити
`createdBy`/`updatedBy` — `Ref` на «Користувачі» з restrict (спека промоції
Пр8), їх заповнює `runCommand` з `current_user_id()`. Ціль — користувач, а не
учасник: агенти діють у багатьох тенантах без членства, нескоуплені об'єкти й
однотенантні застосунки членства не мають, а авторство має пережити вихід з
тенанта. «Автор у тенанті» — з'єднання за унікальністю членства. Власні
посилання застосунку на учасника (виконавець, менеджер) — звичайні `Ref` на
довідник учасників.

## 9. Що модель прибирає в першого споживача

Три рівні першого споживача правильні; дефекти — у тому, що кожен механізм
застосунок написав сам (узагальнено):

- **провізію написано двічі** — дві функції реєстрації, одна без
  `ON CONFLICT`; модель дає одну ідемпотентну функцію платформи;
- **профіль без FK на обліковий запис** — після видалення облікового запису
  профіль лишається сиротою, а пов'язаний 1:1 запис із каскадом зникає;
  модель дає один рядок «Користувачі» і недійсність замість видалення;
- **email скопійовано тригерами** й зроблено унікальним суворіше, ніж у
  провайдера; модель не має email як ключа;
- **«мій учасник у тенанті» написано тричі** з різними правами `EXECUTE`;
  модель виводить одну функцію з `membership`;
- **видалення облікового запису блокують численні FK** слідів роботи;
  модель не має FK на таблицю провайдера, а людина стає недійсною.

## 10. Перехід наявного споживача й промоція

- **До появи довідника «Користувачі»** промоція йде за тимчасовим правилом
  спеки промоції §9.10: власник особистих записів промотується як носій
  скоупу виду `user` із зовнішнім коренем на таблиці провайдера; профіль і
  членство лишаються `CustomTable`; таблиця з FK авторства на провайдера
  отримує гучну відмову.
- **Поява довідника** — промоція профілю: профіль стає довідником
  «Користувачі», `identities` засівається з наявних облікових записів, тригер
  провізії заміщує функції реєстрації застосунку.
- **Остаточний крок** — запланована заміна FK: корінь виду скоупу `user` і
  всі FK на таблицю провайдера переходять на «Користувачі». На Supabase id
  користувача дорівнює id облікового запису, тож значення в даних не
  переписуються; змінюються лише FK. Каскади й `SET NULL` на таблицю
  провайдера стають restrict окремими дозволеними кроками (спека промоції
  §9.5).
- **Членство** — промоція довідника учасників із властивістю `membership`;
  власні функції «мій учасник» і функція множини на `auth.uid()` замінюються
  виведеними.

## 11. Поправки до інших специфікацій і прогалини в репо

### 11.1 Поправки

Вносяться після рев'ю цієї спеки, з власником.

| Де | Зараз | Пропозиція |
| --- | --- | --- |
| Платформна спека Р21, §8.4 | claims через `request.jwt.claims`, тож `auth.uid()`, RLS-предикати й гарди однакові для обох дверей | контракт сесії — `request.jwt.claims` + `simetra.current_user_id()`; `auth.uid()` — деталь адаптера Supabase; act-as — claim `act` |
| Платформна спека Р21, §8.4 («лише згенеровані або явні серверні команди») | запис у таблиці застосунку — лише командами | платформні винятки, названі явно: тригер провізії на таблиці провайдера пише «Користувачі», підписки на таблицях провайдера реагують на запис поза командами; застосунок таких шляхів запису не отримує (§5) |
| Платформна спека §6.8 (форма RLS-шаблонів) | некорельована форма `колонка = ANY(ARRAY(SELECT <функція множини>(…)))` | так само обгортка `(select simetra.current_user_id())` у кожній згенерованій політиці (дані, Storage, Realtime); голий виклик — помилка платформи |
| Платформна спека §6.1 | службова схема `simetra` тримає marker і ledger | склад схеми — §3 цієї спеки: ще `identities`, лічильники нумерації, outbox-таблиця, журнал DDL, функції сесії й адаптера; даних тенанта немає |
| Платформна спека §6.7 | гранти й межа виконання для схем застосунку | схема `simetra`: власник — роль мігратора, ролі застосунку без грантів на таблиці, лише явний `EXECUTE` на службові функції; поза PostgREST |
| Платформна спека §6.12, Р25 | місце outbox-таблиці, журналу DDL і лічильників нумерації не назване | схема `simetra`; ключ виду в лічильниках — мітка виду (спека промоції §9.11) |
| Платформна спека §4 «Види» (кандидат «членство»); спека П2 §6 і §13 («вид "членство"», «моє» — пізніше) | членство — майбутній вид | членство — декларативна властивість `membership` на скоупленому довіднику застосунку (§8); вид не потрібен |
| Спека П2 §6 (скоуп, корінь виду `user`) | корінь виду скоупу `user` — зовнішня таблиця провайдера | корінь — системний довідник «Користувачі»; зовнішній корінь — лише перехідний стан (§10) |
| Спека П2 §5 (стандартні реквізити) | — | роль довідника «користувачі» з платформними реквізитами `userKind`, `invalid`; прапорець виду `trackAuthor` → `createdBy`/`updatedBy`; властивість реквізиту `personalData` |
| Спека П2 §10.1 (синтетичний домен) | членство — `CustomTable` з FK на `auth.users`; корінь `user` — користувач провайдера | довідник «Користувачі», довідник учасників із `membership` |

### 11.2 Прогалини в репо

- Компілятор не резервує PG-схему `simetra` для метаданих застосунку
  (зарезервоване лише ім'я виду скоупу — `packages/simetra/src/compiler/messages.ts`).
- Вид скоупу `user` референсного домену має корінь на таблиці користувачів
  провайдера (`examples/reference/metadata/project.meta.json`).
- Функція множини референсного домену кличе `auth.uid()`
  (`examples/reference/metadata/sql/app/accessible_user_ids.sql`).

## 12. Відкриті питання

| Питання | Пропозиція |
| --- | --- |
| Склад `userKind`: людина й агент ухвалені; чи потрібні окремо анонімний і службовий користувач | вирішити в плані разом з адаптером Supabase (анонімні входи провайдера) і регламентними завданнями |
| Як платформа рендерить вміст `simetra` (з версії пакета, а не з метаданих), як каталожний гейт бачить його дрейф і як схема з'являється при першому застосуванні | платформний шар бажаного стану; marker фіксує версію платформи, тож зміна шару — звичайний план; деталі — план П3 |
| Видимість «Користувачів» (RLS): яку функцію множини платформа дає за замовчуванням | «я + користувачі, що мають учасника в моїх скоупах», коли в проєкті є `membership`; застосунок може дати свою |
| Id користувача в claims (custom access token hook) як оптимізація | ціна — недійсність діє лише після спливання токена; рішення — за вимірами |
| Стандартний реквізит недійсності учасника (вихід з тенанта без видалення) | вивести з `membership`, як `invalid` у «Користувачі» |
| Прив'язка ідентичності до запрошеного користувача без облікового запису і зміна провайдера | платформна функція прив'язки ідентичності; деталі — план |
| Форма журналу act-as | разом з історією версій об'єктів і outbox (платформна спека Р28) |
| Realtime Broadcast і Presence кешують авторизацію на час з'єднання: недійсність користувача діє лише з наступного приєднання до каналу чи оновлення токена (Postgres Changes перевіряє на кожній події) | прийняти як відоме обмеження; чи потрібне примусове від'єднання — вирішити з realtime-сигналами |
| Живі сервіси стека (PostgREST, Storage, Realtime) не проганялися: локально PostgREST не запущений, запити відтворено тими самими налаштуваннями сесії, що їх ставлять сервіси (підтверджено кодом Storage і функцією Realtime) | прогін через живі сервіси — у тестах адаптера Supabase |
