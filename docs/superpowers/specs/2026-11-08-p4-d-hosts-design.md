## 1. Мета й межі П4-D

П4-D дає застосунку екрани з декларації: хости сторінок (список, картка,
створення, пікер, прев'ю), примітиви, форми, теми, переклади, хост діалогу,
гейти хостів, Vite-плагін, шаблон host-а й правила лінту споживача (спека
П4 §2). Критерій успіху платформи — сторінка списку чи картки як один рядок
із параметрами (платформна спека §1).

**Тонкий зріз іде першим** (рішення власника 2026-11-06): одразу після
серії B3 спеки П4-B (§13) і до B2. Мета зрізу — довести вертикаль на
справжній базі: браузер → Server Function → `createDataHandler` →
`CommandRuntime` → Postgres під RLS → ядро T4 → хост T5 → маршрут T6,
з SSR, сесією й гейтами Р36 і Р42. Вигляд зрізу — без візуальної мови.

| Входить у зріз | Решта П4-D (після візуальної мови) |
| --- | --- |
| шаблон host-а на TanStack Start: одна Server Function даних, серверний entry, SSR, сесія Better Auth, профіль `postgres` (§3, §4) | адаптер сесії Supabase Auth і профіль `supabase` у шаблоні |
| хост списку довідника на `useRows` і `VirtualList` (§5.1) | фільтри, пошук, види, масові дії, стан списку в URL |
| хост картки довідника на `useRow`: шапка з редагуванням через чернетку форми, ТЧ лише для читання (§5.2) | редагування ТЧ, створення, позначка видалення, хост створення, хост діалогу, прев'ю |
| поля для читання й редагування за логічним типом без оформлення (§5.3) | примітиви shadcn на Base UI, теми, токени візуальної мови, decimal.js і Temporal на межі полів |
| підписи — логічні імена (Дх6) | `title`, переклади UI |
| посилання показуємо через `include` | пікер посилань, поліморфний `include` |
| `entityListRoute`, `entityCardRoute` і адаптер навігації на TanStack Router у T6 (§6) | чотири рівні кастомізації (Р11), слоти |
| правила лінту споживача проти пулу `simetra_runtime` поза зв'язуванням рантайму (§4.7) | Vite-плагін, лінт T5 на екранах споживача (Рд45) поза шаблоном |
| оракул заборонених кадрів і мережеві бюджети на шаблоні (§8) | калібрування `resumeMinIntervalMs` і `revalidateIntervalMs` (B5) |
| стиснення відповідей і тест `content-encoding` (§4.5) | `doctor` для ТЧ понад зменшену межу (Рд27) |
| межа тіла Server Function до розбору JSON (§4.4) | dev-попередження хука за порядку без індексу (Рд43) — разом з B1d |
| виклик `resume()` на фокусі й видимості та інтервал рантайму — над B5a (§4.6) | приймач сигналів і звірка прав на фокусі (B5b) |
| **умовно** (Дх12): маршрути токенів Centrifugo й JWKS, якщо ПГ-4 і B2 готові | — |

### 4.2 Server Function даних

Одна Server Function даних (`dataFn`, `POST`) — транспорт клієнтського
рантайму (`DataTransport`, спека П4-B §4.5). Порядок кроків:

1. `verifySession(headers)` (§4.3). `null` — відповідь `command.unauthenticated`
   без виклику обробника.
2. Факти походження з заголовків запиту:
   `{ secFetchSite, origin, expectedOrigin }`, де `expectedOrigin` — канонічне
   походження застосунку з конфігу host-а (змінна середовища серверу), а не з
   заголовка `Host` запиту: заголовок `Host` контролює клієнт.
3. `handler(claims, request, origin)` — обробник сам перевіряє походження
   першим кроком, далі конверт, `subject`, сумісність (спека П4-B §4.5).
4. Відповідь `DataResponse` — як є; виняток поза обробником — `command.internal`
   без тексту й запис у журнал host-а.

Server Function не читає cookies, не ставить ролей і не торкається пулу:
усе це — обробник і рантайм. Серверний рантайм даних (SSR) цю функцію не
кличе (Дх7).

### 4.3 Сесія Better Auth

Конфіг Better Auth шаблону — за спекою профілю `postgres` §4.4: схема
`better_auth`, `advanced.database.generateId: "uuid"`, вхід email і пароль,
без `session.cookieCache`, без плагіна `anonymous` (Дх11). `trustedOrigins` —
те саме канонічне походження, що й `expectedOrigin` (§4.2). Міграцію схеми
Better Auth виконує роль `simetra_auth` (`npx auth migrate`) у скрипті
`db:setup` після `simetra apply`.

Адаптер `verifySession` — функція шаблону над `auth.api.getSession({ headers })`
за §4.4 профілю: `null` → `null`; інакше `{ sub: user.id, is_anonymous:
user.isAnonymous === true }`, `sub` — нижнім регістром.

**Межа зі ПГ-3** (узгоджує архітекторка з автором ПГ-3):

| ПГ-3 | Зріз П4-D |
| --- | --- |
| адресні гранти `better_auth` у `roles`, діагностики `plan.identity-table-missing` і `plan.identity-trigger-locked`, тригер провізії, вибір ролі читання за `anonymousClaim` у T3, DB-тести провізії на таблиці справжньої міграції | конфіг Better Auth шаблону, адаптер `verifySession`, маршрут Better Auth, форма входу, `dev:user`, e2e входу й сесії |

**Dev-користувач** (Дх4). `dev:user` — скрипт поза `src/`: відмовляє, якщо
база не має `simetra.environment = 'development'` або хост бази не loopback
(запобіжник від випадкового запуску, як Рт14); заводить користувача через
`auth.api.signUpEmail` з випадковим паролем і друкує пароль один раз; пароля
не пише ні у файл, ні в репозиторій. Повторний запуск змінює пароль тим
самим API.

### 4.4 Серверний entry

`src/server.ts` (`createServerEntry`) обгортає обробник Start (Дх8):

- **Межа тіла.** `POST` на шлях Server Function: `Content-Length` понад межу
  тіла конверта (сталу T0 B1b-2, орієнтир 4 МБ) — відповідь
  `command.invalid` з `reason: "payload-too-large"` без виклику Start;
  без `Content-Length` — тіло обгорнуто потоком-лічильником, який обриває
  читання на межі тією самою відмовою. Тест — обидва випадки на
  `node-server`.
- **Кеш.** На HTML: `Cache-Control: private, no-store` і `Vary: Cookie`
  (Р41). Відповідь Server Function — `Cache-Control: no-store`.
- **Безпекові заголовки** зрізу — лише ті, що не залежать від оформлення:
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`,
  `frame-ancestors 'none'` у `Content-Security-Policy`. Повна CSP — разом з
  оформленням.

### 4.5 Стиснення

Шаблон доводить стиснення відповіді Server Function і HTML на `node-server`
тестом заголовка `content-encoding` (brotli чи gzip від 1 КіБ, Рд42).
Спосіб — штатна опція Nitro пресета, а якщо її немає для динамічних
відповідей — стиснення в серверному entry. Що стискає край Vercel, план
вимірює на збірці пресета й записує в цей розділ (спека П4-B §14.3).
Бюджети міряють нестиснені байти (Рд39), тож стиснення бюджетів не змінює.

### 4.6 Рантайм даних і SSR

За спекою П4-B §6.6 і планом B3-6, лише штатні опції TanStack Start:

- **Сервер.** Фабрика роутера на кожен запит: `beforeLoad` кореня бере claims
  через Server Function сесії; без сесії рантайму даних немає. З сесією —
  `createDataRuntime({ catalog, transport, subject: claims.sub, residency })`,
  де `transport` — прямий виклик `handler(claims, request, { inProcess: true })`
  (Дх7). Loader-и маршрутів з даними кличуть `preload(spec)`;
  `router.options.dehydrate` віддає знімок з тотожністю, після нього
  рантайм — `dispose()`.
- **Клієнт.** `router.options.hydrate` створює рантайм суб'єкта знімка
  (транспорт — `dataFn`) через `RuntimeHolder.hydrateFrom` до першого
  рендера; ефект кореня один раз кличе `endHydration()`; звірка після
  гідратації — одним запитом `read` з частиною `version`.
- **Опції роутера:** `defaultStaleReloadMode: 'blocking'`, `defaultPendingMs`
  великий, `defaultPendingMinMs: 0`, маршрути з даними — `ssr: true`.
- **Вихід і зміна користувача** — тримач замінює рантайм (виняток безпеки,
  спека П4-B §6.5); після виходу маршрути з даними перенаправляють на вхід.
- **`residency`.** `Country` — `full`, `Client` — `window` (Рд19,
  налаштування рантайму шаблону).
- **`resume()` і інтервал** (Додаток А спеки П4-B) — механізм T4 блоку B5a:
  фокус, видимість і інтервал → `revalidate` видимих виглядів з порогом
  `resumeMinIntervalMs`, один таймер на рантайм, звірка `version` на фокусі.
  Шаблон лише вмикає його в клієнтському рантаймі за API B5a; серверний
  рантайм його не вмикає. Звірка прав на фокусі — B5b.

### 4.7 Лінт споживача

Код host-а, що володіє пулом `simetra_runtime`, — домен довіри `runCommand`
(Рт6). Правила `eslint.config.js` шаблону, з негативним тестом кожного:

- `pg` і будь-який драйвер Postgres імпортує лише `src/server/runtime.ts`
  (зв'язування рантайму) і скрипти поза `src/`;
- рядкові літерали й шаблони з `SET ROLE`, `set_config`, `simetra.` чи
  `request.jwt.claims` поза зв'язуванням рантайму — помилка;
- `simetra/server` імпортує лише `src/server/**`; клієнтський код
  (`src/routes`, `src/client.tsx`, компоненти) його не імпортує — межу збірки
  тримає та сама декларація серверних входів (Рт15).

Правила живуть у шаблоні як конфіг споживача; спільний пакет правил для
застосунків поза шаблоном — решта П4-D.

## 5. Хости T5

Хости — компоненти T5 без власного стилю: семантична розмітка, атрибути
контракту оракула (§5.5) і фіксована геометрія слотів (спека П4-B §6.5,
«Правило розмітки»). Розміри слотів — CSS-змінні з типовими значеннями в
одному файлі T5; візуальна мова замінить значення, а не розмітку.

### 5.1 Список — `ListHost`

`ListHost({ object, orderBy?, include? })`:

- **Дані** — `useRows({ object, orderBy, include, count: true })`; стратегію
  обирає рантайм (Дх6). `include` — типово всі одноцільові `Ref` шапки.
- **Колонки** — не ліниві атрибути шапки в порядку каталогу, без службових
  (ключ, версія, колонка скоупу, мітки пар); заголовок — логічне ім'я (Дх6).
  `Ref` показує представлення цілі з `refs` (§5.3).
- **Рендер** — `VirtualList` B3-3; рядок — фіксованої висоти в зрізі
  (оцінка дорівнює висоті), тож гідратація й прокрутка не рухають видимого.
- **Комірка стану** — перша колонка фіксованої ширини: текстова назва стану
  рядка (§5.4) для скринрідера й `data-state`.
- **Панель вибірки** — слот фіксованої висоти над списком: `refreshing`,
  `hasNewRows`, `needsRefresh`, `count` (лінивий, у слоті), `error`,
  `purged`.
- **Відкриття картки** — клік чи `Enter` на рядку кличе `navigation.openCard(object, key)`
  адаптера навігації. Рядок `removed` картки не відкриває.
- **Без дій зміни** в зрізі: дія рядка — лише «Прибрати» для `removed`.

### 5.2 Картка — `CardHost`

`CardHost({ object, id })`:

- **Дані** — `useRow({ object, id, tabularSections: "all" })`; рядок зі
  сховища показується одразу, ліниві поля й ТЧ доливаються в зарезервоване
  місце (спека П4-B §6.5).
- **Шапка** — поле на кожен атрибут шапки в порядку каталогу, крім службових;
  редаговане, лише коли атрибут має `update: true`, `editable` вигляду —
  `true` і `isStale` — `false`.
- **ТЧ** — таблиця кожної ТЧ лише для читання (Дх5), рядки в порядку номера
  рядка; понад `TABULAR_LINES_MAX` — стан `tabular-too-large` з причиною.
- **Чернетка** — хук T5 `useCardDraft(view)` над TanStack Form за спекою
  П4-B §7.1:
  - база — підтверджений рядок і `version`; кожна правка підвищує ревізію;
  - «Зберегти» шле `writer.update(object, id, changed, { expectedVersion: base })`
    лише зміненими атрибутами; поле показує значення чернетки під час
    збереження;
  - успіх ревізії A — скидає лише поля, не змінені після A, і переносить базу
    на версію результату;
  - `conflict` — правки лишаються; картка показує серверний рядок поруч і дії
    «Взяти серверне» й «Перезаписати»;
  - `failed` — правки лишаються; дії «Повторити» й «Скасувати»;
  - `unknown` — «Перевіряємо результат…», розв'язує квитанція (B3-5);
  - «Скасувати» — скидання на підтверджений рядок одним кадром;
  - вигляд отримав `purged` — чернетку скинуто, показано причину;
  - `isStale` — замість «Зберегти» показано «Потрібне оновлення застосунку».
- **Валідація** — на межі поля: значення нормалізує той самий кодек T0, що й
  ядро (спека П4-B §4.4); `required` і `maxLength` — з каталогу; відмову
  команди `command.invalid` з `path` показано біля поля.
- **Навігація з незбереженою чернеткою** — host попереджає підтвердженням
  роутера (`useBlocker` у T6 через адаптер навігації). Збереження під час
  навігації в зрізі немає.

### 5.3 Поля за логічним типом

| Тип | Показ | Редагування в зрізі |
| --- | --- | --- |
| `String`, `Text` | текст | `input` / `textarea`, `maxLength` з каталогу |
| `Integer`, `SmallInt` | число | `input` з цілим, перевірка меж типу кодеком |
| `BigInt`, `Numeric` | рядок з бази без перетворення на `number` | `input` текстом; нормалізація кодеком T0 (масштаб `scale`) |
| `Boolean` | «так» / «ні» | `checkbox` |
| `Date`, `DateTime` | рядок ISO з бази | `input type="date"` / `datetime-local`; перетворення в рядок ISO кодеком |
| `Ref` на перерахування | мітка значення з `enumValues` | `select` з `enumValues` |
| `Ref` на об'єкт | представлення цілі: атрибут `description`, якщо вид його має, інакше `code`, інакше ключ | лише читання (пікер — поза зрізом) |
| `UUID` | рядок | лише читання |
| `Json`, `Bytes`, масиви, пара `Ref` | «не показується в зрізі» | лише читання |

Правило представлення посилання — факт реєстру виду (стандартні атрибути
`description` і `code`), а не гілка за назвою виду.

### 5.4 Стан → показ → дії

Нормативна семантика — таблиця спеки П4-B §6.5 (Р36); зріз реалізує її
текстом без оформлення:

| Стан | Список | Картка | Дії |
| --- | --- | --- | --- |
| `synced` | без позначки | без позначки | відкрити картку / «Зберегти» за змін |
| `pending` (`await`) | підтверджене значення; «Зберігається…» | значення чернетки; «Зберігається…»; «Зберегти» вимкнено | — |
| `pending` (`predict`) | передбачене значення; «Зберігається…» | те саме | — |
| `unknown` | значення користувача; «Перевіряємо результат…» | те саме | «Скасувати показ» |
| `failed` | значення користувача; «Не збережено» (код у підказці) | правки й код біля поля чи в шапці | «Повторити», «Скасувати» |
| `conflict` | значення користувача; «Змінено іншим» | правки й поточний серверний рядок | «Взяти серверне», «Перезаписати» |
| `stale` (рядок) | значення; «Може бути застарілим» (через 500 мс, B3-3) | те саме; «Зберегти» вимкнено (`editable = false`) | — |
| `stale` (поле) | — | значення поля й позначка поля | — |
| `removed` | слот того самого розміру без значень; «Рядок недоступний» | «Рядок недоступний», чернетку скинуто | «Прибрати» (список) |
| вибірка `loading` | лише без даних: слот завантаження | те саме | — |
| вибірка `refreshing` | «Оновлення…» у панелі; рядки видно | те саме в шапці | — |
| `hasNewRows` | «Є нові рядки — показати» | — | `showNew()` |
| `needsRefresh` | «Список змінився — оновити» | «Картка змінилась — оновити» | `refresh()` |
| виняток безпеки (`purged`) | дані зникають одним кадром; «Доступ змінився — дані приховано» | те саме; чернетку скинуто | оновити сторінку |

**Доступність у зрізі** — лише те, що не залежить від оформлення: комірка
стану має текстову назву стану; зміна стану рядка оголошується
`aria-live="polite"`, виняток безпеки — `assertive`; кожна дія — кнопка,
доступна з клавіатури. Повна перевірка — з оформленням (спека П4-B §6.5).

### 5.5 Контракт DOM оракула

Хости ставлять атрибути контракту записувача B3-6: `[data-region]` на
списку, панелі й картці; `[data-row-key]` і `[data-state]` на рядку;
`[data-field]` на полі; `[data-scroll]` на області прокрутки;
`[data-loading]`, `[data-skeleton]`, `[data-stream-slot]` на слотах. Атрибути
ставить T5, а не застосунок: хост, зібраний з T5, проходить оракул без
розмітки екрана.

## 6. Маршрути й навігація (T6)

- **Інтерфейс адаптера навігації** — T5 (`NavigationAdapter`:
  `openCard(object, key)`, `openList(object)`, `blockWhile(dirty)`), провайдер
  — T5. Реалізація на TanStack Router — T6 (`routerNavigation`).
- **Маршрути з одного рядка:**

  ```text
  createFileRoute('/clients/')(entityListRoute(Client))
  createFileRoute('/clients/$id')(entityCardRoute(Client))
  ```

  `entityListRoute(object, options?)` дає опції маршруту: `loader` з
  `preload` вигляду списку, `component` з `ListHost`, `ssr: true`.
  `entityCardRoute(object)` — те саме для `useRow` і `CardHost`, `id` з
  параметрів шляху. `object` — логічне посилання `{ kind, name }`; невідомий
  у каталозі об'єкт — помилка під час створення маршруту (`TypeError`, як
  `createDataRuntime`).
- Шлях маршрутів задає застосунок; T6 шляху не вигадує. `openCard` знаходить
  маршрут картки об'єкта через реєстр, який наповнюють виклики
  `entityCardRoute`.

## 7. Межа T5 / T6 / застосунок

| Що | Де | Чому |
| --- | --- | --- |
| хуки даних, рантайм, тримач | T4 (`simetra/data`, `simetra/data/react`) | спека П4-B Рд5 |
| хости, поля, чернетка, віртуалізатор, інтерфейс навігації | T5 (`simetra/ui`) | Р16: лише React, контракти T4 і інтерфейс навігації |
| маршрути з одного рядка, адаптер навігації, блокування навігації | T6 (`simetra/shell`) | Р16: типовий адаптер на TanStack Router — T6 |
| Server Function, entry, сесія, пул, SSR-фабрика роутера | застосунок шаблону | Start і `better-auth` — лише там (межа фреймворку); пул — домен довіри host-а (Рт6) |

Фабрику роутера з SSR зріз не виносить у T6: опції гідратації — штатні
опції Start, і їхнє перенесення в пакет вимагало б імпорту Start у T6.

## 8. Гейти

### 8.1 Оракул заборонених кадрів

Оракул (Дх9) біжить на шаблоні в Chromium і WebKit, на production- і
dev-збірці, проти справжньої бази стеку `postgres` (`pnpm db:pg:start`) з
тегованою базою прогону (`AGENTS.md`, правила стеку). Сценарії зрізу:

1. SSR-вхід на список `Client` після входу: HTML і перший кадр збігаються,
   після гідратації — лише звірка `version`.
2. Прокрутка вікна `Client` на далекі сторінки й назад (вивантаження й
   повернення знімка показу).
3. Список → картка зі сховища → список у межах `releaseDelayMs`.
4. Правка поля шапки `await` і збереження: значення не блимає старим.
5. Правка з конфліктом (зміна тієї самої картки іншою сесією до збереження):
   правки лишаються, «Взяти серверне» скидає одним кадром.
6. Відмова збереження (`command.invalid` з `path`): правки лишаються, код біля
   поля.
7. Вихід: дані зникають одним кадром, маршрут — вхід.
8. `full`-список `Country` з SSR.
9. Повернення фокуса після зовнішньої зміни видимого рядка (B5a): значення
   оновлюється на місці, склад і порядок не змінюються; новий рядок дає лише
   `hasNewRows`.

Кожен сценарій має кінцеву умову ефекту дії за правилом Р9 плану B3-6
(стан DOM і журнал Server Function з точним результатом). Зовнішню зміну
сценарій робить через `CommandRuntime` від імені другого користувача, а не
через приховане керування застосунком: у шаблоні немає маршруту керування.

### 8.2 Мережеві бюджети

Бюджети спеки П4-B §12 для сценаріїв 1–4, 8 і 9 (рядки `resume()`) (лічильник — обгортка
транспорту T4 у клієнті, звірена з мережевим журналом Playwright, і обгортка
порту бази T3 у зв'язуванні рантайму e2e-збірки). Обгортка порту — лише в
e2e-збірці шаблону (змінна збірки), не в production.

### 8.3 Безпекові кейси e2e

| Кейс | Очікування |
| --- | --- |
| `dataFn` з `Sec-Fetch-Site: cross-site` | `command.forbidden` `origin` |
| `dataFn` без `Sec-Fetch-Site` з чужим `Origin` | `command.forbidden` `origin` |
| `dataFn` без обох заголовків | `command.forbidden` `origin` |
| `dataFn` з `run` з того самого походження без сесії | `command.unauthenticated` |
| тіло понад межу з `Content-Length` і без нього (chunked) | `command.invalid` `payload-too-large` до розбору |
| конверт зі `subject` іншого користувача | `command.unauthenticated` `session-changed` |
| HTML з даними | `Cache-Control: private, no-store`, `Vary: Cookie` |
| SSR сесії A, потім вхід B у тій самій вкладці | жодного значення A в DOM після заміни рантайму |
| анонімний запит сторінки з даними | перенаправлення на вхід; знімка в HTML немає |
| production-збірка (`.output`) | немає `dev:user`, `dev-user`, імені dev-користувача, `signUpEmail` dev-скрипта й рядків паролів; немає `simetra/server/testing` і `simetra/data/testing` |

### 8.4 Інші гейти

- Unit T5 (jsdom): колонки й поля з каталогу, чернетка за контрактом

- Пакування: `simetra/ui` і `simetra/shell` з tarball-а; збірка шаблону з
  tarball-ами на `node-server` і Vercel.

  `packages/frame-oracle` у переліку шляхів. Час ноги план записує сюди.

## 9. Інваріанти зрізу

1. `inProcess` ніколи не доходить до обробника з HTTP-шляху: HTTP-запит
   іде лише через `dataFn`, яка передає факти запиту (Дх7).
2. Перевірка сесії одна для dev і production; production-збірка не містить
   dev-шляху ідентичності (Дх4).
3. Пул `simetra_runtime` і `pg` — лише в зв'язуванні рантайму (§4.7).
4. Рантайм даних на сервері — на запит; анонімний запит його не створює.
5. Хост T5 не імпортує роутера, Start, `better-auth` і `simetra/server`.
6. Відмова збереження не прибирає правок чернетки; виняток безпеки прибирає
   дані й чернетку одним кадром.
7. Сигнал, перечитування й відповідь `run` не змінюють складу й порядку
   видимого списку (Р36) — тримає оракул.
8. Кожен сценарій §8.1 укладається в бюджет §8.2 (Р42).

## 10. Поза зрізом

Решта П4-D (§1, права колонка) і:

- B5b і B6 спеки П4-B — після зрізу: приймач сигналів, знімок прав,
  `useCan`; B2 і маршрути сигналів — умовно (Дх12). До B5b чужа зміна
  доходить до екрана через `resume()` чи інтервал (B5a), `refresh()` і
  перечитування після власного запису;
- профіль `supabase` у шаблоні й адаптер Supabase Auth;
- розгортання на Vercel проти бази, хостований стек, копіювальник
  `create-simetra-app` і публікація — мінімальна доставка;
- дані першого споживача — поза зрізом і поза репозиторієм.
