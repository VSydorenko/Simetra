> **Статус:** чернетка автора спеки П4-D, редакція 2 (після аудиту раунду 1),

## 1. Мета й межі П4-D

П4-D дає застосунку екрани з декларації: хости сторінок (список, картка,
створення, пікер, прев'ю), примітиви, форми, теми, переклади, хост діалогу,
гейти хостів, Vite-плагін, шаблон host-а й правила лінту споживача (спека
П4 §2). Критерій успіху платформи — сторінка списку чи картки як один рядок
із параметрами (платформна спека §1).

**Тонкий зріз іде першим** (рішення власника 2026-11-06): після серії B3
спеки П4-B (§13) і до B2. Мета зрізу — довести вертикаль на справжній базі:
браузер → Server Function → `createDataHandler` → `CommandRuntime` →
Postgres під RLS → ядро T4 → хост T5 → маршрут T6, з SSR, сесією й гейтами
Р36 і Р42. Вигляд зрізу — без візуальної мови.

| Входить у зріз | Решта П4-D (після візуальної мови) |
| --- | --- |
| шаблон host-а на TanStack Start: одна Server Function даних, серверний entry, SSR, сесія Better Auth, профіль `postgres` (§3, §4) | адаптер сесії Supabase Auth і профіль `supabase` у шаблоні |
| хост списку довідника на `useRows` і `VirtualList` (§5.1) | фільтри, пошук, види, масові дії, стан списку в URL |
| хост картки довідника на `useRow`: шапка з редагуванням через чернетку форми, ТЧ лише для читання (§5.2) | редагування ТЧ, створення, позначка видалення, хост створення, хост діалогу, прев'ю |
| поля для читання й редагування за логічним типом без оформлення (§5.3) | примітиви shadcn на Base UI, теми, токени візуальної мови, decimal.js і Temporal на межі полів |
| підписи — логічні імена; тексти станів — мінімальний каталог повідомлень `en`/`uk` (Дх6, Дх13) | `title`, повні переклади UI |
| посилання показуємо через `include` | пікер посилань, поліморфний `include` |
| `entityListRoute`, `entityCardRoute` і адаптер навігації на TanStack Router у T6 (§6) | чотири рівні кастомізації (Р11), слоти, параметр `filter` маршруту списку |
| правила лінту споживача — гігієна домену довіри пулу (§4.7) | Vite-плагін, лінт T5 на екранах споживача (Рд45) поза шаблоном |
| оракул заборонених кадрів і мережеві бюджети на шаблоні (§8) | калібрування `resumeMinIntervalMs` і `revalidateIntervalMs` |
| стиснення відповідей на `node-server` і тест `content-encoding` (§4.5) | стиснення й межа тіла на краю Vercel — мінімальна доставка (§4.5) |
| межа тіла кожного не-`GET` запиту до розбору (§4.4) | `doctor` для ТЧ понад зменшену межу (Рд27) |
| виклик `runtime.resume()` на фокусі й видимості; інтервал рантайму B5a (§4.6) | приймач сигналів і звірка прав на фокусі (B5b) |
| **умовно** (Дх12): маршрути токенів Centrifugo й JWKS | dev-попередження хука за порядку без індексу (Рд43) |

Тест: дерево `template/` і його `package.json` не містять посилань на `test-host`, `frame-oracle` і `simetra/*/testing` (рішення архітекторки 2026-11-08) | спека П4-B §12 і Рд38 роблять оракул гейтом шаблону; копія правил у двох місцях розійшлася б; новий пакет вимагав би рішення власника (`AGENTS.md`: окремий пакет — одиниця з власним життєвим циклом); застосунок споживача, скопійований із шаблону, не мусить нести тестового коду | спека П4-B §12 — оракул як гейт шаблону (Додаток А) |

- Нові залежності T5 і T6 — необов'язкові peer входів `./ui` і `./shell` з
  точним dev-піном (як `@tanstack/react-virtual` у B3-3). `@tanstack/react-form`
  — сімейство, яке Р35 лишає; версію й ліцензію план перевіряє за
  `CONTRIBUTING.md`. Пін Better Auth — той, що закріплює план ПГ-3.
- Вхід `./ui` у `tsdown` і `publishConfig.exports` дає B3-3; зріз додає
  `./shell` і оновлює перевірку необов'язкових peer у тесті пакування.
- Лінт-зона ярусів не змінюється: `FRAMEWORK_PATTERN` уже забороняє T5
  роутер, Start і бібліотеки рушія даних, а `@tanstack/react-form` і
  `@tanstack/react-virtual` під заборону не потрапляють. Межа фреймворку
  (`AGENTS.md`: TanStack Start — лише в шаблоні host-а й студії) потребує
  лише того, щоб зона дозволяла Start саме в
  `packages/create-simetra-app/template/**`; негативний тест — імпорт Start у
  `packages/create-simetra-app/src` відмовлено, у `template/` — прохід.

| `src/instrument.ts` | порожні точки інструментування (`wrapTransport`, `wrapDatabase`, `onDataResponse`, `markHydrated`); e2e-збірка підміняє модуль аліасом (Дх9) |

Цілі збірки — пресети Nitro `node-server` (еталонна ціль, e2e) і Vercel
(збірка зелена; розгортання — мінімальна доставка). Обхід #8139,
дедуплікація пакета під `link:` (`resolve.dedupe`) і перевірка версії Rolldown
у дереві — за [звітом П0 (а)](2026-11-04-p0-a-host-report.md) («Рішення, що
пропонуються»).

**Конфіг сервера.** `SIMETRA_APP_ORIGIN` — канонічне походження застосунку
(схема, хост, порт без шляху); на старті сервер перевіряє, що значення
канонічне (`new URL(v).origin === v`), інакше відмовляє стартувати.
`BETTER_AUTH_SECRET` у production обов'язковий: без нього — відмова старту.

### 4.2 Server Function даних

Одна Server Function даних (`dataFn`, `POST`) — транспорт клієнтського
рантайму (`DataTransport`, спека П4-B §4.5). Порядок кроків:

1. **Походження першим.** Факти `{ secFetchSite, origin, expectedOrigin }`
   з заголовків запиту й `SIMETRA_APP_ORIGIN` (ніколи з `Host` чи
   `X-Forwarded-*`); `checkRequestOrigin` T3 (зріз експортує її з
   `simetra/server`) відмовляє — `command.forbidden` `origin` без кроку
   далі: міжсайтовий запит не доходить і до `getSession`, яка може
   продовжити сесію записом у базу й `Set-Cookie`.
2. `verifySession(headers)` (§4.3); `null` чи анонімна сесія — відповідь
   `command.unauthenticated` без виклику обробника.
3. `handler(claims, request, origin)` — обробник ще раз застосовує правило
   походження першим кроком, далі конверт, `subject`, сумісність (спека
   П4-B §4.5).
4. Відповідь `DataResponse` — як є; виняток поза обробником —
   `command.internal` без тексту й запис у журнал host-а.

Server Function не читає cookies сама, не ставить ролей і не торкається
пулу. Серверний рантайм даних цієї функції не кличе (Дх7).

**Інші серверні функції й loader-и не віддають тексту помилки.** Server
Function сесії ловить виняток і повертає `null`; `errorComponent` кореня в
production показує лише код; помилка `pg` (хост, роль) клієнту не
серіалізується.

### 4.3 Сесія Better Auth

Конфіг шаблону — за спекою профілю `postgres` §4.1 і §4.4:

| Опція | Значення |
| --- | --- |
| база | пул `auth-db.ts`, `database.schemaName: "better_auth"`, `advanced.database.generateId: "uuid"` |
| `baseURL` | `SIMETRA_APP_ORIGIN` |
| `trustedOrigins` | `[SIMETRA_APP_ORIGIN]` |
| `secret` | `BETTER_AUTH_SECRET` (§4.1) |
| `emailAndPassword` | `{ enabled: true, disableSignUp: true }` (Дх4) |
| плагіни | `anonymous` (Дх11) |
| `session.cookieCache` | вимкнено |
| `rateLimit` | `{ enabled: true, storage: "database" }`; окреме правило для `/sign-in/email` |
| IP клієнта | `advanced.ipAddress.ipAddressHeaders` — на ціль: `node-server` без проксі — заголовків не довіряємо; за проксі й на Vercel — заголовок, який ставить сам проксі |
| cookie | `HttpOnly`, `SameSite=Lax`, `Secure` для `https` (правило П4-B §4.5 спирається на `Lax`) |

Адаптер `verifySession` над `auth.api.getSession({ headers })` — за §4.4
профілю: `null` → `null`; інакше `{ sub: user.id, is_anonymous:
user.isAnonymous === true }`, `sub` — нижнім регістром. `is_anonymous` —
завжди булеве значення, ніколи не пропущене: профіль з `anonymousClaim` ≠
`null` вимагає claim аноніма в запиті з суб'єктом (ПГ-3, Р8).

**Межа зі ПГ-3** (узгоджує архітекторка з автором ПГ-3):

| ПГ-3 | Зріз П4-D |
| --- | --- |
| адресні гранти `better_auth` у `roles`, діагностики `plan.identity-table-missing` і `plan.identity-trigger-locked`, тригер провізії, вибір ролі читання за `anonymousClaim` у T3, DB-тести провізії на таблиці справжньої міграції, пін Better Auth | конфіг Better Auth шаблону, адаптер `verifySession`, маршрут Better Auth, форма входу, `db-setup`, `dev-user`, e2e входу й сесії |

**База розробника** (`db-setup`), порядок спеки профілю §4.2: `simetra roles`
від суперкористувача стеку (створює `simetra_auth` і схему `better_auth`) →
міграція Better Auth (`npx auth migrate` від `simetra_auth`) → повторний
`simetra roles` (адресні гранти на `better_auth."user"`) → `simetra apply`
від `simetra_owner`.

**Dev-користувач** (Дх4). `dev-user` — скрипт поза `src/`:

- запобіжник — та сама семантика, що guard даних designer
  (`packages/designer/src/io/data.ts`): ознака `simetra.environment =
  'development'` рівня бази (`ALTER DATABASE … SET`), а не сесійне
  `options=-c …` чи налаштування ролі, і хост бази loopback; інакше відмова;
- заводить користувача власним екземпляром Better Auth з дозволеною
  реєстрацією; пароль — випадковий, друкується один раз, не пишеться ні у
  файл, ні в репозиторій;
- повторний запуск для наявного користувача змінює пароль через внутрішній
  адаптер Better Auth (точне API — за піном ПГ-3).

### 4.4 Серверний entry

`src/server.ts` (`createServerEntry`) обгортає обробник Start (Дх8):

- **Межа тіла.** Тіло не-`GET`/`HEAD` запиту: `Content-Length` понад межу тіла
  конверта (стала T0 B1b-2, орієнтир 4 МБ) — відповідь `command.invalid` з
  `reason: "payload-too-large"` без виклику Start; без `Content-Length` — тіло
  обгорнуто потоком-лічильником (`duplex: "half"`), який на межі кидає
  сентинел-помилку; entry ловить її й відповідає тією самою відмовою.
  `Content-Encoding` тіла, відмінний від `identity`, — `command.invalid`.
- **Кеш.** Кожна неасетна відповідь — `Cache-Control: no-store`; HTML —
  `Cache-Control: private, no-store` і `Vary: Cookie` (Р41).
- **Безпекові заголовки** зрізу — ті, що не залежать від оформлення:
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`,
  `Content-Security-Policy: frame-ancestors 'none'`. Повна CSP — з
  оформленням.

### 4.5 Стиснення

Шаблон доводить стиснення відповіді Server Function і HTML на `node-server`
тестом заголовка `content-encoding` (brotli чи gzip від 1 КіБ, Рд42). Спосіб
— штатна опція пресета Nitro для динамічних відповідей, а якщо її немає —
стиснення в серверному entry. Стиснення й межа тіла на краю Vercel без
розгортання не видно: обидва рядки спеки П4-B §14.3 для Vercel переходять
у мінімальну доставку. Бюджети міряють нестиснені байти (Рд39).

### 4.6 Рантайм даних і SSR

За спекою П4-B §6.6 і планом B3-6, лише штатні опції TanStack Start:

- **Сервер.** Фабрика роутера на кожен запит; `beforeLoad` кореня бере claims
  через Server Function сесії. Без сесії чи з анонімною сесією рантайму
  даних немає (Дх11). З сесією — `createDataRuntime({ catalog, transport:
  ssrTransport, subject: claims.sub, residency, strict, log })`; рантайм і
  тримач ідуть у контекст роутера (`context.data`), звідки їх беруть
  loader-и маршрутів T6 (`preload(spec)`). `router.options.dehydrate` віддає
  знімок з тотожністю, після нього серверний рантайм — `dispose()`.
- **Клієнт.** `router.options.hydrate` створює рантайм суб'єкта знімка з
  транспортом `dataFn` через `RuntimeHolder.hydrateFrom` до першого рендера;
  ефект кореня один раз кличе `endHydration()`; звірка після гідратації —
  одним запитом `read` з частиною `version`.
- **Колбеки рантайму:** `onSessionChanged` і обгортка транспорту з Дх14 —
  заміна рантайму тримачем і перехід на вхід; `onStaleClient` — банер
  «потрібне оновлення застосунку» в слоті кореня (запис вимикає `isStale`
  хуків); `log` — журнал host-а; `strict: true` у dev-збірці, `false` у
  production (спека П4-B §6.1).
- **Опції роутера:** `defaultStaleReloadMode: 'blocking'`, `defaultPendingMs`
  великий, `defaultPendingMinMs: 0`, маршрути з даними — `ssr: true`.
- **Вихід і зміна користувача** — тримач замінює рантайм (виняток безпеки,
  спека П4-B §6.5).
- **`residency`:** `Country` — `full`, `Client` — `window` (Рд19).
- **`resume()` і інтервал.** `runtime.resume()` кличе host, бо T4 не читає
  `document` (спека П4-B §6.1): клієнт шаблону підписується на
  `visibilitychange` і `focus` і кличе `runtime.resume()` поточного рантайму
  тримача. Поріг `resumeMinIntervalMs`, один таймер інтервалу на рантайм,
  `revalidate` лише видимих виглядів і звірку `version` на фокусі дає блок
  T4 B5a (рішення архітекторки 2026-11-08). Звірка прав на фокусі — B5b.
  Серверний рантайм `resume()` не кличе.
- **`defer`** — на кожен виклик бере `waitUntil` поточного запиту з контексту
  запиту Nitro, а не захоплює функцію першого запиту: рантайм на рівні модуля
  живе довше за запит (Рт17).

### 4.7 Лінт споживача

Код host-а, що володіє пулом `simetra_runtime`, — домен довіри `runCommand`
(Рт6). **Лінт — гігієна цього домену, а не межа безпеки:** він ловить
випадкову помилку, а не навмисний обхід. Правила `eslint.config.js` шаблону,
кожне з негативним тестом:

- `pg` і будь-який драйвер Postgres у `src/` імпортують лише
  `src/server/runtime.ts` і `src/server/auth-db.ts`; `test/` і `scripts/`
  поза правилом;
- змінну `SIMETRA_RUNTIME_DATABASE_URL` читає лише `runtime.ts`;
- рядкові літерали й шаблони з `SET ROLE`, `set_config`, `simetra.` чи
  `request.jwt.claims` у `src/` поза `runtime.ts` — помилка;
- `createRequire` і динамічний `import()` з нелітеральним аргументом у `src/`
  — помилка;
- `simetra/server` імпортує лише `src/server/**`; клієнтський код його не
  імпортує — межу збірки тримає та сама декларація серверних входів (Рт15);
- літерал `inProcess` — лише в `src/server/ssr-transport.ts`; `createServerFn`
  у `ssr-transport.ts` і `router.tsx` — помилка (Дх7);
- `template/` не імпортує `test-host` і `simetra/*/testing`; модуль `#instrument` імпортують лише точки, названі в §4.1 (Дх9).

Спільний пакет правил для застосунків поза шаблоном — решта П4-D.

## 5. Хости T5

Хости — компоненти T5 без власного стилю: семантична розмітка, атрибути
контракту оракула (§5.5) і фіксована геометрія слотів (спека П4-B §6.5,
«Правило розмітки»). Розміри слотів — CSS-змінні з типовими значеннями в
одному файлі T5; візуальна мова замінить значення, а не розмітку. Тексти —
ключі каталогу повідомлень (Дх13).

### 5.1 Список — `ListHost`

`ListHost({ object, orderBy?, include? })`:

- **Дані** — `useRows({ object, orderBy, include, count: true })`; стратегію
  обирає рантайм (Дх6). `include` — типово всі одноцільові `Ref` шапки.
  `orderBy` типово — порядок за ключем.
- **Колонки** — не ліниві атрибути шапки в порядку каталогу, без службових
  (ключ, версія, колонка скоупу, мітки пар); заголовок — логічне ім'я (Дх6).
  `Ref` показує представлення цілі з `refs` (§5.3).
- **Рендер** — `VirtualList` B3-3 з фіксованою висотою рядка в зрізі (оцінка
  дорівнює висоті), тож гідратація й прокрутка не рухають видимого.
- **Комірка стану** — перша колонка фіксованої ширини: текстова назва стану
  рядка (§5.4) і `data-state`.
- **Панель вибірки** — слот фіксованої висоти над списком: `refreshing`,
  `hasNewRows`, `needsRefresh`, `count` (лінивий, у слоті), `error`,
  `purged`.
- **Відкриття картки** — клік чи `Enter` на рядку кличе
  `navigation.openCard(object, key)`. Рядок `removed` картки не відкриває.
- **Без дій зміни** в зрізі: дія рядка — лише «Прибрати» для `removed`.

### 5.2 Картка — `CardHost`

`CardHost({ object, id })`:

- **Дані** — `useRow({ object, id, tabularSections })` з усіма ТЧ об'єкта;
  рядок зі сховища показується одразу, ліниві поля й ТЧ доливаються в
  зарезервоване місце (спека П4-B §6.5).
- **Шапка** — поле на кожен атрибут шапки в порядку каталогу, крім
  службових; редаговане, лише коли атрибут має `update: true`, `editable`
  вигляду — `true` і `isStale` — `false`.
- **ТЧ** — таблиця кожної ТЧ лише для читання (Дх5), рядки в порядку номера
  рядка; понад `TABULAR_LINES_MAX` — стан `tabular-too-large` з причиною.
- **Чернетка** — хук T5 `useCardDraft` над TanStack Form за спекою П4-B §7.1:
  - база — підтверджений рядок і `version`; кожна правка підвищує ревізію;
  - «Зберегти» шле `writer.update(object, id, changed, { expectedVersion: base })`
    лише зміненими атрибутами; поле під час збереження показує значення
    чернетки;
  - успіх ревізії A — скидає лише поля, не змінені після A, і переносить базу
    на версію результату;
  - `conflict` — правки лишаються; картка показує серверний рядок поруч і дії
    «Взяти серверне» й «Перезаписати»;
  - `failed` — правки лишаються; дії «Повторити» й «Скасувати»;
  - `unknown` — «Перевіряємо результат…», розв'язує квитанція (B3-5);
  - «Скасувати» — скидання на підтверджений рядок одним кадром;
  - вигляд отримав `purged` — чернетку скинуто, показано причину;
  - `isStale` — замість «Зберегти» — «Потрібне оновлення застосунку».
- **Валідація** — на межі поля: значення нормалізує той самий кодек T0, що й
  ядро (спека П4-B §4.4); `required` і `maxLength` — з каталогу; відмову
  `command.invalid` з `path` показано біля поля.
- **Навігація з незбереженою чернеткою** — підтвердження через
  `navigation.useBlockWhile(dirty)`. Збереження під час навігації в зрізі
  немає.

### 5.3 Поля за логічним типом

| Тип | Показ | Редагування в зрізі |
| --- | --- | --- |
| `String`, `Text` | текст | `input` / `textarea`, `maxLength` з каталогу |
| `Integer`, `SmallInt` | число | `input` з цілим, межі типу перевіряє кодек |
| `BigInt`, `Numeric` | рядок з бази без перетворення на `number` | `input` текстом; нормалізація кодеком T0 (масштаб `scale`) |
| `Boolean` | «так» / «ні» (ключі каталогу) | `checkbox` |
| `Date`, `DateTime` | рядок ISO з бази | `input type="date"` / `datetime-local`; рядок ISO кодеком |
| `Ref` на перерахування | мітка значення з `enumValues` | `select` з `enumValues` |
| `Ref` на об'єкт | представлення цілі: стандартний `description`, якщо вид його має, інакше `code`, інакше ключ | лише читання (пікер — поза зрізом) |
| `UUID` | рядок | лише читання |
| `Json`, `Bytes`, масиви, пара `Ref` | «не показується в зрізі» | лише читання |

Які стандартні атрибути представлення має вид — факт реєстру виду
(`packages/simetra/src/model/kinds/`), а не гілка за назвою виду.

### 5.4 Стан → показ → дії

Нормативна семантика — таблиця спеки П4-B §6.5 (Р36); зріз реалізує її
текстом без оформлення:

| Стан | Список | Картка | Дії |
| --- | --- | --- | --- |
| `synced` | без позначки | без позначки | відкрити картку / «Зберегти» за змін |
| `pending` (`await`) | підтверджене значення; «Зберігається…» | значення чернетки; «Зберігається…»; «Зберегти» вимкнено | — |
| `pending` (`predict`) | передбачене значення; «Зберігається…» | те саме | — |
| `unknown` | значення користувача; «Перевіряємо результат…» | те саме | «Скасувати показ» |
| `failed` | значення користувача; «Не збережено» (код у підказці) | правки й код біля поля чи в шапці | «Повторити», «Скасувати» |
| `conflict` | значення користувача; «Змінено іншим» | правки й поточний серверний рядок | «Взяти серверне», «Перезаписати» |
| `stale` (рядок) | значення; «Може бути застарілим» (через 500 мс, B3-3) | те саме; «Зберегти» вимкнено (`editable = false`) | — |
| `stale` (поле) | — | значення поля й позначка поля | — |
| `removed` | слот того самого розміру без значень; «Рядок недоступний» | «Рядок недоступний», чернетку скинуто | «Прибрати» (список) |
| вибірка `loading` | лише без даних: слот завантаження | те саме | — |
| вибірка `refreshing` | «Оновлення…» у панелі; рядки видно | те саме в шапці | — |
| `hasNewRows` | «Є нові рядки — показати» | — | `showNew()` |
| `needsRefresh` | «Список змінився — оновити» | «Картка змінилась — оновити» | `refresh()` |
| виняток безпеки (`purged`) | дані зникають одним кадром; «Доступ змінився — дані приховано» | те саме; чернетку скинуто | оновити сторінку |

Тексти в таблиці — значення ключів локалі `uk`; локаль `en` — типова (Дх13).

**Доступність у зрізі** — лише те, що не залежить від оформлення: комірка
стану має текстову назву стану; зміна стану рядка оголошується
`aria-live="polite"`, виняток безпеки — `assertive`; кожна дія — кнопка,
доступна з клавіатури. Повна перевірка — з оформленням.

### 5.5 Контракт DOM оракула

Хости ставлять атрибути контракту записувача B3-6: `[data-region]` на
списку, панелі й картці; `[data-row-key]` і `[data-state]` на рядку;
`[data-field]` на полі; `[data-scroll]` на області прокрутки;
`[data-loading]`, `[data-skeleton]`, `[data-stream-slot]` на слотах. Атрибути
ставить T5, а не застосунок. Глобали обв'язки (`window.__oracleHydrated`,
`__oracleRecoverable`, `__oracleBuild`, `__oracleTransport`) і журнал
Server Function з результатом (Р9 плану B3-6) дає лише **e2e-збірка**
шаблону через `#instrument` (§8.2), не production.

## 6. Маршрути й навігація (T6)

- **Інтерфейс навігації** — T5: `NavigationAdapter { openCard(object, key),
  openList(object), useBlockWhile(dirty) }`, провайдер — T5. Реалізація на
  TanStack Router — T6 (`routerNavigation(router)`).
- **Маршрути з одного рядка:**

  ```text
  createFileRoute('/clients/')(entityListRoute(Client))
  createFileRoute('/clients/$id')(entityCardRoute(Client))
  ```

  `entityListRoute(object, options?: { orderBy?, include? })` дає опції
  маршруту: `loader` з `preload` вигляду списку, `component` з `ListHost`,
  `ssr: true`, `staticData: { simetraList: <id об'єкта> }`.
  `entityCardRoute(object)` — те саме для `useRow` і `CardHost` з `id` з
  параметрів шляху і `staticData: { simetraCard: <id об'єкта> }`. `object` —
  логічне посилання `{ kind, name }`; невідомий у каталозі об'єкт — `TypeError`
  під час створення маршруту.
- **Звідки loader бере рантайм:** з контексту роутера `context.data`
  (тримач), який кладе фабрика роутера шаблону (§4.6). Тип контексту — експорт
  T6 (`SimetraRouterContext`).
- **`openCard`** шукає в дереві маршрутів роутера маршрут зі `staticData.simetraCard`
  об'єкта і переходить на його `fullPath` з `{ id }`; маршруту немає —
  `Error`. Шлях задає застосунок; T6 шляху не вигадує.
- `useBlockWhile` — `useBlocker` роутера.

## 7. Межа T5 / T6 / застосунок

| Що | Де | Чому |
| --- | --- | --- |
| хуки даних, рантайм, тримач, `resume()` | T4 (`simetra/data`, `simetra/data/react`) | спека П4-B Рд5, §6.1 |
| хости, поля, чернетка, віртуалізатор, повідомлення, інтерфейс навігації | T5 (`simetra/ui`) | Р16: лише React, контракти T4 і інтерфейс навігації |
| маршрути з одного рядка, адаптер навігації, тип контексту роутера | T6 (`simetra/shell`) | Р16: типовий адаптер на TanStack Router — T6 |
| Server Function, SSR-транспорт, entry, сесія, пули, SSR-фабрика роутера, підписка на фокус | застосунок шаблону | Start і `better-auth` — лише там; пули — домен довіри host-а (Рт6); `document` T4 не читає |

## 8. Гейти

### 8.1 Оракул заборонених кадрів

Оракул (Дх9) біжить на e2e-збірці шаблону в Chromium і WebKit, у
production- і dev-режимі, проти справжньої бази стеку `postgres`
(`pnpm db:pg:start`) з тегованою базою прогону (`AGENTS.md`, правила
стеку). Сценарії:

1. SSR-вхід на список `Client` після входу: HTML і перший кадр збігаються,
   після гідратації — лише звірка `version`.
2. Прокрутка вікна `Client` на далекі сторінки й назад (вивантаження й
   повернення знімка показу).
3. Список → картка зі сховища → список у межах `releaseDelayMs`.
4. Правка поля шапки `await` і збереження: значення не блимає старим.
5. Правка з конфліктом (зміна тієї самої картки другим користувачем до
   збереження): правки лишаються, «Взяти серверне» скидає одним кадром.
6. Відмова збереження (`command.invalid` з `path`): правки лишаються, код
   біля поля.
7. Вихід у поточній вкладці: дані зникають одним кадром, маршрут — вхід.
8. `full`-список `Country` з SSR.
9. Повернення фокуса після зміни видимого рядка другим користувачем (B5a):
   значення оновлюється на місці, склад і порядок не змінюються; новий рядок
   дає лише `hasNewRows`.
10. Вихід в іншій вкладці, потім фокус першої (Дх14): дані зникають одним
    кадром, маршрут — вхід.

Кожен сценарій має кінцеву умову ефекту дії за правилом Р9 плану B3-6 (стан
DOM і журнал Server Function з точним результатом). Зміну другого
користувача сценарій робить через `CommandRuntime` з фікстури тесту, а не
через керування застосунком: маршруту керування в шаблоні немає.

### 8.2 Мережеві бюджети й e2e-збірка

Бюджети спеки П4-B §12 для сценаріїв 1–4, 8 і 9 (рядки `resume()`):
лічильник транспорту T4 у клієнті (`simetra/data/testing`), звірений з
мережевим журналом Playwright, і обгортка порту бази T3 у зв'язуванні
рантайму. **E2e-збірка** — збірка шаблону з e2e-конфігом Vite
(`packages/create-simetra-app/e2e/vite.e2e.ts`), який аліасом `#instrument`
підставляє лічильник, обгортку порту, журнал Server Function і глобали
обв'язки. Production-збірка бере порожній `src/instrument.ts`; тест складу
(§8.3) перевіряє саме її.

### 8.3 Безпекові кейси e2e

Кожен кейс про походження несе дійсний cookie сесії, тож відмова доводить
саме правило походження, а не відсутність сесії. Позитивний контроль:
`run` того самого походження з сесією — `ok`.

| Кейс | Частина | Очікування |
| --- | --- | --- |
| `dataFn` з `Sec-Fetch-Site: cross-site` | D2 | `command.forbidden` `origin` |
| `dataFn` без `Sec-Fetch-Site` з чужим `Origin` | D2 | `command.forbidden` `origin` |
| `dataFn` без обох заголовків | D2 | `command.forbidden` `origin` |
| `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto` і `Origin` атакувальника | D2 | `command.forbidden` `origin` |
| `dataFn` того самого походження без сесії | D2 | `command.unauthenticated` |
| тіло понад межу з `Content-Length` і chunked; тіло з `Content-Encoding: gzip`; завелике тіло `sign-in` | D2 | `command.invalid` до розбору |
| `POST /api/auth/sign-up/email` | D2 | відмова (реєстрацію вимкнено) |
| вхід зі змінним `X-Forwarded-For` | D2 | межа частоти вичерпується (429) |
| конверт зі `subject` іншого користувача | D2 | `command.unauthenticated` `session-changed` |
| `get-session` і HTML | D2 | `Cache-Control: no-store`; HTML — `private, no-store` і `Vary: Cookie` |
| кожен id серверної функції з маніфесту production-збірки: `POST` з сесією й `Sec-Fetch-Site: cross-site` | D3 | жодна відповідь не несе значень рядків |
| SSR сесії A, потім вхід B у тій самій вкладці | D3 | жодного значення A в DOM після заміни рантайму |
| запит без сесії на сторінку з даними | D3 | перенаправлення на вхід; знімка в HTML немає |
| анонімна сесія Better Auth на сторінку з даними | D3 | HTML без рядків і без знімка; перенаправлення на вхід |
| дерево `template/` і `template/package.json` | D2 | немає `test-host`, `frame-oracle`, `simetra/data/testing`, `simetra/server/testing` |
| production-збірка: маркер `dev-user.mjs`, `simetra/server/testing`, `simetra/data/testing`, лічильник, обгортка порту, глобали обв'язки | D2 | відсутні в `.output` |
| збірка з сентинелами `SIMETRA_RUNTIME_DATABASE_URL`, `SIMETRA_AUTH_DATABASE_URL`, `BETTER_AUTH_SECRET` | D2 | жодного сентинела в `.output/public` |

## 9. Інваріанти зрізу

1. `inProcess` ніколи не доходить до обробника з HTTP-шляху (Дх7).
2. Відмова походження передує будь-якому кроку з сесією (§4.2).
3. Перевірка сесії одна для dev і production; production-збірка не містить
   dev-шляху ідентичності й e2e-обв'язки (Дх4, §8.2).
4. Пул `simetra_runtime` — лише в зв'язуванні рантайму (§4.7).
5. Рантайм даних на сервері — на запит; запит без сесії чи з анонімною
   сесією його не створює.
6. Хост T5 не імпортує роутера, Start, `better-auth` і `simetra/server`.
7. Відмова збереження не прибирає правок чернетки; виняток безпеки, зокрема
   розрив сесії в іншій вкладці, прибирає дані й чернетку одним кадром.
8. Сигнал, перечитування й відповідь `run` не змінюють складу й порядку
   видимого списку (Р36) — тримає оракул.
9. Кожен сценарій §8.2 укладається в бюджет (Р42).

## 10. Поза зрізом

Решта П4-D (§1, права колонка) і:

- B5b і B6 спеки П4-B — після зрізу; B2 і маршрути сигналів — умовно
  (Дх12). До B5b чужа зміна доходить до екрана через `resume()` чи інтервал
  (B5a), `refresh()` і перечитування після власного запису;

- розгортання на Vercel, хостований стек, копіювальник `create-simetra-app`
  і публікація — мінімальна доставка;
- дані першого споживача — поза зрізом і поза репозиторієм.
