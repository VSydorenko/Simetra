# Спайк 1 «ядро» рушія клієнтських даних T4 — звіт

> **Статус:** звіт спайку для архітекторки П4-B. Гілка `spike/t4-core`
> (у `main` не зливається). Код — `packages/simetra/src/data/store/`.
> Вхід: [спека П4-B](2026-11-05-p4-b-client-data-design.md) §1–§7, §8.4,
> §10–§12; рішення власника й архітекторки 08.11 (спільні правила спайків).

## Питання й відповідь

**Питання.** Чи можна збудувати власне ядро T4, у якому клас «стан після
`dispose()` / старе покоління» неможливий за будовою, оптимістичні зміни
мають видимий стан, а перехід «оптимістичне → підтверджене» не дає жодного
проміжного кадру?

**Відповідь: так.** Усі сім критеріїв зелені; доказ кожного — тест чи замір
нижче. Модельний тест знайшов справжню прогалину спеки (Рд24 між появами
ключа) і дефект картки після `purge`. Незалежне рев'ю (лінза «після
`dispose()` / старе покоління») знайшло шість major і один minor. Усі
відтворено, виправлено й закрито регресійними тестами (§4a). Головний
урок рев'ю: «запис лише через `commit` з дійсним поколінням» не покриває
**чужих поколінь даних**. Пізня відповідь живої підмножини, прочитана до
видалення чи `purge`, проходить токен. Звідси надгробки з епохою читання —
другий механізм будови поряд з токенами.

## 1. Прецеденти (крок 0)

Ліцензії перевірено за файлами `LICENSE`: Replicache і Zero
(`rocicorp/mono`) — Apache-2.0 (репозиторій `rocicorp/replicache`
заархівовано, без `LICENSE`); Relay, urql, Apollo Client — MIT; розбір Linear
(`wzhudev/reverse-linear-sync-engine`) — **без ліцензії**, беремо лише ідеї.
Код ніде не скопійовано.

| Система | Підтверджене + журнал | Відмова сервера | Перехід без кадру |
| --- | --- | --- | --- |
| Replicache / Zero | snapshot-коміт + локальні коміти; pull будує окрему голову, replay решти, атомарний swap | мутацію пропущено (Replicache) чи відкочено (Zero) — **тихо** | diff ключів + `deepEqual` результату |
| Relay | store + backup; `run()`: restore → серверні дані → повторне накладання → один `notify` | `revertUpdate`, решта перевиконується | `recycleNodesInto` — структурне спільне використання |
| urql Graphcache | шари за ключем операції; commutative-шари резервують позицію за порядком відправлення | шар відкинуто | — |
| Apollo | ланцюг `Layer` над Root; `removeLayer` + replay | `removeOptimistic` — відкат | `markMutationResult`: запис і зняття шару в одному `batch`, один broadcast |
| React 19 | `useSyncExternalStore`: незмінний кешований знімок, `getServerSnapshot` = перший клієнтський кадр; `useOptimistic` живе лише в transition, стану `failed` не має | — | — |
| Linear | модель у пам'яті змінюється одразу; локальна БД — лише підтверджене; транзакція підтверджена, коли прийшла дельта з версією ≥ | rollback до `original` | — |

**Беремо:** атомарність «зняти мутацію + записати відповідь сервера → одне
сповіщення» (Relay, Apollo); структурне спільне використання знімків (Relay);
мутацію як **дані** (поля), а не функцію, — тож перебазування детерміноване й
дешеве; монотонний id мутації й порядок журналу; правило Linear
«підтверджено, коли версія ≥»; знімок SSR як окреме джерело без сповіщень.

**Не беремо:** тиху відмову (у нас `failed` видимий); глобальний
restore/replay усього сховища на кожну відповідь (у нас — за ключем);
блокування запитів на час мутацій (Graphcache); `useOptimistic` як основу
шару; мутабельну модель (Linear).

**Без прецеденту — власні рішення:** жоден прецедент не тримає відмовлену
зміну видимою; правило поглинання полів (Р1) і стан `unknown` — наші. Захисту
від запису після `dispose()` як класу будови теж не знайдено: найближче —
заборона вкладених оновлень (Relay) і ексклюзивний замок (Linear).

## 2. Будова ядра

| Модуль (у `core.ts`, якщо не сказано інакше) | Що робить |
| --- | --- |
| `Session` | епоха, `AbortSignal`, `dispose()`; **єдина точка змін** `commitInternal(fn, token)` |
| `Scope` | область запису: існує лише під час `fn`; методи сховищ без неї кидають |
| `GenerationToken` | сесійний; підмножини (жива й `gen` поточне); спроби мутації (`attempt` і мутація в журналі) |
| `ObjectStore` (`ObjState`) | рядок за ключем, власники, `stale` з мінімальною версією, `removed`; правило версії — одна функція `mergeVersioned` |
| `SectionStore` | ТЧ власника з `ownerVersion` і повнотою; результат з меншою `ownerVersion` відкидається цілком |
| `SubsetRegistry` | форми §6.1 (`keys`, `card`, `section`, `full`, `window`); утримання; single-flight з одним хвостом; ключі по 200 і навпіл на `response-too-large`; відкладене звільнення |
| `Overlay` | журнал мутацій поверх підтвердженого; черга ключа (`pump`); політики `predict`/`await`; дельта рядка ТЧ на базу ключа |
| `Notifier` / `Views` | ревізії рядків, кеш `RowView` зі структурним спільним використанням, одна пачка сповіщень на `commit` |
| `filter.ts` | мінімальний обчислювач фільтра T0 і компаратор `full` за типом |
| `testing/fake-source.ts` | фейковий сервер (версії, `expectedVersion`, ліниві поля, ТЧ) і керований транспорт |

**Чому клас «після `dispose()`» неможливий за будовою.** Будь-яка асинхронна
гілка (завантаження, відповідь `run`, перечитування ТЧ після запису,
`refetchKeys`, розв'язання `unknown`, таймери утримання) пише лише через
`commitInternal(fn, token)`. Перший рядок — `if (!token.valid) return false`:
токен недійсний після `dispose()`, після перезапиту чи звільнення підмножини,
після скасування чи нової спроби мутації. Методи сховищ вимагають `Scope`,
який існує лише всередині `fn`. Пізня відповідь просто не має чим писати. Це
перевіряє модельний тест: фейк навмисно доставляє відповідь і після обриву
`AbortSignal`, тож захист тримає ядро, а не транспорт.

**Інтерфейс v0** — `types.ts` (контрольна точка 958e32f2, далі — з
повідомленнями архітекторці): `view(spec)` — чиста мемоізована функція;
власність дає лише `subscribe` (вимога спайку 2); звільнення після
`releaseDelayMs`; `preload` з TTL; `begin({ policy })`; `retry`/`cancel`;
`commit(fn, token)` з публічним `Writer` (`patch`, `remove`, `markStale(…,
minVersion)`, `purge`, `markViews`) для спайку 3; `dehydrate`/`hydrate`/
`endHydration`.

**Словник станів** (рішення архітекторки 08.11): `synced`, `pending`
(`pendingFields`), `failed`, `conflict` (з `server`), `stale`, `removed`,
`unknown`; пріоритет `removed` > `conflict` > `failed` > `unknown` >
`pending` > `stale` > `synced`. Власне видалення — `pending` з `deleting` на
місці.

## 4. Модельний тест

**Кроки:** підписка й відписка чотирьох виглядів (`keys` ×2, `card`, `full`);
власна правка обох політик; власне видалення; `purge` (втрата доступу);
відповідь на будь-який виклик у польоті в
будь-якому порядку: `ok`, **застаріла репліка** (стан сервера на мить
запиту), `forbidden`, `conflict`, **невідомий результат** (сервер застосував,
клієнт бачить `unavailable`); чужа правка; чуже видалення; сигнал
(`refetchKeys`); `retry`; `cancel`; плин часу (відкладене звільнення);
`dispose()`; в кінці — пізні відповіді на все, що лишилось. Половина прогонів
стартує з уже завантаженими виглядами.

**Інваріанти після кожного кроку:**

1. після `dispose()` — жодного кадру, жодного нового запиту, сховище й
   реєстр порожні;
2. межа пам'яті: кожен рядок тримає підмножина, реєстр створень чи журнал
   (`violations()` порожній), лічильники власників точні;
3. рядок живої чи відмовленої мутації не витісняється (Р3);
4. версія не зменшується; ключ, що повернувся старшою версією, ніж бачено, —
   лише зі `stale`;
5. показаний рядок = еталон (підтверджений ⊕ живі `predict`-мутації за
   порядком журналу з поглинанням Р1; незалежна проста модель журналу);
6. `await`: між дією й commit відповіді показане значення те саме;
7. правило стабільності: відповідь `run`, сигнал, чужа зміна й
   перечитування ключа не змінюють складу й порядку жодного списку (крім
   підтвердженого власного видалення);
8. підтверджене власне видалення не воскресає (пізня відповідь, репліка);
9. картка ключа, що є у сховищі, ніколи не дає знімка без рядка.

**Чутливість (навмисні дефекти, по одному):**

| Дефект | Модель | Цільовий тест |
| --- | --- | --- |
| без перевірки покоління в `commit` | ловить | — |
| версія може зменшитись | ловить | ловить |
| `await` показує значення | ловить | ловить |
| журнал не тримає рядок | ловить | — |
| чуже видалення прибирає рядок зі списку | ловить | ловить |
| без поглинання полів (Р1) | ловить | — |
| забувати версію при вивантаженні | рідко (1 з ~8 прогонів по 20 тис.) | ловить |
| без надгробка (пізня відповідь воскрешає видалення) | ловить (3 з 3 прогонів) | ловить |

**Знахідки моделі:**

- **Прогалина Рд24 між появами ключа (виправлено).** Підмножина вивантажила
  ключ версії 2. Потім застаріла відповідь вибірки, надіслана раніше,
  вставила його знову з версією 1. Спека §6.2 свідомо прибирає мапу версій з
  вивантаженням ключа, тож користувач побачив би відкат. Ядро тепер пам'ятає
  версії вивантажених ключів (обмежено 10 000, LRU). Старший рядок вставляє
  зі `stale` і перечитує. **Вплив на спеку:** §6.2 правило 2 і Рд24.
- **`purge` вирізав ключ зі сталого складу картки (виправлено).** Рядок,
  що повернувся з іншої вибірки, картка вже не показувала.
- **Дія без змін осідає одразу.** `await`-правка зі значенням, рівним
  підтвердженому, не шле `run` і за Р1 поглинає те саме поле відмовленої
  мутації. Це поведінка за рішенням, інваріант тесту уточнено.

**Покриття станів** (2 × 10 000 прогонів, спостереження рядків у кадрах до
посилення генератора): `synced` 24 212, `conflict` 3 016, `pending` 1 543,
`failed` 86, `unknown` 46, `removed` 7. Після посилення (старт з даними,
рідший `dispose`) рідкісних станів більше, але точних чисел не перераховано —
**не перевірено**.

## 4a. Незалежне рев'ю ядра

Агент `code-review` (Opus), лінза correctness, звужена до класу «після
`dispose()` / старе покоління» і осідання оверлею. Кожну знахідку я
відтворила на коді до виправлення, кожна має регресійний тест
(`regressions.test.ts`), і всі 11 тестів файлу падають на старому коді.

| Знахідка | Сер. | Причина | Виправлення |
| --- | --- | --- | --- |
| `pump` пропускає мутацію після осідання `noop` — назавжди `queued` | major | `send` синхронно прибирає мутацію з журналу всередині циклу за індексом | обхід знімка журналу |
| пізня відповідь, прочитана до підтвердженого видалення, воскрешає рядок | major | токен підмножини дійсний; видалення не лишало сліду | надгробки з епохою: читання пам'ятає епоху старту, `putRow` відкидає рядок, видалений пізніше |
| те саме для `purge` (виняток безпеки) | major | те саме | ті самі надгробки |
| `purge` лишав ключ в `owned` підмножин поза їхнім складом — лічильник власників ламався | major | очищення лише там, де ключ у складі | `bury` знімає власність з усіх підмножин |
| запис ТЧ переживав підмножину, коли дельта осідала після відписки | major | `collect` лише для рядків | `collectSection` у `release`, осіданні, `cancel`, `retry`; `violations()` перевіряє ТЧ |
| невдале перечитування ТЧ після `run` ховало доданий рядок і не перечитувало | major | дельта знята, `entry.lines` старі | надісланий масив стає підтвердженим з версією з write-back; видима ТЧ перечитується |
| слухач, що закрив сесію, не зупиняв сповіщень решті | minor | копія слухачів до циклу | перевірка `closed` перед кожним викликом |

Відкинуто рев'ю нижче порогу (для виконавця): `loadAfter()` під час
завантаження губить запит сторінки; автоперебазування перечитує ключі лише
першого об'єкта мутації.

## 5. Продуктивність і пам'ять

**Метод.** `CORE_PERF=1 pnpm --filter simetra test perf`. Node 24.22.1, QEMU
vCPU (16 ядер), `performance.now` навколо операції, 30 прогрівань, далі N
повторів; медіана, p95, максимум. Браузерний замір — спайк 2.

| Замір | N | Медіана | p95 | Макс. | Поріг |
| --- | --- | --- | --- | --- | --- |
| перерахунок `full` 5 000: фільтр T0 (`gte` + `contains`) + сортування `String` колатором і `Number` | 200 | 3,5 мс | 4,6 мс | 6,6 мс | < 16 мс |
| `commit` 200 рядків (латання з новою версією), підписаний вигляд 200 | 500 | 0,22 мс | 0,38 мс | 2,5 мс | < 2 мс |
| дія `predict` → `commit` журналу + знімки `full` 5 000 і `keys` 200 + сповіщення | 1 000 | 3,2 мс | 6,2 мс | 10,7 мс | — |
| та сама дія при 300 мутаціях без відповіді в журналі | 300 | 2,4 мс | 3,4 мс | 7,1 мс | — |

Числа — після виправлень рев'ю (обхід знімка журналу, надгробки). До них
дія мала p95 4,0 мс; різниця в межах шуму VM, окремо не досліджено.

Застереження: журнал сканується лінійно (`liveRecsOf`, `heldByLog`, `pump`).
При ~1 000 одночасних мутаціях без відповіді дія стає квадратичною (замір
перевищив 5 с тайм-ауту). Реальний журнал — одиниці мутацій, але виконавцю
потрібен індекс журналу за ключем. Знімок `full` при правці будується за
O(n) по складу (5 000 переглядів кешу) — це основна частка 2,7 мс; заміна
одного рядка в масиві знімка зробила б її O(1).

**Межа пам'яті в байтах** (`perf.test.ts` «memory», `jsonBytes` рядків):
одночасно `full` 1 000 рядків + `keys` 200 + 50 підмножин ТЧ по 20 рядків —
1 000 рядків шапки, 50 ТЧ, 113 442 байти шапок. Після відписки всіх виглядів
лишаються лише три рядки, які тримають `failed`, `conflict` і `unknown`
(336 байтів), ТЧ — 0. Власне створення, відхилене сервером, — у журналі як
`failed` без рядка сховища. Ліміту з витісненням у ядрі немає: межу тримає
власність, а невирішені зміни не витісняються (Р3).

Плани B3-2a (401 рядок) і B3-3a (719 рядків) — проти готового ядра, а не

домен (потрібен за будь-якого рушія), W — обхід RC, N — пряме
використання. Інвентар — розвідка за заголовками, інтерфейсами й тестами
планів; тіла кроків прочитано вибірково.

| План | Задача | Клас | З ядром |
| --- | --- | --- | --- |
| 2a | T1 колекції, `syncMode`, `retry: false`, `gcTime` | N+W | налаштування RC зникають |
| 2a | T3 монотонність версії (мапа версій, відкладене застосування) | W | одна функція `mergeVersioned` + пам'ять вивантажених версій; гонки з відкладеним застосуванням немає |
| 2a | T5 повнота ТЧ (обгортка запису, `collection.base`) | D+W | домен лишається (`ownerVersion`, повнота, свіжість), обгортка й `base` зникають |
| 2a | T6 картка (обхід `meta` рівня колекції) | D+W | обхід зникає |
| 2a | T8 `dispose`, `cleanup({ dependents })`, `peek` після gc | W | зникає; лишається `dispose` сесії |
| 3a | T2 черга ключа, лічильник транзакцій, порожня транзакція, `DuplicateKey…` | D+W | черга — `pump` над журналом; лічильник, гілка порожньої транзакції й `DuplicateKey…` зникають; підтверджений знімок ключа = саме сховище |
| 3a | T3 write-back: відхилення `writeBatch`, вивантаження в черзі | D+W | усе навколо `writeBatch` зникає: `commit` застосовує синхронно |
| 3a | T4 межа `refetchQueries` проти `refetchAndWaitForApplication` | D+W | найбільший W-блок плану зникає; перечитування ТЧ лишається |

**Підсумок.** Зникає ≈250–300 рядків планів з 1 120 (≈25 %) разом з їхніми
тестами W-сценаріїв: керований фейк RC, спостерігачі `persisting`,
контрактні тести бібліотеки. Це ті самі обходи, що дали ≈половину major і
blocker аудитів B3, зокрема безпекові «стан після `dispose()`». У ядрі цей
клас закрито будовою (§2), а не задачами.

**Чого ядро ще не має з доменних задач:** `include` (лінивий join цілей
`Ref`), оновлення ланцюжка сторінок вікна, переоцінка множини скоупів, повна
еквівалентність обчислювача будівнику T3, лічильник `count`, перенесення
`full` → `window` (`truncated` лише позначається).

**Обсяг ядра проти оцінки.** Оцінка дослідження 08.11 — 1,6–2 тис. рядків
ядра. Факт — ≈2,4 тис. рядків коду `core.ts` у форматуванні Prettier (вузька
ширина роздуває рахунок) без `include` і повного вікна. Тобто в межах
оцінки з запасом ≈20–30 % на решту доменних задач. Чужого коду на гарячому
шляху немає: `@tanstack/db` і `query-db-collection` не потрібні.

## 7. Контрольний варіант: `@tanstack/query-core` як транспортний шар

Питання архітекторки: чи не пояснюється виграш ядра лише відмовою від
TanStack DB. Аналіз — за кодом `@tanstack/query-core` 5.107.1
(`node_modules/@tanstack/query-core/src`); реалізації не було.

| Механізм | Що дає query-core | Що потрібно ядру | Виграш | Примітка |
| --- | --- | --- | --- | --- |
| single-flight | приєднання до активного запиту; `cancelRefetch` скасовує й перезапускає (лише коли дані вже є) | один хвостовий запит після мутації | ні | прапорець `trailing` лишається в ядрі |
| dedup | за `queryKey` | за ключем форми + рядки між підмножинами | ні | `specKey` уже дає те саме |
| ключі по 200 / навпіл | — | так | ні | лишається в `queryFn` |
| gc / утримання | `gcTime` на запит (сервер — `Infinity`) | лічильник власників на рядок, відкладене звільнення, TTL `preload` | частково | замінює лише таймер |
| пізня відповідь | `CancelledError` на `clear`/`cancel` | токени на запис у нормалізоване сховище | частково | токени лишаються: запис іде після проміса |
| скасування | `signal` у `queryFn` | `AbortController`, прив'язаний до `dispose` | ні | рівноцінно, кілька рядків |
| SSR | `dehydrate`/`hydrate` за запитами | нормалізовані рядки + склади підмножин + `subject` | ні | дублює рядки, губить власників |
| структурне спільне використання | `replaceEqualDeep` на відповідь | тотожність рядка й масиву знімка | ні | довелося б вимкнути |
| retry | 3 на клієнті | 0 | ні | обов'язково `retry: false`, `networkMode: "always"` |
| focus / online | слухачі `window` після `mount()` | жодних побічних ефектів у T4 і SSR | ні | правило «не кликати `mount`» |
| залежність | ≈26,5 КБ мін. / ≈8 КБ gzip (`QueryClient` + `dehydrate`/`hydrate`, esbuild) | мінімум | ні | опційна peer-залежність стала б обов'язковою |

**Вердикт.** Під ядром query-core нейтральний чи шкідливий: знімає лише
таймер gc і проміс-dedup, а додає адаптер, обов'язкові налаштування й
подвійне зберігання рядків. Виграш ядра — з нормалізованої моделі рядків із
власністю й токенів поколінь, а не лише з відмови від TanStack DB.
Транспорт B3-1 (власний `send` з перевіркою закриття до й після відповіді)
лишається достатнім; `QueryClient` у рантаймі даних більше не потрібен.

## 8. Оверлей за типової політики `await`

Скільки коду ядра існує лише заради `predict` (оцінка за `core.ts`):

| Механізм | Потрібен для `await` | ≈ рядків |
| --- | --- | --- |
| накладання значень мутацій у `computeRow`, `created` | ні | 25 |
| поглинання полів (Р1) у `settleSuccess`, тінь полів у `retry` | ні: значення відмовленої `await` не показане | 45 |
| автоперебазування після конфлікту | ні (рішення Р2) | 30 |
| база полів (`base`, `chained`) і перевірка розбіжності | частково: для `await` — лише версія | 25 |
| оптимістичні рядки ТЧ (`sectionLines`) | ні | 35 |
| власне створення в складі вигляду на початку | ні: рядок з'являється з відповіддю | 15 |
| перечитування ТЧ перед осіданням (щоб не мигнули оптимістичні рядки) | ні: досить `needsRefresh` | 35 |

Разом ≈ 210 рядків з ~2 200 (≈10 %). Але це найскладніші 10 %. Майже всі
знахідки моделі й усі розвилки Р1–Р2 лежать саме тут. З типовою `await`,
чернеткою форми поза ядром і `predict` лише для простих дій (встановити
поле, перемкнути, видалити) журнал стає «станом без значень» плюс маленьким
шаром передбачень. Тоді: зникає ТЧ-оптимістика; поглинання полів зводиться
до одного поля одного ключа; конфлікт `await` — завжди `conflict` без
перебазування. Рекомендація: так і зробити. `predict` лишити як окремий
шар над журналом із власними тестами.

## 9. Клієнтське перебазування проти CAS за полями на сервері

| | Клієнтське перебазування (зараз) | CAS за полями в T3 |
| --- | --- | --- |
| Що шле клієнт | `expectedVersion` (поточна підтверджена) | `expectedValues` змінених полів (базові значення) |
| Що робить сервер | `version = expected`, інакше `command.conflict` | у тій самій транзакції: рядок під замком, порівняння полів (`IS NOT DISTINCT FROM` закодованих значень), інакше `command.conflict` з полями, що розійшлись, і поточними значеннями |
| Перечитування | так, перед повтором | ні: відповідь несе поточні значення |
| Цикл повторів | до 3 | немає |
| Атомарність рішення | ні: між перечитуванням і повтором вікно | так |
| Клієнтський код | ~55 рядків (база, розбіжність, перебазування) | ~10 рядків (зібрати базу) |

**Що CAS вимагає від T3:** нова форма операції `update` з `expectedValues`
замість `expectedVersion` (схема T0, форма передачі, MCP); у ядрі команди —
порівняння полів під тим самим замком рядка (`SELECT … FOR UPDATE` чи умова
в `UPDATE … WHERE`). Нюанс — рівність типів: `Numeric` з масштабом, `Json`,
масиви — порівнювати закодовану форму, а не JS. Відповідь `conflict` несе
`fields` і поточні значення.

**Що вимагає від правил команд:** версія захищає не лише поля, а й
інваріанти, що залежать від інших полів (статус, проведення, обчислювані
поля хуків `beforeWrite`). CAS за полями їх не бачить. Тому CAS дозволений
лише для простих правок атрибутів об'єкта без модульних обробників запису,
що читають інші поля. Ознаку дає каталог (немає обробника `write` чи обробник
оголошує «польова безпечність»). Для команд, проведення, ТЧ і чернетки —
лише версія. Це та сама межа, що й рішення Р2. Рекомендація: CAS за полями —
кращий шлях для `predict`-правок, він прибирає перечитування й цикл. Це
окрема поправка спеки П4 §6.4 і П4-B §7.1; до неї — клієнтське
перебазування.

## 10. Відкриті розвилки й рекомендації

1. **Індекс журналу за ключем** перед продуктом (див. §5).
2. **Рд24 між появами ключа** — пам'ять бачених версій (10 000) у спеку.
3. **CAS за полями** (§9) замість клієнтського перебазування — окреме
   рішення з T3.
4. **Правка ключа без бази** (до завантаження) зараз — локальний
   `conflict` `no-base`. Варіант: відхиляти синхронно помилкою розробника
   `data.version-required`, як спека §7.1.
5. **Вікно** реалізовано мінімально: перша сторінка, `loadAfter`,
   keyset без NULL; оновлення ланцюжка сторінок (§6.4) — ні.
6. **Надгробки з епохою** (§4a) — у спеку як другий механізм будови поряд
   з токенами: токен захищає від старого покоління запиту, надгробок — від
   старого покоління даних.
7. **Втрата скоупу** — лише `purge` за ключами; переоцінка множини скоупів
   (§6.2 правило 4) — ні.
8. **Обчислювач фільтра** — мінімальний; еквівалентність будівнику T3
   (інв. 16) спайк не доводить.
