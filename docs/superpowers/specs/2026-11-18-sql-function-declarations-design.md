# Декларації функцій SQL застосунку: викликачі, `EXECUTE` і названа перевірка прав

Issue: #271 — статус у GitHub (`track`), не в цьому файлі
Glossary: `docs/GLOSSARY.md` · ADR: ADR-0092, ADR-0093, ADR-0094 · Parent: [платформна спека](2026-09-24-simetra-platform-design.md) §6.7

## 1. Мета

`SECURITY DEFINER`-функція SQL застосунку з `EXECUTE` для ролі користувача
читає й пише від імені власника, тож RLS викликача її не обмежує. Правило
#173 робить таку функцію без декларації помилкою компілятора
`sql.definer-caller-unchecked` у будь-якій одиниці, борг включно
(платформна спека §6.7). Ця спека дає дозволений шлях: **декларацію функції**,
яка називає викликачів і перевірку прав, і **запобіжник виклику**, яким тіло
цю перевірку застосовує. Функцію, яку кличе дослівна політика боргу, платформа
розпізнає сама як **функцію політики** — форму платформи без декларації. Після роботи задекларована definer-функція з
перевіркою компілюється; без декларації чи без застосованої перевірки — помилка
з кодом; прийом бази з такими функціями доходить до порожнього плану.

## 2. Поза межами

- Обов'язкова декларація для функцій `SECURITY INVOKER`: недекларована
  invoker-функція спільного `sql/` і боргу тримає дослівні гранти, як тепер
  (беклог: ACL кожної функції застосунку — у платформи).
- Definer-функція, яку викликає роль запиту без сесії (`anonymous`) — §7,
  OQ-1.
- Перевірка `create` кореня скоупу (новий тенант, Рх9): скоупу ще немає,
  тож ні `row`, ні `scope` його не називають. Створення кореня йде командою
  (П4).
- Перевірка членства без права: член скоупу без ролі з правом отримав би
  доступ, якого модель прав йому не дає (ADR-0093). Функція, що перевіряє
  лише членство, називає право, яке мають члени (роль усіх членів).
- Стеля агента (Рх12) — з'являється у функції запобіжника тоді ж, коли в
  політиках (§5.2).
- Межі того, що робить тіло (Правило 1, дозвільний перелік тіла,
  `sql.definer-reads-rls`) — без змін; запобіжник виклику обмежує лише виклик.
- Кодоген типів RPC — підпис з розбору SQL, ролі з `EXECUTE` — з ACL знімка
  (платформна спека §6.5); сам кодоген — його блок.

## 5. Блоки докладно

### 5.1 Д1 — декларація функції й `EXECUTE`

**Файл.** Декларації функцій одного файлу `<основа>.sql` лежать у
`<основа>.functions.json` у тій самій теці (ADR-0092). Це діє для модуля
об'єкта (`<Ім'я>.sql`), спільного `metadata/sql/<схема>/` і боргу
`CustomTable`. Форма:

```json
{
  "$schema": "<шлях до JSON Schema>",
  "functions": [
    {
      "id": "<uuid>",
      "function": { "schema": "<схема>", "name": "<ім'я>" },
      "callers": ["user", "service"],
      "check": {
        "action": "<дія>",
        "object": { "kind": "<вид>", "name": "<ім'я>" },
        "row": "<параметр>"
      }
    }
  ]
}
```

Reference: `packages/simetra/src/model/schemas/sql-debt.ts` (форма службового
файлу метаданих), `scope.ts` (`setFunction` — посилання `{ schema?, name }`).

- `id` — UUID декларації, ніколи не перевикористовується.
- `function` — функція з SQL сусіднього файлу: `schema` за відсутності —
  `defaultSchema` проєкту (як у `setFunction`).
- `callers` — **викликачі**: призначення ролей, яким платформа дає
  `EXECUTE`, — `user`, `anonymous`, `service`, `command`: явний перелік схеми
  T0, не весь `GrantPurpose` (роль споживача сигналів платформна, функцію
  застосунку їй не відкривають). Порожній
  перелік — `EXECUTE` не має жодна роль застосунку; функцію кличуть лише інші
  функції від власника.
- `check` — названа перевірка (§5.2): `action`, `object` і необов'язкові
  `row` чи `scope` (ім'я параметра; у прикладі — `row`). Схема T0 приймає
  обидва поля як необов'язкові; обидва разом — причина компілятора
  `twoTargets`. Сам `check` необов'язковий у схемі, обов'язковість — правило
  компілятора нижче.
- Масив відсортовано за `function` як записано (запис без `schema` — перед
  записами зі схемою, далі — за схемою й ім'ям), без дублів записаного
  значення — diff показує зміну, а не порядок (правило схеми T0, як у
  `sql-debt.json`). Дублі після підстановки `defaultSchema` і дублі в різних
  файлах — `sql.declaration-duplicate` компілятора.

**Що тримає SQL.** Підпис, мову, волатильність, `SECURITY DEFINER` і
`SET search_path` тримає лише `CREATE FUNCTION`; декларація їх не повторює
(ADR-0092). Задекларована функція в будь-якому файлі мусить бути в закритій
оболонці: Д1 судить її `closedShellProblem` і видає `sql.closed-shell` (зокрема
`SECURITY DEFINER` без `SET search_path = ''`); боргом вона не стає. Окремий
`ALTER FUNCTION` на неї — `sql.function-settings-shell`: Д1 додає задекларовані
функції до `judgedFunctionIdentities`.

**Правила компілятора Д1:**

- декларація називає функцію, якої немає в сусідньому `.sql` —
  `sql.declaration-target-missing`;
- функція має перевантаження (кілька `CREATE` з тим самим `схема.ім'я`) —
  `sql.declaration-overload`: декларація розрізняє функцію лише ім'ям;
- функцію декларують два записи (в одному чи різних файлах) —
  `sql.declaration-duplicate`;
- декларація на форму платформи (функція множини, обробник підписки, функція
  значень виміру, функція політики §5.8) — `sql.declaration-platform-form`: призначення таких функцій
  задають метадані;
- definer-функція з `user` чи `command` серед викликачів без `check` —
  `sql.declaration-check-missing`: роль команд діє від імені користувача
  (спека прав §5.2), тож хук команди з id від клієнта інакше обійшов би RLS;
- definer-функція з `anonymous` серед викликачів —
  `sql.declaration-anonymous-definer` (OQ-1).

**`EXECUTE`.** Для кожної задекларованої функції компілятор генерує гранти
тим самим генератором, що й для функцій платформи (`executeGrants`,
`packages/simetra/src/compiler/sql/execute-grants.ts`): `REVOKE` від `PUBLIC`
і від ролей API провайдера поза викликачами, `GRANT` ролям викликачів;
призначення без ролі в профілі (`service` у профілі `postgres`) пропускається.
ACL задекларованої функції належить платформі повністю: дослівний `GRANT` чи
`REVOKE EXECUTE` на неї (будь-якій ролі) — `sql.generated-grant`, і
`simetra fix` вирізає оператор, усі цілі якого належать платформі (наявний
механізм `generatedGrantConflicts`). Схемі функції платформа дає `USAGE`
кожному отримувачу, як для решти згенерованих грантів (платформна спека §6.7). Підпис гранту — ключ ідентичності функції (кожна частина імені за `quoteIdent`, спека П2 §3). Функція з таким
`EXECUTE` (задекларована, функція значень виміру, функція модуля виду, форма платформи), аргумент якої — `%type`, — помилка
`sql.function-argument-type-reference` без гранту: `pg_proc` зберігає тип колонки на момент `CREATE`, а `GRANT` резолвить `%type` заново, тож після зміни типу колонки грант влучив би в чуже перевантаження (fail-closed; корінь — #300).

**Зв'язок із #173.** `sql.definer-caller-unchecked` діє лише на
недекларовану функцію й рахує роль API чи роль команд серед ролей, що мають
`EXECUTE` (роль команд — лише через `PUBLIC` чи явний грант: типових привілеїв
вона не має). Задекларована definer-функція з `user` чи `command`
судиться правилами Д1 і Д2; лише з `service` — компілюється без перевірки:
сервісна роль не діє від імені користувача. Дослівний `ALTER DEFAULT PRIVILEGES`,
що дає права на функції (`ON FUNCTIONS` чи `ON ROUTINES`), — помилка
`sql.default-privileges-execute` класу ремонту (виправлення — прибрати ADP,
Д4): `EXECUTE` виводить лише платформа. ADP ролі-власника провайдера в керованій
`public`, чиї отримувачі — лише власник чи ролі API, — не SQL застосунку й
правило його не судить: ACL кожної функції там тримає похідний `REVOKE` від
`PUBLIC` і ролей API поза викликачами. Інший отримувач такого ADP (`PUBLIC`,
роль команд чи будь-яка інша роль) — та сама помилка: похідний `REVOKE` його
не знімає.

**`sql.definer-reads-rls`.** Д1 змінює `checkDefinerReads`: недекларована
функція отримує `sql.definer-caller-unchecked`, як на #173, а задекларована
definer-функція з `user` чи `command` серед викликачів — попередження
`sql.definer-reads-rls` з переліком таблиць; ролі беруться з викликачів, а не
з дослівних грантів. Перевірка обмежує виклик, а не обсяг прочитаного.

**Модуль об'єкта виду.** Модуль виду не приймає дослівних грантів
(`sql.statement-not-allowed`), тож `EXECUTE` його функцій дає лише
декларація; функція модуля без декларації, що не є формою платформи,
отримує ті самі гранти, що й декларація з порожніми викликачами (`REVOKE` від
`PUBLIC` і ролей API).

**Функція значень виміру.** Її `EXECUTE` виводить платформа тим самим
генератором, що й для обробника підписки (`buildFunctionExecuteUnits`):
порожні призначення — `REVOKE` від `PUBLIC` і ролей API. Її кличе лише тіло
`rights_dimension_values*` від імені власника (спека прав §5.1); з `EXECUTE`
роль запиту читала б наживо повз знімок. Дослівний `GRANT` чи
`REVOKE EXECUTE` на неї — `sql.generated-grant`.

**Клас ремонту.** Коди `sql.definer-caller-unchecked`,
`sql.declaration-check-missing`, `sql.declaration-check-not-applied` (його
додає Д2), `sql.declaration-platform-form` і `sql.policy-helper-correlated`
(його додає Д5) — клас ремонту декларацій. `sql.declaration-check-form` до
класу не належить: хибна `check` — помилка автора декларації, а не стан
прийнятої бази, тож `repair` її не пропускає.
Компілятор має режим `repair`: помилки класу лишаються помилками в
діагностиках (`ok` — `false`), але модель повертається, якщо інших помилок
немає. Режим — явний параметр, який передають лише операції `create`, `add` і
`declare-function`; спільні `compileInput` і `compileCompletion` за
замовчуванням компілюють чисто, а `promote`, `fix`, `rename` і `delete` режиму
не передають, тож решта шарів, як і тепер, бачать модель лише з чистого
прогону. У режимі `repair` `OperationResult.ok` лишається `false`, а
окреме поле `written` каже обгортці, що зміну записано; командний рядок
завершується ненульовим кодом, MCP повертає `ok: false` з помилками класу.
Тест Д1: `promote` і `fix` на теці з помилками лише класу ремонту не пишуть
нічого. Мутація приймає теку, чиї помилки — лише класу ремонту, і пише
результат, якщо в ньому немає помилок поза класом і немає помилки класу,
якої не було на вході; помилку ототожнює кортеж `code`, `schema`, `name` (не зклеєний
рядок і не JSON-pointer). Мутація, після якої функція стає формою платформи
(`setFunction` виду скоупу, функція значень виміру), у тій самій зміні
видаляє декларацію цієї функції. Якщо виведені призначення форми ширші за
викликачів видаленої декларації, мутація видає попередження
`sql.declaration-platform-form-widens` з переліком доданих ролей. Так тека
після зворотної генерації доходить до 0 помилок крок за кроком.
Недекларована invoker-функція спільного `sql/` і боргу тримає дослівні
гранти (§2). Функція-запит модуля — `LANGUAGE sql` (спека промоції §9.4),
тож definer-функції з `user` там бути не може: запобіжник виклику вимагає plpgsql
(§5.2). Користувацька definer-RPC живе в спільному `sql/` чи в боргу.

### 5.2 Д2 — названа перевірка й запобіжник виклику

**Перевірка** (ADR-0093) — дія контракту прав над об'єктом метаданих:

- `action` — слово словника дій чи ім'я кастомної дії об'єкта (спека прав
  §3); компілятор резолвить ім'я кастомної дії в її UUID;
- `object` — `MetadataRef` об'єкта з правами; компілятор резолвить його в
  `id`, а в запобіжник виклику іде мітка виду об'єкта;
- рівно одна ціль або жодної:
  - `row` — ім'я параметра функції (`IN`, тип `uuid`), чиє значення —
    первинний ключ рядка головної таблиці об'єкта: право дії на цьому рядку;
  - `scope` — ім'я параметра функції (`IN`, тип `uuid`), чиє значення —
    скоуп виду скоупу об'єкта: право дії з обсягом `any` у цьому скоупі.
    Це форма для дій без наявного рядка (`create`) і операцій над скоупом
    цілком; право з вужчим обсягом (`own`, вимір, контейнер) цю перевірку не
    проходить, бо без рядка його носія немає (fail-closed);
  - без цілі — право дії на об'єкті без носіїв.

DML предикатів дії: `read` — `select`, `delete` — `delete`, кожна інша дія —
`update` (стан «до» наявного рядка, як у ядра команди, спека прав §6.2).

Ціль обов'язкова, коли предикати дії над таблицею об'єкта читають носія
рядка (скоуп, власність, вимір, прив'язка до контейнера) чи його читає межа `RESTRICTIVE` читання
(межа «Користувачів»); без носіїв (об'єкт без скоупу з
обсягом `any`) ціль заборонено. `scope` — лише для скоупленого об'єкта.
`create` — лише з `scope` (на скоупленому об'єкті) чи без цілі (на об'єкті
без носіїв): рядка ще немає. Причини `sql.declaration-check-form`:
`unknownAction` (дії немає серед дій об'єкта), `noRights` (об'єкт без
контракту прав), `targetRequired`, `targetForbidden`, `twoTargets` (і `row`,
і `scope`), `targetParameter` (параметра немає, він не `IN` чи не `uuid`),
`rowKey` (`row` на об'єкті, чия основна таблиця не має ключа з однієї колонки
`uuid`, зокрема регістр: адресуйте його через `scope`),
`scopeUnscoped` (`scope` на нескоупленому об'єкті), `createOnRow` (`create` з
`row`), `createOnRoot` (`create` кореня виду скоупу з будь-якою ціллю чи без
неї: його `INSERT` судить окрема булева форма, Рх9), `invoker` (`check` на функції `SECURITY INVOKER`: її вже обмежує RLS
викликача).

**Функції запобіжника** генерує платформа, коли хоч одна декларація має
`check`: `simetra.rights_require(p_action text, p_object text, p_row uuid)` —
для цілі `row` і без цілі, `simetra.rights_require_scope(p_action text,
p_object text, p_scope uuid)` — для цілі `scope`. Обидві:

- `LANGUAGE plpgsql`, `SECURITY INVOKER`, `SET search_path = ''`; `EXECUTE`
  не має жодна роль застосунку. Його кличуть лише definer-функції, тобто від
  імені власника; без `EXECUTE` користувач не отримує оракула наявності
  рядків;
- одна гілка на кожну пару (мітка, дія) з декларацій. Функція запобіжника
  працює від імені власника, тож RLS її не обмежує, і гілка відтворює всю
  умову RLS для DML дії. Гілка з `row` — `EXISTS` рядка головної таблиці з
  `id = p_row`, де виконано AND двох частин: межі `RESTRICTIVE` цього DML
  (межа тенанта й межа «Користувачів», той самий будівник, що й політики,
  `packages/simetra/src/compiler/access-units.ts`) і OR предикатів дії
  (`rightsCheckPredicates` над псевдонімом рядка `EXISTS`; тип кваліфікатора
  рядка розширюється з `CommandRow`,
  `packages/simetra/src/compiler/catalog-command/rights-check.ts`). Гілка без
  `row` — та сама булева форма, що й предикат об'єкта без носіїв
  (`simetra.has_right`). Гілка `rights_require_scope` — `p_scope` належить
  межі тенанта (мої скоупи виду скоупу, той самий будівник) і множині
  скоупів з правом дії з обсягом `any` (функція множини `any` дії, як у
  предикаті `create` політики `INSERT`, спека прав §5.1). Гілка дії, чий DML
  читає наявний рядок (`read`, `update`, `delete`, кастомна дія), бере й межі
  `RESTRICTIVE` читання цього рядка (`readBoundaries`): Postgres застосовує
  політики `SELECT` до наявних рядків `UPDATE` і `DELETE` з `WHERE`/`RETURNING`,
  а без них не застосовує, але гілка бере межу в обох випадках, тож запобіжник
  не слабший за RLS. Виняток — `read` з ціллю `row` на об'єкті з `publicRead`:
  якщо кожна декларація пари (мітка, дія) має лише викликачів `user` і `command`
  (обидві ролі входять до ролей політики `publicRead`), гілка — RLS: умова
  політики `publicRead` і решта меж читання, без предикатів; одна декларація
  пари з іншим викликачем (`service`, `anonymous`) повертає всю пару до
  предикатів. Роль викликача функція запобіжника не визначає. Умова одна з RLS і ядром команди: функція запобіжника не
  дозволяє більше за них;
- у проєкті без функцій прав (немає ролей) функція запобіжника не має гілок:
  вона лише відмовляє (нижче), не кличе функцій прав і не залежить від них у
  порядку створення;
- немає права, немає рядка, ціль `NULL` чи невідома пара — `RAISE` з
  `SQLSTATE '42501'`, `MESSAGE 'rights.forbidden'`, `DETAIL 'no-right'`, без
  даних рядка. Відсутній і чужий рядок дають ту саму відмову;
- поточного користувача функція запобіжника бере з функцій фактів (`rights_*`,
  `simetra.current_user_id()`), тож у транзакції зі знімком прав він судить
  так само, як політики (спека прав §5.1).

**Запобіжник виклику.** Перевірку тіло застосовує лише такою формою
(`guardOf`):

```sql
CREATE FUNCTION <схема>.<ім'я>(<параметр> uuid, …) RETURNS <тип>
LANGUAGE plpgsql <волатильність> SECURITY DEFINER SET search_path = ''
AS $$
BEGIN
  PERFORM simetra.rights_require('<дія>', '<мітка виду>', <параметр>);
  -- для цілі `scope`: simetra.rights_require_scope(…)
  DECLARE
    <змінна> <тип> := <вираз>;
  BEGIN
    …
  END;
END
$$;
```

Зовнішній блок — блок автора: `action` у дереві парсера plpgsql; парсер
додає до його `body` фіктивний `RETURN` у кінці, і його компілятор пропускає.
Лише блок автора з секцією `EXCEPTION` парсер загортає в синтетичний блок
без `lineno`, і тоді блок автора — `body[0]` обгортки (його відхиляє
`exceptionBlock`). Причини `sql.declaration-check-not-applied`:

- `language` — мова тіла не `plpgsql`;
- `declareSection` — зовнішній блок має секцію `DECLARE`: її ініціалізація
  (вирази за замовчуванням, присвоєння `NULL` змінній доменного типу з
  перевіркою `CHECK`) виконується до першого оператора, а `ALIAS` чи змінна з
  ім'ям параметра підмінили б рядок перевірки. Змінні тіло оголошує у
  вкладеному блоці після запобіжника виклику. Дерево парсера не прив'язує оголошення
  до блоку, тож секцію компілятор шукає в тексті тіла на рівні токенів:
  сканер розуміє коментарі (`--`, вкладені `/* */`), ідентифікатори в лапках і
  рядкові літерали (лексика `packages/simetra/src/compiler/sql/rewrite/lex.ts`).
  Після пропуску пробілів і коментарів дозволено лише `<<`, один
  ідентифікатор (простий чи в лапках), `>>`, а далі має бути ключове слово
  `BEGIN` без огляду на регістр. Червоні тести: `DECLARE` після коментаря
  `/* BEGIN */`, після `-- BEGIN` і після мітки в лапках, що містить `>>`;
- `firstStatement` — перший оператор зовнішнього блоку не `PERFORM`
  виклику функції запобіжника форми цілі декларації (виклик у вкладеному блоці, гілці, циклі
  чи після іншого оператора не рахується). Запит `PERFORM` має бути голим
  `SELECT` з рівно однією ціллю — прямим викликом кваліфікованої функції
  запобіжника без іменованих аргументів: порт зберігає весь текст запиту
  (`PERFORM … WHERE false` стає `SELECT … WHERE false`, і Postgres не
  обчислює ціль), тож `FROM`, `WHERE`, `GROUP`/`HAVING`, `LIMIT`/`OFFSET`,
  `ORDER`, `DISTINCT`, `WITH`, операції множин, `WINDOW`, друга ціль чи
  обгортка (`CASE`, `COALESCE`) — `firstStatement`;
- `arguments` — аргументи не дорівнюють декларації: дія (слово чи UUID
  кастомної дії) і мітка — рядкові літерали, рядок — ім'я параметра
  цілі `check.row` чи `check.scope` (без цілі — `NULL`); позиційне `$n` не
  приймається;
- `exceptionBlock` — зовнішній блок має секцію `EXCEPTION`: `WHEN OTHERS`
  перехопив би відмову.

Без секції `DECLARE` зовнішній блок до першого оператора нічого не виконує,
ім'я параметра там не перекрите, а виняток функції запобіжника нікому перехопити —
це й доводить застосування. Вирази `DEFAULT` параметрів обчислює викликач від
свого імені; закрита оболонка судить лише `search_path`, інші `SET` платформних налаштувань відхиляє `sql.command-context-write`, а перевантаження
функції запобіжника — заборона схеми `simetra` (`schema.reserved`).

**Гілка функції запобіжника.** Гілка = перевірка ядра команди «до» над
рядком дії, без воріт контексту команди: межі `RESTRICTIVE` DML дії і OR
предикатів дії тими самими будівниками, що політики й ядро команди (для
`read` — умова читання RLS). Стан «після» (`WITH CHECK`) запобіжник не
судить: подальші записи тіла — обов'язок автора, `explain` його називає
(§6, ADR-0093).

**Виклик платформної функції.** `sql.platform-function-call` дозволяє
функції запобіжника лише в запобіжнику виклику задекларованої функції в
перевіреній формі; деінде виклик — помилка. Виняток діє лише для
першого оператора в доведеній формі `PERFORM` — голий `SELECT` з однією
ціллю, прямим викликом кваліфікованої функції запобіжника форми цілі `check`
без іменованих аргументів, без `WHERE`, `FROM`, обгорток і другої цілі, —
хоч би які викликачі в декларації: `guardOf` судить лише викликачів від імені
користувача, тож службова функція з `PERFORM … WHERE false` викликом
запобіжника не звільняється. Форму перевіряє одна функція `firstStatementOk`
(`packages/simetra/src/compiler/sql/guard-of.ts`) і для `guardOf`, і для
винятку.

### 5.3 Узгодження з наявними правилами

- **Правило 1** (включно зі схемою `simetra`, #173) — без змін: тіло
  задекларованої функції не пише таблиць виду й таблиць платформи.
- **Дозвільний перелік тіла** (`sql.function-body-statement`) і заборона
  динамічного SQL — без змін; задекларована функція з динамічним SQL —
  помилка, а не борг.
- **`sql.definer-reads-rls`** — для задекларованої definer-функції з
  перевіркою лишається попередженням з переліком таблиць (§5.1, зміна
  `checkDefinerReads`).
- **Борг.** Задекларована функція боргом не є: поза закритою оболонкою вона
  — помилка `sql.closed-shell` (§5.1), а не запис ратчета.
- **Форми платформи** (обробники, функції множини, функції значень виміру,
  функції політик §5.8)
  декларацій не мають (`sql.declaration-platform-form`); `EXECUTE` кожної виводить генератор
  платформи (§5.1).
- **Згенеровані функції** платформи декларацій не мають: їхні гранти задає
  генератор.

### 5.4 Ідентичність

- Ідентичність декларації — її `id`. Діагностики й інструменти designer
  вказують на запис за `id` і JSON-pointer.
- Функцію декларація називає ім'ям із SQL (`{ schema?, name }`). У дослівного
  SQL немає `physicalName`: ім'я в `CREATE` і є логічним ім'ям функції, а
  перейменування — правка `CREATE`, декларації й запобіжників викликів в
  одній зміні; план бачить його як нову функцію, як і для решти дослівних
  функцій. Жоден механізм не зберігає ім'я функції між версіями.
- Об'єкт перевірки — `MetadataRef` `{ kind, name }`, який компілятор
  резолвить в `id`; запобіжник виклику містить мітку виду, а не ім'я таблиці, тож
  перейменування об'єкта чи промоція тексту тіла не змінюють. Кастомна дія —
  за UUID, тож її перейменування теж.

### 5.5 Д3 — прийом і промоція

Зворотна генерація (`packages/simetra/src/schema/reverse/`) для кожної
функції застосунку з `SECURITY DEFINER` і дієвим `EXECUTE` для ролі API чи
`PUBLIC`, крім функції політики (§5.8: її кличе вираз відновленої дослівної
політики; ні декларації, ні дослівних грантів `EXECUTE` для неї зворотна
генерація не пише, і помилок класу ремонту вона не дає, якщо має форму
функції політики). Це виняток Д5: до неї функція, яку кличе дослівна політика,
отримує декларацію без `check` (`sql.declaration-check-missing`). Дієвий
`EXECUTE` береться з каталогу бази, а не з одиниць extract (одиниці не несуть
типового `PUBLIC`, типових привілеїв провайдера, грантора, опції передачі й
членства): `introspect` читає факти в одному знімку з extract і передає їх
у `reverseGenerate`; без них при definer-функціях — помилка. Викликачі виводяться зі знімка (`aclexplode` ACL функції й схеми з типовими ACL, рекурсивне членство з урахуванням `inherit`, власник; межа — лише ролі профілю), знімок звіряється зі свіжим каталогом за відбитком прав (функції, схеми, ролі профілю й членство); розбіжність — `introspect.definer-acl-changed`, нічого не записано; `has_function_privilege` і `has_schema_privilege` звіряють семантику виведення. Функція поза
закритою оболонкою Д1, у sidecar таблиці чи у збереженому файлі декларації не
отримує: її гранти лишаються дослівними, компіляція дає
`sql.definer-caller-unchecked` (клас ремонту). Тека, чиї помилки лише класу
ремонту, записується; будь-яка інша помилка — нічого не записано:

1. пише декларацію в `<основа>.functions.json` поруч із `.sql` функції;
   `callers` — з фактів `EXECUTE` оберненням `grantRole` профілю (`PROVIDER_API_ROLES`
   провайдера й `PLATFORM_ROLES`); `PUBLIC` дає `user`, `service` і
   `command`; `id` — новий UUID. Функція лише власника (жодної ролі профілю
   з `EXECUTE`) із запобіжником виклику в тілі отримує декларацію
   `callers: []` з прочитаним `check`: без неї виклик запобіжника в тілі
   відмовила б компіляція (`sql.platform-function-call`); без запобіжника
   декларації немає. Функція, яку не можна задекларувати (відкрита оболонка,
   перевантаження, процедура), із запобіжником у тілі лишається відмовою
   компіляції, а `introspect.definer-check-unknown` називає причину;
2. роль без сесії (`anonymous`, зокрема через `PUBLIC` чи типові привілеї
   провайдера) у викликачі не пише й видає попередження
   `introspect.definer-anonymous-dropped`: definer-функції без сесії немає
   (OQ-1), тож план відкличе цей `EXECUTE`;
3. гранти `EXECUTE` цієї функції дослівно не пише: їх відтворює генератор
   §5.1;
4. якщо тіло має запобіжник виклику у формі `guardOf` — пише `check` з його
   аргументів: мітка → `MetadataRef` об'єкта, UUID кастомної дії → її ім'я,
   параметр → `row` чи `scope` за функцією запобіжника;
5. інакше декларація лишається без `check`, а зворотна генерація видає
   `introspect.definer-check-unknown` з підказкою: додати `check`
   (`declare-function`) і запобіжник виклику (`simetra fix` вставляє його за
   `check`, §5.6) або прибрати `user` і `command` з викликачів. Компіляція такої теки — помилка
   `sql.declaration-check-missing`, план не складається.

**Форми платформи після прийому.** Зворотна генерація не знає видів скоупу й
вимірів доступу, тож функція множини скоупу чи функція значень виміру
наявної бази (`SECURITY DEFINER`, `EXECUTE` для ролей API) приходить як
звичайна функція SQL застосунку: кроки 1–5 пишуть їй декларацію без `check`,
і компіляція дає `sql.declaration-check-missing`. Функцію без аргументів, що
повертає `SETOF uuid`, зворотна генерація позначає попередженням
`introspect.definer-platform-form-candidate` з підказкою. Вихід —
один із двох:

- **форма платформи.** Людина чи агент оголошує вид скоупу з `setFunction`
  (чи вимір доступу з функцією значень), що називає цю функцію, —
  мутаціями `create`/`add`. Мутація `add` виду скоупу у тій самій зміні
  оголошує скоуп прийнятих `CustomTable` (вхід `scopes`: ім'я таблиці →
  вид); дослівні політики скоупу лишаються у файлі таблиці. Мутація приймає
  теку з помилками класу ремонту
  й у тій самій зміні видаляє декларацію цієї функції (§5.1); `EXECUTE`
  форми виводить генератор платформи, а дослівних грантів зворотна
  генерація цій функції не писала (крок 3);
- **RPC.** `declare-function` з `check` і `simetra fix` (запобіжник виклику)
  — §5.6; план змінює тіло функції.

Перевірка — тест «прийом з нуля» (Д4): база з функцією множини скоупу й
definer-RPC → зворотна генерація → `sql.declaration-check-missing` на обох
→ оголошення виду скоупу і `fix` для першої, `declare-function` з `check` і
`fix` для другої → 0 помилок компіляції → застосування плану → наступний
план порожній.

ACL функції з грантом ролі поза призначеннями (власна роль застосунку) —
`introspect.definer-foreign-grant`: ACL задекларованої функції належить
платформі, а членство такої ролі в ролі API обійшло б перевірку викликачів.
Підказка — прибрати грант у базі або описати доступ викликачами.

Наслідок: база, чиї definer-функції вже мають запобіжник виклику і не мають
`EXECUTE` для ролі без сесії, проходить round-trip з порожнім планом. База без запобіжника виклику не приймається мовчки:
після правки тіла й застосування плану наступний план порожній; так само
після застосування відкликаного `EXECUTE` ролі без сесії. Поступок
сумісності з наявною базою немає (рішення власника 2026-11-18).

**Промоція.** Промоція переписує тіла функцій (спека промоції §6); запобіжник виклику
містить мітку виду, а не ім'я таблиці, тож промоція його не змінює. Декларація йде за своєю
функцією: `promote` пише кожну в `.functions.json` поруч із тим `.sql`, куди переносить
її функцію (Д1), тож множина декларацій до й після промоції та сама.
Функція-запит модуля виду лишається invoker-формою (§5.1).

### 5.6 Д4 — інструменти designer

Усі — інструменти одного каталогу (`packages/designer/src/tools/catalog.ts`),
отже доступні з командного рядка й MCP.

- **`declare-function`** (вісь `files`, мутація): створює чи змінює запис
  декларації за `schema.name` функції — `callers` і `check`; новому запису
  призначає `id`; тримає порядок масиву. Неможливе (немає функції в `.sql`,
  перевантаження) — діагностика тим самим кодом, що й компілятор. Нову помилку
  класу ремонту мутація не додає, крім переходу самої цілі в
  `sql.declaration-check-not-applied` з причиною `firstStatement` (тіло без
  запобіжника, який вставляє `fix` (в)); ціль, що вже форма платформи, —
  відмова `sql.declaration-platform-form`.
- **`fix`**: (а) призначає відсутній `id`; (б) вирізає дослівні гранти на
  задекларовану функцію (наявний механізм); (в) вставляє запобіжник виклику першим
  оператором зовнішнього блоку, коли декларація має `check`, тіло —
  `plpgsql` без запобіжника виклику, а інших причин `check-not-applied` немає; (г)
  видаляє декларацію функції, яка стала формою платформи
  (`sql.declaration-platform-form`).
  (д) вирізає цілою інструкцією дослівний `ALTER DEFAULT PRIVILEGES … ON
  FUNCTIONS|ROUTINES` (`sql.default-privileges-execute`), зокрема зі змішаними
  отримувачами: `EXECUTE` виводить лише платформа; інструкцію власника
  провайдера в керованій `public` з пресетом серед отримувачів не чіпає. Глобальний
  ADP (без `IN SCHEMA`) вирізає, лише коли всі отримувачі — `PUBLIC` чи ролі
  API: план його не відкликає, а похідний `REVOKE` інших ролей не знімає.
  Крок (г) не пише, коли форма платформи відкрила б `EXECUTE` ширше за
  декларацію (`sql.declaration-platform-form-widens`). `fix` працює в режимі ремонту, як
  мутації: пише, коли підсумок не додає нових помилок класу ремонту, прибирає
  хоча б одну й не має помилок поза класом (чистий підсумок — як і раніше).
- **`compile`**: діагностики `sql.declaration-*` вказують на файл
  `.functions.json` і JSON-pointer запису; `check-not-applied` — на рядок
  тіла.
- **`explain`** і підказка `sql.policy-helper-correlated`: для предиката
  політики пропонують цільову форму — функцію множини без параметрів, що
  читає актора з claims, — і переписування викликів у політиках на
  `<колонка> IN (SELECT f())`. Переписування змінює семантику, тож `fix` його
  не робить: зміну пише людина чи агент, а застосовує звичайний план.
- **`explain`**: приймає ще й функцію SQL за `schema.name` і повертає
  викликачів, ролі з `EXECUTE` у профілі, перевірку словами («дія `post`
  документа `Order` на рядку `p_order`») і стан застосування.

### 5.8 Д5 — функції політик боргу

Дослівні політики прийнятих таблиць (борг SQL) кличуть definer-функції, які
обчислюють, що бачить актор. `EXECUTE` їм потрібен, бо політика кличе їх від
імені запиту, а `EXECUTE` видається ролі, не місцю виклику: роль запиту може
викликати таку функцію й як RPC. Шлях для них — форма платформи, яку спека
промоції §9 називає «корельовані хелпери → функції множини (C)» (ADR-0094).
Безпека тримається на нешкідливості прямого виклику, а не на його
недосяжності.

**Функція політики** — функція SQL застосунку, яку кличе вираз дослівної
політики боргу (`USING` чи `WITH CHECK`), у формі:

- без параметрів; `RETURNS SETOF uuid`; `LANGUAGE sql STABLE SECURITY DEFINER
  SET search_path = ''`;
- голова за Правилом 3 (спека прав §6.1) — той самий суддя голів, що й для
  функцій множини скоупу (`packages/simetra/src/compiler/sql/heads.ts`);
- тіло — один `SELECT` без операцій над множинами (`UNION`, `INTERSECT`,
  `EXCEPT`); у `FROM` — лише базові таблиці, з'єднані комою чи внутрішнім
  `JOIN` (без похідних таблиць, `WITH`, `VALUES`, функцій, що повертають
  множину, `LATERAL` і зовнішніх з'єднань); вивід — одне голе посилання на
  колонку первинного ключа таблиці T, на якій стоять усі політики-викликачі
  (одна функція політики — одна таблиця T; ключ T — одна колонка `uuid`);
  T у `FROM` — рівно один раз;
- результат прив'язаний до актора: `WHERE` — кон'юнкція верхнього рівня, і
  хоч один її кон'юнкт має рівно форму `<колонка R> = <актор>` (функція
  ідентичності провайдера чи `simetra.current_user_id()`) або
  `<колонка R> IN (SELECT g())` / `<колонка R> = ANY(ARRAY(SELECT g()))`, де
  `g` — інша функція політики чи функція множини скоупу. Без `OR` і `NOT`
  навколо нього й без інших операторів порівняння (`<>`, `<`, `>=` …). Колонка
  результату належить таблиці R або таблиці, з'єднаній з R ланцюжком
  кон'юнктів рівності колонок (зв'язність графа з'єднань від таблиці
  результату до R). Ланцюжок рахує кон'юнкти верхнього рівня `WHERE` і `ON`
  внутрішніх з'єднань; `OR` і `NOT` у `ON` — не форма; перехресне з'єднання
  без ланцюжка — не форма;
- межі `RESTRICTIVE` таблиці T: вираз `USING` кожної `RESTRICTIVE`-політики T
  для команди `SELECT` чи `ALL`, чиє `TO` містить `PUBLIC`, роль політики-
  викликача чи роль, членом якої роль політики-викликача є (прямо чи
  транзитивно), — кон'юнкт верхнього рівня `WHERE` функції. Порівнюють
  дерева після резолву посилань на колонки в пару (вхід `FROM`, колонка):
  колонка T у виразі межі — колонка єдиного входу T у функції. Кожен такий вираз (транзитивно, через функції, які він кличе) проходить
  окрему перевірку Д5, а не лише суддю голів, який цих конструкцій не
  відхиляє: без функцій ролі сесії (`current_user`, `current_role`,
  `session_user`, `user`), без функцій ролей і привілеїв (`pg_has_role`,
  `has_*_privilege`, `row_security_active`), без відношення з RLS, що не
  `off`, без подань і матеріалізованих подань (подання з `security_invoker`
  у політиці читає базову таблицю під RLS сесії, а в тілі — від власника), і з `current_setting` лише за правилом актора нижче. У тілі від
  імені власника вони означали б інше, ніж у політиці; T без таких меж цю умову виконує сама;
- вираз кожної політики, що її кличе, — один атом
  `<ключ T> IN (SELECT f())` чи `<ключ T> = ANY(ARRAY(SELECT f()))` над тією
  самою колонкою ключа або `OR` таких атомів над функціями політик; без
  `AND`, `NOT` та інших умов.
  Так множина кожної функції — підмножина того, що політика дає цьому
  актору, і RPC не оминає прихованого звуження (дві умови, що звужують одна
  одну, автор зводить в одну функцію політики); атоми — некорельований
  `InitPlan`, як у шаблонів платформної спеки §6.8;
- `TO` кожної політики-викликача — ролі, які обертаються `grantRole`
  профілю на призначення `user`, `service` чи `command`; `TO PUBLIC`, роль
  без сесії чи роль поза призначеннями — не форма (ремонт нижче). Кожна роль,
  що отримує `EXECUTE`, стоїть у `TO` хоч однієї політики-викликача
  `FOR SELECT` чи `FOR ALL`, де функцію кличе `USING`: інакше RPC відкрив би
  ключі рядків, які роль може змінити, але не читати.

Прямий виклик дає підмножину ключів рядків T, які permissive-політика
викликача й так дозволяє актору читати, з тими самими межами `RESTRICTIVE`
(ADR-0094). Ключ іншої таблиці (співчлени, множина тенантів для політики
на іншій таблиці) формою не буває: такий предикат — ремонт, і підказка
пропонує звести його до функції множини виду скоупу — форми платформи, що
повертає власні факти актора.

Компілятор розпізнає функцію політики за графом викликів (`policyFunctions`):
її кличе вираз дослівної політики. Функція, що вже є формою платформи
(функція множини виду скоупу, функція значень виміру, обробник підписки),
функцією політики не буває: діють правила її власної форми. Політика, що
кличе функцію значень виміру, — `sql.policy-helper-correlated`: ця функція не
має `EXECUTE` для ролей запиту (§5.1). Декларації функція політики не має;
декларація на неї — `sql.declaration-platform-form` (Д5 додає цю форму до
правила Д1). `EXECUTE` виводить платформа генератором `executeGrants` за
призначеннями ролей `TO` політик-викликачів; ролі без сесії — ніколи.
Дослівний `GRANT` чи `REVOKE` на функцію політики — `sql.generated-grant`.

Функція політики — у закритій оболонці, тож боргом не є, як кожна функція в
оболонці (`debtPredicate`, спека прав §5.3); від
`sql.definer-caller-unchecked` вона звільнена поряд із `ruledFunctions`.
Борг тут — дослівні політики, що її кличуть: їх тримає ратчет.

**Вихід.** Функція політики зникає двома шляхами:

- промоція: таблиця стає видом, а предикат — функцією множини виду скоупу з
  прийнятим джерелом членства чи призначень (спека прав §4.7);
- видалення останньої політики-викликача: генерований `EXECUTE` зникає разом
  із формою. Функція, що лишилася без політики-викликача й без декларації,
  судиться як звичайна definer-функція: типовий `EXECUTE` `PUBLIC` Postgres
  (без `REVOKE`) компілятор вважає доступом ролей API, тож
  `sql.definer-caller-unchecked` — функцію видаляють чи декларують.

**Решта предикатів політик — ремонт.** Definer-функція, яку кличе дослівна
політика, але не у формі функції політики, — помилка класу ремонту
`sql.policy-helper-correlated` з причиною: `parameters` (параметризована чи
корельована з рядком), `language` (`plpgsql`), `volatility` (`VOLATILE`),
`returns` (булева чи інший тип), `outputKey` (вивід — не ключ таблиці T політики-викликача, зокрема id
співчленів через з'єднання таблиці членств із собою; політики-викликачі на
кількох таблицях; ключ T — не одна колонка `uuid`; T у `FROM` більше одного
разу; підказка — функція множини виду скоупу), `restrictiveBound` (межі `RESTRICTIVE` таблиці T немає в `WHERE` функції над єдиним входом T чи
її вираз не проходить перевірку меж Д5), `actorUnbound` (результат не прив'язаний до актора за
формою вище, зокрема
`<>`, `OR true`, перехресне з'єднання без ланцюжка рівностей, `UNION`,
вираз чи скалярний підзапит у виводі, похідна таблиця, `WITH`, функція, що
повертає множину, чи зовнішнє з'єднання у `FROM`), `policyShape` (`AND`, `NOT`, стороння умова, атом над колонкою, що не є
ключем T, чи інша форма виклику в політиці), `policyRoles` (`TO PUBLIC`, роль без сесії, роль поза призначеннями чи роль
лише з політик `UPDATE`/`DELETE`/`INSERT`; підказка — `TO` ролі запиту
користувача в політиці `FOR SELECT`). Як прийнятий стан
її не залишають: її переписують у функцію політики (§5.6), а зміну
застосовує звичайний план. Переписана функція в оболонці боргом не є, тож
ратчет не росте; вихід колишньої одиниці боргу з переліку прибирає `fix`
(`sql.debt-stale`).

**Актор у голові.** Кожна голова (функція множини скоупу, функція значень
виміру, функція політики) читає актора лише через функцію ідентичності
провайдера (claims JWT) чи `simetra.current_user_id()`, транзитивно.
`current_setting` у голові дозволено лише з літеральною назвою з префіксом
із `PROTECTED_SESSION_SETTINGS.prefixes`
(`packages/simetra/src/model/schemas/project.ts`): `request.jwt.` і
`simetra.`. Назви з `PROTECTED_SESSION_SETTINGS.names` (`role`,
`session_authorization`, `session_replication_role`) — не актор, тож теж
заборонені. Будь-яка інша назва (заголовки, cookies, шлях, метод запиту,
власні `app.*`) і нелітеральна назва — `sql.head-not-allowed` (конструкція
`setting`): такі
значення задає клієнт чи будь-який SQL застосунку. Запис `request.jwt.*` з
боргового SQL — лише попередження (`sql.debt-session-write`, спека прав
§5.3); це той самий залишковий ризик, який уже несе функція ідентичності
провайдера. Зараз `current_setting` є в
дозвільному переліку вбудованих функцій
(`packages/simetra/src/compiler/sql/builtin-functions.ts`); Д5 звужує його
для голів.

## 6. Безпека й цілісність даних

- **Хто може викликати.** Definer-функцію з `user` чи `command` викликають
  лише через запобіжник виклику з умовою, тотожною RLS (межі `RESTRICTIVE` і
  предикати прав) і ядру команди. Обхід формою (перевірка в гілці, після
  запису, під `EXCEPTION`, секція `DECLARE` зовнішнього блоку з виразами,
  доменами, `ALIAS` чи тінню параметра) відхиляє `guardOf`.
- **Що тіло робить після перевірки.** Запобіжник виклику доводить право на
  рядок `row` чи право з обсягом `any` у скоупі `scope`, а не на кожен рядок,
  який тіло читає чи пише. Тіло, що створює рядок за ціллю `scope`, пише
  колонку скоупу з того самого параметра: RLS і межа тенанта тіло
  definer-функції не судять. `explain` функції (§5.6) називає цей обов'язок. Межі тіла тримають
  Правило 1, дозвільний перелік тіла й `sql.definer-reads-rls`; рецензія
  тіла лишається на авторі застосунку.
- **Оракул наявності.** Функція запобіжника відповідає однаково на відсутній
  і чужий рядок і не має `EXECUTE` для ролей застосунку. Її кличуть від імені
  власника definer-функції — роль застосування, що володіє й об'єктами
  `simetra` (гейт власника, платформна спека §6.7).
- **ACL.** ACL задекларованої функції повністю генерує платформа:
  `REVOKE` від `PUBLIC` і ролей API поза викликачами; дослівний грант —
  помилка; грант власній ролі відхиляє прийом.
- **Функції політик.** Функція політики читає повз RLS від імені власника,
  а її `EXECUTE` має роль запиту, тож вона доступна й як RPC. Форма обмежує
  відповідь: без параметрів, результат прив'язаний до актора, актор лише з
  claims JWT чи `simetra.current_user_id()`, вивід — ключ таблиці політики,
  межі `RESTRICTIVE` — у `WHERE` функції, а політика — лише `OR` атомів
  функцій політик над цим ключем. Тож RPC дає підмножину ключів рядків, які
  актор і так читає, і нічого про іншого користувача. Параметризований
  предикат (оракул «що може інший користувач») формою не буває
  (`sql.policy-helper-correlated`). Політика `TO PUBLIC` формою не буває теж:
  вона діє й на роль без сесії, а `EXECUTE` перевіряється на всю політику.
- **`anonymous`.** Definer-функції без сесії немає (OQ-1): перевірка права
  без користувача завжди хибна. Прийом не переносить `EXECUTE` ролі без сесії
  (`introspect.definer-anonymous-dropped`).
- **Стеля агента (Рх12).** Коли стеля з'явиться в політиках `RESTRICTIVE`,
  функція запобіжника бере її з того самого будівника; до того агент у
  функції запобіжника обмежений так само, як у RLS.
- **Деструктивні операції.** Перехід на декларації змінює ACL функцій
  (відкликає `PUBLIC`): план показує ці кроки як зміну грантів. Даних не
  зачіпає.
