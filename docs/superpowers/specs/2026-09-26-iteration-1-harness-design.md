> **Статус:** дизайн ухвалено власником 2026-09-26 у брейнштормі. Наступний крок —
> план імплементації (`superpowers:writing-plans`).
> **Контекст:** архітектура платформи — `2026-09-24-simetra-platform-design.md`
> (далі «платформна спека»). Ця ітерація — витягнутий уперед крок П1 (харнес, §11)
> плюс підготовка П0; коду платформи й видалення прототипу тут немає.
> **Гілка:** уся ітерація — у `docs/platform-design`, одним PR у `main`.

## 1. Мета

Після ітерації репо готове до роботи агентом Claude Code за патерном MetaHub, не
бреше про напрям і має затверджувані хартії спайків П0.

**Позиціонування (уточнення власника):** Simetra — загальна платформа
бізнес-застосунків на метаданих «як 1С:Підприємство» для будь-якого проєкту.
Досвід MetaHub — значні доповнення до концепції; MetaHub — перший споживач, а не
єдина мета.

**Критерії успіху ітерації:**

1. Усі тести (≈800 наявних + тести CLI) і typecheck/lint зелені локально й у CI
   на оновлених залежностях.
2. Свіжа сесія агента знаходить дорогу через `AGENTS.md`, не читаючи всі доки.
3. `scripts/check-doc-anchors.py` зелений.
4. README, BRD, ROADMAP описують платформу за платформною спекою; жодного
   документа, що описує скасований напрям як чинний.
5. Хартії спайків П0 (а–г) подано власнику на апрув.

## 3. Блок 1 — залежності й CI

- `.node-version` = `24.15.0`; `packageManager: pnpm@11.4.0`; `engines.node` —
  `>=24`.
- Оновлення всіх залежностей у всіх workspace-ах до latest (`pnpm up -r --latest`,
  вирівнювання `syncpack`); поломки від мажорних оновлень виправляються.
  **Виняток:** пакет, що йде під видалення в П1 (`form-runtime`, `app-runtime`,
  `data-provider*`, `apps/runtime`), якщо ламається глибоко — зупинка й питання
  власнику (варіант — видалити раніше), а не глибокий ремонт.
- Дрібний борг: скрипт `test` у `packages/cli` (зараз тести CLI не запускаються
  turbo); дрейф Prettier (≈22 файли в рантайм-пакетах); закомічений
  `__pycache__`.
- `.github/workflows/ci.yml`: на `pull_request` і `push` у `main` —
  install (кеш pnpm) → `format:check` → `lint` → `typecheck` → `test`.
- **Готово, коли:** гейти зелені локально й у першому прогоні CI.

## 4. Блок 2 — харнес агентів

Еталон — MetaHub (`~/github/metahub`): `AGENTS.md` + `CLAUDE.md` з `@AGENTS.md`,
скіли в `.agents/skills` з симлінками в `.claude/skills`, три агенти, набір команд.
Переноситься патерн, а не вміст: жодних ID інфраструктури MetaHub, доменних скілів
MetaHub, memory, `settings.local.json`, імен тенантів чи секретів.

## 5. Блок 3 — документація під напрям

- **BRD** (`docs/BRD.md`, замінює `docs/BRD-metadata-configurator.md`),
  українською, орієнтир 400–700 рядків: бачення 1С-подібної платформи для
  будь-яких проєктів; користувачі й сценарії; доменні концепції (види, реквізити,
  табличні частини, регістри, проведення, підсистеми, скоуп, права); що береться з
  досвіду MetaHub; не-цілі. Технічні механізми не дублюються — посилання на
  платформну спеку. **Перед написанням — окремий короткий брейншторм змісту з
  власником** (це продуктове бачення).
- **README.md** — англійською: що таке Simetra, статус pre-alpha, посилання на
  BRD, спеку, ROADMAP; ліцензія.
- **Видалити:** `docs/architecture/*` (І6); 6 планів у `docs/tasks/`.
- **`docs/ROADMAP.md`** — українською: П0–П6 зі статусами й посиланнями на
  платформну спеку, без копіювання її змісту; ця ітерація — як виконаний крок.
- `docs/research/*` лишаються.
- Про видалення `docs/architecture` і межу BRD ↔ спека повідомляється архітектор
  (сесія `platform-design-spec`); зміни, що зачіпають платформну спеку, — лише
  через нього.

## 6. Блок 4 — хартії спайків П0

Документ `docs/superpowers/specs/2026-09-26-p0-spike-charters.md`. На кожен спайк
(а–г, платформна спека §12): питання → проба → критерій успіху → де виконується →
що викидається.

- (а) host на TanStack Start + tarball пакета під pnpm symlink-layout + пресет
  Vercel (#8139) — у Simetra, одноразова тека/гілка.
- (б) прийом схеми, (в) `Database` ≡ typegen — код проби загальний, але дамп
  схеми, типи й результати з деталями MetaHub **не комітяться** в публічне репо.
- (г) аліаси PostgREST, мапінг payload realtime, тригери синхронізації + RLS +
  broadcast — синтетична схема; потрібен Supabase-проєкт (гілка чи тимчасовий) —
  вартість виноситься в хартію як рішення власника.

**Готово, коли:** власник апрувнув хартії.

## 7. Процес виконання

- Блоки 1–2 — Workflow: реалізація → рев'ю лінзами → верифікація знахідок →
  фікс (≤2 раунди) → гейти.
- Блоки 3–4 — новими командами харнесу (`/виконай-задачу`,
  `/перевір-роботу-агента-кодування`), що одночасно перевіряє харнес.
- Агенти, що комітять, — послідовно; коміти від імені власника, без трейлерів.
- Між блоками — коротка точка звітування власнику.

## 8. Поза межами

Код платформи, реорганізація в яруси, видалення прототипу (П1); публікація в npm,
canary, пілот із tarball (П1); резервування імен у npm (рішення власника, окремо);
статуслайн і user-level хуки (вже налаштовані глобально).
