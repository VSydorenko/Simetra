## 1. Мета й межі

П4-B дає клієнтському коду застосунку дані бази без ручного коду доступу:
згенерований хост (П4-D) читає списки й картки, пише командами й бачить чужі
зміни без перезавантаження, а інтерфейс знає, які дії користувачу доступні.
Безпека даних лишається в базі: RLS для читання, ядро команд і RLS для
запису. Усе, що П4-B додає в клієнт, — зручність і швидкість, а не межа.

**Критерії успіху:**

1. Список і картка довідника читаються й пишуться через фасад T4 однаково в
   обох джерелах (PostgREST і Server Function); код хоста джерела не знає.
2. Оптимістична зміна або підтверджується рядком бази, або відкочується; у
   колекції не лишається рядка, якого база не підтвердила.
3. Зміна, зроблена в іншій вкладці чи іншим користувачем, доходить до
   колекції через сигнал і перечитування під RLS; сигнал не несе даних.
4. Підписник не отримує сигналу каналу, читати об'єкт у скоупі якого він не
   має права.
5. Інтерфейс питає «чи можу я дію над цим рядком» в обчислювача T4, який
   побудовано з контракту прав і який збігається з перевіркою права ядра на
   тестових фікстурах.
6. Запис від збірки з іншою моделлю відхиляється до бази з окремим кодом.

**Входить:**

- запит читання T0 другої форми й серверне читання T3 над ним (§4);
- кодек передачі значень між сервером і клієнтом (§4.4);
- конверт запиту даних і серверний обробник, який host прив'язує до своєї
  Server Function (§4.5);
- адаптери джерела T4: Server Function і PostgREST (§5);
- колекції за фасадом: on-demand і повні, ключі, підмножини, рядок без
  власника-підмножини (§6);
- фасад запису: пакет фаз, write-back з рядків результату, конфлікт версії,
  мапінг помилок (§7);
- сигнал реального часу: функція сигналу в ядрі, канал, авторизація каналу,
  транспорт профілю `supabase`, порт транспорту для `postgres` (§8);
- кеш прав клієнта й обчислювач (§9);
- звірка версії моделі клієнта й контракт сесії (§10).

**Не входить:**

| Що | Де |
| --- | --- |
| запис повз команди П4-A | ніколи (П4 §2) |
| читання документів, регістрів, віртуальних таблиць регістрів, `CustomTable` | частина, що вводить вид у каталог рантайму (П4-C для документа; Р-1 у §2) |
| реалізація транспорту сигналу профілю `postgres` (outbox у форматі сервера сигналів, токен каналу) | блок B8 після детальної спеки профілю `postgres` (§13) |
| черга мутацій offline-transactions | за першою потребою споживача |
| мінімальна підтримувана версія клієнта й автоматичне звуження | П3-4 (платформна спека §7, §12) |
| хуки React для екранів, стан списку в URL, форми | П4-D; T4 дає фасад, на якому вони стоять |
| поля представлення як метадані, введення за рядком | П4-D, П4-E |
| поліморфний `include` (`allowedTypes`) | разом із пікером поліморфного посилання (П4-D) |

## 2. Рішення

| № | Рішення | Чому | Вплив на спеку |
| --- | --- | --- | --- |
| Рд1 | **Читає П4-B лише об'єкти каталогу рантайму** (зараз — довідники з ядром команд). Формат запису каталогу допускає об'єкт лише для читання — без `operations`: `CustomTable`, регістри й віртуальні таблиці додаються новими записами того самого формату, а не новим форматом чи окремою проєкцією (Р-1, рішення архітекторки 2026-11-05) | каталог уже несе фізичні й логічні імена, типи, пари й перерахування — усе, що треба мапінгу й декодуванню; друге джерело мапінгу розійшлося б із першим | спека П4 §6.3 — запис лише для читання (Додаток А) |
| Рд2 | **Запит читання T0 другої форми замінює форму П4-A** (§4.1): фільтр-дерево над логічними іменами, сортування за збереженими реквізитами, ключ як останній ключ сортування, `limit` до 200, `offset`, `include` посилань, ТЧ картки, лічильник. Форму П4-A не зберігають поруч (принцип 5 `AGENTS.md`) | один будівник для серверного читання, `ctx.read` хуків, MCP і адаптера PostgREST; фільтр-дерево виражає й keyset-курсор, тож окремого поняття курсора немає | спека П4 §6.4, §6.11 (Додаток А) |
| Рд3 | **Один декодер на клієнті й загальний адаптер.** Обидва адаптери віддають сирий JSON; T4 декодує його за каталогом одним кодеком T0 (§4.4). Адаптер PostgREST будує запит у рантаймі з каталогу й запиту T0, а не з згенерованого коду на об'єкт; типи рядків для застосунку — з кодогену (`entities.d.ts`) на межі фасаду | фільтр фасаду — дані рантайму, тож типізація всередині адаптера нічого не захищає; однакові значення незалежно від джерела; спайк (г) п. 1 довів, що згенерований літерал `select` типізується supabase-js, — двері для згенерованого коду на об'єкт лишаються відкритими (§5.3); залежність T4 — лише HTTP (`fetch`), без виведення типів postgrest-js (Р-6, рішення архітекторки 2026-11-05) | немає |
| Рд4 | **Конверт запиту даних і серверний обробник T3.** Host прив'язує одну Server Function до `createDataHandler(runtime)`; запит — `{ request }` (запис — з хешами контрактів об'єктів), відповідь — значення `{ ok, value } \| { ok: false, error }`, а не виняток (§4.5). T4 бачить лише тип транспорту з T0 | Рт15: T4 не імпортує `simetra/server`; помилка як значення переживає серіалізацію Server Function без втрати полів | немає (реалізує Рт15) |
| Рд5 | **Рушій колекцій прихований за фасадом T4.** Публічний API T4 не має типів TanStack DB; лише модуль фасаду викликає `write*`, `refetch`, `begin/write/commit`. Межу тримають лінт-зона T4 і AST-гард, а не домовленість | Р16, Р19: заміна чи оновлення бібліотеки — зміна модуля фасаду; урок першого споживача — лінт ловить не всі обходи (деструктуризація `utils`, доступ за рядком) | немає |
| Рд6 | **Write-back — з рядків результату команди.** Результат T3 уже несе рядки після запису (§6.4 П4); обробник фасаду пише їх `writeUpsert` у колекції їхніх об'єктів, а `delete` — `writeDelete`, і лише потім завершується (`Promise<void>`). Набір змін — для перечитування колекцій, яких рядки результату не покривають | закриває відкрите питання П4 §9 і платформної §13: підтверджений рядок уже є, перечитування не потрібне; обробник не залежить від автоматичного рефетчу, якого в RC немає | платформна спека §8.1, §13; спека П4 §9 (Додаток А) |
| Рд7 | **Рядок без власника-підмножини звіряє сигнал, а не повний рефетч.** Новий рядок прямого запису живе в колекції без власника; його оновлює чи прибирає перечитування за ключем (сигнал, конфлікт, відмова) — невидимий під RLS рядок прибирається | повний необмежений результат того самого скоупу на великому довіднику не настає ніколи; перечитування за ключем — дешеве й під RLS | платформна спека §8.1 (Додаток А) |
| Рд8 | **Сигнал — на фазу, з ядра, без даних** (§8): згенероване ядро після DML кличе `simetra.signal(...)`; сигнал несе UUID об'єкта, операцію, ключі вкладеним об'єктом і версію рядка. Проведення документа — одна фаза, тож один сигнал на документ (рядки ТЧ і рухи сигналів не дають). Тригер прийнятої таблиці шле той самий формат через `realtime.send`, а не `broadcast_changes` (Р-4, рішення архітекторки; знахідка В спайку (г)) | так сигнал бачить кожен запис командою, зокрема фази хуків (`ctx.run`) і створення тенанта; UUID об'єкта не змінюється при перейменуванні (Р4, Р5); версія відсіює власне відлуння; одна форма — один розбір на клієнті | платформна спека §8.2, Р31 — «один сигнал на фазу; проведення — одна фаза; тригер прийнятої таблиці — той самий формат» (Додаток А) |
| Рд9 | **Канал — пара (скоуп, UUID об'єкта); авторизує одна SQL-функція** `simetra.signal_topic_allowed(topic)`: її кличуть політика `SELECT` на `realtime.messages` для ролі запиту, політика `INSERT` для `simetra_command` у `supabase` і видача токена каналу в `postgres`. Ролі API в канал не шлють (політики `INSERT` для них немає) (Р-4, рішення архітекторки) | канал на весь скоуп показав би учаснику id і версії рядків об'єктів, яких він не читає; одна функція — одне правило для обох транспортів | платформна спека §8.2 (Додаток А) |
| Рд10 | **Транспорт сигналу — порт T4 і тіло функції сигналу за профілем.** Реалізація `supabase` (`realtime.send`, приватний канал) — у П4-B; реалізація `postgres` (outbox у форматі вбудованого споживача сервера сигналів, токен каналу) — блок B8 після детальної спеки профілю (Р-3, рекомендація) | профілю `postgres` у коді ще немає (`DATABASE_PROVIDERS` має лише `supabase`); формат outbox і логін споживача — відкриті питання спеки профілів §5 | спека профілів §4 (Додаток А) |
| Рд11 | **Кеш прав клієнта — знімок власних фактів і згенерований обчислювач** (§9). Знімок дає одна definer-функція `simetra.rights_client_snapshot()` «що можу я» (лише про себе); обчислювач T4 інтерпретує контракт прав клієнтського каталогу й відповідає `true`, `false` чи `unknown`; ключ кешу — версія проєкції й версії прав скоупів, свіжість — сигнал версії прав | спека прав §6.3, Рх15, Рх17; `unknown` для обсягів без гарантованої свіжості, щоб інтерфейс не ховав дію, яку база дозволить | спека прав §6.3 (Додаток А) |
| Рд12 | **Звірка моделі клієнта — хеш контракту об'єкта на записі** (§10): запис каталогу несе `contractHash` — хеш входів операцій, мапінгу імен і версії ядра об'єкта; конверт `run` несе хеші об'єктів своїх операцій; операція над об'єктом з іншим хешем — `command.stale-client` до бази. Глобальний `snapshotHash` лишається для звірки рантайму з базою (Рт11). Читання при розбіжності працює (Р5); перезавантаження — пропозиція, не автоматично. Мінімальна підтримувана версія й звуження — П3-4 (Р-2, рішення архітекторки 2026-11-05) | глобальний хеш змінюється з будь-якою зміною метаданих: кожен деплой змушував би всіх клієнтів перезавантажитись перед записом і губити незбережені форми, хоч об'єкт форми не змінився; старий контракт об'єкта мапить логічні імена інакше, тож запис від нього — тиха помилка або `command.invalid` | платформна спека §7, §9; спека П4 §6.3 — `contractHash` у записі каталогу (Додаток А) |

| Рд14 | **ТЧ — окрема колекція на табличну частину**, ключ — id рядка ТЧ, підмножина — власник. Зміна ТЧ іде командою власника з повним масивом рядків (Рт4, §6.6 П4) | оновлення рядка шапки зі списку не стирає ТЧ, завантажених карткою; write-back ТЧ — заміна рядків власника | немає |
| Рд15 | **Версії бібліотек — точний pin RC**, контрактні тести фасаду на закріпленій версії (Р19): `@tanstack/db` і `@tanstack/react-db` 1.0.0-rc.1.3, `@tanstack/query-db-collection` 1.5.1 на дату спеки; план B3 бере версії свіжими на свою дату й записує в карту перевикористання | Р19; дослідження RC: фасад першого споживача переходить на RC без переписування | карта перевикористання розділ 6 (план B3) |

## 3. Будова T4

```text
simetra/model   (T0)  запит читання, фільтр, кодек передачі, конверт, клієнтський каталог, порт транспорту даних і сигналу
simetra/server  (T3)  будівник читання, createDataHandler, авторизація каналів postgres (B8)
simetra/data    (T4)  фасад колекцій, адаптери джерела, фасад запису, приймач сигналів, кеш прав
```

- **T4 імпортує** T0, `zod`, бібліотеки рушія колекцій і React (хуки фасаду).
  `simetra/server` — ніколи (лінт-зона, Рт15). Supabase-клієнт — ні: адаптер
  PostgREST шле `fetch`, транспорт сигналу `supabase` — окремий вхід
  `simetra/data/supabase` з необов'язковою peer-залежністю
  `@supabase/realtime-js`, щоб застосунок профілю `postgres` її не тягнув.
- **Модуль фасаду** (`src/data/facade/`) — єдине місце, що імпортує API
  рушія колекцій на запис. Лінт-зона T4 забороняє поза ним імпорт
  `@tanstack/query-db-collection` і виклики `utils.write*`, `utils.refetch`;
  AST-гард у тестах ловить обходи, яких лінт не бачить (деструктуризація
  `utils`, доступ за рядковим ключем, динамічний імпорт). Правило
  `@typescript-eslint/no-floating-promises` — `error` у T4.
- **Клієнтський каталог** — проєкція каталогу рантайму, яку будує T1 поряд із
  `runtime-catalog.json` (`client-catalog.json`): об'єкти, реквізити з
  логічними й фізичними іменами, типи, перерахування, пари, ТЧ, ключі FK для
  `include`, контракт прав для обчислювача (§9), `contractHash` кожного
  об'єкта (§10) і `snapshotHash`. Без функцій ядра, контекстів дій, обмежень
  і `pgType`. Фізичні імена в браузері вже є
  в запитах PostgREST, тож проєкція їх не ховає; серверних секретів у ній
  немає (§3.3 платформної).
- **Запис лише для читання** (Рд1). Схема запису каталогу рантайму
  (`runtimeObjectSchema`) приймає об'єкт без `operations`: такий об'єкт
  читається, а команда над ним — `command.invalid` до бази. Перший такий
  запис з'явиться разом із видом, що його потребує; формат — уже зараз, із
  тестом форми.
- **Публікація.** `publishConfig.exports` отримує `./data` і
  `./data/supabase`; гейт пакування імпортує обидва з tarball-а.

## 4. Запит читання і серверне читання

### 4.1 Запит читання T0

`readQuerySchema` (`packages/simetra/src/model/runtime/read.ts`) отримує
форму:

```text
{ object, id, tabularSections?: true | [<ім'я ТЧ>], include?: [<реквізит Ref>] }
{ object, where?: Filter, orderBy?: [{ attribute, direction, nulls? }],
  offset?, limit, include?: [<реквізит Ref>] }
{ object, where?: Filter, count: true }
```

- **`Filter`** — дерево: `{ and: Filter[] }`, `{ or: Filter[] }`,
  `{ not: Filter }`, `{ attribute, op, value? }`. Оператори: `eq`, `ne`, `lt`,
  `lte`, `gt`, `gte`, `in`, `isNull`, `contains`, `startsWith`. `contains` і
  `startsWith` — лише для рядкових типів, без урахування регістру; символи
  шаблону у значенні екрануються. `in` — до 200 значень. Глибина дерева й
  кількість вузлів обмежені (типово 8 і 64): запит лишається дешевим для
  перевірки до бази.
- **`attribute`** — логічне ім'я реквізиту об'єкта, ключа (`keyName`),
  версії (`versionName`) чи скоупу; для пари поліморфного `Ref` — значення
  `{ type, id }`, як у декодованому рядку.
- **`orderBy`** — лише збережені реквізити об'єкта (§8.1 платформної);
  будівник завжди додає ключ останнім, тож порядок сталий. Keyset-курсор
  виражає сам фільтр (умова «після рядка» над ключами сортування), окремого
  курсора немає.
- **`limit`** — 1…200 (`READ_LIMIT_MAX`); **`offset`** — до 10 000: далі
  лише keyset.
- **`count`** — кількість рядків під RLS, обмежена 10 000: більше — відповідь
  `{ count: 10000, capped: true }`.
- **`include`** — реквізити одноцільового `Ref`, чия ціль є в каталозі: у
  відповідь додаються рядки цілей, видимі читачеві (§4.2).
- **`tabularSections`** — ТЧ картки: рядки названих ТЧ разом із рядком
  шапки, впорядковані за номером рядка.

Перевірка до бази: невідомий реквізит, оператор не для типу, значення, що не
проходить Zod типу каталогу, сортування за не збереженим реквізитом,
перевищення меж — `command.invalid` з `path`. Рядок із `\u0000` чи непарним
сурогатом — та сама відмова, як у команді (§6.5 П4).

### 4.2 Будівник T3

`buildReadStatement` (`packages/simetra/src/server/read.ts`) рендерить запит
лише з каталогу й зв'язаних параметрів (Рт13): ідентифікатори — з каталогу,
значення — `$n` з приведенням `castType`, `in` — `= ANY($n::<cast>[])`,
`contains` — `ILIKE $n` з екранованим значенням. Тексту SQL ззовні немає.

- **Транзакція** — та сама, що в §6.11 П4: `READ COMMITTED READ ONLY`,
  claims, роль запиту профілю або запасний шлях, `COMMIT`. Нове:
  `SET LOCAL statement_timeout` з опції рантайму (типово 15 с): серверне
  читання доступне з браузера, тож довгий запит не тримає з'єднання пулу.
- **`include`** — другий оператор у тій самій транзакції:
  `SELECT … FROM <ціль> WHERE <ключ> = ANY($1::uuid[])` за id з рядків
  першого. RLS цілі застосовується так само; невидима ціль просто відсутня.
  Окремий оператор замість `JOIN`: рядок цілі має ту саму форму, що й
  власне читання цілі, і декодується тим самим кодом.
- **ТЧ картки** — оператор на кожну названу ТЧ за власником, у тій самій
  транзакції.
- **Результат** — `{ rows, included?: { "<kind>.<name>": rows } }` або
  `{ count, capped? }`; рядки — логічні імена, декодовані за каталогом (Рт1).
- `ctx.read` хуків бере ту саму форму (§6.9 П4: розширення будівника діють і
  там); `count` у хуку теж дозволено.

### 4.3 Еквівалентність дверей

Інваріант 10 П4 («серверне читання бачить рівно те, що PostgREST з тими
самими claims») поширюється на запит другої форми: той самий запит через
обидва адаптери дає ту саму множину рядків і ті самі декодовані значення
(§12, B4).

### 4.4 Кодек передачі

JSON не має `bigint` і не тримає точність `numeric`, тож T0 дає кодек
`wire` (`packages/simetra/src/model/runtime/wire.ts`): `encodeRow` на сервері
й `decodeRow` на клієнті за типами каталогу.

| Логічний тип | У передачі | У колекції |
| --- | --- | --- |
| `BigInt`, версія | рядок цілого | JS `bigint` (версія — `number`, §6.4 П4) |
| `Numeric` | рядок десяткового | той самий рядок, як його віддав Postgres: масштаб зберігається (`10.50` лишається `10.50`) |
| `DateTime` | рядок | ISO 8601 UTC фіксованої ширини з мікросекундами: лексикографічний порядок = часовий |
| `Date` | `YYYY-MM-DD` | те саме |
| перерахування | логічне ім'я значення | те саме |
| пара `Ref` | `{ type, id }` | те саме |

- Адаптер PostgREST отримує значення в іншій формі: `numeric` без
  приведення приходить JSON-числом і втрачає масштаб (`10.50` → `10.5`),
  `timestamptz` — зі змінною дробовою частиною. Тому адаптер у `select`
  приводить до тексту (`::text`) колонки всіх логічних типів, які T4 тримає
  рядком чи `bigint` за Рт1 (`Numeric`, `BigInt`, версія), а решту нормалізує
  той самий `decodeRow` (спайк (г), Г1). Порівняння двох джерел — тест кодека (§12).
- Сортування колекції за `Numeric` у живому запиті: рядок десяткового не
  сортується лексикографічно. План B3 перевіряє на закріпленій версії
  бібліотеки, як задати порівняння (власний компаратор чи похідне поле);
  доки рішення немає, хост сортує `Numeric` лише сервером (§14.1).

### 4.5 Конверт і серверний обробник

T0 (`packages/simetra/src/model/runtime/envelope.ts`):

```text
DataRequest  = { request:
                 { type: "read", query }
               | { type: "run", operation | batch, contracts: { "<UUID об'єкта>": contractHash } }
               | { type: "rights" } | { type: "version" } }
DataResponse = { ok: true, value, serverHash } | { ok: false, error: CommandError, serverHash }
DataTransport = (request: DataRequest) => Promise<DataResponse>
```

T3 дає `createDataHandler(runtime)` →
`(session: SessionClaims, request: unknown) => Promise<DataResponse>`:

1. валідує конверт Zod-схемою T0 (порушення — `command.invalid`);
2. `run`, у якому хеш контракту об'єкта будь-якої операції (з `contracts`)
   відсутній чи не дорівнює `contractHash` каталогу рантайму, —
   `command.stale-client` з цим об'єктом до бази (§10);
3. `read`, `run`, `rights` — `runtime.read`, `runtime.run`,
   `runtime.rightsSnapshot` (§9.1); `version` — `{ snapshotHash, contracts }`
   каталогу рантайму;
4. значення кодує `wire` (§4.4); `CommandFailure` стає `{ ok: false, error }`;
   будь-який інший виняток — `command.internal` без тексту й запис у журнал
   рантайму.

Host у шаблоні (П4-D) робить одну Server Function: перевіряє сесію портом
ідентичності (Рт19), а без сесії відповідає `command.unauthenticated`; кличе
обробник. Обробник не читає заголовків і cookies: сесію дає host.

## 5. Адаптери джерела

### 5.1 Порт адаптера (T4)

```text
SourceAdapter = {
  read(query): Promise<{ rows, included? }>,
  count(query): Promise<{ count, capped? }>,
  capabilities: { include: boolean, count: boolean, search: boolean }
}
```

Адаптер приймає запит T0 (§4.1) і повертає **сирий** JSON рядків; декодує T4
(Рд3). Запис через адаптер не йде ніколи: запис — `DataTransport` `run`
(§7). Вибір адаптера: типовий — за профілем каталогу (`supabase` —
PostgREST, інакше — Server Function); застосунок перевизначає його для
об'єкта в налаштуваннях рантайму даних. Поле метаданих сутності для вибору
адаптера (платформна спека §8.2) додає П4-D разом із декларацією сутності.

### 5.2 Адаптер Server Function

Тонкий: `read` → `transport({ request: { type: "read", query } })`.
Помилка відповіді стає `CommandFailure` того самого коду. Цей адаптер —
типовий для `postgres` (ПП2) і запасний для об'єктів, яких PostgREST не
покриває.

### 5.3 Адаптер PostgREST

Шле `fetch` до PostgREST провайдера; адресу й заголовки (`apikey`,
`Authorization` з токеном сесії) дає host функцією `headers()`, бо токен
оновлюється. Запит будується в рантаймі з каталогу (Рд3).

- **`select`** — аліаси `логічне:фізичне` з каталогу; колонки логічних
  типів, які T4 тримає рядком чи `bigint` (Рт1), — з приведенням до тексту
  (`логічне:фізичне::text`); фільтр і сортування за тією самою фізичною
  колонкою з приведенням сумісні (спайк (г), Г1). `NULL` лишається `null`. Пара `Ref` —
  дві колонки; декодер складає `{ type, id }`.
- **Схема** — заголовок `Accept-Profile` зі схеми таблиці каталогу; схема
  мусить бути серед відкритих PostgREST (налаштування провайдера, перевіряє
  `doctor` хоста в П4-D).
- **Фільтри** — дерево §4.1 у синтаксис PostgREST над фізичними іменами
  (`and=(…)`, `or=(…)`, `not.`). Побудова в рантаймі — безпекова поверхня:
  імена колонок, таблиць і FK беруться лише з каталогу, ніколи з запиту;
  кожне значення фільтра йде в синтаксис лише в лапках з екрануванням
  зарезервованих символів PostgREST (`,`, `(`, `)`, `"`, `.`, `:`, `\`, `*`
  тощо), зокрема всередині `in.(…)` і `or=(…)`, а потім кодується як
  компонент URL. Сирого значення в синтаксисі немає. Доказ — окремий
  unit-набір з ворожими значеннями й мутаційна перевірка (§12). Трансляцію предикатів копіюють з
  `@supabase-labs/tanstack-db` з атрибуцією (платформна спека §8.2;
  `CONTRIBUTING.md`).
- **Сортування й межі** — `order=…,<ключ>.asc`, `limit`, `offset`.
- **`include`** — embed цілі **завжди** з підказкою FK `!<ім'я обмеження>` з
  каталогу: два FK на одну ціль без підказки — помилка PostgREST, а у
  скоупленого об'єкта FK складений (скоуп + id). Ціль, невидима під RLS,
  дає ключ зі значенням `null` — і для `NOT NULL` FK; складений FK робить
  невидимість питанням прав, а не скоупу. Зворотний embed — масив (спайк
  (г), п. 1, Г2). `!inner` адаптер не ставить: рядок не зникає зі списку
  через права на пов'язаний об'єкт. Вкладені рядки адаптер виносить у
  `included` тієї самої форми, що й Server Function.
- **ТЧ картки** — зворотний embed ТЧ за FK власника з `order` за номером
  рядка.
- **`count`** — `Prefer: count=exact` з `limit=0`, межа 10 000 — як у §4.1.
- Помилка PostgREST (`4xx`/`5xx`) — `command.invalid` для `400` з кодом
  `PGRST1xx`/`22P02`, `command.unauthenticated` для `401`, інакше
  `command.unavailable`; текст відповіді назовні не йде.

**Факти спайку (г), п. 1** (supabase-js 2.119.0, PostgREST v16.5): виведення
supabase-js з **літерала** `select` з аліасами й embed `!<fk>` дає точний тип
рядка з логічними ключами, коли тип `Database` — з typegen чи структурно
рівний кодогену (П0 (в)); рядок, зібраний у рантаймі, виведення не дає;
фільтри типізуються за фізичними іменами. Загальний адаптер (Рд3) цього
виведення не використовує. Якщо згенерований код на об'єкт колись знадобиться
(наприклад, `rpc` чи екран поза фасадом), кодоген видає `select` лише
літералом (`as const`), карту «логічне → фізичне» — const-літералом, завжди
ставить `!<fk>` і типізує to-one embed на таблицю з RLS як `… | null`
незалежно від `NOT NULL` FK.

## 6. Колекції за фасадом

### 6.1 Модель

- **Рантайм даних** — `createDataRuntime({ catalog, transport, sources,
  signals?, residency?, onStaleClient })` (форма, не остаточний API) на
  сесію користувача (Рд13). `dispose()` знищує колекції, підписки й кеш прав;
  host кличе його при виході й зміні користувача.
- **Колекція об'єкта** — одна на об'єкт, ключ — id рядка (рядок UUID; ключі
  RC — лише string чи number). Рядок — декодований рядок шапки з версією.
- **Колекція ТЧ** — одна на табличну частину (Рд14), ключ — id рядка ТЧ,
  підмножина — власник.
- **Режими:**
  - `on-demand` (типовий) — колекція запитів TanStack DB у режимі
    on-demand; підмножину задає живий запит фасаду (фільтр, сортування,
    межа), а `loadSubset` перекладає її в запит T0 (§4.1) і пише рядки через
    `begin/write/commit`;
  - `full` — для малих довідників, які застосунок позначив у `residency`:
    колекція читає всю видиму множину сторінками по 200 до межі (типово
    5 000 рядків); перевищення — помилка рантайму, а не тихе обрізання.
    Повний результат володіє рядками, тож рядок без власника тут не
    виникає.
- **Предикати.** Фасад перекладає в запит T0 лише вирази, які має фільтр
  §4.1; невідомий вираз — помилка розробника (`data.unsupported-predicate`),
  а не завантаження всієї таблиці. Обчислюваний вираз у сортуванні з `limit`
  вимикає ліниве завантаження в RC, тож фасад його не дає.

### 6.2 Рядок без власника-підмножини

Прямий запис (`write*`) у колекцію on-demand латає лише ключі активних
результатів; новий рядок (створення, `include`, перечитування за ключем)
лишається без власника й переживає вивантаження підмножини (§8.1
платформної). Правила фасаду:

1. рядок без власника живий доти, доки його не звірило перечитування за
   ключем: сигнал (§8.4), конфлікт чи відмова запису (§7.3), явне оновлення
   картки;
2. перечитування за ключем, що не повернуло рядка, прибирає його
   `writeDelete` (рядок видалено чи він невидимий під RLS);
3. живі запити фасаду завжди фільтрують колекцію своїм предикатом, тож
   зайвий рядок не потрапляє в список, якому не належить;
4. `dispose()` прибирає все.

### 6.3 Життєвий цикл

- `peek` колекції після `cleanup` (сплив `gcTime`) повертає `undefined`;
  write-back у прибрану колекцію не пише (урок першого споживача: інакше —
  `SyncNotInitializedError` після успіху сервера).
- `waitPendingSettled(collection)` — очікування, поки осядуть усі
  незавершені транзакції колекції; ніколи не відхиляється. RC має лише
  `tx.when('settled')` на одну транзакцію, тож фасад рахує транзакції сам.
- Оновлення підмножин — single-flight з одним хвостовим запитом: запити
  оновлення під час активного зливаються в один наступний.
- Збій однієї колекції (`health` RC) не зупиняє інших; фасад віддає стан
  колекції хосту (`status`, `health`) без типів бібліотеки.

## 7. Фасад запису

### 7.1 Операції

Фасад дає `create`, `update`, `markDeletion`, `delete` і `batch` над
логічними іменами (§6.4 П4). Один виклик — одна оптимістична транзакція
TanStack DB над колекціями об'єктів і їхніх ТЧ і **один** виклик
`DataTransport` `run` з пакетом фаз у порядку мутацій — тож одна транзакція
бази (урок першого споживача «зміна через кілька колекцій»).

- `create` — id дає клієнт (`crypto.randomUUID`, оптимістичний патерн §4
  платформної); у кореня виду скоупу id генерує T3 (§6.13 П4), тож
  оптимістичного рядка такий `create` не має: фасад пише рядок лише з
  результату.
- `update` — `expectedVersion` — версія рядка в синхронізованому стані
  колекції (не оптимістичному); зміна ТЧ — повний масив рядків ТЧ власника
  зі стану колекції ТЧ.
- `markDeletion`, `delete` — за id і версією.

### 7.2 Обробник і write-back

Обробник мутації — `Promise<void>` закріпленої RC (Рд6):

1. викликає транспорт; помилка — §7.3;
2. пише `result.rows` у колекції їхніх об'єктів одним `writeBatch`:
   `writeUpsert` рядка шапки; для кожної ТЧ у рядку — заміна рядків
   власника в колекції ТЧ (`writeUpsert` наявних і нових, `writeDelete`
   відсутніх); `delete` — `writeDelete` рядка й рядків його ТЧ;
3. рядки об'єктів без колекції в рантаймі не пишуться;
4. зміни набору змін, яких `rows` не покривають, — перечитування за
   ключем, як сигнал (§8.4);
5. завершується лише після запису: оптимістичний стан заміняє підтверджений
   рядок, а не повертається до старого.

Відлуння власної команди: сигнал прийде з тією самою версією, що вже в
колекції, і фасад його відкидає (§8.4).

### 7.3 Помилки

Фасад відхиляє транзакцію `CommandFailure` з тим самим `CommandError` T0
(§6.10 П4), без нового типу; RC відкочує оптимістичний стан. Додатково:

| Код | Що робить фасад |
| --- | --- |
| `command.conflict` `version` | перечитує рядок за ключем і пише його: користувач бачить поточний стан і версію (`currentVersion`) |
| `command.forbidden` | перечитує рядки фаз за ключем; невидимий рядок прибирається (§6.2) |
| `command.stale-client` | кличе `onStaleClient(object)` і позначає об'єкт застарілим (§10) |
| `command.unavailable` | нічого: рядок повертається до синхронізованого стану, повтор — рішення хоста |
| решта | лише відхилення |

`path` помилки — логічний шлях реквізиту; прив'язку до поля форми робить
П4-D.

## 8. Сигнал реального часу

Механіку профілю `supabase` доведено спайком (г), п. 2 (Realtime v2.147.1,
supabase-js 2.119.0): команда шле `realtime.send` з фізичними ключами,
адаптер мапить їх за каталогом і перечитує тим самим запитом — логічні
ключі й та сама версія; 20 команд — 20 сигналів рівно раз; чужий приватний
канал — `CHANNEL_ERROR Unauthorized` (політика `SELECT` на
`realtime.messages`), перечитування чужих ключів — нуль рядків; відкат
транзакції прибирає сигнал.

### 8.1 Формат

```text
change: { object: <UUID об'єкта каталогу>, op: "create" | "update" | "markDeletion" | "delete",
          keys: { <фізична колонка ключа>: <значення> }, row_ver: <версія рядка> }
rights: { row_ver: <версія прав скоупу> }
```

- `object` — UUID об'єкта з каталогу рантайму, а не ім'я: перейменування не
  ламає старих клієнтів (Р4, Р5). Слово `kind` у Simetra — вид метаданих,
  тож поле має іншу назву.
- `keys` — вкладений об'єкт: `realtime.send` дописує в повідомлення верхній
  `id`, і ключ рядка `id` з ним зіткнувся б (знахідка Б спайку (г)). Верхній
  `id` — id повідомлення; приймач дедуплікує за ним. Ключі фізичні: формат
  той самий для майбутніх записів каталогу зі складеним ключем (регістр);
  на логічні їх мапить приймач за каталогом.
- Значень полів, логічних імен і даних рядка сигнал не несе (Р31); тест
  форми payload — §12.

### 8.2 Хто шле

Генератор ядра (`packages/simetra/src/compiler/catalog-command/units.ts`) у
кожній функції ядра після DML шапки й ТЧ додає
`PERFORM simetra.signal(<об'єкт>, <вид скоупу>, <скоуп>, <ключі>, <версія>, <операція>)`
з версією рядка після запису; `<t>_delete` — з версією й скоупом стану «до».
Те саме для функції створення кореня скоупу (§6.13 П4).

`simetra.signal(p_object uuid, p_scope_kind uuid, p_scope uuid, p_keys jsonb,
p_version bigint, p_operation text) RETURNS void` — у схемі `simetra`,
`SECURITY INVOKER`, `SET search_path = ''`, `EXECUTE` лише `simetra_command`.
Тіло — за профілем:

- `supabase` — `realtime.send(<payload>, 'change', <канал>, true)` (приватний
  канал) під роллю `simetra_command`; генератор дає їй грант і політику
  `INSERT` на `realtime.messages` (§8.3, Рд16);
- `postgres` — рядок outbox (B8, Рд10).

`simetra.rights_bump` (`packages/simetra/src/compiler/rights/functions.ts`)
після підвищення кличе `simetra.signal_rights(p_scope_kind, p_scope,
<нова версія>)` з тим самим вибором тіла: сигнал версії прав (спека прав
§6.3, Рх15). `rights_bump` — `SECURITY DEFINER`, тож `realtime.send` там
виконується від власника об'єктів Simetra; план B2 доводить DB-тестом, що
сигнал прав доходить, і дає власнику потрібний грант, якщо його бракує.

**Прийнята таблиця** (до переведення на команди) шле той самий формат
тригером, що кличе `realtime.send`, а не `broadcast_changes` з `record` і
`old_record` (Рд8): приймач розбирає одну форму. Тригер генерується разом із
записом каталогу лише для читання цієї таблиці (Рд1), тобто з першим
застосунком, якому він потрібен; формат фіксує ця спека. Тригер має гард
дозаповнення `WHEN (current_setting('simetra.backfill', true) IS DISTINCT
FROM 'on')`: інакше дозаповнення фази розширення шле сигнал на кожен рядок
(спайк (г), п. 3–4). Гард гасить лише зайві сигнали й безпеки не стосується;
ядро команд гарду не потребує.

**Сплеск.** Локально 500, 2 000 і 5 000 `realtime.send` в одній транзакції
доходять усі (останній — через 31, 130 і 290 мс після `COMMIT`); ліміт
тенанта на broadcast із бази локально не діє (спайк (г), Г6). Кожен
`realtime.send` — рядок `realtime.messages`, тож пакет із 500 фаз — 500
`INSERT`: їхню ціну міряє бенчмарк плану B2. Ліміти хостингу — у перевірці
хостованого Supabase (§9 П4, Додаток А). Сигнал на фазу лишається (Рд8).

Сигнал транзакційний: `realtime.send` пише рядок `realtime.messages` у тій
самій транзакції, тож `ROLLBACK` і невдала спроба повтору (§6.5 П4) сигналу
не дають. Запис повз ядро (імпорт, мігратор, провізія «Користувачів»)
сигналу не шле: клієнт бачить такі зміни після перепідключення чи
оновлення (§8.4).

**Мовчазна втрата.** `realtime.send` ковтає будь-яку помилку у `WARNING`
(знахідка А спайку (г)): без гранту, без політики `INSERT` чи коли політика
відмовила, сигнал зникає, а команда успішна. Це свідомо — бізнес-запис через
збій сигналу не падає. Втрату ловить гейт: DB-тест «команда → сигнал дійшов
до авторизованого підписника» на кожному профілі й кожній формі ядра (§12).
Окремий випадок — створення тенанта: політика `INSERT` судить право читання
нового скоупу в тій самій транзакції; план B2 доводить, що доповнений знімок
актора (§6.13 П4) його дає.

### 8.3 Канал і авторизація

- **Канал змін** — `simetra:<вид скоупу>:<скоуп>:<об'єкт>`; нескоуплений
  об'єкт — нульові UUID виду й скоупу (`ZERO_UUID`).
- **Канал прав** — `simetra-rights:<вид скоупу>:<скоуп>`; глобальний рівень —
  нульові UUID.
- **`simetra.signal_topic_allowed(p_topic text) RETURNS boolean`** —
  `STABLE SECURITY DEFINER SET search_path = ''`, `EXECUTE` — роль запиту
  користувача й `simetra_command`. Розбирає канал суворо (інший формат —
  `false`) і відповідає:
  - канал змін скоупленого об'єкта — скоуп серед моїх скоупів цього виду
    **і** я маю хоч один обсяг права `read` на об'єкт у цьому скоупі; вираз
    будує той самий будівник, що й політику читання об'єкта, у формі,
    незалежній від рядка (множини обсягів без носіїв рядка);
  - нескоуплений об'єкт — булева перевірка права `read` (`has_right`);
    об'єкт з `publicRead` — будь-який дійсний користувач;
  - канал прав скоупу — скоуп серед моїх скоупів; глобальний — дійсний
    користувач (`current_user_id()` не `NULL`);
  - без дійсного користувача — `false`.
- **Політики `supabase`** на `realtime.messages` (обидві — з обгорткою
  `(SELECT …)`, С9):
  - `FOR SELECT TO authenticated USING (extension = 'broadcast' AND
    (SELECT simetra.signal_topic_allowed((SELECT realtime.topic()))))`;
  - `FOR INSERT TO simetra_command WITH CHECK` — той самий вираз;
  - для ролей API політики `INSERT` немає: вони в канал не шлють (Рд9).
  Політики — об'єкти застосунку в чужій схемі, тож входять у гейт (§6.9
  платформної) і рендеряться лише в профілі `supabase`. На локальному стеку
  їх створює роль `postgres` у міграції, хоча власник таблиці —
  `supabase_realtime_admin`; на хостингу це не перевірено — рядок перевірки
  хостованого Supabase мінімальної доставки (§9 П4, Додаток А), не блокер
  П4-B (знахідка Г спайку (г)).

### 8.4 Приймач сигналів (T4)

- **Підписки** — канали (скоуп, об'єкт) для кожної колекції з активними
  підмножинами й кожного мого скоупу виду об'єкта (скоупи — зі знімка прав,
  §9.1); канали прав — для моїх скоупів і глобальний.
- **Розбір** — `object` → об'єкт каталогу, `keys` → логічні ключі за
  каталогом; невідомий `object` (об'єкт, якого немає в збірці) — сигнал
  відкидається. Дедуплікація — за верхнім `id` повідомлення.
- **Пачкування** — сигнали збираються у вікно (типово 50 мс) і групуються за
  об'єктом. Чим пачкувати (`@tanstack/pacer-lite` з ядра RC чи власний
  таймер) — план B5 перевіряє на закріпленій версії.
- **Обробка пачки об'єкта:**
  1. ключ у колекції з версією ≥ `row_ver` — відкинути (відлуння);
  2. ключі в колекції з меншою версією — одне перечитування за ключами
     (`where: { id in [...] }`) через адаптер; повернутий рядок —
     `writeUpsert`, відсутній — `writeDelete` (§6.2);
  3. ключі, яких немає в колекції, — оновлення активних підмножин об'єкта
     в цьому скоупі (single-flight, §6.3): новий чи змінений рядок може
     увійти в підмножину, якої фасад не бачить без запиту;
  4. `delete` — `writeDelete` рядка й рядків його ТЧ без перечитування.
- **Кожен `SUBSCRIBED`**, зокрема після автоперепідключення транспорту, і
  повернення вкладки — оновлення активних підмножин і запит `version`
  (§10): сигнали з проміжку втрачено (спайк (г) бачив збій транспорту з
  автоперепідключенням); сигнал міг загубитися (Realtime не гарантує
  доставки; у `postgres` споживач outbox губить сигнал на нетимчасовій
  помилці, ПП3).

### 8.5 Порт транспорту

```text
SignalTransport = {
  subscribe(channels, onSignal): Unsubscribe,
  onReconnect(handler): Unsubscribe
}
```

T4 знає лише порт. Реалізація `supabase` — `simetra/data/supabase` над
`@supabase/realtime-js` (приватний канал, токен сесії від host-а).
Реалізація `postgres` (B8) отримує токени каналів від сервера: T3 дає
`runtime.authorizeChannels(session, channels)` — читання під роллю запиту, що
кличе ту саму `signal_topic_allowed` і повертає дозволені канали; підпис
токена — адаптер сервера сигналів у host-і.

### 8.6 Відомі обмеження П4-B

- **Id і версії поза обсягом читання.** Користувач лише з обсягом `own` чи
  вимірним правом на об'єкт підписаний на канал (скоуп, об'єкт) і бачить у
  сигналі ключі й версії рядків, яких читати не може (обсяги — [спека
  прав](2026-10-17-rights-design.md) §5.2). Вмісту рядків сигнал не несе, а
  перечитування під RLS такі ключі відсіює (§8.4). Залишок прийнято свідомо
  (Р-4); id — UUID v4, як у залишку оракула наявності (§6.10 П4).
- **Кеш авторизації Realtime.** Realtime кешує авторизацію каналу на час
  з'єднання (спека системної схеми, відкриті питання): відкликане право діє
  з наступного приєднання чи оновлення токена. Наслідок — залишок вище на час
  з'єднання; фасад перепідписується після сигналу прав свого скоупу (§9.3).
- **Мовчазна втрата сигналу** ловиться гейтом, а не рантаймом (§8.2).
- **Запис повз ядро** сигналу не дає (§8.2).

## 9. Кеш прав клієнта

### 9.1 Знімок

`simetra.rights_client_snapshot() RETURNS jsonb` — `STABLE SECURITY DEFINER
SET search_path = ''`, `EXECUTE` — роль запиту користувача й
`simetra_command`; генерується лише в проєкті з довідниками прав. Повертає
лише факти поточного користувача (аналіз «що можу я», Рх17):

```text
{ projectionVersion, versions: [{ scopeKind, scope, version }],
  rights: [{ object, action, form, level, levelId, … }],
  scopes: [{ scopeKind, scope, member }], dimensionValues: […], containers: […] }
```

Склад полів — рядки `rights_mine()`, `rights_my_scopes()`,
`rights_versions()`, `rights_projection_version()` і моїх значень вимірів та
контейнерів; функції значень вимірів гранту ролі запиту не мають, тож знімок
читає їх від власника лише для поточного користувача. Джерело для
`supabase` — `rpc` PostgREST; для Server Function — запит `rights` (§4.5),
`runtime.rightsSnapshot(session)` під роллю запиту. У транзакції `READ ONLY`
знімок читає живі факти (§6.11 П4).

### 9.2 Обчислювач

- T1 кладе в клієнтський каталог контракт прав об'єкта: дії, обсяги й форми
  носіїв (`own` — колонки носія, вимір — колонка носія й вимір, контейнер —
  колонка контейнера), граф вимог уже розгорнуто в рядки знімка.
- T4 інтерпретує його: `can(action, object, { scope?, row? })` → `true`,
  `false` чи `unknown`. Без рядка — «чи маю право дії хоч на щось у скоупі»
  (кнопка «Створити»); з рядком — носії рядка проти моїх id, значень і
  контейнерів. Колонки носіїв і копії носіїв (`type: "Raw"`) рядок колекції
  має, бо читання повертає всі видимі колонки.
- `unknown` — для обсягу за виміром із дослівною функцією чи зв'язком через
  прийняту `CustomTable` (свіжість не гарантована, спека прав §6.3) і для
  відсутнього в рядку носія. Хост показує дію з `unknown` доступною: база —
  бар'єр.
- Обчислювач — не захист: помилка в ньому дає зайву чи сховану кнопку, а не
  доступ.

### 9.3 Версія й свіжість

- Ключ кешу — `projectionVersion` і версії скоупів знімка.
- Сигнал каналу прав із версією, більшою за кешовану, — перечитування знімка
  (single-flight).
- Відповідь будь-якого запиту даних із `serverHash`, відмінним від хешу
  кешу знімка, — перечитування знімка: зміна моделі може змінити проєкцію.
- `projectionVersion` інша, ніж у знімку, отриманому раніше, — повна заміна
  знімка й перепідписка каналів (§8.4): змінилися мої скоупи чи права.

## 10. Звірка моделі клієнта й контракт сесії

- **Хеш контракту об'єкта** (Рд12) — `contractHash` запису каталогу
  рантайму: хеш входів операцій (реквізити `insert`/`update` з типами й
  межами, ТЧ), мапінгу «логічне → фізичне» й версії форми ядра (імена
  функцій і контекстів). Будує T1 детерміновано; зміна подання, прав чи
  інших об'єктів його не змінює. Запис лише для читання (Рд1) теж має хеш —
  за мапінгом імен.
- **Збірка клієнта** несе `contractHash` кожного об'єкта клієнтського
  каталогу; рантайм даних кладе в `run` хеші об'єктів операцій пакета.
- **Сервер** звіряє їх з каталогом свого рантайму (звіреного з базою при
  створенні за глобальним `snapshotHash`, Рт11). Операція над об'єктом з
  іншим чи відсутнім хешем — `command.stale-client` з `object` і обома
  хешами, до бази; фази, які запускають хуки через `ctx.run`, не звіряються:
  їх будує сервер своїм каталогом. Новий код T0 у `COMMAND_ERROR_CODES`.
- **Читання** при розбіжності виконується: стара збірка просить старі
  логічні імена, сервер мапить їх своїм каталогом; перейменування без DDL
  (Р5) читання не ламає, а прибрані реквізити дадуть `command.invalid`.
- **Відповідь** кожного запиту даних несе `serverHash` (глобальний
  `snapshotHash`): його зміна — сигнал клієнту запросити `version` і
  позначити об'єкти, чий `contractHash` інший.
- **`onStaleClient(object)`** — колбек host-а (П4-D): пропонує
  перезавантаження; автоматично не перезавантажує (незбережені форми інших
  об'єктів не губляться). Форма застарілого об'єкта показує стан «потрібне
  оновлення застосунку» замість кнопки запису. Під час розкатки інстанси зі
  старим і новим каталогом можуть обслуговувати ту саму вкладку по черзі:
  запис тоді вдається з повтором після оновлення, а не циклом
  перезавантажень.
- **Перевірка версії** — запит `version` на перепідключенні сигналів, на
  поверненні вкладки, при зміні `serverHash` у відповіді й не частіше разу на
  хвилину при навігації (§7 платформної).
- **Адаптер PostgREST** хешу не звіряє: читання від старої збірки — той
  самий випадок, що й читання вище; запис іде лише через `run`.
- **Версія кешу в контракті сесії** (§9 платформної: «версія кешу» команди) —
  хеші контрактів об'єктів запиту й `projectionVersion` знімка прав клієнта.
  Права команди вирішує база, тож команда не відмовляє через застарілий кеш
  прав.
- **Перемикання збірки після розширення.** Після DDL розширення PostgREST
  оновлює кеш схеми асинхронно, і перші звернення нової збірки до нової
  колонки дають `PGRST204` (спайк (г), п. 3–4). Тому нову збірку клієнта
  вмикають лише після кроку застосування «кеш PostgREST бачить нові
  колонки» (підтверджений `reload schema`). Механізм кроку — П3-4; П4-B від
  нього лише залежить.
- **Межа:** мінімальна підтримувана версія, публікація її сервером і
  автоматичне звуження — П3-4 разом із першою зміною наявної колонки (§7,
  §12 платформної); рядок §13 платформної лишається відкритим до П3-4.

## 11. Інваріанти П4-B

Кожен тримає тест (§12):

1. T4 не імпортує `simetra/server`; публічний API T4 не має типів рушія
   колекцій; поза модулем фасаду немає `write*`, `refetch` і прямого імпорту
   `@tanstack/query-db-collection`.
2. Запит читання T0 рендериться лише з каталогу й зв'язаних параметрів;
   невідомий реквізит, оператор чи межа — `command.invalid` до бази.
3. Обидва адаптери для того самого запиту й claims дають ту саму множину
   рядків і ті самі декодовані значення.
4. Обробник мутації завершується лише після запису підтверджених рядків або
   відхиленням; після завершення транзакції в колекції немає
   непідтвердженого рядка.
5. Одна транзакція фасаду — один виклик `run` — одна транзакція бази.
6. Сигнал шле лише ядро, `rights_bump` і тригер прийнятої таблиці в
   транзакції запису; відкат і невдала спроба повтору сигналу не дають;
   payload — лише `object`, `op`, `keys` і `row_ver`, без значень полів.
7. Підписник отримує сигнал каналу лише тоді, коли `signal_topic_allowed`
   для нього істинна; ролі API не можуть слати в канали; команда кожної
   форми ядра доводить сигнал до авторизованого підписника (гейт проти
   мовчазної втрати).
8. Сигнал із версією, не більшою за версію в колекції, не дає запиту.
9. Рядок, який перечитування за ключем не повернуло, прибирається з
   колекції.
10. Обчислювач прав на фікстурах збігається з перевіркою права ядра там, де
    відповідає `true` чи `false`.
11. Операція над об'єктом, чий `contractHash` у збірці інший, не доходить до
    бази; зміна іншого об'єкта чи подання запису не блокує.
12. Колекції однієї сесії не переживають `dispose()`; колекції двох
    користувачів не діляться рядками.
