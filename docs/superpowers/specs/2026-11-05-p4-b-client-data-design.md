## 1. Мета й межі

П4-B дає клієнтському коду застосунку дані бази без ручного коду доступу:
згенерований хост (П4-D) читає списки й картки, пише командами й бачить чужі
зміни без перезавантаження, а інтерфейс знає, які дії користувачу доступні.
Безпека даних лишається в базі: RLS для читання, ядро команд і RLS для
запису. Усе, що П4-B додає в клієнт, — зручність і швидкість, а не межа.

**Критерії успіху:**

1. Список і картка довідника читаються й пишуться через фасад T4 однаково в
   обох джерелах (PostgREST і Server Function); код хоста джерела не знає.
2. Оптимістична зміна або підтверджується рядком бази, або відкочується; у
   колекції не лишається рядка, якого база не підтвердила.
3. Зміна, зроблена в іншій вкладці чи іншим користувачем, доходить до
   колекції через сигнал і перечитування під RLS; сигнал не несе даних.
4. Підписник не отримує сигналу каналу, читати об'єкт у скоупі якого він не
   має права.
5. Інтерфейс питає «чи можу я дію над цим рядком» в обчислювача T4, який
   побудовано з контракту прав і який збігається з перевіркою права ядра на
   тестових фікстурах.
6. Перейменування й сумісне розширення схеми (новий необов'язковий реквізит)
   не ламають відкритих вкладок ні на читанні, ні на записі; запит від
   збірки з несумісним контрактом об'єкта відхиляється до бази з окремим
   кодом.

**Входить:**

- запит читання T0 другої форми, форма передачі й серверне читання T3 (§4);
- кодек значень і декодер рядка (§4.4);
- конверт запиту даних і серверний обробник, який host прив'язує до своєї
  Server Function (§4.5);
- адаптери джерела: Server Function і PostgREST (§5);
- колекції за фасадом: on-demand і повні, ключі, підмножини, рядок без
  власника-підмножини, публічний API читання (§6);
- фасад запису: пакет фаз, write-back з рядків результату, конфлікт версії,
  мапінг помилок (§7);
- сигнал реального часу: функція сигналу в ядрі, канали, авторизація каналу,
  транспорт профілю `supabase`, порт транспорту (§8);
- кеш прав клієнта й обчислювач (§9);
- звірка сумісності контракту об'єкта й контракт сесії (§10);
- окремий e2e-стек для наскрізних тестів PostgREST і Realtime (§12).

**Не входить:**

| Що | Де |
| --- | --- |
| запис повз команди П4-A | ніколи (П4 §2) |
| читання документів, регістрів, віртуальних таблиць регістрів, `CustomTable` | частина, що вводить вид у каталог рантайму (П4-C для документа; Рд1) |
| сигнал прийнятої таблиці (тригер) | блок, що додає запис каталогу цієї таблиці (§8.2 — формат і вимоги) |
| реалізація транспорту сигналу профілю `postgres` (outbox у форматі сервера сигналів, токен каналу) | блок B8 після детальної спеки профілю `postgres` (§13) |
| черга мутацій offline-transactions | за першою потребою споживача |
| мінімальна підтримувана версія клієнта й автоматичне звуження | П3-4 (платформна спека §7, §12) |
| екранні хуки й хости, стан списку в URL, форми, перетворення значень у decimal.js і Temporal | П4-D; T4 дає публічний API читання й запису (§6.4, §7), на якому вони стоять |
| поля представлення як метадані, введення за рядком | П4-D, П4-E |
| поліморфний `include` (`allowedTypes`) | разом із пікером поліморфного посилання (П4-D) |
| сигнали для анонімного читача (`anon`) об'єкта з `publicRead` | за першим застосунком, якому це потрібно (§8.6) |
| умова стелі агента в авторизації каналу | П4-F разом зі стелею (§8.3) |

## 4. Читання

### 4.0 Дві форми: логічна й передачі

Одне місце, де описано межу (Рд17):

| | Логічна форма | Форма передачі |
| --- | --- | --- |
| Хто | API в процесі: `runtime.run`, `runtime.read`, `ctx.read` і `ctx.run` хуків, MCP, серверний код host-а | лише між T4 і `createDataHandler` (Server Function) і між адаптером PostgREST і PostgREST |
| Об'єкт | `MetadataRef { kind, name }` (§6.4 П4) | UUID об'єкта каталогу |
| Реквізит, ключ, версія, скоуп | логічне ім'я | фізична колонка |
| ТЧ | логічне ім'я ТЧ | фізична таблиця ТЧ |
| Значення | типи рантайму (`bigint`, рядок `Numeric`) | JSON; типи, які T4 тримає рядком чи `bigint`, — текстом (§4.4) |
| Поля помилки (`path`, `object`, `attributes`) | логічні | фізичний шлях, UUID об'єкта, фізичні колонки; T4 мапить їх своїм каталогом |
| Набір змін (`changes[].object`) | `MetadataRef` | UUID об'єкта |
| `creatorMember` створення кореня (§6.13 П4) | логічні реквізити довідника членства | фізичні колонки (звіряються, як колонки операції) |
| Рядок результату | декодований, логічні імена | сирий, фізичні ключі |

- **Сервер** (`createDataHandler`) спершу звіряє сумісність запиту зі своїм
  каталогом (§4.5, §10), потім переводить форму передачі в логічну своїм
  каталогом і кличе ті самі `runtime.read` і `runtime.run`; рядки результату
  кодує назад у фізичну форму. Імена до SQL доходять лише з каталогу
  сервера, ніколи з запиту.
- **T4** переводить логічні імена фасаду у фізичні своїм каталогом і декодує
  відповідь одним декодером (§4.4) — тим самим, що й рядки PostgREST.
- **Межа гарантії.** Перейменування без DDL (Р5) не змінює фізичної форми, а
  сумісне розширення лише додає колонки, тож стара вкладка читає й пише
  далі. Промоція прийнятої таблиці перепризначає фізичні імена (Р5,
  виняток) — після неї старі вкладки несумісні (§10); гарантія старим
  клієнтам на промоцію й так не поширюється (§7 платформної).

### 4.1 Запит читання T0

`readQuerySchema` (`packages/simetra/src/model/runtime/read.ts`) отримує
форму (адресація полів — за формою з §4.0):

```text
{ object, id, tabularSections?: true | [<ТЧ>], include?: [<реквізит Ref>] }
{ object, where?: Filter, orderBy?: [{ attribute, direction, nulls? }],
  offset?, limit, include?: [<реквізит Ref>] }
{ object, where?: Filter, count: true }
```

- **`Filter`** — дерево: `{ and: Filter[] }`, `{ or: Filter[] }`,
  `{ not: Filter }`, `{ attribute, op, value? }`. Оператори: `eq`, `ne`, `lt`,
  `lte`, `gt`, `gte`, `in`, `isNull`, `contains`, `startsWith`. `contains` і
  `startsWith` — лише для рядкових типів, без урахування регістру; символи
  шаблону у значенні екрануються. `in` — до 200 значень. Глибина дерева й
  кількість вузлів обмежені (типово 8 і 64): запит лишається дешевим для
  перевірки до бази.
- **`attribute`** — реквізит об'єкта, ключ, версія чи скоуп; для пари
  поліморфного `Ref` — значення `{ type, id }`.
- **`orderBy`** — лише збережені реквізити об'єкта (§8.1 платформної);
  будівник завжди додає ключ останнім, тож порядок сталий. Keyset-курсор
  виражає сам фільтр (умова «після рядка» над ключами сортування), окремого
  курсора немає.
- **`limit`** — 1…200 (`READ_LIMIT_MAX`); **`offset`** — до 10 000: далі
  лише keyset.
- **`count`** — кількість рядків під RLS, обмежена 10 000: більше — відповідь
  `{ count: 10000, capped: true }`. Лічильник іде лише через Server Function
  (§5.3).
- **`include`** — реквізити одноцільового `Ref`, чия ціль є в каталозі
  (`ref` запису реквізиту, §3): у відповідь додаються рядки цілей, видимі
  читачеві (§4.2).
- **`tabularSections`** — ТЧ картки: рядки названих ТЧ разом із рядком
  шапки, впорядковані за номером рядка.

Перевірка до бази: невідомий реквізит, оператор не для типу, значення, що не
проходить Zod типу каталогу, сортування за не збереженим реквізитом,
перевищення меж — `command.invalid` з `path`. Рядок із `\u0000` чи непарним
сурогатом — та сама відмова, як у команді (§6.5 П4). У формі передачі
невідомий об'єкт чи колонка — несумісність (`command.stale-client`, §4.5),
бо T4 будує запит лише зі свого каталогу.

### 4.2 Будівник T3

`buildReadStatement` (`packages/simetra/src/server/read.ts`) рендерить запит
лише з каталогу й зв'язаних параметрів (Рт13): ідентифікатори — з каталогу,
значення — `$n` з приведенням `castType`, `in` — `= ANY($n::<cast>[])`,
`contains` — `ILIKE $n` з екранованим значенням. Тексту SQL ззовні немає.

- **Транзакція** — та сама, що в §6.11 П4: `READ COMMITTED READ ONLY`,
  claims, роль запиту профілю або запасний шлях, `COMMIT`. Нове:
  `SET LOCAL statement_timeout` з опції рантайму (типово 15 с): серверне
  читання доступне з браузера, тож довгий запит не тримає з'єднання пулу.
- **`include`** — другий оператор у тій самій транзакції:
  `SELECT … FROM <ціль> WHERE <ключ> = ANY($1::uuid[])` за id з рядків
  першого. RLS цілі застосовується так само; невидима ціль просто відсутня, а
  рядок першого оператора лишається. Окремий оператор замість `JOIN`: рядок
  цілі має ту саму форму, що й власне читання цілі.
- **ТЧ картки** — оператор на кожну названу ТЧ за власником, у тій самій
  транзакції.
- **Результат** — `{ rows, included?: { "<UUID об'єкта>": rows } }` або
  `{ count, capped? }`.
- `ctx.read` хуків бере ту саму логічну форму (§6.9 П4: розширення будівника
  діють і там); `count` у хуку теж дозволено.

### 4.3 Еквівалентність дверей

Інваріант 10 П4 («серверне читання бачить рівно те, що PostgREST з тими
самими claims») поширюється на запит другої форми: той самий запит через
обидва адаптери дає ту саму множину рядків і той самий декодований рядок.
Швидкий доказ — DB-тест із симуляцією claims; наскрізний — через живий
PostgREST на e2e-стеку (§12, Рд18).

### 4.4 Кодек і декодер

T0 дає `wire` (`packages/simetra/src/model/runtime/wire.ts`): `encodeRow`
(сервер: рядок рантайму → фізична форма передачі) і `decodeRow` (клієнт:
сирий рядок будь-якого джерела → рядок колекції за каталогом). `decodeRow`
один: його кличуть і адаптер Server Function, і адаптер PostgREST.

| Логічний тип | У передачі | У колекції |
| --- | --- | --- |
| `BigInt` | рядок цілого | JS `bigint` |
| версія | рядок цілого | `number` (безпечне ціле, §6.4 П4) |
| `Numeric` | рядок десяткового | той самий рядок, як його віддав Postgres: масштаб зберігається (`10.50` лишається `10.50`) |
| `DateTime` | рядок | ISO 8601 UTC фіксованої ширини з мікросекундами: лексикографічний порядок = часовий |
| `Date` | `YYYY-MM-DD` | те саме |
| перерахування | мітка бази | логічне ім'я значення |
| пара `Ref` | дві колонки | `{ type, id }` |

- **Сумісність із розширенням.** `decodeRow` ігнорує фізичні ключі, яких
  немає в клієнтському каталозі (колонка, додана після збірки), а відсутній
  ключ дає відсутнє поле. Інакше після кожного розширення читання старої
  вкладки ламалося б.
- PostgREST віддає `numeric` без приведення JSON-числом і втрачає масштаб
  (`10.50` → `10.5`), а `bigint` понад 2^53 — точність; `timestamptz` — зі
  змінною дробовою частиною. Тому адаптер приводить у `select` до тексту
  (`::text`) колонки типів, які T4 тримає рядком чи `bigint` (`Numeric`,
  `BigInt`, версія), а решту нормалізує `decodeRow` (спайк (г), Г1).
- **Межа з T5.** У колекції значення — рядки й `bigint`; перетворення в
  decimal.js і Temporal (§8.5 платформної) робить межа полів T5 (П4-D), а не
  T0 чи T4: T0 лишається лише з `zod`.
- Сортування колекції за `Numeric` у живому запиті: рядок десяткового не
  сортується лексикографічно. План B3 перевіряє на закріпленій версії
  бібліотеки, як задати порівняння (власний компаратор чи похідне поле);
  доки рішення немає, хост сортує `Numeric` лише сервером (§14.1).

### 4.5 Конверт і серверний обробник

T0 (`packages/simetra/src/model/runtime/envelope.ts`):

```text
DataRequest  = { subject: <sub сесії рантайму>, request:
                 { type: "read", query }
               | { type: "run", operation | batch, kernels?: { "<UUID об'єкта>": kernelHash } }
               | { type: "rights" } | { type: "version" } }        — форма передачі (§4.0)
DataResponse = { ok: true, value, serverHash } | { ok: false, error: CommandError, serverHash }
DataTransport = (request: DataRequest) => Promise<DataResponse>
```

T3 дає `createDataHandler(runtime)` →
`(session: SessionClaims, request: unknown) => Promise<DataResponse>`.
Порядок кроків важить:

1. валідує конверт Zod-схемою T0 (порушення — `command.invalid`); `kernels`
   у схемі необов'язкові, щоб відсутність ловила звірка, а не Zod;
2. `subject` ≠ `sub` сесії — `command.unauthenticated` з `reason:
   "session-changed"` без звернення до бази: вкладка належить рантайму іншого
   користувача (§6.1). Звірка йде за `sub` (ідентичність провайдера), а не за
   id «Користувачів»: id дає лише база (`current_user_id()`), і поза С8
   спеки системної схеми вони різні;
3. **звірка сумісності** (§10) — до перекладу й до бази: невідомий UUID
   об'єкта; для `run` — відсутній чи інший `kernelHash` об'єкта будь-якої
   операції, колонка операції (шапки, рядків ТЧ, `creatorMember`) поза
   переліком вставки чи зміни каталогу сервера, невідома таблиця ТЧ; для
   `read` — колонка фільтра, сортування, `include` чи ТЧ поза переліком
   читання. Несумісність — `command.stale-client` з `object`; пакет
   із хоч однією несумісною операцією відмовляє цілком;
4. переводить форму передачі в логічну своїм каталогом (§4.0);
5. `read`, `run`, `rights` — `runtime.read`, `runtime.run`,
   `runtime.rightsSnapshot` (§9.1); `version` — `{ snapshotHash, objects: {
   "<UUID>": kernelHash } }` каталогу рантайму;
6. значення кодує `wire` у форму передачі; `CommandFailure` стає
   `{ ok: false, error }` з фізичним `path`; будь-який інший виняток —
   `command.internal` без тексту й запис у журнал рантайму.

Запит `rights` з'являється в конверті в блоці, що дає `runtime.rightsSnapshot`
(B5), а не раніше: між блоками напівмеханізмів немає.

**Вимоги до host-а** (шаблон і їхні тести — П4-D):

- одна Server Function: перевіряє сесію портом ідентичності (Рт19), без
  сесії відповідає `command.unauthenticated`, кличе обробник;
- **захист від підробки запиту** — для HTTP-виклику Server Function
  (RPC-ендпоінта), до виклику обробника, fail-closed: `Sec-Fetch-Site`
  присутній і ≠ `same-origin` — відмова; інакше `Origin` присутній і ≠
  власному походженню — відмова; обох заголовків немає — відмова. Виклик у
  процесі під час SSR (заголовки — від навігації, `Sec-Fetch-Site: none` чи
  `cross-site` для переходу з закладки чи листа) перевірці не підлягає:
  він не з браузера. Правило — чиста функція T3
  `checkRequestOrigin({ secFetchSite, origin }, expectedOrigin)` з
  unit-тестом трьох гілок у B1; шаблон host (П4-D) лише кличе її для
  RPC-виклику. Обробник заголовків і cookies не читає: з сесією в cookie
  міжсайтовий запит інакше виконав би `run` від імені жертви;
- рантайм на сервері не тримає даних користувача на рівні модуля: обробник
  безстановий, стан сесії — лише в аргументах.

## 5. Адаптери джерела

### 5.1 Порт адаптера (T0)

```text
SourceAdapter = {
  read(query): Promise<{ rows, included? }>,     — запит і рядки у формі передачі
  capabilities: { include: boolean, search: boolean }
}
```

Адаптер повертає **сирі** рядки; декодує T4 (Рд3). Запис через адаптер не
йде ніколи: запис — `DataTransport` `run` (§7); лічильник і знімок прав —
теж `DataTransport` (`read` з `count`, `rights`). Вибір адаптера: типовий —
за профілем каталогу (`supabase` — PostgREST, інакше — Server Function);
застосунок перевизначає його для об'єкта в налаштуваннях рантайму даних.
Доки адаптера PostgREST немає (до B4), типовий для обох профілів — Server
Function. Поле метаданих сутності для вибору адаптера (платформна спека §8.2)
додає П4-D разом із декларацією сутності.

### 5.2 Адаптер Server Function

Тонкий: `read` → `transport({ subject, request: { type: "read", query } })`.
Помилка відповіді стає `CommandFailure` того самого коду. Цей адаптер —
типовий для `postgres` (ПП2) і запасний для об'єктів, яких PostgREST не
покриває.

### 5.3 Адаптер PostgREST

Шле `fetch` до PostgREST провайдера; адресу й заголовки (`apikey`,
`Authorization` з токеном сесії) дає host функцією `headers()`, бо токен
оновлюється. Перед запитом адаптер звіряє `sub` токена із `subject`
рантайму: інший — `command.unauthenticated` `session-changed` без запиту
(§6.1). Запит будується в рантаймі з каталогу (Рд3).

- **`select`** — фізичні колонки з каталогу; колонки типів, які T4 тримає
  рядком чи `bigint` (Рт1), — з приведенням `колонка:колонка::text`; фільтр і
  сортування за тією самою фізичною колонкою з приведенням сумісні (спайк
  (г), Г1). `NULL` лишається `null`. Рядок приходить у фізичних іменах — тій
  самій формі, що й від Server Function, і декодується тим самим `decodeRow`.
- **Схема** — заголовок `Accept-Profile` зі схеми таблиці каталогу; схема
  мусить бути серед відкритих PostgREST (налаштування провайдера, перевіряє
  `doctor` хоста в П4-D). Схема `simetra` відкритою не буває (С1 спеки
  системної схеми).
- **Фільтри** — дерево §4.1 у синтаксис PostgREST над фізичними іменами
  (`and=(…)`, `or=(…)`, `not.`). Побудова в рантаймі — безпекова поверхня:
  імена колонок, таблиць і FK беруться лише з каталогу, ніколи з запиту
  (ім'я поза каталогом — відмова до HTTP); кожне значення фільтра йде в
  синтаксис лише в лапках з екрануванням зарезервованих символів PostgREST
  (`,`, `(`, `)`, `"`, `.`, `:`, `\`, `*` тощо), зокрема всередині `in.(…)`
  і `or=(…)`, а потім кодується як компонент URL. Сирого значення в
  синтаксисі немає. Доказ — окремий unit-набір з ворожими значеннями й
  мутаційна перевірка (§12). Трансляцію предикатів копіюють з
  `@supabase-labs/tanstack-db` з атрибуцією (платформна спека §8.2;
  `CONTRIBUTING.md`).
- **Сортування й межі** — `order=…,<ключ>.asc`, `limit`, `offset`.
- **`include`** — embed цілі **завжди** з підказкою FK `!<ім'я обмеження>` з
  `ref` каталогу: два FK на одну ціль без підказки — помилка PostgREST, а у
  скоупленого об'єкта FK складений (скоуп + id). Ціль, невидима під RLS,
  дає ключ зі значенням `null` — і для `NOT NULL` FK; складений FK робить
  невидимість питанням прав, а не скоупу (спайк (г), п. 1, Г2). `!inner`
  адаптер не ставить: рядок не зникає зі списку через права на пов'язаний
  об'єкт. Вкладені рядки адаптер виносить у `included` тієї самої форми, що
  й Server Function.
- **ТЧ картки** — зворотний embed ТЧ (масив) з підказкою
  `!<parentConstraint>` і `order` за номером рядка: ТЧ з реквізитом `Ref` на
  об'єкт-власника інакше дала б два зв'язки між таблицями.
- **Лічильника немає**: `Prefer: count=exact` рахує всю видиму множину без
  межі на сервері, тож `count` іде через Server Function (§4.1).
- **Помилки** (текст відповіді назовні не йде):

  | Відповідь PostgREST | Код фасаду | Дія |
  | --- | --- | --- |
  | розбіжність схеми: `42703`, `42P01`, `PGRST200`, `PGRST204`, `PGRST205` | `command.unavailable` з `reason: "schema"` | запит `version` і переоцінка позначки (§10) |
  | інший `400` (`PGRST1xx`, `22P02`) | `command.invalid` | лише відхилення |
  | `401` | `command.unauthenticated` | — |
  | решта | `command.unavailable` | — |

**Факти спайку (г), п. 1** (supabase-js 2.119.0, PostgREST v16.5): виведення
supabase-js з **літерала** `select` з аліасами й embed `!<fk>` дає точний тип
рядка з логічними ключами, коли тип `Database` — з typegen чи структурно
рівний кодогену (П0 (в)); рядок, зібраний у рантаймі, виведення не дає;
фільтри типізуються за фізичними іменами. Загальний адаптер (Рд3) цього
виведення не використовує. Якщо згенерований код на об'єкт колись знадобиться
(наприклад, екран поза фасадом), кодоген видає `select` лише літералом
(`as const`), карту «логічне → фізичне» — const-літералом, завжди ставить
`!<fk>` і типізує to-one embed на таблицю з RLS як `… | null` незалежно від
`NOT NULL` FK.

## 6. Колекції за фасадом

### 6.1 Модель

- **Повернення вкладки** — `runtime.resume()`: host (П4-D) кличе його на
  поверненні вкладки; T4 не читає `document` (він імпортується й у SSR).
- **Рантайм даних** — `createDataRuntime({ catalog, transport, sources,
  signals?, residency?, subject, onStaleClient, onSessionChanged })` (форма,
  не остаточний API) на сесію користувача (Рд13). `subject` — `sub` сесії;
  кожен `DataRequest` несе його (§4.5), а адаптер PostgREST звіряє з `sub`
  токена (§5.3). Id користувача («Користувачі») рантайм бере зі знімка прав
  (`userId`, §9.1) — для каналу прав користувача. Відповідь `session-changed` — сесію змінено (зокрема в
  іншій вкладці): рантайм кличе `onSessionChanged` і `dispose()`, і рядки
  нового користувача в кеш попереднього не потрапляють.
- **Ізоляція кешу.** Рантайм створює власний `QueryClient`; `queryKey`
  колекцій містить ключ рантайму — `subject` і випадковий nonce рантайму. `dispose()` знищує колекції, очищує `QueryClient`, знімає
  підписки й кеш прав; host кличе його при виході й зміні користувача. На
  сервері (SSR) рантайм даних на рівні модуля не створюється.
- **Колекція об'єкта** — одна на об'єкт, ключ — id рядка (рядок UUID; ключі
  RC — лише string чи number). Рядок — декодований рядок шапки з версією.
- **Колекція ТЧ** — одна на табличну частину (Рд14), ключ — id рядка ТЧ,
  підмножина — власник.
- **Режими:**
  - `on-demand` (типовий) — колекція запитів TanStack DB
    (`queryCollectionOptions`, `syncMode: 'on-demand'`); підмножину задає
    живий запит фасаду (§6.4), а `queryFn` перекладає
    `ctx.meta.loadSubsetOptions` у запит T0 (§4.1) і **повертає** рядки:
    результат `queryFn` і дає підмножині власність на рядки (§6.2). Власного
    адаптера синхронізації (`begin/write/commit`) фасад не будує;
  - `full` — для малих довідників, які застосунок позначив у `residency`:
    колекція читає всю видиму множину сторінками по 200 keyset-курсором (не
    `offset`) до межі (типово 5 000 рядків); перевищення — помилка рантайму,
    а не тихе обрізання. Повний результат володіє рядками, тож рядок без
    власника тут не виникає.
- **Предикати.** Фасад перекладає в запит T0 лише вирази, які має фільтр
  §4.1; невідомий вираз — помилка розробника (`data.unsupported-predicate`),
  а не завантаження всієї таблиці. Обчислюваний вираз у сортуванні з `limit`
  вимикає ліниве завантаження в RC, тож фасад його не дає.

### 6.2 Рядок без власника-підмножини

Прямий запис (`write*`) у колекцію on-demand латає лише ключі активних
результатів; новий рядок (створення, `include`, перечитування за ключем)
лишається без власника й переживає вивантаження підмножини (§8.1
платформної). Правила фасаду:

1. фасад веде реєстр рядків без власника; кожен такий рядок звіряє
   перечитування за ключем: сигнал (§8.4), конфлікт чи відмова запису (§7.3),
   явне оновлення картки, а також **кожен `SUBSCRIBED`** і зміна множини моїх
   скоупів — пакетне перечитування за ключами всього реєстру (`in` до 200 на
   запит);
2. при зміні множини моїх скоупів рядки зі втрачених скоупів (рядок несе
   колонку скоупу) прибираються одразу з **усіх** колекцій — і рядки без
   власника, і рядки активних підмножин, — а підмножини з фільтром цього
   скоупу інвалідуються: підписку на канал утраченого скоупу знято, і такі
   рядки більше не свіжіли б;
3. перечитування за ключем, що не повернуло рядка, прибирає його
   `writeDelete` разом із рядками його ТЧ (рядок видалено чи він невидимий
   під RLS);
4. живі запити фасаду завжди фільтрують колекцію своїм предикатом, тож
   зайвий рядок не потрапляє в список, якому не належить;
5. `dispose()` прибирає все.

### 6.3 Життєвий цикл

- `peek` колекції після `cleanup` (сплив `gcTime`) повертає `undefined`;
  write-back у прибрану колекцію не пише (урок першого споживача: інакше —
  `SyncNotInitializedError` після успіху сервера).
- `waitPendingSettled(collection)` — очікування, поки осядуть усі
  незавершені транзакції колекції; ніколи не відхиляється. RC має лише
  `tx.when('settled')` на одну транзакцію, тож фасад рахує транзакції сам.
- Оновлення підмножин — single-flight з одним хвостовим запитом: запити
  оновлення під час активного зливаються в один наступний.
- Збій однієї колекції (`health` RC) не зупиняє інших; фасад віддає стан
  колекції хосту (`status`, `health`) без типів бібліотеки.

### 6.4 Публічний API читання

T5 не імпортує `@tanstack/(react-)?db` (лінт-зона), а публічні типи T4 не
мають типів бібліотеки (Рд5), тож прив'язку живого запиту до React дає T4.
Форма (не остаточні імена):

```text
useRows({ object, where?: Filter, orderBy?, limit? })
  → { rows, status, health, loadMore(), isStale }
useRow({ object, id, tabularSections? })
  → { row, tabularSections, status, health, isStale }
useCan(action, object, { scope?, row? }) → true | false | "unknown"
```

- Вхід — логічні імена й фільтр-дерево T0 (§4.1), не вирази бібліотеки;
  результат — декодовані рядки й стани без типів `@tanstack/*`.
- `isStale` — об'єкт несумісний зі збіркою (§10); екран показує «потрібне
  оновлення застосунку» замість кнопки запису.
- Екранні хуки, стан списку в URL і хости П4-D будуються над цим API.

## 7. Фасад запису

### 7.1 Операції

Фасад дає `create`, `update`, `markDeletion`, `delete` і `batch` над
логічними іменами; на дроті — форма передачі (§4.0). Один виклик — одна
оптимістична транзакція TanStack DB над колекціями об'єктів і їхніх ТЧ і
**один** виклик `DataTransport` `run` з пакетом фаз у порядку мутацій — тож
одна транзакція бази (урок першого споживача «зміна через кілька колекцій»).

- `create` — id дає клієнт (`crypto.randomUUID`, оптимістичний патерн §4
  платформної); у кореня виду скоупу id генерує T3 (§6.13 П4), тож
  оптимістичного рядка такий `create` не має.
- `update` — `expectedVersion` — версія рядка в синхронізованому стані
  колекції (не оптимістичному) на момент запуску обробника; зміна ТЧ —
  повний масив рядків ТЧ власника зі стану колекції ТЧ.
- **Черговість одного ключа.** Мутації того самого рядка фасад виконує
  послідовно: обробник наступної стартує після осідання попередньої й бере
  версію вже після її write-back. Інакше друга з двох швидких правок
  дістала б `command.conflict` і відкотилась.
- `markDeletion`, `delete` — за id і версією.
- Об'єкт, позначений застарілим (§10), запису не приймає: фасад відмовляє
  `command.stale-client` без виклику транспорту.

### 7.2 Обробник і write-back

Обробник мутації — `Promise<void>` закріпленої RC (Рд6):

1. викликає транспорт; помилка — §7.3;
2. декодує `result.rows` і пише їх у колекції їхніх об'єктів одним
   `writeBatch`: `writeUpsert` рядка шапки; для кожної ТЧ у рядку — заміна
   рядків власника в колекції ТЧ (`writeUpsert` наявних і нових,
   `writeDelete` відсутніх); `delete` — `writeDelete` рядка й рядків його ТЧ;
3. неповний рядок (лише ключ і версія — створення кореня скоупу без ролі
   `rootCreator`, §6.13 П4) не пишеться: фасад перечитує його за ключем, і
   невидимий рядок у колекцію не потрапляє;
4. рядки об'єктів без колекції в рантаймі не пишуться;
5. зміни набору змін, яких `rows` не покривають, — перечитування за
   ключем, як сигнал (§8.4);
6. завершується лише після запису: оптимістичний стан заміняє підтверджений
   рядок, а не повертається до старого.

Відлуння власної команди: сигнал прийде з тією самою версією, що вже в
колекції, і фасад його відкидає (§8.4).

### 7.3 Помилки

Фасад відхиляє транзакцію `CommandFailure` (T0) з тим самим `CommandError`
(§6.10 П4), без нового типу; `path` фасад мапить з фізичного в логічний
своїм каталогом. RC відкочує оптимістичний стан. Додатково (запис і
читання):

| Код | Що робить фасад |
| --- | --- |
| `command.conflict` `version` | перечитує рядок за ключем і пише його: користувач бачить поточний стан і версію (`currentVersion`) |
| `command.forbidden` | перечитує рядки фаз за ключем; невидимий рядок прибирається (§6.2) |
| `command.stale-client` | запит `version` і переоцінка позначки (§10); `onStaleClient(object)`; автоматичного повтору немає |
| `command.unavailable` `schema` (PostgREST, §5.3) | запит `version` і переоцінка сумісності |
| `command.unauthenticated` `session-changed` | `onSessionChanged` і `dispose()` (§6.1) |
| `command.unavailable` | нічого: рядок повертається до синхронізованого стану, повтор — рішення хоста |
| решта | лише відхилення |

Прив'язку `path` до поля форми робить П4-D.

## 8. Сигнал реального часу

Механіку профілю `supabase` доведено спайком (г), п. 2 (Realtime v2.147.1,
supabase-js 2.119.0): команда шле `realtime.send` з фізичними ключами,
адаптер мапить їх за каталогом і перечитує тим самим запитом — логічні
ключі й та сама версія; 20 команд — 20 сигналів рівно раз; чужий приватний
канал — `CHANNEL_ERROR Unauthorized` (політика `SELECT` на
`realtime.messages`), перечитування чужих ключів — нуль рядків; відкат
транзакції прибирає сигнал.

### 8.1 Формат

Схеми й формат каналу — у T0 (§3). Схем дві:

- **схема відправки** — рівно те, що шле генератор:

  ```text
  change: { object: <UUID об'єкта каталогу>, op: "create" | "update" | "markDeletion" | "delete",
            keys: { <фізична колонка ключа>: <UUID> }, row_ver: <версія рядка> }
  rights: { op: "rights", row_ver: <версія прав> }
  ```

  Зміна — рівно чотири поля, права — рівно два.

- **схема прийнятого повідомлення** — схема відправки плюс верхній `id`
  (UUID): `realtime.send` дописує його в payload, якщо його немає, і пише
  той самий id у `realtime.messages.id`. Приймач дедуплікує за ним. Обидві
  схеми суворі: зайве поле — відмова розбору.

Правила:

- `object` — UUID об'єкта з каталогу рантайму, а не ім'я: перейменування не
  ламає старих клієнтів (Р4, Р5). Слово `kind` у Simetra — вид метаданих,
  тож поле має іншу назву.
- `keys` — вкладений об'єкт, бо верхній `id` зайнятий id повідомлення
  (знахідка Б спайку (г)).
- **Лише сурогатний ключ UUID.** Сигнал шле лише об'єкт, чий ключ — одна
  колонка UUID: складений чи природний ключ — це значення полів (виміри, код,
  пошта), і через канал, авторизований без рядка, вони дійшли б до
  підписника з вужчим обсягом. Об'єкт з іншим ключем сигналу не шле, доки
  окреме рішення не задасть його формат.
- Значень полів, логічних імен і даних рядка сигнал не несе (Р31).

### 8.2 Хто шле

Генератор ядра (`packages/simetra/src/compiler/catalog-command/units.ts`) у
кожній функції ядра **сигнального** об'єкта (§8.3) після DML шапки й ТЧ
додає
`PERFORM simetra.signal(<об'єкт>, <вид скоупу>, <скоуп>, <ключі>, <версія>, <операція>)`
з версією рядка після запису; `<t>_delete` — з версією й скоупом стану «до».
Корінь виду скоупу — сигнальний об'єкт: його носій скоупу — власний `id`,
тож канал кореня — `simetra:<вид>:<id кореня>:<об'єкт кореня>` (§8.3), і
сигнал шлють усі його функції ядра. Функція створення кореня (§6.13 П4) теж
кличе сигнал; доходить він лише в моделі з роллю `rootCreator` (творець
читає новий скоуп у тій самій транзакції). У моделі оператора актор нового скоупу не читає, тож політика
`INSERT` сигнал відхиляє — і це правильно: учасників скоупу ще немає, а про
новий скоуп творця повідомляє канал прав користувача.

`simetra.signal(p_object uuid, p_scope_kind uuid, p_scope uuid, p_keys jsonb,
p_version bigint, p_operation text) RETURNS void` — у схемі `simetra`,
`SECURITY INVOKER`, `SET search_path = ''`, `EXECUTE` лише `simetra_command`.
Тіло — за профілем:

- `supabase` — `realtime.send(<payload>, 'change', <канал>, true)` (приватний
  канал) під роллю `simetra_command`; генератор дає їй `USAGE` схеми
  `realtime`, `EXECUTE realtime.send`, `INSERT` на `realtime.messages` і
  політику `INSERT` (§8.3, Рд16);
- `postgres` — рядок outbox (B8, Рд10).

**Сигнали прав.** `simetra.rights_bump`
(`packages/simetra/src/compiler/rights/functions.ts`) після підвищення кличе
`simetra.signal_rights(p_scope_kind, p_scope, <нова версія>)` — у канал прав
скоупу. Тригери членства й призначень ролей (`guard-units.ts`) додатково
шлють у **канал прав користувача** кожного зачепленого учасника
(`simetra.signal_user_rights(<id користувача>, <версія прав скоупу>)`): так
користувач, доданий у новий скоуп, дізнається про нього, хоч на канал
нового скоупу ще не підписаний. Обидві функції кличуть лише definer-код
платформи (`SECURITY DEFINER SET row_security = off` від власника об'єктів
Simetra з `BYPASSRLS`, §9 П4), тож `realtime.send` там виконується від
власника, і політика його не судить; грант власника на `realtime.messages`
план B6 доводить тестом і додає, якщо бракує.

**Прийнята таблиця** (до переведення на команди) шле той самий формат
тригером, що кличе `realtime.send`, а не `broadcast_changes` з `record` і
`old_record` (Рд8): приймач розбирає одну форму. Тригер генерує блок, що
додає запис каталогу лише для читання цієї таблиці (Рд1); ця спека фіксує
формат і вимоги до нього:

- функція тригера — `SECURITY DEFINER` від власника об'єктів Simetra
  (`BYPASSRLS`), як `rights_bump`: прийняту таблицю пишуть ролі запиту,
  фонові записувачі без claims і функції споживача, а для них політики
  `INSERT` немає (Рд9) — від їхнього імені сигнал зникав би мовчки;
- тригер має гард дозаповнення `WHEN (current_setting('simetra.backfill',
  true) IS DISTINCT FROM 'on')`: інакше дозаповнення фази розширення шле
  сигнал на кожен рядок (спайк (г), п. 3–4). Гард гасить лише зайві сигнали
  й безпеки не стосується; ядро команд гарду не потребує;
- `CustomTable` не має контракту прав (спека прав §4.1), тож авторизація
  каналу такої таблиці — fail-closed, доки застосунок не оголосить її правило;
- тригер входить у наскрізний гейт мовчазної втрати (§12).

**Сплеск.** Локально 500, 2 000 і 5 000 `realtime.send` в одній транзакції
доходять усі (останній — через 31, 130 і 290 мс після `COMMIT`); ліміт
тенанта на broadcast із бази локально не діє (спайк (г), Г6). Кожен
`realtime.send` — рядок `realtime.messages`, тож пакет із 500 фаз — 500
`INSERT`: план B2 фіксує їхню ціну бенчмарком (число, без порогу). Ліміти
хостингу — у перевірці хостованого Supabase (§9 П4, Додаток А). Сигнал на
фазу лишається (Рд8).

Сигнал транзакційний: `realtime.send` пише рядок `realtime.messages` у тій
самій транзакції, тож `ROLLBACK` і невдала спроба повтору (§6.5 П4) сигналу
не дають. Запис повз ядро (імпорт, мігратор, провізія «Користувачів»,
рядки членства й призначення, які вставляє функція створення тенанта,
§6.13 П4) сигналу змін не шле: клієнт бачить такі зміни після перепідписки
чи оновлення (§8.4); зміну прав від них несуть сигнали прав (тригери).

**Мовчазна втрата.** `realtime.send` ковтає будь-яку помилку у `WARNING`
(знахідка А спайку (г)): без гранту, без політики `INSERT` чи коли політика
відмовила, сигнал зникає, а команда успішна. Це свідомо — бізнес-запис через
збій сигналу не падає. Втрату ловить гейт на e2e-стеку (Рд18): «команда →
сигнал дійшов до авторизованого підписника» на кожній формі ядра й кожному
сигналі прав (§12).

### 8.3 Канали й авторизація

- **Канал змін** — `simetra:<вид скоупу>:<скоуп>:<об'єкт>`; нескоуплений
  об'єкт — нульові UUID виду й скоупу (`ZERO_UUID`).
- **Канал прав скоупу** — `simetra-rights:<вид скоупу>:<скоуп>`; глобальний
  рівень — нульові UUID.
- **Канал прав користувача** — `simetra-user:<id користувача>`; payload —
  лише «права змінились» і нова версія прав, без переліку скоупів.
- **Сигнальний об'єкт.** Об'єкт шле сигнал змін, лише коли (а) його ключ —
  сурогатний UUID (§8.1) і (б) кожна `RESTRICTIVE`-межа читання об'єкта
  виражається без рядка: межа тенанта над колонкою-носієм скоупу (у кореня —
  над його `id`) — так, бо скоуп несе сам канал; межа, що залежить від інших
  колонок рядка, — ні (так у «Користувачів»: межа «я й учасники моїх
  скоупів», спека прав §5.2). Рішення ухвалює компілятор тим самим аналізом,
  що будує політики, і пише його двічі з одного джерела: виклик сигналу в
  ядрі й ознаку `signal` у клієнтському каталозі. Несигнальний об'єкт ядро
  сигналом не супроводжує, а приймач на його канали не підписується; його
  колекції свіжіють перепідпискою й оновленням (§8.4). Інакше канал
  нескоупленого об'єкта видав би id і моменти змін рядків, яких RLS не
  показує, зокрема користувачів чужих тенантів. `RESTRICTIVE`-політики стелі
  агента (`<t>_agent`, Рх12) — теж межі читання: П4-F, вводячи їх, додає
  умову стелі в `signal_topic_allowed` чи робить об'єкт із рядковою стелею
  несигнальним.
- **`simetra.signal_topic_allowed(p_topic text) RETURNS boolean`** —
  `STABLE SECURITY DEFINER SET search_path = ''`, `EXECUTE` — `PUBLIC`:
  `RESTRICTIVE`-політики нижче діють для всіх ролей, а Postgres перевіряє
  `EXECUTE` функції виразу політики навіть тоді, коли гілку не обчислює, тож
  без гранту будь-яка роль застосунку падала б на власних каналах. Функція
  відповідає лише про права поточного користувача й без нього повертає
  `false`, тож `PUBLIC` нічого не розкриває. Розбирає канал суворо (інший формат, невідомий чи несигнальний
  об'єкт — `false`) і відповідає:
  - канал змін скоупленого об'єкта — скоуп проходить ту саму межу тенанта,
    що й `<t>_scope_read` (для виду з дослівною функцією множини — той самий
    `scopeSetCall`, `packages/simetra/src/compiler/access-units.ts`), **і** я
    маю хоч один обсяг права `read` на об'єкт у цьому скоупі — `any`, `own`
    чи вимір; лише контейнерне право канал **не** відкриває: роль на одному
    контейнері інакше показала б id і версії рядків усіх контейнерів скоупу
    (з тієї самої причини `has_right` контейнерних рядків не бачить), а
    залишок Р-4 прийнято лише для `own` і виміру. Вираз будує той самий
    будівник, що й політику читання об'єкта, у формі, незалежній від рядка
    (множини обсягів без носіїв рядка);
  - канал кореня виду скоупу — скоуп (= `id` кореня) серед моїх скоупів і
    право `read` кореня за тим самим правилом;
  - скоуплений об'єкт з `publicRead` (межі скоупу немає, спека прав §5.2) —
    будь-який дійсний користувач;
  - нескоуплений сигнальний об'єкт — хоч одна перевірка права `read`
    (`has_right`) за обсягами `any`, `own` чи вимір контракту об'єкта
    (контейнерні рядки `has_right` не бачить, тож контейнерне право канал
    не відкриває); з `publicRead` — будь-який дійсний користувач;
  - канал прав скоупу — скоуп серед моїх скоупів; глобальний — дійсний
    користувач (`current_user_id()` не `NULL`);
  - канал прав користувача — `<id> = current_user_id()`;
  - без дійсного користувача — `false`.
- **Політики `supabase`** на `realtime.messages` (з обгорткою `(SELECT …)`,
  С9):
  - `PERMISSIVE FOR SELECT TO authenticated USING (extension = 'broadcast'
    AND (SELECT simetra.signal_topic_allowed((SELECT realtime.topic()))))`;
  - `PERMISSIVE FOR INSERT TO simetra_command WITH CHECK (extension =
    'broadcast' AND simetra.signal_topic_allowed(topic))` — над колонкою
    `topic` рядка, що вставляється, а не над налаштуванням
    `realtime.topic()`: те живе до кінця транзакції після першого
    `realtime.send`, і інший `INSERT` у тій самій транзакції пройшов би за
    чужим каналом;
  - `RESTRICTIVE FOR SELECT` для всіх ролей — резерв префіксів: топік з
    префіксом `simetra:`, `simetra-rights:` чи `simetra-user:` (за
    `realtime.topic()`, як у `PERMISSIVE`) проходить лише за
    `signal_topic_allowed`;
  - `RESTRICTIVE FOR INSERT` для всіх ролей — над колонкою `topic`: рядок з
    префіксом Simetra проходить лише від `simetra_command` і лише за
    `signal_topic_allowed(topic)`. Власник об'єктів Simetra (`BYPASSRLS`)
    політик не проходить.
  Без резерву будь-яка широка `PERMISSIVE`-політика застосунку для власних
  каналів відкрила б канали Simetra на читання й запис. Політики — об'єкти
  застосунку в чужій схемі, тож входять у гейт (§6.9 платформної) і
  рендеряться лише в профілі `supabase`. На локальному стеку їх створює роль
  `postgres` у міграції, хоча власник таблиці — `supabase_realtime_admin`; на
  хостингу це не перевірено — рядок перевірки хостованого Supabase
  мінімальної доставки (§9 П4, Додаток А), не блокер П4-B (знахідка Г спайку
  (г)).
- **Публічний канал з тим самим ім'ям.** Політики судять приватне
  приєднання й відправку з бази; що публічне приєднання до топіка Simetra
  сигналу не отримує і що публічна відправка клієнтом у топік Simetra не
  доходить до приватного підписника, доводить гейт на e2e-стеку (§12). Якщо отримує — вимога режиму «лише
  приватні канали» йде в перевірку хостованого Supabase.
- **Сервісна роль** (`service_role`) має `BYPASSRLS` і гранти на
  `realtime.messages`: вона довірена (серверний ключ) і поза гарантіями
  Рд9; її ключ у браузер не потрапляє.

### 8.4 Приймач сигналів (T4)

- **Підписки** обчислюються зі знімка прав (§9.1) і перераховуються на кожну
  його заміну:
  - канали змін — для кожної колекції сигнального об'єкта з активними
    підмножинами й кожного мого скоупу виду об'єкта, де знімок має право
    `read` на об'єкт у цьому скоупі за правилом `signal_topic_allowed`
    (`any`, `own` чи вимір; не лише контейнер); для скоупленого `publicRead` —
    також скоупи, які є в активних підмножинах; нескоуплений сигнальний
    об'єкт — канал із `ZERO_UUID`, коли знімок має таке право на глобальному
    рівні. Предикат підписки — одна функція T4 над знімком; її еквівалентність
    із `signal_topic_allowed` доводить DB-тест (§12);
  - канали прав моїх скоупів, глобальний і канал прав користувача (B6).
  `CHANNEL_ERROR` авторизації приєднання не повторює до наступної заміни
  знімка: інакше відхилений канал навантажував би авторизацію безперервно.
- **Розбір** — схемою прийнятого повідомлення (§8.1): `object` → об'єкт
  каталогу, `keys` → ключ за каталогом; невідомий `object` (об'єкта немає в
  збірці) — сигнал відкидається. Дедуплікація — за `id` повідомлення.
- **Пачкування** — сигнали збираються у вікно (типово 50 мс) і групуються за
  об'єктом. Чим пачкувати (`@tanstack/pacer-lite` з ядра RC чи власний
  таймер) — план B5 перевіряє на закріпленій версії.
- **Обробка пачки об'єкта** (порядок кроків важить):
  1. `delete` — першим, до перевірки версії: ключа немає (зокрема власне
     відлуння) — нічого; ключ є — перечитування за ключем у тому самому
     пакетному запиті, що й крок 3, і `writeDelete` рядка й рядків його ТЧ,
     лише якщо рядок не повернувся. Сигнал `delete` несе версію стану «до»,
     тож перевірка версії відкинула б чуже видалення, а без перечитування
     вміст сигналу міг би прибрати рядок, якого ніхто не видаляв;
  2. ключ у колекції з версією ≥ `row_ver` — відкинути (відлуння);
  3. ключі в колекції з меншою версією — одне перечитування за ключами
     (`where: { <ключ> in [...] }`) через адаптер; ключі, чий власник має
     активну підмножину в колекції ТЧ, перечитуються з `tabularSections`, і
     рядки ТЧ власника заміняються, як у write-back (§7.2); повернутий рядок —
     `writeUpsert`, відсутній — `writeDelete` (§6.2);
  4. ключі, яких немає в колекції, — оновлення активних підмножин об'єкта
     в цьому скоупі (single-flight, §6.3): новий чи змінений рядок може
     увійти в підмножину, якої фасад не бачить без запиту.
- **Сигнали прав** — перечитування знімка (§9.3).
- **Кожен `SUBSCRIBED`**, зокрема після автоперепідключення транспорту, і
  повернення вкладки — оновлення активних підмножин, звірка реєстру рядків
  без власника (§6.2), перечитування знімка прав і запит `version` (§10);
  повернення вкладки приходить від host-а через `runtime.resume()` (§6.1):
  сигнали з проміжку втрачено (спайк (г) бачив збій транспорту з
  автоперепідключенням; Realtime не гарантує доставки; у `postgres` споживач
  outbox губить сигнал на нетимчасовій помилці, ПП3).

### 8.5 Порт транспорту (T0)

```text
SignalTransport = {
  subscribe(channels, onSignal, onError): Unsubscribe,
  onSubscribed(handler): Unsubscribe     — кожне (пере)підключення
}
```

T4 знає лише порт. Реалізація `supabase` — `simetra/data/supabase` над
`@supabase/realtime-js` (приватний канал, токен сесії від host-а).
Реалізація `postgres` (B8) отримує токени каналів від сервера: T3 дає
`runtime.authorizeChannels(session, channels)` — читання під роллю запиту, що
кличе ту саму `signal_topic_allowed` і повертає дозволені канали; підпис
токена — адаптер сервера сигналів у host-і.

### 8.6 Відомі обмеження П4-B

- **Id і версії поза обсягом читання.** Користувач лише з обсягом `own` чи
  вимірним правом на об'єкт підписаний на канал (скоуп, об'єкт) і бачить у
  сигналі ключі й версії рядків, яких читати не може (обсяги — [спека
  прав](2026-10-17-rights-design.md) §5.2). Вмісту рядків сигнал не несе, а
  перечитування під RLS такі ключі відсіює (§8.4). Залишок прийнято свідомо
  (Р-4); id — UUID v4, як у залишку оракула наявності (§6.10 П4).
- **Кеш авторизації Realtime.** Realtime кешує авторизацію каналу на час
  з'єднання (спека системної схеми, відкриті питання): відкликане право діє
  з наступного приєднання чи оновлення токена. Наслідок — залишок вище на час
  з'єднання; фасад перепідписується після сигналу прав (§9.3).
- **Несигнальні об'єкти** («Користувачі», об'єкти з не-UUID ключем)
  свіжіють лише перепідпискою й оновленням (§8.3).
- **Читач лише з контейнерним правом** сигналів змін не отримує (§8.3).
  Зміни він бачить після перечитування, і для нього діють ті самі тригери,
  що й для всіх: кожен `SUBSCRIBED` (оновлення активних підмножин, §8.4),
  повернення вкладки (`runtime.resume()`, §6.1), навігація, що монтує список
  чи картку заново (нова підмножина), ручне оновлення хоста, а також власний
  запис (write-back, §7.2) і перечитування після конфлікту чи відмови
  (§7.3). Сигнал прав (§9.3) теж оновлює його підписки й знімок.
- **Анонімний читач** об'єкта з `publicRead` сигналів не отримує: політика
  `SELECT` — лише `TO authenticated`.
- **Створення кореня в моделі оператора** сигналу змін не дає (§8.2).
- **Мовчазна втрата сигналу** ловиться гейтом, а не рантаймом (§8.2).
- **Запис повз ядро** сигналу змін не дає (§8.2).

## 9. Кеш прав клієнта

### 9.1 Знімок

`simetra.rights_client_snapshot() RETURNS jsonb` — `STABLE SECURITY INVOKER
SET search_path = ''`, `EXECUTE` — роль запиту користувача й
`simetra_command`; тіло кличе лише публічні функції фактів, які роль запиту
вже виконує (`rights_mine()`, `rights_my_scopes()`,
`rights_dimension_values()`, `rights_versions()`,
`rights_projection_version()`), тож нової definer-поверхні не додає.
Повертає лише факти поточного користувача (аналіз «що можу я», Рх17); схема
— у T0:

```text
{ userId, projectionVersion?, versions?: [{ scopeKind, scope, version }],
  rights: [{ object, action, form, level, levelId, … }],
  scopes: [{ scopeKind, scope, member }], dimensionValues: […], containers: […] }
```

- Генерується в кожному проєкті з функціями прав (є ролі й користувач
  сесії), а не лише з довідниками прав. Без довідників прав `rights_bump`,
  `rights_versions()` і `rights_projection_version()` не генеруються: тоді
  `versions` і `projectionVersion` відсутні, сигналів прав немає, і знімок
  свіжіє лише перечитуванням (§9.3).
- Джерело — лише `DataTransport` `{ type: "rights" }` →
  `runtime.rightsSnapshot(session)` під роллю запиту, і в профілі
  `supabase`: схема `simetra` поза схемами API PostgREST (С1 спеки системної
  схеми), і відкривати її не можна — кожна функція з `EXECUTE` для
  `authenticated`, зокрема функції аналізу, стала б HTTP-ендпоінтом.
- У транзакції `READ ONLY` знімок читає живі факти (§6.11 П4).
- `userId` — `current_user_id()`: з нього приймач будує канал прав
  користувача (§8.3).
- Скоупи й права знімка потрібні приймачу сигналів (§8.4), тож знімок і його
  читання приходять у B5, а обчислювач — у B6 (§13).

### 9.2 Обчислювач

- Компілятор (T1) кладе в клієнтський каталог контракт прав об'єкта: дії,
  обсяги й форми носіїв (`own` — колонки носія, вимір — колонка носія й
  вимір, контейнер — колонка контейнера); граф вимог уже розгорнуто в рядки
  знімка.
- T4 обчислює за ним `can(action, object, { scope?, row? })` → `true`,
  `false` чи `unknown`. Код обчислювача загальний і не пишеться під
  застосунок: усе, що залежить від застосунку, — у згенерованому контракті.
  Без рядка — «чи маю право дії хоч на щось у скоупі» (кнопка «Створити»); з
  рядком — носії рядка проти моїх id, значень і контейнерів. Колонки носіїв і
  копії носіїв (`type: "Raw"`) рядок колекції має, бо читання повертає всі
  видимі колонки.
- `unknown` — для обсягу за виміром із дослівною функцією чи зв'язком через
  прийняту `CustomTable` (свіжість не гарантована, спека прав §6.3), для
  відсутнього в рядку носія і для знімка без версій (проєкт без довідників
  прав) на обсягах, що залежать від членства. Хост показує дію з `unknown`
  доступною: база — бар'єр.
- Обчислювач — не захист: помилка в ньому дає зайву чи сховану кнопку, а не
  доступ.

### 9.3 Версія й свіжість

- Ключ кешу — `projectionVersion` і версії скоупів знімка (коли вони є).
- Сигнал каналу прав скоупу з версією, більшою за кешовану, і будь-який
  сигнал каналу прав користувача — перечитування знімка (single-flight).
- Відповідь будь-якого запиту даних із `serverHash`, відмінним від хешу,
  з яким знято знімок, — перечитування знімка: зміна моделі може змінити
  проєкцію.
- Кожен `SUBSCRIBED` і повернення вкладки — перечитування знімка (§8.4).
- Кожна заміна знімка — перерахунок підписок (§8.4); зміна множини моїх
  скоупів — ще й прибирання рядків утрачених скоупів (§6.2).

## 10. Звірка сумісності контракту й контракт сесії

- **Контракт об'єкта** (Рд12) у записі каталогу рантайму — `kernelHash`
  (хеш форми ядра: імена функцій і контексти дій) і переліки фізичних
  колонок шапки й кожної ТЧ (за фізичною таблицею ТЧ):
  - вставки й зміни — колонки реквізитів з `insert`/`update`;
  - читання — `key`, `versionColumn`, `scopeColumn`, `column` і
    `pair.typeColumn` кожного реквізиту; для ТЧ — `key`, `parent`,
    `lineNumber` і колонки реквізитів ТЧ.
  Будує T1 детерміновано; перейменування, подання, права й інші об'єкти
  контракту не змінюють.
- **Сумісність** — запит із форми передачі сумісний з каталогом сервера,
  коли: UUID об'єкта відомий; для запису — `kernelHash` об'єкта рівний, а
  кожна колонка операції є в переліку вставки чи зміни для її дії; для
  читання — кожна колонка фільтра, сортування, `include` і ТЧ є в переліку
  читання. Новий необов'язковий реквізит шапки чи ТЧ перелік лише розширює,
  тож стара вкладка пише далі без `stale-client`; зміна типу за §7
  платформної — нова колонка, а значення далі валідує Zod каталогу сервера.
  Реквізит, видалений на фазі розширення, відхиляє лише запит, що його
  називає.
- **Сервер** звіряє сумісність кроком 3 обробника (§4.5) — до перекладу й до
  бази: прибрана колонка в запиті старої вкладки — `command.stale-client`, а
  не `command.invalid`. Фази, які запускають хуки через `ctx.run`, не
  звіряються: їх будує сервер своїм каталогом. Звірка належить конверту
  передачі: API в процесі (`runtime.run`) її не робить — там каталог один
  (Рт11). Новий код T0 у `COMMAND_ERROR_CODES`.
- **Відповідь** кожного запиту даних несе `serverHash` (глобальний
  `snapshotHash`): його зміна — сигнал клієнту запросити `version`.
- **Позначка «застарілий»** на весь об'єкт — лише за невідомим об'єктом чи
  іншим `kernelHash`: тоді жоден запис над ним не пройде. Клієнт обчислює її
  на кожній відповіді `version` і **знімає**, коли хеш збігся. Несумісна
  колонка позначки не ставить: `stale-client` відхиляє лише свій запит,
  фасад кличе `onStaleClient(object)` і не повторює запит автоматично, тож
  циклу повторів немає.
  Під час розкатки інстанси зі старим і новим каталогом можуть відповідати
  вкладці по черзі: позначка ставиться й знімається з кожною відповіддю, а
  не залипає, і запис вдається з повтором, а не циклом перезавантажень.
- **`onStaleClient(object)`** — колбек host-а (П4-D): пропонує
  перезавантаження; автоматично не перезавантажує (незбережені форми інших
  об'єктів не губляться). Форма застарілого об'єкта показує стан «потрібне
  оновлення застосунку» замість кнопки запису (`isStale`, §6.4).
- **Перевірка версії** — запит `version` на кожному `SUBSCRIBED`, на
  поверненні вкладки, при зміні `serverHash` у відповіді, після
  `stale-client` і розбіжності схеми PostgREST (§5.3) і не частіше разу на
  хвилину при навігації (§7 платформної).
- **Адаптер PostgREST** сумісності не звіряє: розбіжність схеми в його
  відповіді веде до запиту `version` (§5.3); запис іде лише через `run`.
- **Версія кешу в контракті сесії** (§9 платформної: «версія кешу» команди) —
  `kernelHash` об'єктів запиту і `subject` рантайму: обидва конверт несе й
  сервер звіряє. Кеш прав клієнта (`projectionVersion`) до контракту сесії не
  входить: права команди вирішує база, і команда через застарілий кеш прав
  не відмовляє; `projectionVersion` — лише ключ кешу клієнта (§9.3).
- **Перемикання збірки після розширення.** Після DDL розширення PostgREST
  оновлює кеш схеми асинхронно, і перші звернення нової збірки до нової
  колонки дають `PGRST204` (спайк (г), п. 3–4). Тому нову збірку клієнта
  вмикають лише після кроку застосування «кеш PostgREST бачить нові
  колонки» (підтверджений `reload schema`). Механізм кроку — П3-4; П4-B від
  нього лише залежить.
- **Межа:** мінімальна підтримувана версія, публікація її сервером і
  автоматичне звуження — П3-4 разом із першою зміною наявної колонки (§7,
  §12 платформної); рядок §13 платформної лишається відкритим до П3-4.
  Промоція прийнятої таблиці робить старі вкладки несумісними (§4.0).

## 11. Інваріанти П4-B

Кожен тримає тест (§12):

1. T4 імпортує лише дозволене блоком чистоти (§3) у кожній своїй теці;
   публічні типи `simetra/data` не посилаються на `@tanstack/*`; поза модулем
   фасаду немає `write*`, `refetch`, `createTransaction`,
   `createOptimisticAction`, створення `QueryClient` і імпорту
   `@tanstack/query-db-collection` чи `@tanstack/query-core`; T5 не імпортує
   `simetra/data/supabase`.
2. Запит читання й операція у формі передачі доходять до SQL лише з іменами
   каталогу сервера й зв'язаними параметрами; несумісний запит —
   `command.stale-client`, невалідний — `command.invalid`, обидва до бази.
3. Обидва адаптери для того самого запиту й claims дають ту саму множину
   рядків і той самий декодований рядок, зокрема для типів із тихою втратою
   (`BigInt` понад 2^53, `Numeric` з масштабом).
4. Обробник мутації завершується лише після запису підтверджених рядків або
   відхиленням; після завершення транзакції в колекції немає
   непідтвердженого рядка й неповного рядка результату; дві мутації одного
   ключа не конфліктують одна з одною.
5. Одна транзакція фасаду — один виклик `run` — одна транзакція бази.
6. Сигнал змін шле лише ядро сигнального об'єкта (і, в блоці, що його
   додасть, тригер прийнятої таблиці) у транзакції запису; сигнал прав —
   `rights_bump` і тригери членства й призначень; відкат і невдала спроба
   повтору сигналу не дають. Сигнал змін — рівно `object`, `op`, `keys`
   (лише UUID) і `row_ver`; сигнал прав — рівно `op` і `row_ver`; прийняте
   повідомлення додає лише `id`; значень полів немає.
7. Підписник отримує сигнал каналу Simetra лише приватним приєднанням і лише
   тоді, коли `signal_topic_allowed` для нього істинна, і жодна інша політика
   `realtime.messages` цього не обходить; ні ролі запиту, ні публічна
   відправка в канали Simetra не доходять до підписника; лише контейнерне
   право каналу змін не відкриває; команда кожної форми ядра й кожен сигнал
   прав доходять до авторизованого підписника (гейт проти мовчазної
   втрати).
8. Сигнал змін, крім `delete`, з версією, не більшою за версію в колекції,
   не дає запиту; `delete` прибирає рядок лише тоді, коли перечитування за
   ключем його не повернуло.
9. Рядок, який перечитування за ключем не повернуло, прибирається з
   колекції разом із рядками його ТЧ; рядки без власника звіряються на
   кожному `SUBSCRIBED`; рядки втраченого скоупу прибираються з усіх
   колекцій.
10. Обчислювач прав на фікстурах відповідає однозначно (`true`/`false`) для
    обсягів `own`, виміру з оголошеним зв'язком і контейнера і збігається з
    перевіркою права ядра; `unknown` — лише у випадках §9.2; предикат
    підписки над знімком збігається з `signal_topic_allowed`.
11. Несумісна операція чи запит не доходять до бази; перейменування,
    сумісне розширення шапки чи ТЧ, видалення іншого реквізиту, зміна іншого
    об'єкта чи подання запису не блокують; позначка «застарілий» ставиться
    лише за `kernelHash` чи невідомим об'єктом і знімається, коли хеш збігся.
12. Колекції, `QueryClient`, підписки й кеш прав однієї сесії не переживають
    `dispose()`; рантайм другого користувача не бачить рядків першого;
    відповідь для іншого `subject` у рантайм не пишеться.
