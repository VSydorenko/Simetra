## 1. Мета й межі

П4-B дає клієнтському коду застосунку дані бази без ручного коду доступу:
згенерований хост (П4-D) читає списки й картки, пише командами й бачить чужі
зміни без перезавантаження, а інтерфейс знає, які дії користувачу доступні.
Безпека даних лишається в базі: RLS для читання, ядро команд і RLS для
запису. Усе, що П4-B додає в клієнт, — зручність і швидкість, а не межа.

**Критерії успіху:**

1. Список і картка довідника читаються й пишуться через фасад T4 однаково в
   обох джерелах (PostgREST і Server Function); код хоста джерела не знає.
2. Оптимістична зміна або підтверджується рядком бази, або відкочується; у
   колекції не лишається рядка, якого база не підтвердила.
3. Зміна, зроблена в іншій вкладці чи іншим користувачем, доходить до
   колекції через сигнал і перечитування під RLS; сигнал не несе даних.
4. Підписник не отримує сигналу каналу, читати об'єкт у скоупі якого він не
   має права.
5. Інтерфейс питає «чи можу я дію над цим рядком» в обчислювача T4, який
   побудовано з контракту прав і який збігається з перевіркою права ядра на
   тестових фікстурах.
6. Перейменування й сумісне розширення схеми (новий необов'язковий реквізит)
   не ламають відкритих вкладок ні на читанні, ні на записі; запит від
   збірки з несумісним контрактом об'єкта відхиляється до бази з окремим
   кодом.

**Входить:**

- запит читання T0 другої форми, ТЧ як ціль списочного читання, лінивий
  атрибут, форма передачі й серверне читання T3 (§4);
- кодек значень і декодер рядка (§4.4);
- конверт запиту даних і серверний обробник, який host прив'язує до своєї
  Server Function (§4.5);
- межі запиту й команди: пакет, рядки ТЧ, розмір атрибута й тіла конверта,
  тайм-аути транзакції команди (§4.5, §7.1);
- адаптери джерела: Server Function і PostgREST (§5);
- колекції за фасадом: стратегії списку `full` і `window`, картка за
  ключем, сторінки вікна, власність рядків, монотонність версії, публічний
  API читання (§6);
- фасад запису: пакет фаз, write-back з рядків результату, конфлікт версії,
  мапінг помилок (§7);
- сигнал реального часу: функція сигналу в ядрі, сигнал інвалідації й
  злиття сигналів, канали, авторизація каналу, транспорт профілю `supabase`,
  порт транспорту (§8);
- кеш прав клієнта й обчислювач (§9);
- звірка сумісності контракту об'єкта й контракт сесії (§10);
- окремий e2e-стек для наскрізних тестів PostgREST і Realtime (§12).

## 2. Рішення

| № | Рішення | Чому | Вплив на спеку |
| --- | --- | --- | --- |
| Рд1 | **Читає П4-B лише об'єкти каталогу рантайму** (зараз — довідники з ядром команд). `operations` у записі каталогу необов'язкові: об'єкт без них лише читається. Інші види додаються записами каталогу; форму ключа, версії й типів (`PgEnum`, складений ключ, таблиця без версії) вид, якому вона потрібна, вводить разом із собою (Р-1, рішення архітекторки 2026-11-05) | каталог уже несе фізичні й логічні імена, типи, пари й перерахування — усе, що треба мапінгу й декодуванню; друге джерело мапінгу розійшлося б із першим | спека П4 §6.3 (Додаток А) |
| Рд2 | **Запит читання T0 другої форми замінює форму П4-A** (§4.1): фільтр-дерево, сортування за збереженими реквізитами, ключ як останній ключ сортування, `limit` до 200, `offset`, `include` посилань, ТЧ картки, ТЧ як ціль списку (Рд27), лічильник. Форму П4-A не зберігають поруч (принцип 5 `AGENTS.md`) | один будівник для серверного читання, `ctx.read` хуків, MCP і обох адаптерів; фільтр-дерево виражає й keyset-курсор, тож окремого поняття курсора немає | спека П4 §6.4, §6.11 (Додаток А) |
| Рд3 | **Один декодер на клієнті й загальний адаптер.** Обидва джерела віддають сирі рядки у фізичних іменах; T4 декодує їх одним декодером за своїм каталогом (§4.4). Адаптер PostgREST будує запит у рантаймі з каталогу й запиту; залежність T4 — лише HTTP (`fetch`), без виведення типів postgrest-js; типи рядків для застосунку — з кодогену (`entities.d.ts`) на межі фасаду (Р-6, рішення архітекторки 2026-11-05) | фільтр фасаду — дані рантайму, тож типізація всередині адаптера нічого не захищає; однакові значення незалежно від джерела; спайк (г) п. 1 довів, що згенерований літерал `select` типізується supabase-js, — двері для згенерованого коду на об'єкт лишаються відкритими (§5.3) | платформна спека §7 п. 1, §8.2 — мапінг імен робить T4, а не аліаси PostgREST (Додаток А) |
| Рд4 | **Конверт запиту даних і серверний обробник T3.** Host прив'язує одну Server Function до `createDataHandler(runtime)`; запит і відповідь — у формі передачі (Рд17); відповідь — значення `{ ok, value } \| { ok: false, error }`, а не виняток (§4.5). T4 бачить лише тип транспорту з T0 | Рт15: T4 не імпортує `simetra/server`; помилка як значення переживає серіалізацію Server Function без втрати полів | немає (реалізує Рт15) |
| Рд5 | **Рушій колекцій прихований за фасадом T4.** Публічний API T4 не має типів TanStack DB; лише модуль фасаду викликає `write*`, `refetch`, `createTransaction`, `createOptimisticAction`, створює `QueryClient` і імпортує `@tanstack/query-db-collection` і `@tanstack/query-core`. Межу тримають лінт-зона T4, AST-гард і перевірка `.d.ts`, а не домовленість | Р16, Р19: заміна чи оновлення бібліотеки — зміна модуля фасаду; урок першого споживача — лінт ловить не всі обходи (деструктуризація `utils`, доступ за рядком); транзакція поза фасадом оминула б один `run` на транзакцію | немає |
| Рд6 | **Write-back — з рядків результату команди.** Результат T3 уже несе рядки після запису (§6.4 П4); обробник фасаду пише їх `writeUpsert` у колекції їхніх об'єктів — лише для присутніх ключів і власних створень (Рд22) і без зменшення версії (Рд24), — а `delete` — `writeDelete`, і лише потім завершується (`Promise<void>`). Рядки ТЧ обробник не пише: він перезапитує підмножину ТЧ власника (Рд27). Неповний рядок результату (лише `{ id, version }`, §6.13 П4) не пишеться — його заступає перечитування за ключем | закриває відкрите питання П4 §9 і платформної §13: підтверджений рядок уже є; обробник не залежить від автоматичного рефетчу, якого в RC немає | платформна спека §8.1, §13; спека П4 §9 (Додаток А) |
| Рд7 | **Власне створення без власника-підмножини звіряє перечитування за ключем, а не повний рефетч.** Рядок без власника буває лише один: рядок власного `create` рантайму до першого запиту, що його поверне (Рд22). Його оновлює чи прибирає перечитування за ключем (сигнал, конфлікт, відмова, перепідписка) — невидимий під RLS рядок прибирається | повний необмежений результат того самого скоупу на великому довіднику не настає ніколи; перечитування за ключем — дешеве й під RLS | платформна спека §8.1 (Додаток А) |
| Рд8 | **Сигнал — на фазу, з ядра, без даних** (§8): згенероване ядро після DML кличе `simetra.signal(...)`; сигнал несе UUID об'єкта, операцію, ключ вкладеним об'єктом і версію рядка. Проведення документа — одна фаза, тож один сигнал на документ (рядки ТЧ і рухи сигналів не дають). Понад поріг сигнальних фаз транзакції сигнали зливаються в `invalidate` (Рд28). Сигнал шле лише сигнальний об'єкт — сурогатний ключ UUID і межа читання, виражена без рядка (§8.3); тригер прийнятої таблиці шле той самий формат через `realtime.send`, а не `broadcast_changes` (Р-4, рішення архітекторки; знахідка В спайку (г)) | так сигнал бачить кожен запис командою, зокрема фази хуків (`ctx.run`) і створення тенанта; UUID об'єкта не змінюється при перейменуванні (Р4, Р5); версія відсіює власне відлуння; складений чи природний ключ — уже значення полів | платформна спека §8.2, Р31 (Додаток А) |
| Рд9 | **Канал — пара (скоуп, UUID об'єкта); авторизує одна SQL-функція** `simetra.signal_topic_allowed(topic)`: її кличуть політика `SELECT` на `realtime.messages` для ролі запиту користувача, політика `INSERT` для `simetra_command` у `supabase` і видача токена каналу в `postgres`. Увесь простір каналів `simetra*` зарезервовано `RESTRICTIVE`-політиками (Рд28); ролі запиту (`authenticated`, `anon`) у канали Simetra не шлють; сервісна роль — довірена й поза гарантією (Р-4, рішення архітекторки) | канал на весь скоуп показав би учаснику id і версії рядків об'єктів, яких він не читає; одна функція — одне правило для обох транспортів; `PERMISSIVE`-політики об'єднуються через OR, тож без резерву широка політика застосунку відкрила б канали Simetra | платформна спека §8.2 (Додаток А) |
| Рд10 | **Транспорт сигналу — порт T0 і тіло функції сигналу за профілем.** Реалізація `supabase` (`realtime.send`, приватний канал) — у П4-B; реалізація `postgres` (outbox у форматі вбудованого споживача сервера сигналів, токен каналу) — блок B8 після детальної спеки профілю (Р-3, рішення архітекторки 2026-11-05) | профілю `postgres` у коді ще немає (`DATABASE_PROVIDERS` має лише `supabase`); формат outbox і логін споживача — відкриті питання спеки профілів §5 | спека профілів §4 (Додаток А) |
| Рд11 | **Кеш прав клієнта — знімок власних фактів і обчислювач за контрактом** (§9). Знімок дає `simetra.rights_client_snapshot()` («що можу я», лише про себе; `SECURITY INVOKER` над наявними публічними функціями фактів) і лише через `DataTransport` `rights` — і в профілі `supabase`, бо схема `simetra` поза PostgREST. Компілятор кладе контракт прав у клієнтський каталог, T4 обчислює за ним `true`, `false` чи `unknown`; ключ кешу — версія проєкції й версії прав скоупів, свіжість — сигнали прав скоупу й користувача | спека прав §6.3, Рх15, Рх17, спека системної схеми С1; `unknown` для обсягів без гарантованої свіжості, щоб інтерфейс не ховав дію, яку база дозволить; відкрити `simetra` в PostgREST означало б зробити HTTP-ендпоінтом кожну функцію з `EXECUTE` для `authenticated` | спека прав §6.3 (Додаток А) |

| Рд28 | **Сигнал інвалідації й злиття сигналів** (§8.1, §8.2, §8.4). Схема відправки має третій вид `invalidate`: «об'єкт у скоупі змінився», без ключів; канал і авторизація ті самі. T3 рахує сигнальні фази транзакції, зокрема фази `ctx.run`. Коли лік досягає порогу (типово ~50), T3 вмикає режим злиття для решти фаз (лише в один бік: вимкнено → увімкнено); після цього ядро не шле сигналу на фазу. У режимі злиття T3 кличе `simetra.signal_invalidate` для пари (скоуп, сигнальний об'єкт) на першій фазі, що зачіпає цю пару після вмикання режиму, — одна відправка на пару; доставка — після `COMMIT`. Без режиму злиття `invalidate` не шлеться. Сигнали, надіслані на фазу до вмикання, лишаються: дубль нешкідливий. Повідомлення каналу змін, яке не проходить суворої схеми, приймач обробляє як `invalidate` для (скоуп, об'єкт) з топіка; таке повідомлення каналу прав — як сигнал прав; невідомий канал ігнорує. Резерв префіксів — увесь простір `simetra*` | ліміти хостингу Supabase: Pro — 500 повідомлень/с, і розсилка рахується на підписника. | Рд29 | **Порядок рядків задає база; клієнт вікно не сортує** (§4.2, §6.1). Будівник не ставить явного `COLLATE`: порядок — колляція колонки чи бази. | Рд30 | **Запит читання розширюється новими вузлами `where` без зламу** (§4.1). Фільтр `eq` чи `in` за колонкою `Ref` (чи парою `{ type, id }`) — звичайний вузол уже зараз. | Рд31 | **Кеш і функціональні опції** (§4.5, §9, §10). Дані користувача на сервері між запитами не кешуються; Redis не стоїть на шляху даних.   `src/data/**` вмикає `parserOptions.projectService` з
  `allowDefaultProject` для шляхів віртуальних фікстур
  `packages/simetra/test/tier-boundary.test.ts`: без нього фікстура дає
  `Parsing error`, і негативні тести ярусів мовчки зеленіють.
- **Клієнтський каталог** = проєкція каталогу рантайму + контракт прав
  об'єкта + ознака `signal` (`client-catalog.json`, будує T1, пише
  `compileArtifacts` designer, `packages/designer/src/tools/artifacts.ts`,
  поряд із `runtime-catalog.json`). Обидва каталоги мають спільну
  структурну частину запису об'єкта (UUID, `kindLabel`, імена й колонки,
  типи, переліки, ТЧ з id кожної ТЧ — UUID, у стандартної ТЧ синтетичний id елемента
  `<UUID об'єкта>#<ім'я>`, — ознака `signal`), оголошену в T0:
  id ТЧ потрібен формі передачі, а `signal` — T3 для
  `signal_invalidate` (§8.2); функції мапінгу T0 типізовано над
  нею, тож сервер мапить каталогом рантайму, а T4 — клієнтським, тим самим
  кодом. Вміст: об'єкти з UUID і `kindLabel` (мітка виду — ідентичність
  об'єкта в знімку прав), реквізити з логічними й фізичними іменами, типи, перерахування, пари, ціль
  одноцільового `Ref` (`ref`), ознака лінивого атрибута (`load`, Рд25),
  ТЧ з іменем FK власника (`parentConstraint`), UUID довідника членства
  кореня з творцем (`creatorMembership`: ним мапиться `creatorMember`),
  `kernelHash`, ознака
  сигнального об'єкта `signal` (§8.3), контракт прав для обчислювача (§9.2)
  і `snapshotHash`. Переліки колонок вставки, зміни й читання шапки й
  кожної ТЧ (читання — звичайні й ліниві, §10) запис не зберігає: їх
  виводить функція T0 `objectColumns(entry)` зі спільної частини запису, і
  кожна сторона рахує їх зі свого каталогу. Без функцій ядра, контекстів дій, інших обмежень і
  `pgType`. Фізичні імена в браузері вже є в запитах PostgREST, тож проєкція
  їх не ховає; серверних секретів у ній немає (§3.3 платформної).
- **Запис лише для читання** (Рд1). `runtimeObjectSchema` приймає об'єкт без
  `operations`; команда над ним — `command.invalid` до бази.
- **Ціль `Ref` і FK власника ТЧ у каталозі.** Запис реквізиту одноцільового
  `Ref` отримує `ref: { object: <UUID цілі>, constraint: <ім'я FK> }`, запис
  ТЧ — `parentConstraint`: з них будують `include` і ТЧ картки будівник T3 і
  адаптер PostgREST.
- **Публікація й залежності.** `publishConfig.exports` і dev-`exports`
  отримують `./data` і `./data/supabase`; tsdown — входи `data/index` і
  `data/supabase/index` у наявній конфігурації (`platform: "node"`; T4
  імпортується і в SSR). `react`, `@tanstack/db`, `@tanstack/react-db`,
  `@tanstack/query-db-collection`, `@tanstack/query-core` — `peerDependencies`
  з `peerDependenciesMeta.optional` (серверний споживач їх не ставить):
  точний pin лише для RC-пакетів (`db`, `react-db`, `query-db-collection`),
  `react` — діапазон мажора, `query-core` — діапазон peer-а
  `query-db-collection`, щоб host зі своїм `@tanstack/react-query` мав одну
  копію. Точні версії для розробки — у `devDependencies` пакета;

- **Гейт `pnpm deps:check`** (`syncpack lint` у CI) за замовчуванням вимагає

- **Гейт єдиності** — перенесений із П0 (а) у `test:packaging` (план B3):

## 4. Читання

### 4.0 Дві форми: логічна й передачі

Одне місце, де описано межу (Рд17):

| | Логічна форма | Форма передачі |
| --- | --- | --- |
| Хто | API в процесі: `runtime.run`, `runtime.read`, `ctx.read` і `ctx.run` хуків, MCP, серверний код host-а | лише між T4 і `createDataHandler` (Server Function) і між адаптером PostgREST і PostgREST |
| Об'єкт | `MetadataRef { kind, name }` (§6.4 П4) | UUID об'єкта каталогу |
| Реквізит, ключ, версія, скоуп | логічне ім'я | фізична колонка |
| ТЧ | логічне ім'я ТЧ | id ТЧ (UUID; у стандартної ТЧ — синтетичний id елемента `<UUID об'єкта>#<ім'я>`); фізична таблиця ТЧ — лише в SQL і між адаптером PostgREST і PostgREST |
| Значення | типи рантайму (`bigint`, рядок `Numeric`) | JSON; типи, які T4 тримає рядком чи `bigint`, — текстом (§4.4) |
| Поля помилки (`path`, `object`, `attributes`) | логічні; кожна помилка з `path` чи `attributes` несе `object` (у пакеті — об'єкт операції, що відмовила), бо шлях мапиться записом об'єкта | фізичний шлях (перший сегмент шляху ТЧ — id ТЧ), UUID об'єкта, фізичні колонки; T4 мапить їх своїм каталогом |
| Набір змін (`changes[].object`) | `MetadataRef` | UUID об'єкта |
| `creatorMember` створення кореня (§6.13 П4) | логічні реквізити довідника членства | фізичні колонки (звіряються, як колонки операції) |
| Рядок результату | декодований, логічні імена | сирий, фізичні ключі |

- **Сервер** (`createDataHandler`) спершу звіряє сумісність запиту зі своїм
  каталогом (§4.5, §10), потім переводить форму передачі в логічну своїм
  каталогом і кличе ті самі `runtime.read` і `runtime.run`; рядки результату
  кодує назад у фізичну форму. Імена до SQL доходять лише з каталогу
  сервера, ніколи з запиту.
- **T4** переводить логічні імена фасаду у фізичні своїм каталогом і декодує
  відповідь одним декодером (§4.4) — тим самим, що й рядки PostgREST.
- **Межа гарантії.** Перейменування без DDL (Р5) не змінює фізичної форми, а
  сумісне розширення лише додає колонки, тож стара вкладка читає й пише
  далі. Промоція прийнятої таблиці перепризначає фізичні імена (Р5,
  виняток) — після неї старі вкладки несумісні (§10); гарантія старим
  клієнтам на промоцію й так не поширюється (§7 платформної).

### 4.1 Запит читання T0

`readQuerySchema` (`packages/simetra/src/model/runtime/read.ts`) отримує
форму (адресація полів — за формою з §4.0):

```text
{ object, id, tabularSections?: true | [<ТЧ>], include?: [<реквізит Ref>] }
{ object, where?: Filter, orderBy?: [{ attribute, direction, nulls? }],
  offset?, limit, include?: [<реквізит Ref>] }
{ object, where?: Filter, count: true }
{ object, tabularSection, owner: <id власника> }
{ object, tabularSection, where?: Filter, orderBy?, offset?, limit }
{ object, tabularSection, where?: Filter, count: true }
```

Перша форма — **форма картки**: шапка за ключем з лінивими колонками
(Рд25). Нею фасад читає підмножину картки `eq(<ключ>)` (§6.1). Четверта
форма — **«ТЧ власника»** (Рд27): нею фасад читає підмножину ТЧ картки.

- **`Filter`** — дерево: `{ and: Filter[] }`, `{ or: Filter[] }`,
  `{ not: Filter }`, `{ attribute, op, value? }`. Оператори: `eq`, `ne`, `lt`,
  `lte`, `gt`, `gte`, `in`, `isNull`, `contains`, `startsWith`. `contains` і
  `startsWith` — лише для рядкових типів, без урахування регістру (`ILIKE`);
  символи шаблону у значенні екрануються. `in` — до 200 значень. Глибина
  дерева й кількість вузлів обмежені (типово 8 і 64): запит лишається
  дешевим для перевірки до бази.
- **Розширення** (Рд30) — лише новими вузлами `where` без зламу: пошук,
  фільтр за реквізитом цілі посилання (шлях) і напівз'єднання додаються
  пізніше. Невідомий вузол — `command.invalid`; новий оператор
  розкочується спершу на сервер. Фільтр за шляхом посилання — лише через
  Server Function (`EXISTS` під RLS цілі).
- **`attribute`** — реквізит об'єкта, ключ, версія чи скоуп; для пари
  поліморфного `Ref` — значення `{ type, id }`. `eq` чи `in` за колонкою
  `Ref` чи за парою — звичайний вузол.
- **`orderBy`** — лише збережені реквізити об'єкта (§8.1 платформної);
  ключ — лише останнім, а без нього будівник додає ключ останнім, тож
  порядок сталий. Keyset-курсор
  виражає сам фільтр (умова «після рядка» над ключами сортування), окремого
  курсора немає.
- **`limit`** — 1…200 (`READ_LIMIT_MAX`); **`offset`** — до 10 000: далі
  лише keyset.
- **`count`** — кількість рядків під RLS, обмежена 10 000: більше — відповідь
  `{ count: 10000, capped: true }`. Лічильник іде лише через Server Function
  (§5.3).
- **`include`** — реквізити одноцільового `Ref`, чия ціль є в каталозі
  (`ref` запису реквізиту, §3): у відповідь додаються рядки цілей, видимі
  читачеві (§4.2). Один запит — до 16 реквізитів (`INCLUDE_MAX`): кожна ціль
  — окремий оператор. `include` за лінивим `Ref` у списочній формі —
  `command.invalid` з `reason: "lazy"`, як фільтр і сортування за лінивою
  колонкою.
- **`tabularSections`** — лише у формі картки: ТЧ разом із рядком шапки,
  впорядковані за номером рядка. Кожна ТЧ читається з межею
  `TABULAR_LINES_MAX + 1` рядків; понад `TABULAR_LINES_MAX` — `command.invalid`
  з `reason: "tabular-too-large"` і `path` ТЧ, без обрізання (Рд27). Те саме
  правило діє для `ctx.read` і MCP `data-read`. Межа читання — стала
  платформи `TABULAR_LINES_MAX`; налаштування рантайму її не змінює (§7.1).
  Шапку й ТЧ дає один оператор (§4.2).
- **«ТЧ власника»** (`owner`) — усі рядки ТЧ одного власника, впорядковані
  за номером рядка, з межею `TABULAR_LINES_MAX + 1`, і `ownerVersion` —
  версія рядка власника, прочитана тим самим оператором (§4.2). Відповідь —
  `{ rows, ownerVersion }`. Понад межу — `command.invalid`
  `tabular-too-large`, без обрізання й без переходу на вікно. Реквізити ТЧ
  лінивими не бувають (Рд25).
- **`tabularSection` зі сторінкою** — ТЧ як ціль списочного читання (Рд27)
  для `ctx.read`, MCP і пізнішого перегляду великої ТЧ; колекцій фасаду
  ця форма не наповнює (§6.1). З кон'юнктом верхнього рівня `parent eq
  <один id>` відповідь несе й `ownerVersion`, прочитану тим самим
  оператором. У `where` — власник
  (`parent`), номер рядка й реквізити ТЧ; типовий порядок — номер рядка,
  ключ останнім. `count` без межі 10 000 — лише тоді, коли кон'юнкт
  верхнього рівня — `parent eq <один id>`; будь-який інший `count` ТЧ
  (зокрема з `or`, `in` чи `not` над власником) має межу 10 000.
- **Лінивий атрибут** (`load: "lazy"`, Рд25) — списочна форма його не
  віддає, форма картки віддає. Довільна проєкція колонок — пізніше
  необов'язковим полем запиту без зламу.
- **Бюджет відповіді** (Рд26, §4.5). `more: true` буває лише в
  упорядкованому читанні сторінки (списочна форма з `orderBy`, без фільтра
  за ключем): понад бюджет вона приходить найдовшим непорожнім префіксом,
  що вміщується. Перший рядок понад бюджет — `command.invalid` з `reason:
  "response-too-large"`. Читання за ключами (`eq` чи `in` за ключем:
  картка, перечитування, перечитування сторінки, звірка реєстру,
  перечитування після запису), форма картки й «ТЧ власника» не обрізаються:
  понад бюджет — `response-too-large`.

Перевірка до бази: невідомий реквізит, оператор не для типу, значення, що не
проходить Zod типу каталогу, сортування за не збереженим реквізитом, фільтр
чи сортування за лінивим атрибутом, невідомий вузол фільтра, перевищення
меж — `command.invalid` з `path`. Фільтр чи сортування за лінивим атрибутом
— завжди `command.invalid`, а не `command.stale-client`: колонка є в
каталозі (§10). Рядок із `\u0000` чи непарним
сурогатом — та сама відмова, як у команді (§6.5 П4). У формі передачі
невідомий об'єкт чи колонка — несумісність (`command.stale-client`, §4.5),
бо T4 будує запит лише зі свого каталогу.

### 4.2 Будівник T3

`buildReadStatement` (`packages/simetra/src/server/read.ts`) рендерить запит
лише з каталогу й зв'язаних параметрів (Рт13): ідентифікатори — з каталогу,
значення — `$n` з приведенням `castType`, `contains` — `ILIKE $n` з
екранованим значенням. `in` — `= ANY(ARRAY[$1::<cast>, …])`, параметр на
значення: літерал масиву Postgres зламав би значення з `"`, `\` чи `NULL`.
Тексту SQL ззовні немає.

- **Транзакція** — та сама, що в §6.11 П4: `READ COMMITTED READ ONLY`,
  claims, роль запиту профілю або запасний шлях, `COMMIT`. Нове:
  `SET LOCAL statement_timeout` з опції рантайму (типово 15 с): серверне
  читання доступне з браузера, тож довгий запит не тримає з'єднання пулу.
  `57014` читання стає `command.timeout` (B1a).
- **`include`** — другий оператор у тій самій транзакції:
  `SELECT … FROM <ціль> WHERE <ключ> = ANY(ARRAY[$1::uuid, …])` за id з
  рядків першого, параметр на id — з тієї самої причини, що й в `in`. RLS
  цілі застосовується так само; невидима ціль просто відсутня, а рядок
  першого оператора лишається. Окремий оператор замість `JOIN`: рядок
  цілі має ту саму форму, що й власне читання цілі. Серверний `include`
  служить логічній формі в процесі (хуки, MCP, серверний код host-а); фасад
  через нього в колекції не пише (Рд22).
- **Один оператор для власника й ТЧ.** Форма картки з `tabularSections` і
  форма «ТЧ власника» читають рядок власника й рядки ТЧ **одним
  оператором**: рядок власника з корельованим підзапитом на кожну ТЧ, що
  агрегує її рядки (порядок — номер рядка, `LIMIT TABULAR_LINES_MAX + 1`
  усередині підзапиту). Однієї транзакції замало: у `READ COMMITTED` кожен
  оператор бере свій знімок, і коміт між двома операторами дав би старі
  рядки ТЧ з новою версією власника. Понад межу — `tabular-too-large`
  (§4.1). Те саме правило діє для `ctx.read` і MCP `data-read`, а також
  для `ownerVersion` сторінкової форми ТЧ одного власника. Невидимий
  власник — порожній результат без `ownerVersion`.
- **ТЧ як ціль списку** — оператор над таблицею ТЧ тими самими правилами
  фільтра, сортування й меж, що й список об'єкта.
- **Лінивий атрибут** — списочна форма будує рядок явним переліком
  звичайних колонок (`jsonb_build_object` названих колонок), а не з
  `to_jsonb(t)`: увесь рядок розпакував би з TOAST ліниві тіла, а колонки
  з приведенням до тексту, додані після, повернули б ліниву текстову
  колонку. Форма картки може брати весь рядок.
- **Колляція** (Рд29) — явного `COLLATE` немає: порядок — колляція колонки
  чи бази. Локальний стек: `datlocprovider = i` (ICU), `datlocale = en-US`,
  PostgreSQL 17.11; колляцію
  бази хостованого Supabase порівнює з ним перевірка хостованого Supabase
  мінімальної доставки ([спека П4](2026-10-26-p4-runtime-design.md) §9).
- **Результат** у логічній формі — `{ rows, included?: { "<kind>.<name>":
  rows }, more? }`, `{ rows, ownerVersion }` чи `{ count, capped? }`; у формі
  передачі ключ `included` — UUID об'єкта. Рядок форми картки несе ТЧ у
  полі `tabularSections`: у логічній формі ключ — логічне ім'я ТЧ, у формі
  передачі — id ТЧ. `decodeRow` розбирає обидві частини.
- **Відоме обмеження.** Список «з усіх моїх тенантів» (`scope = ANY(…)`)
  індекс `(scope, key, id)` не обслуговує; такий список — з фільтром скоупу
  чи з межею.
- `ctx.read` хуків бере ту саму логічну форму (§6.9 П4: розширення будівника
  діють і там); `count` у хуку теж дозволено.

### 4.3 Еквівалентність дверей

Інваріант 10 П4 («серверне читання бачить рівно те, що PostgREST з тими
самими claims») поширюється на запит другої форми: той самий запит через
обидва адаптери дає ту саму множину рядків і той самий декодований рядок.
Швидкий доказ — DB-тест із симуляцією claims; наскрізний — через живий
PostgREST на e2e-стеку (§12, Рд18).

### 4.4 Кодек і декодер

T0 дає `wire` (`packages/simetra/src/model/runtime/wire.ts`): `encodeRow`
(сервер: рядок рантайму → фізична форма передачі) і `decodeRow` (клієнт:
сирий рядок будь-якого джерела → рядок колекції за каталогом). `decodeRow`
один: його кличуть і адаптер Server Function, і адаптер PostgREST.

| Логічний тип | У передачі | У колекції |
| --- | --- | --- |
| `BigInt` | рядок цілого | JS `bigint` |
| версія | рядок цілого | `number` (безпечне ціле, §6.4 П4) |
| `Numeric` | рядок десяткового | той самий рядок, як його віддав Postgres: масштаб зберігається (`10.50` лишається `10.50`) |
| `DateTime` | рядок | ISO 8601 UTC фіксованої ширини з мікросекундами: лексикографічний порядок = часовий |
| `Date` | `YYYY-MM-DD` | те саме |
| перерахування | мітка бази | логічне ім'я значення |
| пара `Ref` | дві колонки | `{ type, id }` |
| `Json` | значення JSON | те саме значення |
| `Bytes` | шістнадцятковий текст Postgres (`\x…`) | той самий рядок; перетворення — межа полів T5 |

- **Сумісність із розширенням.** `decodeRow` ігнорує фізичні ключі, яких
  немає в клієнтському каталозі (колонка, додана після збірки), а відсутній
  ключ дає відсутнє поле. Інакше після кожного розширення читання старої
  вкладки ламалося б.
  Так само невідома мітка перерахування чи цілі пари (нове значення на
  сервері) дає відсутнє поле, а не помилку. Чернетка старої вкладки чужого
  значення не стирає, поки поле на дроті відсутнє, а не `null`: ядро лишає
  старе значення для ключа, відсутнього в рядку (`sectionLines`), тож
  ні мапінг, ні фасад відсутнє поле на `null` не перетворюють.
- **Один декодер.** Сервер декодує рядки бази тим самим `decodeRow` T0
  (B1b-2), тож семантика значень (зокрема `DateTime` фіксованої ширини) у
  `runtime.read` і на клієнті одна.
- PostgREST віддає `numeric` без приведення JSON-числом і втрачає масштаб
  (`10.50` → `10.5`), а `bigint` понад 2^53 — точність; `timestamptz` — зі
  змінною дробовою частиною. Тому адаптер приводить у `select` до тексту
  (`::text`) колонки типів, які T4 тримає рядком чи `bigint` (`Numeric`,
  `BigInt`, версія), а решту нормалізує `decodeRow` (спайк (г), Г1).
- **Межа з T5.** У колекції значення — рядки й `bigint`; перетворення в
  decimal.js і Temporal (§8.5 платформної) робить межа полів T5 (П4-D), а не
  T0 чи T4: T0 лишається лише з `zod`.
- Сортування за `Numeric`: рядок десяткового не сортується
  лексикографічно. У `full` локальне сортування `Numeric` бере власний
  компаратор у живому запиті без `limit` (§6.1); у `window` сортує сервер.

### 4.5 Конверт і серверний обробник

T0 (`packages/simetra/src/model/runtime/envelope.ts`):

```text
DataRequest  = { subject: <sub сесії рантайму>, request:
                 { type: "read", query }
               | { type: "run", operation | batch, kernels?: { "<UUID об'єкта>": kernelHash } }
               | { type: "rights" } | { type: "version" } }        — форма передачі (§4.0)
DataResponse = { ok: true, value, serverHash } | { ok: false, error: WireCommandError, serverHash }
DataTransport = (request: DataRequest) => Promise<DataResponse>
```

`WireCommandError` і набір змін у формі передачі — окремі схеми T0 у
`envelope.ts`: `object` — UUID, `path` і `attributes` — фізичні (§4.0);
логічний `CommandError` (`object: MetadataRef`) лишається для API в процесі.

T3 дає `createDataHandler(runtime)` →
`(session: SessionClaims, request: unknown, origin: RequestOrigin) => Promise<DataResponse>`,
де `RequestOrigin` = `{ secFetchSite?, origin?, expectedOrigin }` для
HTTP-виклику або `{ inProcess: true }` для виклику в процесі під час SSR.
Аргумент обов'язковий: обробник сам застосовує правило походження
(внутрішня `checkRequestOrigin`, нижче) першим кроком, тож host, зібраний
вручну, не може його забути; правильність розрізнення RPC-виклику й виклику
в процесі — тест шаблону host (П4-D). Порядок кроків важить:

0. перевіряє походження (`RequestOrigin`); відмова — `command.forbidden` з
   `reason: "origin"` без жодного кроку далі;
1. валідує конверт Zod-схемою T0 (порушення — `command.invalid`), зокрема
   сталі `BATCH_MAX` і `TABULAR_LINES_MAX` (§7.1); межі, зменшені
   налаштуваннями рантайму T3, перевіряє `runtime.run` (§7.1); `kernels`
   у схемі необов'язкові, щоб відсутність ловила звірка, а не Zod;
2. `subject` ≠ `sub` сесії — `command.unauthenticated` з `reason:
   "session-changed"` без звернення до бази: вкладка належить рантайму іншого
   користувача (§6.1). Звірка йде за `sub` (ідентичність провайдера), а не за
   id «Користувачів»: id дає лише база (`current_user_id()`), і поза С8
   спеки системної схеми вони різні;
3. **звірка сумісності** (§10) — до перекладу й до бази: невідомий UUID
   об'єкта; для `run` — відсутній чи інший `kernelHash` об'єкта будь-якої
   операції, колонка операції (шапки, рядків ТЧ, `creatorMember`) поза
   переліком вставки чи зміни каталогу сервера, невідома таблиця ТЧ; для
   `read` — колонка фільтра, сортування, `include` чи ТЧ поза об'єднанням
   звичайного й лінивого переліків читання. Несумісність — `command.stale-client` з `object`; пакет
   із хоч однією несумісною операцією відмовляє цілком;
4. переводить форму передачі в логічну своїм каталогом (§4.0);
5. `read`, `run`, `rights` — `runtime.read`, `runtime.run`,
   `runtime.rightsSnapshot` (§9.1); `version` — `{ snapshotHash, objects: {
   "<UUID>": kernelHash } }` каталогу рантайму;
6. значення кодує `wire` у форму передачі. Рядки результату `run` ідуть без
   лінивих колонок і без рядків ТЧ (Рд26, Рд27). Обробник вимірює кожну
   закодовану відповідь — і читання, і `run` — проти бюджету відповіді
   (орієнтир 4 МБ, нижче межі 4,5 МБ Vercel). Понад бюджет: упорядкована
   сторінка — найдовший непорожній префікс з `more: true`; читання за
   ключами, форма картки й «ТЧ власника», а також перший рядок сторінки
   понад бюджет — `command.invalid` `response-too-large` (§4.1); результат
   `run` — без `rows`, і фасад перечитує за ключем (§7.2).
   `CommandFailure` стає
   `{ ok: false, error }` з фізичним `path`; будь-який інший виняток —
   `command.internal` без тексту й запис у журнал рантайму.

Запит `rights` з'являється в конверті в блоці, що дає `runtime.rightsSnapshot`
(B5), а не раніше: між блоками напівмеханізмів немає.

**Вимоги до host-а** (шаблон і їхні тести — П4-D):

- одна Server Function: перевіряє сесію портом ідентичності (Рт19), без
  сесії відповідає `command.unauthenticated`, кличе обробник;
- **межа тіла запиту** — host відхиляє тіло понад межу тіла конверта
  (орієнтир 4 МБ, нижче межі 4,5 МБ Vercel; Рд26) до розбору JSON і
  відповідає `command.invalid` з `reason: "payload-too-large"`: лише host
  бачить сирий потік, а обробник отримує вже розібраний `request`. Фасад
  T4 перевіряє розмір серіалізованого запиту до надсилання й відмовляє тим
  самим кодом без транспорту, тож межа хоста ловить лише чужого клієнта;
- **захист від підробки запиту** — для HTTP-виклику Server Function
  (RPC-ендпоінта) host передає обробнику факти запиту, і обробник
  відмовляє fail-closed: `Sec-Fetch-Site`
  присутній і ≠ `same-origin` — відмова; інакше `Origin` присутній і ≠
  власному походженню — відмова; обох заголовків немає — відмова. Виклик у
  процесі під час SSR (заголовки — від навігації, `Sec-Fetch-Site: none` чи
  `cross-site` для переходу з закладки чи листа) перевірці не підлягає:
  він не з браузера, і host передає `{ inProcess: true }`. `inProcess`
  допускає лише `read`, `rights` і `version`; `run` вимагає фактів
  HTTP-запиту, тож host, що завжди передає `inProcess`, не відкриває запису
  міжсайтовій навігації з cookie `SameSite=Lax`. Правило —
  внутрішня чиста функція T3 `checkRequestOrigin` з unit-тестом усіх гілок у
  B1b-2; шаблон host (П4-D) лише розрізняє RPC-виклик і виклик у процесі.
  Обробник заголовків і cookies сам не читає: з сесією в cookie
  міжсайтовий запит інакше виконав би `run` від імені жертви;
- рантайм на сервері не тримає даних користувача на рівні модуля: обробник
  безстановий, стан сесії — лише в аргументах. Дані користувача між
  запитами на сервері не кешуються; Redis на шляху даних не стоїть (Рд31).

## 5. Адаптери джерела

### 5.1 Порт адаптера (T0)

```text
SourceAdapter = {
  read(query): Promise<{ rows, included?, more?, ownerVersion? }>,  — запит і рядки у формі передачі
  capabilities: { include: boolean }
}
```

Адаптер повертає **сирі** рядки; декодує T4 (Рд3). Запис через адаптер не
йде ніколи: запис — `DataTransport` `run` (§7); лічильник і знімок прав —
теж `DataTransport` (`read` з `count`, `rights`). Вибір адаптера: типовий
для обох профілів — Server Function; застосунок перевизначає його для
об'єкта в налаштуваннях рантайму даних. Адаптер PostgREST (B4) будується за
потребою: коли перший екран чи споживач покаже потребу в меншій затримці
читання чи розвантаженні сервера (рішення власника 2026-11-06). Тоді блок B4
вирішує й типовий адаптер для `supabase`. Поле метаданих сутності для вибору
адаптера (платформна спека §8.2) додає П4-D разом із декларацією сутності.

Поруч із вибором адаптера стоїть вибір стратегії читання об'єкта (Рд19,
§6.1): метадані (`residency`, типово `window`) її задають, застосунок
перевизначає в налаштуваннях рантайму даних. До П4-D поля метаданих немає,
тож стратегію дають лише налаштування рантайму.

### 5.2 Адаптер Server Function

Тонкий: `read` → `transport({ subject, request: { type: "read", query } })`.
Помилка відповіді стає `CommandFailure` того самого коду. Цей адаптер —
типовий для обох профілів (§5.1).

### 5.3 Адаптер PostgREST

Шле `fetch` до PostgREST провайдера; адресу й заголовки (`apikey`,
`Authorization` з токеном сесії) дає host функцією `headers()`, бо токен
оновлюється. Перед запитом адаптер звіряє `sub` токена із `subject`
рантайму: інший — `command.unauthenticated` `session-changed` без запиту
(§6.1). Запит будується в рантаймі з каталогу (Рд3).

- **`select`** — фізичні колонки з каталогу; колонки типів, які T4 тримає
  рядком чи `bigint` (Рт1), — з приведенням `колонка:колонка::text`; фільтр і
  сортування за тією самою фізичною колонкою з приведенням сумісні (спайк
  (г), Г1). `NULL` лишається `null`. Рядок приходить у фізичних іменах — тій
  самій формі, що й від Server Function, і декодується тим самим `decodeRow`.
  Списочна форма лінивих колонок не просить (Рд25).
- **Схема** — заголовок `Accept-Profile` зі схеми таблиці каталогу; схема
  мусить бути серед відкритих PostgREST (налаштування провайдера, перевіряє
  `doctor` хоста в П4-D). Схема `simetra` відкритою не буває (С1 спеки
  системної схеми).
- **Фільтри** — дерево §4.1 у синтаксис PostgREST над фізичними іменами
  (`and=(…)`, `or=(…)`, `not.`). Побудова в рантаймі — безпекова поверхня:
  імена колонок, таблиць і FK беруться лише з каталогу, ніколи з запиту
  (ім'я поза каталогом — відмова до HTTP); кожне значення фільтра йде в
  синтаксис лише в лапках з екрануванням зарезервованих символів PostgREST
  (`,`, `(`, `)`, `"`, `.`, `:`, `\`, `*` тощо), зокрема всередині `in.(…)`
  і `or=(…)`, а потім кодується як компонент URL. Сирого значення в
  синтаксисі немає. Доказ — окремий unit-набір з ворожими значеннями й
  мутаційна перевірка (§12). Трансляцію предикатів копіюють з
  `@supabase-labs/tanstack-db` з атрибуцією (платформна спека §8.2;
  `CONTRIBUTING.md`).
- **Сортування й межі** — `order=…,<ключ>.asc`, `limit`, `offset`.
- **`include`** — embed цілі **завжди** з підказкою FK `!<ім'я обмеження>` з
  `ref` каталогу: два FK на одну ціль без підказки — помилка PostgREST, а у
  скоупленого об'єкта FK складений (скоуп + id). Ціль, невидима під RLS,
  дає ключ зі значенням `null` — і для `NOT NULL` FK; складений FK робить
  невидимість питанням прав, а не скоупу (спайк (г), п. 1, Г2). `!inner`
  адаптер не ставить: рядок не зникає зі списку через права на пов'язаний
  об'єкт. Вкладені рядки адаптер виносить у `included` тієї самої форми, що
  й Server Function.
- **ТЧ картки** — зворотний embed ТЧ (масив) з підказкою
  `!<parentConstraint>`, `order` за номером рядка й `limit`
  `TABULAR_LINES_MAX + 1` на вкладеному ресурсі: ТЧ з реквізитом `Ref` на
  об'єкт-власника інакше дала б два зв'язки між таблицями. Понад межу
  адаптер відмовляє `tabular-too-large` (§4.1).
- **ТЧ як ціль списку** — запит до таблиці ТЧ тими самими правилами фільтра,
  сортування й меж.
- **«ТЧ власника»** — один запит до таблиці власника за ключем: версія
  власника й зворотний embed ТЧ з межею `TABULAR_LINES_MAX + 1`, тож обидва
  значення дає один оператор.
- **Лічильника немає**: `Prefer: count=exact` рахує всю видиму множину без
  межі на сервері, тож `count` іде через Server Function (§4.1).
- **Помилки** (текст відповіді назовні не йде):

  | Відповідь PostgREST | Код фасаду | Дія |
  | --- | --- | --- |
  | розбіжність схеми: `42703`, `42P01`, `PGRST200`, `PGRST204`, `PGRST205` | `command.unavailable` з `reason: "schema"` | запит `version` і переоцінка позначки (§10) |
  | інший `400` (`PGRST1xx`, `22P02`) | `command.invalid` | лише відхилення |
  | `401` | `command.unauthenticated` | — |
  | решта | `command.unavailable` | — |

**Факти спайку (г), п. 1** (supabase-js 2.119.0, PostgREST v16.5): виведення
supabase-js з **літерала** `select` з аліасами й embed `!<fk>` дає точний тип
рядка з логічними ключами, коли тип `Database` — з typegen чи структурно
рівний кодогену (П0 (в)); рядок, зібраний у рантаймі, виведення не дає;
фільтри типізуються за фізичними іменами. Загальний адаптер (Рд3) цього
виведення не використовує. Якщо згенерований код на об'єкт колись знадобиться
(наприклад, екран поза фасадом), кодоген видає `select` лише літералом
(`as const`), карту «логічне → фізичне» — const-літералом, завжди ставить
`!<fk>` і типізує to-one embed на таблицю з RLS як `… | null` незалежно від
`NOT NULL` FK.

## 6. Колекції за фасадом

### 6.1 Модель

- **Події host-а** — `runtime.resume()` на поверненні вкладки і
  `runtime.navigated()` на навігації; їх кличе host (П4-D), бо T4 не читає
  `document` і роутера (він імпортується й у SSR, Р16).
- **Рантайм даних** — `createDataRuntime({ catalog, transport, sources,
  signals?, residency?, subject, onStaleClient, onSessionChanged })` (форма,
  не остаточний API) на сесію користувача (Рд13). `subject` — `sub` сесії;
  кожен `DataRequest` несе його (§4.5), а адаптер PostgREST звіряє з `sub`
  токена (§5.3). Id користувача («Користувачі») рантайм бере зі знімка прав
  (`userId`, §9.1) — для каналу прав користувача. Відповідь `session-changed` — сесію змінено (зокрема в
  іншій вкладці): рантайм кличе `onSessionChanged` і `dispose()`, і рядки
  нового користувача в кеш попереднього не потрапляють.
- **Ізоляція кешу.** Рантайм створює власний `QueryClient`; `queryKey`
  колекцій містить ключ рантайму — `subject` і випадковий nonce рантайму. `dispose()` знищує колекції, очищує `QueryClient`, знімає
  підписки й кеш прав; host кличе його при виході й зміні користувача. На
  сервері (SSR) рантайм даних на рівні модуля не створюється.
- **Колекція об'єкта** — одна на об'єкт, ключ — id рядка (рядок UUID; ключі
  RC — лише string чи number). Рядок — декодований рядок шапки з версією.
  Будь-який відбір — скоуп, власник, батько, FK, зв'язка — підмножина цієї
  колекції; колекції на зріз немає (Рд21). Рядок у пам'яті один, тож
  оптимістична зміна, write-back і сигнал доходять до всіх списків, де рядок
  видимий.
- **Колекція ТЧ** — одна на табличну частину (Рд14), ключ — id рядка ТЧ,
  підмножина — власник. Фасад наповнює колекцію ТЧ лише результатами форми
  «ТЧ власника» (форма 3 нижче). Сторінкова форма ТЧ (§4.1) служить
  `ctx.read`, MCP і пізнішому перегляду великої ТЧ, а колекцій фасаду не
  наповнює. Кожен рядок ТЧ у колекції несе клієнтське поле `ownerVersion` —
  версію власника, з якою він прийшов (Рд24 порівнює рядки ТЧ за ним).
- **Колекція запитів.** Колекції — колекції запитів TanStack DB
  (`queryCollectionOptions`). Злиття рядків — типовий `rowUpdateMode:
  'partial'` у `SyncConfig` `@tanstack/db`; `query-db-collection` його не
  перевизначає, і контрактний тест тримає це. Власного адаптера
  синхронізації (`begin/write/commit`) фасад не будує. `queryFn`
  **повертає** рядки: результат `queryFn` і дає підмножині власність на
  рядки (§6.2).
- **Режим синхронізації.** Колекція об'єкта — `syncMode: 'on-demand'` для
  `window` чи `syncMode: 'eager'` для `full` (одна колекція на об'єкт,
  Рд13). Колекції ТЧ — `on-demand`.
- **Колекція `on-demand`** (об'єкт `window`, ТЧ). Підмножину
  задає живий запит фасаду (§6.4), а `queryFn` перекладає
  `ctx.meta.loadSubsetOptions` у запит T0 (§4.1). `queryFn` приймає лише
  такі форми підмножин:
  1. **за ключем** — `eq` чи `in` за ключем; `in` ділиться на запити по 200
     ключів. Підмножина картки `eq(<ключ>)` іде формою картки
     `{ object, id }` з лінивими колонками (§4.1). На `response-too-large`
     фасад ділить ключі навпіл аж до одного; один ключ понад бюджет —
     `response-too-large` викликачу;
  2. **сторінка вікна** — `inArray(<ключ>, <ключі сторінки>)`, до 200
     ключів (Рд20);
  3. **ТЧ власника** — форма «ТЧ власника» (§4.1, Рд27).

  Будь-яка інша форма (без `limit`, з `limit` понад 200, з невідомим
  виразом) — помилка розробника `data.unbounded-subset`.
- **Колекція `full`** — `syncMode: 'eager'`. Її `queryFn` — власне
  keyset-читання фасаду (вибірка) сторінками по 200 до межі `full`;
  вибірка зупиняється лише на сторінці без `more` і з меншою за `limit`
  кількістю рядків. Живі запити над нею фільтрують і сортують локально й
  `loadSubset` не кличуть; підмножин on-demand колекція `eager` не має.
  Перечитаний рядок, що підходить множині, фасад вставляє прямо: власник —
  сама колекція, межа — межа `full`; повної вибірки на кожен новий ключ
  немає. Картку об'єкта `full` фасад читає формою картки власним викликом
  транспорту й латає наявний ключ `writeUpdate` за правилом версії (Рд24):
  так приходять і ліниві поля.
- **Стратегії списку** (Рд19). Шлях один для всіх таблиць: `useRows` чи
  `useRow` → фасад → колекція → адаптер → серверне читання під RLS. Дані
  живуть лише в пам'яті вкладки. Стратегію об'єкта обирає §5.1; `residency`
  — `full` чи `window`.
  - `window` (типова) — список будь-якого розміру. Сторінку читає фасад
    (Рд20): запит T0 з `orderBy`, keyset-умовою в `where` (повний кортеж
    сортування плюс ключ) і `limit` ≤ 200 через адаптер. Результат дає
    впорядкований масив ключів сторінки. Сторінку з `more: true` (бюджет
    відповіді, §4.5) фасад вважає коротшою й продовжує keyset-ом від її
    останнього рядка. Keyset-запиту без просування курсора фасад ніколи не
    повторює. У колекції сторінка — підмножина
    форми 2 без `orderBy` і `limit`: її `queryFn` спершу віддає рядки щойно
    прочитаної сторінки (за токеном сторінки), а далі перечитує за ключами.
    Порядок у вікні — серверний масив ключів; значення — рядки колекції за
    ключем. Клієнт рядків вікна не сортує й не порівнює. Фасад тримає
    видимий діапазон плюс запас сторінок і вивантажує далекі сторінки: їхні
    рядки зникають з колекції, якщо їх не тримає інша підмножина. `offset`
    понад 10 000 фасад не вживає. Лічильник — `count` з межею 10 000,
    ліниво;
  - `full` — малий довідник, пікер: уся видима множина в пам'яті.
    Колекція `eager` вибирає її власним keyset-читанням сторінками по 200
    (не `offset`) до межі `full` (типово 5 000 рядків; окреме налаштування
    рантайму даних). Локальні фільтр і сортування робить RC з типовим
    `stringSort: 'locale'` — порядок мови користувача (Рд29). Понад межу
    тихого обрізання немає. Опція рантайму даних `strict` (host ставить її;
    у розробці — `true`) вирішує поведінку: `strict` — помилка
    `DataError` з кодом `data.full-too-large`; без `strict` — рантайм даних
    чекає осідання транзакцій колекції, створює колекцію об'єкта наново
    зі стратегією `window` і переносить у неї реєстр власних створень і
    незавершені write-back; пише запис у журнал і ставить `truncated: true`
    (§6.4). Вибірка володіє рядками;
  - **картка** (`useRow`) — режим хука, а не значення `residency`:
    підмножина шапки `eq(<ключ>)` (форма картки; для об'єкта `full` —
    власний виклик транспорту, вище) і підмножина кожної названої ТЧ
    (форма «ТЧ власника»), паралельно (§6.2, §6.4).
- **Предикати.** Фасад перекладає фільтр T0 у вираз бібліотеки для
  локальних перевірок (`full`, точкове оновлення за сигналом, §8.4) і
  назад; фільтр, якого він не перекладає, — помилка розробника
  `data.unsupported-predicate`, а не завантаження всієї таблиці. Живі
  запити фасаду не мають залишкового `where`, не-`left` join, `fnWhere`,
  `groupBy` і `distinct`: кожен із них змушує RC просити все джерело.
  Власного компаратора рядків немає в живих запитах з `limit`: упорядкований
  завантажувач RC стартує лише з `limit` (`compiler/order-by.ts`).
  Сортування `full` без `limit` може мати власний компаратор (наприклад,
  `Numeric`, §4.4).
- **Помилки розробника** фасаду — клас `DataError` T4 з полем `code`
  (`data.unsupported-predicate`, `data.unbounded-subset`,
  `data.tabular-incomplete`, `data.version-required`,
  `data.full-too-large`). Фасад кидає його
  синхронно з виклику або відхиляє ним проміс мутації чи хука; до
  транспорту такий виклик не доходить.
- **Порядок рядків** (Рд29). У `window` порядок — серверний масив ключів, а
  порядок бази задає колляція колонки чи бази. У `full` порядок дає
  локальне сортування RC (`locale`).

### 6.2 Власність рядків

Рядок, що не належить жодній підмножині, переживає вивантаження підмножини
(§8.1 платформної). Тому кожне читання, що вносить рядки в колекцію, —
підмножина з власником (Рд22):

- **список** — сторінка `window` (форма 2, §6.1) чи вибірка колекції
  `full`;
- **`include`** — лінивий `leftJoin` живого запиту фасаду від сторони з
  фільтром. Лише `left`: для `inner` бібліотека обирає активну сторону за
  поточним розміром колекції, а в on-demand це випадково; `full` join не
  оптимізується. Лінива сторона отримує `loadSubset` з
  `inArray(<поле>, [ключі])` (форма 1); `queryFn` ділить його на запити по
  200 ключів і повертає їх об'єднання. Рядки цілі належать підмножині й
  зникають разом зі списком;
- **картка** (`useRow`) — паралельні підмножини: шапка — форма картки за
  ключем, кожна ТЧ — форма «ТЧ власника». Закриття останньої підмножини ТЧ
  власника прибирає його залишкові рядки ТЧ;
- **прямий запис** (`write*`) лише латає ключі, вже присутні в колекції.
  Нові ключі він пише лише для власних `create` рантайму (§7.2).

Межа пам'яті: колекція тримає лише рядки активних підмножин (сторінки вікон,
вибірки `full`, лінива сторона їхніх `include`, підмножини відкритих
карток) і реєстр власних створень.

**Повна підмножина ТЧ** (Рд27) — підмножина форми «ТЧ власника» цього
власника, яку не скинуто, з `ownerVersion`, рівною синхронізованій версії
рядка шапки. Фасад зберігає `ownerVersion` на кожній підмножині ТЧ і
оновлює її лише після того, як рядки результату застосовано:
`query-db-collection` відкладає застосування результату, поки триває
мутація. Будь-який запис у ключі ТЧ власника, що не прийшов з результату
«ТЧ власника» цього власника (прямий `writeDelete` за втратою скоупу чи
перечитуванням без рядка, будь-який інший запис), скидає повноту
підмножини. Оптимістичний стан дельти рядка (§7.1) повноти не скидає.

**Свіжість ТЧ картки** (Рд27). Коли синхронізована версія шапки власника з
активною підмножиною ТЧ стає більшою за `ownerVersion` підмножини, фасад
перезапитує підмножину (single-flight). Джерело нової версії не важить:
сигнал, власний write-back, сторінка списку, репліка. Видима підмножина з
`needsRefresh` оновлюється одразу, невидима — коли стає видимою.

Правила фасаду:

1. реєстр рядків без власника тримає лише власні створення (Рд7). Перший
   результат запиту, що поверне такий рядок, дає йому власника, і рядок
   виходить з реєстру. Рядок реєстру звіряє перечитування за ключем: сигнал
   (§8.4), конфлікт чи відмова запису (§7.3), а також **кожен `SUBSCRIBED`**,
   `invalidate` його об'єкта і зміна множини моїх скоупів — пакетне
   перечитування за ключами реєстру (`in` до 200 на запит);
2. фасад ніколи не заміняє рядок колекції рядком з меншою версією (Рд24):
   ні на write-back, ні на перечитуванні, ні на сигналі, ні в результаті
   `queryFn`. Якщо колекція має ключ з більшою версією, фасад лишає рядок
   колекції. Рядки ТЧ фасад порівнює за їхнім `ownerVersion`;
3. злиття рядків часткове (типовий `rowUpdateMode: 'partial'`, §6.1, Рд25): рядок без
   лінивої колонки лишає її значення в колекції. Якщо такий рядок має
   більшу версію, а ключ має активну підмножину картки, фасад перезапитує
   цю підмножину (single-flight), і ліниве поле свіжіє;
4. при зміні множини моїх скоупів рядки зі втрачених скоупів (рядок несе
   колонку скоупу) прибираються одразу з **усіх** колекцій — і рядки без
   власника, і рядки активних підмножин; рядки ТЧ — через прибраних
   власників. Підмножини з фільтром цього скоупу отримують `needsRefresh`:
   підписку на канал утраченого скоупу знято, і такі рядки більше не
   свіжіли б;
5. перечитування за ключем, що не повернуло рядка, прибирає його
   `writeDelete` разом із рядками його ТЧ (рядок видалено чи він невидимий
   під RLS);
6. живі запити фасаду завжди фільтрують колекцію своїм предикатом, тож
   зайвий рядок не потрапляє в список, якому не належить;
7. `dispose()` прибирає все.

### 6.3 Життєвий цикл

- `peek` колекції після `cleanup` (сплив `gcTime`) повертає `undefined`;
  write-back у прибрану колекцію не пише (урок першого споживача: інакше —
  `SyncNotInitializedError` після успіху сервера).
- `waitPendingSettled(collection)` — очікування, поки осядуть усі
  незавершені транзакції колекції; ніколи не відхиляється. RC має лише
  `tx.when('settled')` на одну транзакцію, тож фасад рахує транзакції сам.
- Оновлення підмножин — single-flight з одним хвостовим запитом: запити
  оновлення під час активного зливаються в один наступний.
- Збій однієї колекції (`health` RC) не зупиняє інших; фасад віддає стан
  колекції хосту (`status`, `health`) без типів бібліотеки.

### 6.4 Публічний API читання

T5 не імпортує `@tanstack/(react-)?db` (лінт-зона), а публічні типи T4 не
мають типів бібліотеки (Рд5), тож прив'язку живого запиту до React дає T4.
Форма (не остаточні імена):

```text
useRows({ object, where?: Filter, orderBy?, include? })
  → { rows, status, health, strategy, truncated, count?, hasNewRows,
      isStale, setVisibleRange(range), loadBefore(), loadAfter(),
      goTo(value), goToStart(), goToEnd(), showNew() }
useRow({ object, id, tabularSections? })
  → { row, tabularSections, version, editable, status, health, isStale }
useCan(action, object, { scope?, row? }) → true | false | "unknown"
```

- Вхід — логічні імена й фільтр-дерево T0 (§4.1), не вирази бібліотеки;
  результат — декодовані рядки й стани без типів `@tanstack/*`.
- **Вікно `useRows`** (`window`, Рд20). `setVisibleRange` отримує видимий
  діапазон від віртуалізації T5; фасад тримає його плюс запас сторінок і
  вивантажує далекі. `loadBefore()` і `loadAfter()` читають сусідню
  сторінку keyset-умовою від межі наявної сторінки. `goTo(value)` —
  перехід «до значення» (keyset `gte`). `goToStart()` і `goToEnd()` — на
  початок і в кінець; у кінець — зворотне сортування keyset. `offset`
  понад 10 000 не вживається.
- **Позиція в сторінці.** Змінений рядок лишається на своїй позиції в
  сторінці, доки сторінка не оновиться. Власний `create`, що підходить
  предикату списку `window`, фасад показує на початку першої завантаженої
  сторінки цього списку — і оптимістично, і після write-back; там рядок
  лишається до оновлення сторінки. Це лише показ: ключ не входить в
  `inArray` підмножини сторінки (сторінка лишається ≤ 200 ключів), а
  рядком володіє реєстр власних створень.
- **Оновлення сторінки** (single-flight) читає діапазон між межами сусідніх
  сторінок і заміняє масив ключів сторінки. За `more: true` чи зсувом межі
  фасад вставляє проміжну сторінку чи перебудовує ланцюжок сторінок до
  кінця вікна: жоден рядок не випадає між сторінками.
- `hasNewRows` — позначка «є нові записи»: рядок підходить предикату
  списку тепер і не підходив зі старим рядком колекції (чи був відсутній),
  а його позиція невідома (§8.4). `showNew()` скидає
  позначку: фасад оновлює вікно від початку поточного сортування.
- `strategy` — `full` чи `window`; `truncated` — `full` понад межу перейшов
  на `window` (§6.1). Локальні операції над усією множиною (підсумки,
  «виділити все», перевірка наявності в пікері) дозволені лише при
  `strategy = full` без `truncated`.
- `count` — ліниво, з межею 10 000 (`capped` — «10 000+»); свіжіє після
  власного write-back і сигналу об'єкта.
- `include` — реквізити одноцільового `Ref`; рядки цілей вносить лінивий
  `leftJoin` (§6.2). Кожен рядок результату отримує
  `refs: { <реквізит>: <рядок цілі> | null }`.
- **Картка `useRow`** — паралельні підмножини: шапка формою картки з
  лінивими колонками, кожна названа ТЧ — формою «ТЧ власника» (Рд22,
  Рд27). Понад `TABULAR_LINES_MAX` — `tabular-too-large` (§4.1). `version`
  — версія шапки. `editable` — `false`, доки версія шапки відрізняється від
  `ownerVersion` підмножин ТЧ картки чи будь-яка підмножина картки має
  `needsRefresh` (§6.2). Форма (П4-D)
  на початку редагування фіксує чернетку `{ row, tabularSections,
  version }` і шле з неї повні масиви ТЧ з `expectedVersion` = `version`
  чернетки (§7.1).
- `isStale` — об'єкт несумісний зі збіркою (§10); екран показує «потрібне
  оновлення застосунку» замість кнопки запису. Стан підмножини, яку треба
  оновити, — `needsRefresh` (§8.4), а не `isStale`.
- Екранні хуки, стан списку в URL і хости П4-D будуються над цим API.

## 7. Фасад запису

### 7.1 Операції

Фасад дає `create`, `update`, `markDeletion`, `delete` і `batch` над
логічними іменами; на дроті — форма передачі (§4.0). Один виклик — одна
оптимістична транзакція TanStack DB над колекціями об'єктів і їхніх ТЧ і
**один** виклик `DataTransport` `run` з пакетом фаз у порядку мутацій — тож
одна транзакція бази (урок першого споживача «зміна через кілька колекцій»).

- `create` — id дає клієнт (`crypto.randomUUID`, оптимістичний патерн §4
  платформної); у кореня виду скоупу id генерує T3 (§6.13 П4), тож
  оптимістичного рядка такий `create` не має.
- `update` — шле лише змінені атрибути: ядро приймає частковий `p_item`
  (Рд25). `expectedVersion` — версія рядка в синхронізованому стані
  колекції (не оптимістичному) на момент запуску обробника.
- **Зміна ТЧ** — завжди повний масив рядків ТЧ власника (Рд27). Видів
  два:
  1. **Чернетка форми** — `update` з `tabularSections`: повні масиви з
     чернетки форми (§6.4) і явний `expectedVersion` = базова версія
     чернетки. Без нього — помилка розробника `data.version-required`.
     `expectedVersion` чернетки ніколи не змінюється: будь-яка зміна після
     бази дає `command.conflict`, і користувач бачить поточний стан
     (§7.3). Фасад не переносить чернетку на новіший знімок.
  2. **Дельта рядка** — `addLine`, `updateLine` (лише змінені поля одного
     рядка ТЧ), `removeLine` (форма, не остаточні імена). Фасад накладає
     дельту на початку обробника: після осідання попередньої мутації того
     самого ключа й застосування її перезапиту ТЧ; незавершений перезапит
     ТЧ він чекає з межею часу. Дельта лягає на повну підмножину ТЧ (§6.2),
     чия `ownerVersion` дорівнює синхронізованій версії шапки; фасад шле
     повний масив з цією версією як `expectedVersion`. Злиття — за полями:
     паралельна зміна інших рядків чи інших полів зберігається. Рядка-цілі
     немає (його видалили паралельно) — `command.conflict` викликачу, без
     тихого повторного вставлення. Розбіжність, що лишилась після
     перезапиту, — теж `command.conflict`.

  `data.tabular-incomplete` — лише для помилки розробника: явної спроби
  будувати масив з підмножини, про яку відомо, що вона неповна. Неповний
  масив неприпустимий: ядро видаляє рядки, яких немає в масиві, тож він
  тихо видалив би незавантажені рядки.
- **Черговість одного ключа.** Мутації того самого рядка фасад виконує
  послідовно: обробник наступної стартує лише після того, як попередня
  осіла й її результат застосовано (§7.2, крок 6). Операції лише над шапкою
  й дельти рядка беруть версію вже після write-back попередньої. Інакше
  друга з двох швидких правок дістала б `command.conflict` і відкотилась.
  Чернетки це правило не стосується: її `expectedVersion` — базова версія.
- `markDeletion`, `delete` — за id і версією.
- `batch` — завжди один `run`, атомарний, до `BATCH_MAX` фаз (Рд32). Понад
  сталу межу фасад відмовляє `command.invalid` `batch-too-large` без
  виклику транспорту; про межу, зменшену налаштуванням T3, фасад дізнається
  лише з відмови. Тихого розбиття немає. Команда над вибіркою — пізніша служба
  (§1); виділення «усе за відбором» у `window` — лише фільтром.
- Об'єкт, позначений застарілим (§10), запису не приймає: фасад відмовляє
  `command.stale-client` без виклику транспорту.

**Межі й тайм-аути команди** (Рд26). Межі перевіряються до бази:

| Межа | Значення | Де перевіряється | Відмова |
| --- | --- | --- | --- |
| `BATCH_MAX` | 500 фаз | схема пакета T0, конверт, MCP `data-write`; зменшена межа — `runtime.run`; фази `ctx.run` у межу пакета не рахуються | `command.invalid` `batch-too-large` |
| `TABULAR_LINES_MAX` | орієнтир 5 000 (число й ширину в байтах фіксує бенчмарк B2) | схема операції T0, MCP `data-write`; зменшена межа запису — `runtime.run` | `command.invalid` `tabular-too-large` з `path` ТЧ |
| `maxBytes` атрибута | орієнтир 1 МБ для `Json` і `RichText` | валідація значення за каталогом | `command.invalid` `too-large` |
| тіло конверта | орієнтир 4 МБ (нижче межі 4,5 МБ Vercel) | host до розбору JSON і фасад до надсилання (§4.5) | `command.invalid` `payload-too-large` |
| відповідь (читання й `run`) | орієнтир 4 МБ | крок 6 обробника (§4.5) | упорядкована сторінка — непорожній префікс з `more: true`; читання за ключами, картка й «ТЧ власника» — `command.invalid` `response-too-large`; `run` — результат без `rows`, фасад перечитує за ключем |

- **Зменшені межі.** Налаштування рантайму T3 лише зменшує `BATCH_MAX` і
  межу запису ТЧ. Зменшені межі перевіряє `runtime.run` на кожному вході:
  конверт, MCP, серверний код host-а і фази `ctx.run`. Межу читання ТЧ (форма картки й «ТЧ власника») тримає стала
  платформи `TABULAR_LINES_MAX`. Межа `full` — окреме налаштування
  рантайму даних (§6.1).
- **Хук** отримує в `draft.tabularSections` лише ТЧ, які містить операція, і
  кожну — цілком після операції.
- **Масив ТЧ з MCP `data-write` чи `ctx.run`** має назвати кожен наявний
  рядок ТЧ власника — у масиві чи в явному переліку `deleteIds`. Масив, що
  пропускає наявний id, — відмова: агент чи хук схильні слати лише
  змінений рядок. Настанова скілу споживача: будувати масив ТЧ лише з
  форми картки чи «ТЧ власника».
- **Компілятор і бюджет відповіді:**
  - помилка — один рядок списочної форми може перевищити бюджет (сума
    `maxBytes` звичайних колонок шапки понад бюджет); так само для одного
    рядка ТЧ;
  - попередження — сума `maxBytes` лінивих полів об'єкта перевищує бюджет
    форми картки.

  Сторінку понад бюджет рантайм віддає префіксом, а «ТЧ власника» —
  відмовою `response-too-large` (§4.5).
- **Час.** Головний механізм — бюджет часу транзакції в T3 (орієнтир
  60 с). T3 перевіряє його між фазами й перед кожним оператором порту.
  `SET LOCAL statement_timeout` T3 ставить лише тоді, коли залишок бюджету
  менший за стелю на оператор (30 с): значення — залишок, округлений
  вгору, не менше 1 мс (0 вимкнув би тайм-аут у Postgres). Залишок ≤ 1 мс —
  `command.timeout` без виконання оператора. `lock_timeout` — орієнтир 5 с.
  `transaction_timeout` (PostgreSQL 17+; версію хостованого Supabase
  перевіряє B1b-3) — лише запобіжник понад бюджет;
  `idle_in_transaction_session_timeout` ловить завислу транзакцію. Обидва
  рвуть з'єднання з `FATAL` `25P04` чи `25P03` (перевірено на PostgreSQL
  17.11).
- **Утрата з'єднання.** Порт `fromPgPool` на час видачі клієнта вішає на
  нього слухача `error` (pg-pool знімає свого слухача простою при видачі),
  зберігає помилку з кодом і знімає слухача при поверненні: `FATAL` на
  клієнті без запиту не валить процес. Збережений `25P03` чи `25P04` T3
  мапить на `command.timeout` і знищує з'єднання — лише тоді, коли `COMMIT`
  ще не надіслано. Утрата з'єднання під час надсилання `COMMIT` чи після —
  `command.unavailable`: результат невідомий (§7.3).
- Кількість фаз `ctx.run` в одній транзакції обмежено (орієнтир —
  `BATCH_MAX`). `55P03` стає `command.busy`, `57014` — `command.timeout`
  (§7.3). Повтор `40P01` (§6.5 П4) іде з паузою й джитером.

### 7.2 Обробник і write-back

Обробник мутації — `Promise<void>` закріпленої RC (Рд6):

1. викликає транспорт; помилка — §7.3;
2. декодує `result.rows` (без лінивих колонок і без рядків ТЧ, §4.5) і
   пише їх одним `writeBatch` на колекцію. Усередині колбека фасад
   синхронно відбирає ключі за присутністю: `writeUpdate` чи `writeDelete`
   відсутнього ключа кидає виняток, а ключ, присутній лише в
   оптимістичному стані, вважається відсутнім. Рядок пишеться лише для
   ключа, вже присутнього в колекції, чи для власного `create` (Рд22), і
   лише з версією, не меншою за версію в колекції (Рд24). Власний `create`,
   чий ключ відсутній, — `writeInsert`; власний `create`, чий ключ уже
   синхронізовано (його принесла інша підмножина), — `writeUpdate` за
   правилом версії (`writeInsert` дав би `DuplicateKeySyncError`).
   Дублікати ключа в одному пакеті фасад зводить до рядка з найбільшою
   версією (`DuplicateKeyInBatchError`). `delete` — `writeDelete` рядка й
   рядків його ТЧ. Рядків ТЧ обробник напряму не пише (Рд27);
3. неповний рядок (лише ключ і версія — створення кореня скоупу без ролі
   `rootCreator`, §6.13 П4) не пишеться: фасад перечитує його за ключем, і
   невидимий рядок у колекцію не потрапляє;
4. рядки об'єктів без колекції в рантаймі не пишуться;
5. зміни набору змін, яких `rows` не покривають (зокрема результат без
   `rows` понад бюджет відповіді), — перечитування за ключем, як сигнал
   (§8.4);
6. **перечитування після запису.** Обробник запускає й чекає з межею часу
   (орієнтир 5 с): підмножину картки — коли операція змінила лінивий
   атрибут чи результат прийшов без `rows`; підмножини «ТЧ власника»
   змінених власників (точний ключ запиту, single-flight). Обробник чекає
   межі вибірки — відповідь отримано, — а не застосування:
   `query-db-collection` відкладає застосування результату, поки триває
   обробник мутації. Застосування й оновлення `ownerVersion` настають
   після осідання транзакції; наступна мутація того самого ключа стартує
   лише після цього застосування (§7.1). Після тайм-ауту чи збою ці
   підмножини отримують `needsRefresh`; транзакцію обробник не відхиляє —
   вона вже зафіксована;
7. збій write-back після `COMMIT` бази фасад пише в журнал і закриває
   перечитуванням за ключем. Транзакцію він не відхиляє: RC відкотила б
   уже зафіксований запис;
8. завершується лише після запису: оптимістичний стан заміняє підтверджений
   рядок, а не повертається до старого.

Відлуння власної команди: сигнал прийде з тією самою версією, що вже в
колекції, і фасад його відкидає (§8.4).

### 7.3 Помилки

Фасад відхиляє транзакцію `CommandFailure` (T0) з тим самим `CommandError`
(§6.10 П4), без нового типу; `path` фасад мапить з фізичного в логічний
своїм каталогом. RC відкочує оптимістичний стан. Додатково (запис і
читання):

| Код | Що робить фасад |
| --- | --- |
| `command.conflict` `version` | перечитує рядок за ключем і пише його, а для власника з підмножиною ТЧ — перезапитує й її: користувач бачить поточний стан і версію (`currentVersion`). Чернетку й дельту рядка фасад не накладає повторно: конфлікт доходить до викликача |
| `command.forbidden` | перечитує рядки фаз за ключем; невидимий рядок прибирається (§6.2) |
| `command.stale-client` | запит `version` і переоцінка позначки (§10); `onStaleClient(object)`; автоматичного повтору немає |
| `command.unavailable` `schema` (PostgREST, §5.3) | запит `version` і переоцінка сумісності |
| `command.unauthenticated` `session-changed` | `onSessionChanged` і `dispose()` (§6.1) |
| `command.unavailable` на читанні | нічого: повтор — рішення хоста |
| `command.unavailable` на `run` | результат невідомий: фасад перечитує ключі операції; для `create` кореня виду скоупу (id дає T3) — перечитує знімок прав і перелік скоупів; автоматичного повтору немає |
| `command.busy` (`55P03`), `command.timeout` (`57014`; `25P04` і `25P03` до надсилання `COMMIT`; і для читання) | відкат без автоповтору; повтор — рішення хоста |
| решта | лише відхилення |

Помилки розробника фасаду — `DataError` з кодом `data.*` (§6.1), а не
`CommandError`: до транспорту вони не доходять.

Прив'язку `path` до поля форми робить П4-D.

## 8. Сигнал реального часу

Механіку профілю `supabase` доведено спайком (г), п. 2 (Realtime v2.147.1,
supabase-js 2.119.0): команда шле `realtime.send` з фізичними ключами,
адаптер мапить їх за каталогом і перечитує тим самим запитом — логічні
ключі й та сама версія; 20 команд — 20 сигналів рівно раз; чужий приватний
канал — `CHANNEL_ERROR Unauthorized` (політика `SELECT` на
`realtime.messages`), перечитування чужих ключів — нуль рядків; відкат
транзакції прибирає сигнал.

### 8.1 Формат

Схеми й формат каналу — у T0 (§3). Схем дві:

- **схема відправки** — рівно те, що шле генератор:

  ```text
  change:     { object: <UUID об'єкта каталогу>, op: "create" | "update" | "markDeletion" | "delete",
                keys: { <фізична колонка ключа>: <UUID> }, row_ver: <версія рядка> }
  invalidate: { object: <UUID об'єкта каталогу>, op: "invalidate" }
  rights:     { op: "rights", row_ver: <версія прав> }
  ```

  Зміна — рівно чотири поля, інвалідація — рівно два, права — рівно два. Схема відправки сувора: генератор не шле зайвого
  поля.

- **схема прийнятого повідомлення** — схема відправки плюс верхній `id`
  (UUID): `realtime.send` дописує його в payload, якщо його немає, і пише
  той самий id у `realtime.messages.id`. Приймач дедуплікує за ним. Відомі
  види приймач розбирає суворо. **Сумісність уперед** (Рд28), без збою:
  - повідомлення каналу змін, яке схеми не проходить (невідомий `op` чи
    зайве поле), — `invalidate` для (скоуп, об'єкт) з топіка;
  - `payload.object`, відмінний від об'єкта топіка, — `invalidate` об'єкта
    топіка;
  - нерозібране повідомлення каналу прав (`simetra-rights:`,
    `simetra-user:`) — перечитування знімка прав;
  - розбираються лише події broadcast `change` і `rights`; системні події
    транспорту приймач пропускає;
  - повідомлення невідомого каналу — ігнорує.

Правила:

- `object` — UUID об'єкта з каталогу рантайму, а не ім'я: перейменування не
  ламає старих клієнтів (Р4, Р5). Слово `kind` у Simetra — вид метаданих,
  тож поле має іншу назву.
- `keys` — вкладений об'єкт, бо верхній `id` зайнятий id повідомлення
  (знахідка Б спайку (г)).
- **Лише сурогатний ключ UUID.** Сигнал шле лише об'єкт, чий ключ — одна
  колонка UUID: складений чи природний ключ — це значення полів (виміри, код,
  пошта), і через канал, авторизований без рядка, вони дійшли б до
  підписника з вужчим обсягом. Об'єкт з іншим ключем сигналу не шле, доки
  окреме рішення не задасть його формат.
- Поля про змінені ТЧ сигнал не несе: фасад перезапитує ТЧ картки, щойно
  версія шапки перевищить `ownerVersion` підмножини ТЧ (§6.2).
- `invalidate` — «об'єкт у скоупі змінився», без ключів: канал несе скоуп і
  об'єкт. Його шле режим злиття (§8.2) і пізніша команда над вибіркою
  (Рд32), лише для сигнальних об'єктів.
- Значень полів, логічних імен і даних рядка сигнал не несе (Р31).

### 8.2 Хто шле

Генератор ядра (`packages/simetra/src/compiler/catalog-command/units.ts`) у
кожній функції ядра **сигнального** об'єкта (§8.3) після DML шапки й ТЧ
додає
`PERFORM simetra.signal(<об'єкт>, <вид скоупу>, <скоуп>, <ключі>, <версія>, <операція>)`
з версією рядка після запису; `<t>_delete` — з версією й скоупом стану «до».
Корінь виду скоупу — сигнальний об'єкт: його носій скоупу — власний `id`,
тож канал кореня — `simetra:<вид>:<id кореня>:<об'єкт кореня>` (§8.3), і
сигнал шлють усі його функції ядра. Функція створення кореня (§6.13 П4) теж
кличе сигнал — останнім кроком, після функції гранту й читання рядка, з
версією з прочитаного рядка: `INSERT` кореня йде без `RETURNING`, а
членство й права творця з'являються лише в функції гранту. Доходить сигнал
лише в моделі з роллю `rootCreator` (творець читає новий скоуп у тій самій
транзакції). У моделі оператора актор нового скоупу не читає, тож політика
`INSERT` сигнал відхиляє — і це правильно: учасників скоупу ще немає, а про
новий скоуп творця повідомляє канал прав користувача.

`simetra.signal(p_object uuid, p_scope_kind uuid, p_scope uuid, p_keys jsonb,
p_version bigint, p_operation text) RETURNS void` — у
схемі `simetra`, `SECURITY INVOKER`, `SET search_path = ''`, `EXECUTE` лише
`simetra_command`.
Тіло — за профілем:

- `supabase` — `realtime.send(<payload>, 'change', <канал>, true)` (приватний
  канал) під роллю `simetra_command`; генератор дає їй `USAGE` схеми
  `realtime`, `EXECUTE realtime.send`, `INSERT` на `realtime.messages` і
  політику `INSERT` (§8.3, Рд16);
- `postgres` — рядок outbox (B8, Рд10).

**Сигнали прав.** `simetra.rights_bump`
(`packages/simetra/src/compiler/rights/functions.ts`) після підвищення кличе
`simetra.signal_rights(p_scope_kind, p_scope, <нова версія>)` — у канал прав
скоупу. Тригери членства й призначень ролей (`guard-units.ts`) додатково
шлють у **канал прав користувача** кожного зачепленого учасника
(`simetra.signal_user_rights(<id користувача>, <версія прав скоупу>)`): так
користувач, доданий у новий скоуп, дізнається про нього, хоч на канал
нового скоупу ще не підписаний. `signal_rights` і `signal_user_rights` —
`SECURITY INVOKER`, `REVOKE EXECUTE … FROM PUBLIC`, без гранту ролям API
і `simetra_command`: інакше будь-яка роль слала б підроблені сигнали прав і
штормила перепідписки. Обидві функції кличе лише definer-код
платформи (`SECURITY DEFINER SET row_security = off` від власника об'єктів
Simetra з `BYPASSRLS`, §9 П4), тож `realtime.send` там виконується від
власника, і політика його не судить; грант власника на `realtime.messages`
план B6 доводить тестом і додає, якщо бракує.

**Прийнята таблиця** (до переведення на команди) шле той самий формат
тригером, що кличе `realtime.send`, а не `broadcast_changes` з `record` і
`old_record` (Рд8): приймач розбирає одну форму. Тригер генерує блок, що
додає запис каталогу лише для читання цієї таблиці (Рд1); ця спека фіксує
формат і вимоги до нього:

- функція тригера — `SECURITY DEFINER` від власника об'єктів Simetra
  (`BYPASSRLS`), як `rights_bump`: прийняту таблицю пишуть ролі запиту,
  фонові записувачі без claims і функції споживача, а для них політики
  `INSERT` немає (Рд9) — від їхнього імені сигнал зникав би мовчки;
- тригер має гард дозаповнення `WHEN (current_setting('simetra.backfill',
  true) IS DISTINCT FROM 'on')`: інакше дозаповнення фази розширення шле
  сигнал на кожен рядок (спайк (г), п. 3–4). Гард гасить лише зайві сигнали
  й безпеки не стосується; ядро команд гарду не потребує;
- `CustomTable` не має контракту прав (спека прав §4.1), тож авторизація
  каналу такої таблиці — fail-closed, доки застосунок не оголосить її правило;
- тригер входить у наскрізний гейт мовчазної втрати (§12).

**Сплеск.** Локально 500, 2 000 і 5 000 `realtime.send` в одній транзакції
доходять усі (останній — через 31, 130 і 290 мс після `COMMIT`); ліміт
тенанта на broadcast із бази локально не діє (спайк (г), Г6). Кожен
`realtime.send` — рядок `realtime.messages`, тож пакет із 500 фаз — 500
`INSERT`: план B2 фіксує їхню ціну бенчмарком, а з неї — поріг злиття.
Ліміти хостингу — у перевірці хостованого Supabase (§9 П4, Додаток А).
Сигнал на фазу лишається до порогу злиття (Рд8, Рд28).

**Злиття сигналів** (Рд28). Ліміти хостингу Supabase: Pro — 500
повідомлень/с, і розсилка рахується на підписника. Тому T3 вмикає режим
злиття посеред транзакції:

- T3 рахує сигнальні фази транзакції, зокрема фази `ctx.run`.
- Коли лік досягає порогу (типово ~50; число уточнює бенчмарк B2), T3
  ставить налаштування транзакції `simetra.signal_mode` для решти фаз.
  Перемикання одностороннє: вимкнено → увімкнено.
- Налаштування `simetra.*` не пише ні SQL застосунку (спека прав §5.3), ні
  хук (Рт6).
- Режим відкритий за замовчуванням: сигнал на фазу гасить лише точне
  значення режиму злиття; будь-яке інше значення лишає сигнал на фазу.
- Після вмикання режиму ядро не шле сигналу на фазу. Сигнали, надіслані на
  фазу до порогу, лишаються: дубль з `invalidate` нешкідливий.
- `simetra.signal_invalidate(<об'єкт>, <вид скоупу>, <скоуп>)` T3 кличе
  лише в режимі злиття: для пари (скоуп, об'єкт) на першій фазі, що
  зачіпає цю пару після вмикання режиму, — одна відправка на пару. Пари,
  яких фази після вмикання не зачіпають, уже отримали сигнал на фазу.
  Відправка на фазі, а не перед `COMMIT`: пізніша фаза може вивести писаря
  зі скоупу, і політика відправки відхилила б сигнал. Доставка — після
  `COMMIT`, як у будь-якого сигналу. Без режиму злиття `invalidate` не
  шлеться.
- `signal_invalidate` — лише для сигнальних об'єктів: спільна частина
  запису каталогу рантайму несе ознаку `signal` (§3).
- `signal_invalidate` шле `invalidate` (§8.1) у канал змін тієї пари; тіло
  за профілем, права, гранти й політика відправки — ті самі, що в
  `simetra.signal`.
- Відкат прибирає й ці сигнали: вони транзакційні.

Сигнал транзакційний: `realtime.send` пише рядок `realtime.messages` у тій
самій транзакції, тож `ROLLBACK` і невдала спроба повтору (§6.5 П4) сигналу
не дають. Запис повз ядро (імпорт, мігратор, провізія «Користувачів»,
рядки членства й призначення, які вставляє функція створення тенанта,
§6.13 П4) сигналу змін не шле: клієнт бачить такі зміни після перепідписки
чи оновлення (§8.4); зміну прав від них несуть сигнали прав (тригери).

**Мовчазна втрата.** `realtime.send` ковтає будь-яку помилку у `WARNING`
(знахідка А спайку (г)): без гранту, без політики `INSERT` чи коли політика
відмовила, сигнал зникає, а команда успішна. Це свідомо — бізнес-запис через
збій сигналу не падає. Втрату ловить гейт на e2e-стеку (Рд18): «команда →
сигнал дійшов до авторизованого підписника» на кожній формі ядра й кожному
сигналі прав (§12).

### 8.3 Канали й авторизація

- **Канал змін** — `simetra:<вид скоупу>:<скоуп>:<об'єкт>`; нескоуплений
  об'єкт — нульові UUID виду й скоупу (`ZERO_UUID`).
- **Канал прав скоупу** — `simetra-rights:<вид скоупу>:<скоуп>`; глобальний
  рівень — нульові UUID.
- **Канал прав користувача** — `simetra-user:<id користувача>`; payload —
  лише «права змінились» і нова версія прав, без переліку скоупів.
- **Сигнальний об'єкт.** Об'єкт шле сигнал змін, лише коли (а) його ключ —
  сурогатний UUID (§8.1) і (б) кожна `RESTRICTIVE`-межа читання об'єкта
  виражається без рядка: межа тенанта над колонкою-носієм скоупу (у кореня —
  над його `id`) — так, бо скоуп несе сам канал; межа, що залежить від інших
  колонок рядка, — ні (так у «Користувачів»: межа «я й учасники моїх
  скоупів», спека прав §5.2). Рішення ухвалює компілятор тим самим аналізом,
  що будує політики, і пише його двічі з одного джерела: виклик сигналу в
  ядрі й ознаку `signal` у клієнтському каталозі. Несигнальний об'єкт ядро
  сигналом не супроводжує, а приймач на його канали не підписується; його
  колекції свіжіють перепідпискою й оновленням (§8.4). Інакше канал
  нескоупленого об'єкта видав би id і моменти змін рядків, яких RLS не
  показує, зокрема користувачів чужих тенантів. `RESTRICTIVE`-політики стелі
  агента (`<t>_agent`, Рх12) — теж межі читання: П4-F, вводячи їх, додає
  умову стелі в `signal_topic_allowed` чи робить об'єкт із рядковою стелею
  несигнальним.
- **`simetra.signal_topic_allowed(p_topic text, p_send boolean) RETURNS boolean`** —
  `STABLE SECURITY DEFINER SET search_path = ''`, `EXECUTE` — `PUBLIC`:
  `RESTRICTIVE`-політики нижче діють для всіх ролей, а Postgres перевіряє
  `EXECUTE` функції виразу політики навіть тоді, коли гілку не обчислює, тож
  без гранту будь-яка роль застосунку падала б на власних каналах. Функція
  відповідає лише про права поточного користувача й без нього повертає
  `false`, тож `PUBLIC` нічого не розкриває. Режимів два:
  - **відправка** (`p_send = true`, політика `INSERT`) — суворий розбір
    каналу, вид у топіку дорівнює виду скоупу об'єкта, об'єкт сигнальний, і:
    скоуплений об'єкт — скоуп проходить межу тенанта писаря (`scopeSetCall`);
    корінь виду скоупу — його `id` проходить ту саму межу; нескоуплений
    об'єкт — нульові вид і скоуп і дійсний користувач. Канали
    `simetra-rights:` і `simetra-user:` у режимі відправки — завжди `false`:
    сигнали прав шле лише definer-код власника, а `simetra_command` інакше
    підробляв би їх через `realtime.send`. Право запису вже перевірило ядро,
    а судити право читання писаря не можна: писар лише з контейнерною роллю
    має право запису без права каналу, і його сигнал мовчки зник би для всіх
    підписників;
  - **підписка** (`p_send = false`, політика `SELECT` і токен `postgres`) —
    за правилами нижче. Розбирає канал суворо (інший формат, невідомий чи несигнальний
  об'єкт — `false`) і відповідає:
  - канал змін скоупленого об'єкта — скоуп проходить ту саму межу тенанта,
    що й `<t>_scope_read` (для виду з дослівною функцією множини — той самий
    `scopeSetCall`, `packages/simetra/src/compiler/access-units.ts`), **і** я
    маю хоч один обсяг права `read` на об'єкт у цьому скоупі — `any`, `own`
    чи вимір; лише контейнерне право канал **не** відкриває: роль на одному
    контейнері інакше показала б id і версії рядків усіх контейнерів скоупу
    (з тієї самої причини `has_right` контейнерних рядків не бачить), а
    залишок Р-4 прийнято лише для `own` і виміру. Вираз будує той самий
    будівник, що й політику читання об'єкта, у формі, незалежній від рядка
    (множини обсягів без носіїв рядка);
  - канал кореня виду скоупу — скоуп (= `id` кореня) проходить ту саму межу
    тенанта (`scopeSetCall`) і право `read` кореня за тим самим правилом;
  - скоуплений об'єкт з `publicRead` (межі скоупу немає, спека прав §5.2) —
    будь-який дійсний користувач;
  - нескоуплений сигнальний об'єкт — хоч одна перевірка права `read`
    (`has_right`) за обсягами `any`, `own` чи вимір контракту об'єкта
    (контейнерні рядки `has_right` не бачить, тож контейнерне право канал
    не відкриває); з `publicRead` — будь-який дійсний користувач;
  - канал прав скоупу — скоуп проходить межу тенанта виду (`scopeSetCall`);
    глобальний — дійсний
    користувач (`current_user_id()` не `NULL`);
  - канал прав користувача — `<id> = current_user_id()`;
  - без дійсного користувача — `false`.
- **Політики `supabase`** на `realtime.messages` (з обгорткою `(SELECT …)`,
  С9):
  - `PERMISSIVE FOR SELECT TO authenticated USING (extension = 'broadcast'
    AND topic = (SELECT realtime.topic()) AND (SELECT
    simetra.signal_topic_allowed((SELECT realtime.topic()), false)))` —
    з умовою на колонку `topic`: інакше сесія з прямим SQL, поставивши
    дозволений топік Simetra, читала б через OR рядки приватних каналів
    застосунку;
  - `PERMISSIVE FOR INSERT TO simetra_command WITH CHECK (extension =
    'broadcast' AND private AND simetra.signal_topic_allowed(topic, true))`
    — приватний канал і режим відправки, над колонкою
    `topic` рядка, що вставляється, а не над налаштуванням
    `realtime.topic()`: те живе до кінця транзакції після першого
    `realtime.send`, і інший `INSERT` у тій самій транзакції пройшов би за
    чужим каналом;
  - `RESTRICTIVE FOR SELECT` для всіх ролей — резерв префіксів над колонкою
    `topic` рядка на весь простір `simetra*` (Рд28): канали змін, прав,
    користувача й майбутні канали, зокрема функціональних опцій. Рядок із
    таким топіком проходить лише за `topic = realtime.topic() AND
    signal_topic_allowed(topic, false)`; невідомий канал простору функція
    не дозволяє. Налаштування `realtime.topic()` може
    поставити будь-яка сесія, тож резерв, що судив би лише його, пропустив би
    пряме читання `realtime.messages` поза Realtime;
  - `RESTRICTIVE FOR INSERT` для всіх ролей — над колонкою `topic`: рядок з
    топіком простору `simetra*` проходить лише від `simetra_command`, лише приватний
    (`private`) і лише за `signal_topic_allowed(topic, true)`. Власник об'єктів Simetra (`BYPASSRLS`)
    політик не проходить.
  Без резерву будь-яка широка `PERMISSIVE`-політика застосунку для власних
  каналів відкрила б канали Simetra на читання й запис. Політики — об'єкти
  застосунку в чужій схемі, тож входять у гейт (§6.9 платформної) і
  рендеряться лише в профілі `supabase`. На локальному стеку їх створює роль
  `postgres` у міграції, хоча власник таблиці — `supabase_realtime_admin`; на
  хостингу це не перевірено — рядок перевірки хостованого Supabase
  мінімальної доставки (§9 П4, Додаток А), не блокер П4-B (знахідка Г спайку
  (г)).
- **Публічний канал з тим самим ім'ям.** Політики судять приватне
  приєднання й відправку з бази; що публічне приєднання до топіка Simetra
  сигналу не отримує і що публічна відправка клієнтом у топік Simetra не
  доходить до приватного підписника, доводить гейт на e2e-стеку (§12). Якщо отримує — вимога режиму «лише
  приватні канали» йде в перевірку хостованого Supabase.
- **Сервісна роль** (`service_role`) має `BYPASSRLS` і гранти на
  `realtime.messages`: вона довірена (серверний ключ) і поза гарантіями
  Рд9; її ключ у браузер не потрапляє.

### 8.4 Приймач сигналів (T4)

- **Підписки** обчислюються зі знімка прав (§9.1) і перераховуються на кожну
  його заміну:
  - канали змін — для кожної колекції сигнального об'єкта з активними
    підмножинами. Дві окремі речі:
    - **предикат дозволу** — функція T4 над знімком, дзеркало режиму
      підписки `signal_topic_allowed`: скоуп є в `scopeSets` знімка для виду
      (межа тенанта, зокрема дослівна функція множини) і знімок має рядок
      права `read` на об'єкт у цьому скоупі з обсягом `any`, `own` чи вимір
      (не лише контейнер); нескоуплений об'єкт — будь-який такий рядок
      знімка на будь-якому рівні, крім контейнерного (так рахує `has_right`);
      `publicRead` — будь-який дійсний користувач. Його еквівалентність із
      `signal_topic_allowed` доводить DB-тест (§12);
    - **вибір скоупів для підписки** — мої скоупи з `scopeSets`, для яких
      предикат істинний; для скоупленого `publicRead` — ще й скоупи, які є в
      активних підмножинах; нескоуплений — канал із `ZERO_UUID`;
  - канали прав скоупів із `scopeSets` знімка, глобальний і канал прав
    користувача (B6).
  `CHANNEL_ERROR` авторизації приєднання не повторює до наступної заміни
  знімка: інакше відхилений канал навантажував би авторизацію безперервно.
- **Розбір** — схемою прийнятого повідомлення (§8.1): `object` → об'єкт
  каталогу, `keys` → ключ за каталогом; невідомий `object` (об'єкта немає в
  збірці) — сигнал відкидається. Нерозібране повідомлення приймач обробляє
  за правилами сумісності вперед (§8.1, Рд28). Дедуплікація — за `id`
  повідомлення.
- **Видима підмножина** — підмножина змонтованого хука, що покриває видимий
  діапазон (§6.4): сторінки видимого діапазону `window`, множина `full`,
  картка. Сторінки запасу вікна — невидимі.
- **Пачкування** (Рд23) — сигнали збираються у вікно й групуються за
  об'єктом. Вікно адаптивне: 50 мс, для «гарячого» об'єкта росте до 1–5 с;
  точні числа й бібліотеку (`@tanstack/pacer-lite` з ядра RC чи власний
  таймер) план B5 перевіряє на закріпленій версії.
- **Обробка пачки об'єкта** (порядок кроків важить):
  1. `delete` — першим, до перевірки версії: ключа немає (зокрема власне
     відлуння) — нічого; ключ є — перечитування за ключем у тому самому
     пакетному запиті, що й крок 3, і `writeDelete` рядка й рядків його ТЧ,
     лише якщо рядок не повернувся. Сигнал `delete` несе версію стану «до»,
     тож перевірка версії відкинула б чуже видалення, а без перечитування
     вміст сигналу міг би прибрати рядок, якого ніхто не видаляв;
  2. ключ у колекції з версією ≥ `row_ver` — відкинути (відлуння);
  3. ключі в колекції з меншою версією — одне перечитування за ключами
     (`where: { <ключ> in [...] }`) через адаптер, спільне з кроком 4.
     Повернутий рядок — `writeUpsert`, лише якщо його версія не менша за
     версію в колекції (Рд24); відсутній — `writeDelete` (§6.2). Нова
     версія шапки власника з активною підмножиною ТЧ веде до перезапиту
     цієї підмножини за правилом свіжості ТЧ картки (§6.2). Рядок сторінки
     вікна лишається на своїй позиції до оновлення сторінки (§6.4). Для
     списків `window`, чиї масиви ключів цього ключа не містять, фасад
     перевіряє їхній предикат: `hasNewRows` (§6.4) ставить лише рядок, що
     підходить предикату тепер і не підходив зі старим рядком колекції;
  4. ключі, яких немає в колекції (Рд23), — те саме перечитування за
     ключами пачки. Фасад перевіряє повернуті рядки локально предикатами
     активних підмножин об'єкта в цьому скоупі й оновлює (single-flight,
     §6.3) лише ті підмножини, яким рядок підходить. Рядок, що не підходить
     жодній, не пишеться. Сторінка вікна (`inArray` ключів) нового ключа не
     містить: рядок, що підходить предикату списку `window`, ставить
     позначку «є нові записи» (`hasNewRows`, §6.4) замість перечитування
     сторінок, бо його позиція невідома. Умова коректності — інваріант 16
     (§11);
  5. `invalidate` — оновлення видимих підмножин об'єкта в скоупі з топіка
     і видимих підмножин ТЧ його власників (колекції ТЧ окремі),
     single-flight, і звірка реєстру власних створень цього об'єкта.
     Невидимі підмножини отримують `needsRefresh` і оновлюються, коли
     стають видимими.
- **Сигнали прав** — перечитування знімка (§9.3).
- **Кожен `SUBSCRIBED`**, зокрема після автоперепідключення транспорту, і
  повернення вкладки — оновлення лише видимих підмножин із затримкою з
  джитером (невидимі отримують `needsRefresh`), звірка реєстру рядків
  без власника (§6.2), перечитування знімка прав і запит `version` (§10).
  Джитер не дає рестарту Realtime стати лавиною оновлень від усіх клієнтів;
  повернення вкладки приходить від host-а через `runtime.resume()` (§6.1):
  сигнали з проміжку втрачено (спайк (г) бачив збій транспорту з
  автоперепідключенням; Realtime не гарантує доставки; у `postgres` споживач
  outbox губить сигнал на нетимчасовій помилці, ПП3).

### 8.5 Порт транспорту (T0)

```text
SignalTransport = {
  subscribe(channels, onSignal, onError(kind: "auth" | "transport")): Unsubscribe,
  onSubscribed(handler): Unsubscribe     — кожне (пере)підключення
}
```

T4 знає лише порт. Вид помилки розрізняє правило §8.4: `auth`
(`CHANNEL_ERROR` авторизації) — без повтору до заміни знімка, `transport`
(`TIMED_OUT`, `CLOSED`, розрив) — перепідключення й `onSubscribed`. Реалізація
`supabase` — `simetra/data/supabase` над `@supabase/realtime-js`
(приватний канал, токен сесії від host-а); вона мапить статуси бібліотеки на
ці види, а її тест (B5) — розрив сокета дає повторний `onSubscribed`,
відмова авторизації — `auth` без автоповтору.
Реалізація `postgres` (B8) отримує токени каналів від сервера: T3 дає
`runtime.authorizeChannels(session, channels)` — читання під роллю запиту, що
кличе ту саму `signal_topic_allowed` і повертає дозволені канали; підпис
токена — адаптер сервера сигналів у host-і.

### 8.6 Відомі обмеження П4-B

- **Id і версії поза обсягом читання.** Користувач лише з обсягом `own` чи
  вимірним правом на об'єкт підписаний на канал (скоуп, об'єкт) і бачить у
  сигналі ключі й версії рядків, яких читати не може (обсяги — [спека
  прав](2026-10-17-rights-design.md) §5.2). Вмісту рядків сигнал не несе, а
  перечитування під RLS такі ключі відсіює (§8.4). Залишок прийнято свідомо
  (Р-4); id — UUID v4, як у залишку оракула наявності (§6.10 П4).
- **Кеш авторизації Realtime.** Realtime кешує авторизацію каналу на час
  з'єднання (спека системної схеми, відкриті питання): відкликане право діє
  з наступного приєднання чи оновлення токена. Наслідок — залишок вище на час
  з'єднання; фасад перепідписується після сигналу прав (§9.3).
- **Несигнальні об'єкти** («Користувачі», об'єкти з не-UUID ключем)
  свіжіють лише перепідпискою й оновленням (§8.3).
- **Читач лише з контейнерним правом** сигналів змін не отримує (§8.3).
  Зміни він бачить після перечитування, і для нього діють ті самі тригери,
  що й для всіх: кожен `SUBSCRIBED` (оновлення видимих підмножин, §8.4),
  повернення вкладки (`runtime.resume()`, §6.1), навігація, що монтує список
  чи картку заново (нова підмножина), ручне оновлення хоста, а також власний
  запис (write-back, §7.2) і перечитування після конфлікту чи відмови
  (§7.3). Сигнал прав (§9.3) теж оновлює його підписки й знімок.
- **Анонімний читач** об'єкта з `publicRead` сигналів не отримує: політика
  `SELECT` — лише `TO authenticated`.
- **Створення кореня в моделі оператора** сигналу змін не дає (§8.2).
- **Режим відправки.** Роль `simetra_command` може надіслати сигнал у
  будь-який сигнальний канал тенанта писаря, бо режим відправки не судить
  права читання (§8.3); наслідок — лише зайве перечитування під RLS.
  Клієнтський `INSERT` у канали Simetra заборонено в обох режимах: ролі
  запиту політики `INSERT` не мають, а `RESTRICTIVE`-резерв пропускає лише
  `simetra_command`.
- **Мовчазна втрата сигналу** ловиться гейтом, а не рантаймом (§8.2).
- **Запис повз ядро** сигналу змін не дає (§8.2).
- **Зміна ТЧ повз ядро.** Кожна зміна змістових колонок рядків ТЧ
  (вставка, видалення, зміна колонок запиту) підвищує версію власника
  (Рд27). Виняток — поширення копій носіїв (спека прав §5.2, Рх21): воно
  версії не підвищує, а клієнт копій носіїв не шле. Довірені записувачі
  поза ядром (імпорт, мігратор — `write_mode`, §6.15 П4) мусять іти через
  ядро чи підвищувати версію явно. Доки `write_mode` немає, рядок ТЧ,
  вставлений повз ядро без підвищення версії, може зникнути за наступної
  повної заміни ТЧ з картки, бо базова версія правки цього рядка не
  бачить.

## 9. Кеш прав клієнта

### 9.1 Знімок

`simetra.rights_client_snapshot() RETURNS jsonb` — `STABLE SECURITY INVOKER
SET search_path = ''`, `EXECUTE` — роль запиту користувача й
`simetra_command`; тіло кличе лише публічні функції фактів, які роль запиту
вже виконує (`rights_mine()`, `rights_my_scopes()`,
`rights_dimension_values(<вимір>)` на кожен вимір контракту, межу тенанта
кожного виду скоупу тим самим виразом `scopeSetCall`, що й `<t>_scope_read`
(функція членства виду, а для виду з дослівною функцією множини —
`rights_scope_set(<вид>)`), `rights_versions()`,
`rights_projection_version()`), тож нової definer-поверхні не додає.
Повертає лише факти поточного користувача (аналіз «що можу я», Рх17); схема
— у T0:

```text
{ userId, projectionVersion?, versions?: [{ scopeKind, scope, version }],
  scopeSets: [{ scopeKind, scope }],
  rights: [{ object, action, form, level, levelId, … }],
  scopes: [{ scopeKind, scope, member }], dimensionValues: […], containers: […] }
```

- Генерується в кожному проєкті з функціями прав (є ролі й користувач
  сесії), а не лише з довідниками прав. Без довідників прав `rights_bump`,
  `rights_versions()` і `rights_projection_version()` не генеруються: тоді
  `versions` і `projectionVersion` відсутні, сигналів прав немає, і знімок
  свіжіє лише перечитуванням (§9.3).
- Джерело — лише `DataTransport` `{ type: "rights" }` →
  `runtime.rightsSnapshot(session)` під роллю запиту, і в профілі
  `supabase`: схема `simetra` поза схемами API PostgREST (С1 спеки системної
  схеми), і відкривати її не можна — кожна функція з `EXECUTE` для
  `authenticated`, зокрема функції аналізу, стала б HTTP-ендпоінтом.
- У транзакції `READ ONLY` знімок читає живі факти (§6.11 П4).
- `userId` — `current_user_id()`: з нього приймач будує канал прав
  користувача (§8.3).
- `scopeSets` — вихід `scopeSetCall` на кожен вид
  (`packages/simetra/src/compiler/access-units.ts`): межа тенанта, яку судять
  `<t>_scope_read` і `signal_topic_allowed`. Не `rights_scope_set` для всіх
  видів: та функція є лише в проєкті з довідниками прав і покриває лише
  дослівні функції множини, тож для виду з членством `scopeSets` був би
  порожній, і клієнт не підписався б ні на що. Без неї предикат підписки й обчислювач розійшлися б
  із базою для виду з дослівною функцією.
- Об'єкт у рядках знімка — мітка виду (`kindLabel`); T4 мапить її на UUID
  об'єкта клієнтським каталогом (§3).
- Скоупи й права знімка потрібні приймачу сигналів (§8.4), тож знімок і його
  читання приходять у B5, а обчислювач — у B6 (§13).

### 9.2 Обчислювач

- Компілятор (T1) кладе в клієнтський каталог контракт прав об'єкта: дії,
  обсяги й форми носіїв (`own` — колонки носія, вимір — колонка носія й
  вимір, контейнер — колонка контейнера); граф вимог уже розгорнуто в рядки
  знімка.
- T4 обчислює за ним `can(action, object, { scope?, row? })` → `true`,
  `false` чи `unknown`. Код обчислювача загальний і не пишеться під
  застосунок: усе, що залежить від застосунку, — у згенерованому контракті.
  Без рядка — «чи маю право дії хоч на щось у скоупі» (кнопка «Створити»); з
  рядком — носії рядка проти моїх id, значень і контейнерів. Скоуп поза
  `scopeSets` — `false` (межа тенанта, як у базі). Колонки носіїв і
  копії носіїв (`type: "Raw"`) рядок колекції має, бо читання повертає всі
  видимі колонки, крім лінивих (Рд25). Носій прав лінивим не буває:
  компілятор відхиляє `load: "lazy"` на колонці носія (B1a).
- `useCan` рахує лише права. Функціональні опції — подання, а не умова
  `can`: їх рахує окремий обчислювач (П4-E, Рд31).
- `unknown` — для обсягу за виміром із дослівною функцією чи зв'язком через
  прийняту `CustomTable` (свіжість не гарантована, спека прав §6.3), для
  відсутнього в рядку носія і для знімка без версій (проєкт без довідників
  прав) на обсягах, що залежать від членства. Хост показує дію з `unknown`
  доступною: база — бар'єр.
- Обчислювач — не захист: помилка в ньому дає зайву чи сховану кнопку, а не
  доступ.

### 9.3 Версія й свіжість

- Ключ кешу — `projectionVersion` і версії скоупів знімка (коли вони є).
- Сигнал каналу прав скоупу з версією, більшою за кешовану, і будь-який
  сигнал каналу прав користувача — перечитування знімка (single-flight).
- Відповідь будь-якого запиту даних із `serverHash`, відмінним від хешу,
  з яким знято знімок, — перечитування знімка: зміна моделі може змінити
  проєкцію.
- Кожен `SUBSCRIBED` і повернення вкладки — перечитування знімка (§8.4).
- Кожна заміна знімка — перерахунок підписок (§8.4); зміна множини моїх
  скоупів — ще й прибирання рядків утрачених скоупів (§6.2).
- **Загальний механізм** (Рд31). Фасад будує «знімок + канал +
  перечитування» загальним: знімок через `DataTransport`, сигнал каналу з
  версією, перечитування single-flight, перечитування на `SUBSCRIBED` і
  `resume()`, ключ кешу з версій. Кеш прав — перший його екземпляр; знімок
  функціональних опцій (П4-E) стане другим.

## 10. Звірка сумісності контракту й контракт сесії

- **Контракт об'єкта** (Рд12) — `kernelHash` у записі каталогу рантайму
  (хеш форми ядра: імена функцій і контексти дій) і переліки фізичних
  колонок шапки й кожної ТЧ (за id ТЧ), виведені функцією T0
  `objectColumns(entry)` зі спільної частини запису (чиста, детермінована,
  порядок колонок — порядок атрибутів):
  - вставки й зміни — колонки реквізитів з `insert`/`update`;
  - читання — `key`, `versionColumn`, `scopeColumn`, `column` і
    `pair.typeColumn` кожного реквізиту; для ТЧ — `key`, `parent`,
    `lineNumber` і колонки реквізитів ТЧ. Перелік читання ділиться на
    звичайні й ліниві колонки (Рд25): списочна форма бере лише звичайні,
    форма картки — обидва переліки.
  `kernelHash` будує T1 детерміновано; перейменування, подання, функціональні опції
  (Рд31), права й інші об'єкти контракту не змінюють. Зміна `load` —
  подання: `kernelHash` вона не змінює; список старої вкладки просто
  втрачає колонку, а фільтр чи сортування старої вкладки за нею —
  `command.invalid` (§4.1).
- **Сумісність** — запит із форми передачі сумісний з каталогом сервера,
  коли: UUID об'єкта відомий; для запису — `kernelHash` об'єкта рівний, а
  кожна колонка операції є в переліку вставки чи зміни для її дії; для
  читання — кожна колонка фільтра, сортування, `include` і ТЧ є в
  об'єднанні звичайного й лінивого переліків читання. Новий необов'язковий реквізит шапки чи ТЧ перелік лише розширює,
  тож стара вкладка пише далі без `stale-client`; зміна типу за §7
  платформної — нова колонка, а значення далі валідує Zod каталогу сервера.
  Реквізит, видалений на фазі розширення, відхиляє лише запит, що його
  називає.
- **Обмеження читання при зміні типу.** На фазі розширення зміни типу
  сервер кодує рядок своїм каталогом, де реквізит — уже нова колонка; стара
  вкладка через Server Function бачить цей реквізит порожнім (`decodeRow`
  ігнорує невідомий ключ), а через PostgREST — стару синхронізовану колонку.
  Розбіжність триває лише до перезавантаження вкладки; запис старої вкладки
  в стару колонку переносить тригер синхронізації (§7 платформної).
- **Сервер** звіряє сумісність кроком 3 обробника (§4.5) — до перекладу й до
  бази: прибрана колонка в запиті старої вкладки — `command.stale-client`, а
  не `command.invalid`. Фази, які запускають хуки через `ctx.run`, не
  звіряються: їх будує сервер своїм каталогом. Звірка належить конверту
  передачі: API в процесі (`runtime.run`) її не робить — там каталог один
  (Рт11). Новий код T0 у `COMMAND_ERROR_CODES`.
- **Відповідь** кожного запиту даних несе `serverHash` (глобальний
  `snapshotHash`): його зміна — сигнал клієнту запросити `version`.
- **Позначка «застарілий»** на весь об'єкт — лише за невідомим об'єктом чи
  іншим `kernelHash`: тоді жоден запис над ним не пройде. Клієнт обчислює її
  на кожній відповіді `version` і **знімає**, коли хеш збігся. Несумісна
  колонка позначки не ставить: `stale-client` відхиляє лише свій запит,
  фасад кличе `onStaleClient(object)` і не повторює запит автоматично, тож
  циклу повторів немає.
  Під час розкатки інстанси зі старим і новим каталогом можуть відповідати
  вкладці по черзі: позначка ставиться й знімається з кожною відповіддю, а
  не залипає, і запис вдається з повтором, а не циклом перезавантажень.
- **`onStaleClient(object)`** — колбек host-а (П4-D): пропонує
  перезавантаження; автоматично не перезавантажує (незбережені форми інших
  об'єктів не губляться). Форма застарілого об'єкта показує стан «потрібне
  оновлення застосунку» замість кнопки запису (`isStale`, §6.4).
- **Перевірка версії** — запит `version` на кожному `SUBSCRIBED`, на
  поверненні вкладки (`resume()`), при зміні `serverHash` у відповіді, після
  `stale-client` і розбіжності схеми PostgREST (§5.3) і не частіше разу на
  хвилину при навігації (`navigated()`, §7 платформної).
- **Адаптер PostgREST** сумісності не звіряє: розбіжність схеми в його
  відповіді веде до запиту `version` (§5.3); запис іде лише через `run`.
- **Версія кешу в контракті сесії** (§9 платформної: «версія кешу» команди) —
  `kernelHash` об'єктів запиту і `subject` рантайму: обидва конверт несе й
  сервер звіряє. Кеш прав клієнта (`projectionVersion`) до контракту сесії не
  входить: права команди вирішує база, і команда через застарілий кеш прав
  не відмовляє; `projectionVersion` — лише ключ кешу клієнта (§9.3).
- **Перемикання збірки після розширення.** Після DDL розширення PostgREST
  оновлює кеш схеми асинхронно, і перші звернення нової збірки до нової
  колонки дають `PGRST204` (спайк (г), п. 3–4). Тому нову збірку клієнта
  вмикають лише після кроку застосування «кеш PostgREST бачить нові
  колонки» (підтверджений `reload schema`). Механізм кроку — П3-4; П4-B від
  нього лише залежить.
- **Межа:** мінімальна підтримувана версія, публікація її сервером і
  автоматичне звуження — П3-4 разом із першою зміною наявної колонки (§7,
  §12 платформної); рядок §13 платформної лишається відкритим до П3-4.
  Промоція прийнятої таблиці робить старі вкладки несумісними (§4.0).

## 11. Інваріанти П4-B

Кожен тримає тест (§12):

1. T4 імпортує лише дозволене блоком чистоти (§3) у кожній своїй теці;
   публічні типи `simetra/data` не посилаються на `@tanstack/*`; поза модулем
   фасаду немає `write*`, `refetch`, `createTransaction`,
   `createOptimisticAction`, створення `QueryClient` і імпорту
   `@tanstack/query-db-collection` чи `@tanstack/query-core`; T5 не імпортує
   `simetra/data/supabase`.
2. Запит читання й операція у формі передачі доходять до SQL лише з іменами
   каталогу сервера й зв'язаними параметрами; несумісний запит —
   `command.stale-client`, невалідний — `command.invalid`, обидва до бази.
3. Обидва адаптери для того самого запиту й claims дають ту саму множину
   рядків і той самий декодований рядок, зокрема для типів із тихою втратою
   (`BigInt` понад 2^53, `Numeric` з масштабом).
4. Обробник мутації завершується лише після запису підтверджених рядків або
   відхиленням; після завершення транзакції в колекції немає
   непідтвердженого рядка й неповного рядка результату; дві мутації одного
   ключа не конфліктують одна з одною.
5. Одна транзакція фасаду — один виклик `run` — одна транзакція бази.
6. Сигнал змін шле лише ядро сигнального об'єкта (і, в блоці, що його
   додасть, тригер прийнятої таблиці) у транзакції запису; сигнал прав —
   `rights_bump` і тригери членства й призначень; відкат і невдала спроба
   повтору сигналу не дають. Сигнал змін — рівно `object`, `op`, `keys`
   (лише UUID) і `row_ver`; сигнал `invalidate` —
   рівно `object` і `op`; сигнал прав — рівно `op` і `row_ver`; прийняте
   повідомлення додає лише `id`; значень полів немає. Після вмикання
   режиму злиття ядро не шле сигналу на фазу, а транзакція шле
   `invalidate` для кожної пари (скоуп, сигнальний об'єкт), яку зачіпає
   фаза після вмикання, — один раз на пару, на першій такій фазі; без
   режиму злиття `invalidate` немає.
   Режим вмикає T3, коли лік сигнальних фаз, зокрема фаз `ctx.run`,
   досягає порогу; вимкнути його до кінця транзакції не можна.
   Нерозібране повідомлення каналу змін приймач обробляє як `invalidate`,
   а каналу прав — як сигнал прав, і не відкидає.
7. Підписник отримує сигнал каналу Simetra лише приватним приєднанням і лише
   тоді, коли `signal_topic_allowed` для нього істинна, і жодна інша політика
   `realtime.messages` цього не обходить; ні ролі запиту, ні публічна
   відправка в канали Simetra не доходять до підписника; лише контейнерне
   право каналу змін не відкриває; відправку судить режим відправки (межа
   тенанта писаря), тож сигнал писаря з будь-яким правом запису доходить;
   команда кожної форми ядра й кожен сигнал прав доходять до
   авторизованого підписника (гейт проти мовчазної втрати).
8. Сигнал змін, крім `delete`, з версією, не більшою за версію в колекції,
   не дає запиту; `delete` прибирає рядок лише тоді, коли перечитування за
   ключем його не повернуло.
9. Рядок, який перечитування за ключем не повернуло, прибирається з
   колекції разом із рядками його ТЧ; рядки без власника звіряються на
