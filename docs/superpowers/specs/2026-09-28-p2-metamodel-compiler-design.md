## 1. Мета й критерії успіху

П2 будує метамодель, якою можна фізично описати будь-яку таблицю застосунку, і
компілятор — єдині двері до неї (Р3). Критичний шлях іде через схему БД
(платформна спека §12, «Порядок виконання — модель БД першою»), тож мета П2 —
повнота фізичного опису, а не широта видів.

**Критерії успіху:**

1. **Повнота.** Метамодель описує кожну таблицю першого споживача на
   фізичному рівні: видом 1С, якщо таблиця відповідає йому строго, інакше —
   видом `Table`; усе, що не є таблицею (функції, тригери, політики, в'юхи,
   гранти), — дослівним `*.sql`. Доказ — round-trip (§9) на синтетичних схемах
   у CI і приватно на schema-only копії схеми першого споживача. Прийом цілком
   (гейт, baseline) — П3; решта таблиць переходить у види поступово,
   міграціями після прийому.
2. **Паперовий тест — структурний.** Види 1С доведені на синтетичному
   документі (§10) і приватною звіркою найменшого документа споживача з рухами
   регістрів: різниця «скомпільоване ↔ прийняте» для таблиць документа, його
   ТЧ і регістрів дорівнює рівно відсутнім стандартним реквізитам 1С, і для
   кожного оголошеного руху є запит. Список різниць — план міграції цього
   документа для П3. **Семантичну** рівність рухів і підсумків (проведення на
   тестових даних) П2 не доводить: для неї потрібні згенеровані оболонка
   проведення й DDL, тож це приймальний тест П3.
3. **Компілятор — єдині двері.** Нижче компілятора ніщо не читає сирі файли
   метаданих; помилка будь-якої стадії 1–5 — ненульовий код і діагностика з
   файлом, JSON-pointer та id правила (§8).
4. **Гейти зелені** після кожного кроку §11 — чотири гейти `AGENTS.md` плюс
   тести з Postgres у CI (§10.4).

## 3. Ідентичність, імена, файли

**Ідентичність (Р4).** UUID має кожен іменований елемент моделі, який можна
перейменувати: об'єкт, реквізит (разом із вимірами й ресурсами регістрів),
табличну частину, значення перерахування, вид скоупу. Призначає інструмент при
створенні (`simetra fix`, згодом конфігуратор); id ніколи не
перевикористовується. Відсутній чи дубльований id — помилка стадії 2 з
підказкою `simetra fix`.

**Посилання — за логічним іменем.** У JSON посилання мають єдину форму
`MetadataRef` `{ kind, name }` (правило `AGENTS.md`); компілятор на стадії 2
резолвить їх у UUID, і скомпільований знімок містить лише UUID. Файли читають і
пишуть люди й агенти, тож імена тримають diff і merge читабельними.
Перейменування — операція інструмента з каскадом по всіх посиланнях, зокрема в
рядках конструктора рухів (референс логіки каскаду —
`apps/web/src/stores/metadata-store.ts`, граф посилань —
`packages/core/src/find-references.ts`). Ручне перейменування без каскаду дає
зламане посилання — помилку стадії 2, а не тиху зміну. Той самий id із новим
ім'ям — перейменування, DDL немає (платформна спека §7).

**Фізичні імена (Р5).** `physicalName` призначається раз при створенні й далі
не змінюється:

- новий об'єкт чи реквізит — snake_case логічного імені без префіксів виду
  (прототипні префікси з `packages/core/src/schemas/physical-naming.ts`
  зникають);
- колонки посилань — за правилом прототипу
  `packages/generator-pg/src/column-naming.ts` (суфікс `_id`; пара `_type` +
  `_id` для поліморфного), але тепер як факт моделі, а не генератора;
- прийнята таблиця — поточне ім'я.

Унікальність фізичних імен у межах PG-схеми й заборону SQL-зарезервованих слів
компілятор перевіряє для `physicalName`; логічні імена — не SQL і цих обмежень
не мають.

**Кілька PG-схем.** Об'єкт оголошує свою PG-схему; за замовчуванням — схема
проєкту. У першого споживача таблиці розкладено по кількох схемах.

**Регістр імен.** Об'єкти — PascalCase, реквізити й табличні частини —
camelCase, латиницею (прототип мав snake_case для реквізитів і ТЧ).

**Файли.** Об'єкт — тека `metadata/<тека виду>/<Ім'я>/` з `<Ім'я>.meta.json`,
опційними `<Ім'я>.module.ts` (поведінка) і `<Ім'я>.sql` (запити рухів,
функції, тригери, в'юхи, політики, гранти). Проєкт — `project.meta.json`: види
скоупу, модулі, PG-схема за замовчуванням. Константа — окремий об'єкт у
власній теці; спільний файл констант прототипу зникає. Форми
(`forms/*.form.json`, `packages/core/src/schemas/form.ts`,
`packages/core/src/autoform.ts`) видаляються: UI — П4.

**Налаштування генератора — поза моделлю.** Блоки `generation` (префікс
таблиць, стратегії перерахувань і констант) і `deployment` прототипного
`project.meta.json` (`packages/core/src/schemas/project.ts`) не належать до
метамоделі. Усе, що визначає фізичну форму, — факт моделі (`physicalName`,
типи, правила виду); ідентифікатори розгортання у файлах метаданих не живуть.

**Форма файлу.** Diff/merge-дружній JSON без мінливих даних; порядок ключів і
форматування канонічні — їх наводить серіалізатор і `simetra fix`.

```text
// metadata/<тека виду>/Contract/Contract.meta.json — форма, не остаточний API
{ "id": "<uuid>", "kind": "Catalog", "name": "Contract", "physicalName": "contract",
  "title": { "uk": "Договори" }, "scope": "org",
  "owners": [{ "kind": "Catalog", "name": "Counterparty" }],
  "attributes": [
    { "id": "<uuid>", "name": "currency", "physicalName": "currency_id",
      "type": "Ref", "ref": { "kind": "Catalog", "name": "Currency" } } ] }
```

## 4. Вид `Table` і система типів

**`Table`** — наступник прототипного `CustomTable` — точний фізичний опис
таблиці, з якого нічого не виводиться:

- колонки: тип, `NOT NULL`, `DEFAULT` у нормалізованій формі Postgres (як її
  повертає `pg_get_expr`), identity (`ALWAYS` чи `BY DEFAULT`), коментар;
- первинний ключ — одноколонковий, складений або відсутній;
- унікальні обмеження й індекси, зокрема часткові (`WHERE`), виразні,
  `NULLS NOT DISTINCT`;
- `CHECK` у нормалізованій формі;
- зовнішні ключі — складені, з `ON DELETE`/`ON UPDATE`, на таблиці інших схем,
  зокрема на таблицю користувачів провайдера (`auth.users` у Supabase);
- коментарі таблиці й колонок.

Функції, тригери, політики, в'юхи й гранти прийнятої БД живуть дослівно в
`*.sql` (платформна спека §6.3–§6.4). `Table` теж оголошує скоуп (§6); оскільки
вона нічого не виводить, скоуп-колонку описує явно, а компілятор перевіряє, що
колонка є й відповідає виду скоупу. `Ref` з об'єкта виду 1С на `Table` можливий,
коли первинний ключ таблиці — одна uuid-колонка: фізично `Ref` — FK саме на
такий ключ.

**Строгість і точність.** Вид 1С завжди строгий (повний набір стандартних
реквізитів, §5), `Table` завжди точний (нічого похідного). Проміжної форми «вид
із частиною стандартних реквізитів» немає. Промоція `Table` → вид 1С —
міграція схеми (П3), а не правка метаданих; список відсутніх стандартних
реквізитів і є її планом (§1).

**Система типів.** Логічні типи доступні всім видам; фізичне подання кожного —
правило моделі. SSOT — Zod-схема типів (сьогодні
`packages/core/src/schemas/field-type.ts`) і мапінг на Postgres (сьогодні
`packages/generator-pg/src/type-mapping.ts`, у П2 переїжджає в модель).
Доповнення, яких вимагає інвентаризація:

| Потреба прийнятої схеми | У моделі |
| --- | --- |
| jsonb масово: rich text, адреси, налаштування, payload | `Json` |
| масиви рядків і посилань | масив будь-якого логічного типу |
| 64- і 16-бітні цілі; лічильники й журнали з identity | `BigInt`, `SmallInt`; identity — у `Table` |
| numeric без точності | `Numeric` з опційними `precision`/`scale` |
| varchar(n) і text — різні типи | `String` з довжиною ≠ `Text`, без тихого зведення |
| бінарний стан | `Bytes` (замість прототипного `Binary`) |
| енам-типи Postgres | PG-енам: значення й порядок — у моделі; еволюція — лише додавання значень (П3) |
| усе, чого логічні типи не покривають | «сирий» PG-тип — **лише в `Table`** |

## 5. Види 1С, стандартні реквізити, патерн запису, нумерація

**Види П2:** довідник (`Catalog`), документ (`Document`), перерахування
(`Enumeration`), регістр відомостей (`InformationRegister`), регістр
накопичення (`AccumulationRegister`), константа (`Constant`) — плюс `Table`.
Решта кандидатів платформної спеки §4 (запис, журнал, налаштування, членство) і
прогалини інвентаризації (зв'язок M:N, технічні таблиці, упорядкований
довідник) — пізніше й адитивно; до того такі таблиці — `Table`.

**Строгий набір стандартних реквізитів.** Для кожного виду — набір прототипу:
набір 1С разом зі службовими датами створення й оновлення (SSOT —
`packages/core/src/schemas/standard-attributes.ts`, після §8.1 — запис виду в
реєстрі). Службові дати — єдине свідоме доповнення до 1С. Опційних підмножин
немає: у довідника є код, найменування й позначка видалення, у рухів регістра —
номер рядка й активність, навіть коли прийнята таблиця їх не має; така таблиця
лишається `Table` до міграції (М3). Стандартні реквізити виводяться з виду та
його налаштувань (ієрархія, власники, періодичність, режим запису, реєстратори)
і ніколи не записуються як власні реквізити у файлах (правило `AGENTS.md`).

**Логічні й фізичні імена стандартних реквізитів.** Логічні — camelCase,
фізичні — імена прототипу. Ключ логічно `ref` (як «Ссылка» 1С), фізично `id`;
стандартні посилання логічно без суфікса (`parent` ↔ `parent_id`, `owner` ↔
`owner_id`, `recorder` ↔ пара `recorder_type` + `recorder_id`); решта —
пряма зміна регістру (`deletionMark` ↔ `deletion_mark`). Повна відповідність —
у реєстрі видів.

**Фізика стандартних реквізитів — у моделі.** Первинний ключ, `DEFAULT`,
`NOT NULL`, `CHECK` виду руху, індекси стандартних реквізитів, зв'язок рядка ТЧ
з власником сьогодні знає генератор (`STANDARD_ATTR_DEFAULTS` у
`packages/generator-pg/src/type-mapping.ts`, правила ТЧ і поліморфних
посилань у `packages/generator-pg/src/generate-table.ts`). У П2 ці факти
переїжджають у реєстр видів і з'являються у фізичному знімку компілятора
(§8.3); генератор П3 про види не знає. Стандартні вирази компілятор видає
одразу в нормалізованій формі Postgres, щоб порівняння з каталогом (§9) не
давало хибних різниць.

**Патерн запису — властивість виду** (платформна спека §4). Довідник і
перерахування — оптимістичний: id дає клієнт, у DDL `id` без `DEFAULT`
(прототипний `DEFAULT gen_random_uuid()` довідника не переноситься), код
довідника призначає тригер у межах скоупу. Для перерахування це має зміст
лише у формі таблиці значень (§14). Документ і регістри — серверний: усе через
RPC, `id` — `DEFAULT` на сервері.

**Нумерація.** Номер документа призначає сервер у межах скоупу, з
періодичністю (прототипна `numberPeriodicity`) і префіксом; номер унікальний у
межах «скоуп + період». Довжина й тип номера та коду — налаштування виду, як у
прототипі.

**Константа** — окремий об'єкт із власним `physicalName` і декларацією
скоупу: у скоупленої константи значення одне на кожне значення скоупу.

## 6. Скоуп

Скоуп — розділювач даних і межа ізоляції (тенант), а не модель доступу: що
може учасник скоупу, вирішують права, яких П2 не будує. Формулювання Р10, яке
П2 пропонує для платформної спеки (погодження — §12):

> **Р10.** Скоуп — розділювач даних і межа ізоляції. Застосунок оголошує на
> рівні проєкту нуль або більше видів скоупу; вид має ім'я, фізичну колонку,
> корінь (сутність застосунку або користувач провайдера) і функцію множини
> доступних id (без аргументів, `SETOF uuid`, `STABLE`, act-as-перевірка
> всередині). Якщо проєкт оголошує хоч один вид, кожен об'єкт, включно з
> `Table`, оголошує рівно один вид або явно «без скоупу»; пропуск декларації —
> помилка компілятора. Табличні частини, рухи регістрів і підлеглі записи
> успадковують скоуп власника: денормалізована колонка скоупу й складений FK на
> власника. Посилання між об'єктами одного виду скоупу — складений FK
> `(scope, ref) → (scope, id)` з `UNIQUE (scope, id)` на цілі; посилання зі
> скоупленого на глобальне дозволене; з глобального на скоуплене й між різними
> видами — помилка без явного `crossScope`. Семантику членства визначає
> застосунок. Однотенантний застосунок видів скоупу не оголошує, його об'єкти
> скоупу не декларують, і він нічим за скоуп не платить.

**Не в П2** (адитивно пізніше): вкладений рівень (підскоуп усередині скоупу),
видимість «моє», share, ролі, вид «членство», ієрархія видів скоупу.

**Наслідки для моделі:**

- Корінь скоупу — об'єкт, чий ключ і є значенням скоупу: він оголошує свій вид,
  скоуп-колонкою йому служить власний ключ. Для кореня «користувач провайдера»
  значення скоупу — id користувача провайдера.
- Реєстратор рухів — пара без FK (§7), тож складеного FK на власника в рухах
  немає: скоуп рухів записує оболонка проведення з документа, а компілятор
  вимагає, щоб вид скоупу регістра збігався з видом скоупу кожного реєстратора.
  Ключ підсумків містить скоуп.
- Посилання рядка ТЧ чи виміру регістра на скоуплений об'єкт того самого виду —
  теж складений FK.
- Посилання з `crossScope` — звичайний FK без скоуп-колонки; його сенс —
  відповідальність застосунку.
- Декларація виду скоупу — у `project.meta.json`; тіло функції множини —
  дослівно в `*.sql`. Компілятор перевіряє, що функція є (стадія 5); її
  сигнатуру й форму RLS-предиката (платформна спека §6.8) перевіряє П3 через
  тінь.

## 7. Документ, проведення, регістри

**Документ.** Строгий набір: номер, дата, проведеність (`posted`, як у 1С),
позначка видалення, службові дати. Табличні частини — окремі таблиці зі
стандартними реквізитами рядка (ключ, номер рядка) і зв'язком із власником;
скоуп успадковують (§6).

**Проведення (М5).** Документ оголошує `registerMovements` — регістри, у які
пише. Рухи кожного оголошеного регістра дає одне з двох:

- **запит рухів** — іменований блок у `<Ім'я>.sql` документа. Компілятор
  обгортає його у функцію `RETURNS TABLE` з колонками рухів регістра;
  параметр — ключ документа. Запит — повний SQL: агрегація кількох ТЧ, вирази
  над рядком і шапкою, розіменування посилань, вид руху зі знака суми — усе, що
  не покриє жоден DSL;
- **конструктор рухів** — декларативний DSL прототипу
  (`packages/core/src/schemas/posting.ts`), опційний, для простих випадків.
  Компілятор перекладає його в такий самий запит, тож далі шлях один.

Сьогодні DSL перевіряється регулярними виразами в core, перекладається в
`packages/generator-pg/src/generate-posting.ts`, а семантично перевіряється в
`apps/web/src/hooks/use-model-validation.ts` і
`packages/core/src/posting-compatibility.ts`. У П2 розбір — T0, перевірка —
стадія 4, переклад у запит — T1.

**Оболонка проведення — від платформи.** post/unpost: блокування рядка
документа, перевірка статусу, перевірка права дії post/unpost (словник дій
виду, Р9), ідемпотентне видалення рухів цього реєстратора, вставка рухів із
функції запиту, позначка проведеності. Актор береться із сесії, а не з
параметра. Проведений документ незмінний (шапка й кожна ТЧ), видалити його не
можна. Модуль оболонку не пише й не перевизначає. П2 фіксує контракт оболонки в
моделі; генерація її SQL — П3.

**Регістр накопичення.** Таблиця рухів + таблиця підсумків, яку веде
згенерований тригер (платформна спека §4). Реєстратор — пара «тип + id» без FK:
регістр пишуть кілька видів документів. Виміри `NOT NULL`, тож ключ підсумків —
скоуп разом із вимірами; рядок підсумків, що став нульовим, видаляється.
Регістр залишків має вид руху (прихід/витрата), оборотний — ні. Ресурси —
`Integer` або `Numeric` (правило `AGENTS.md`).

**Регістр відомостей.** Періодичний чи ні, незалежний чи підлеглий
реєстратору — налаштування прототипу; запис — серверний патерн.

## 8. Компілятор

### 8.1 Реєстр видів

Кожен вид — один запис реєстру в T0: Zod-схема файлу, тека виду, порядок ключів
серіалізатора, стандартні реквізити з фізичними фактами, патерн запису, словник
дій, дозволені дочірні елементи (ТЧ, виміри, ресурси), чи можна на вид
посилатися, правила стадій 3–4. Кожне місце коду, яке сьогодні розгалужується за
видом, читає реєстр; новий вид — новий запис плюс тести. Сьогодні знання про
види розмазані між core, генератором, CLI і UI (приклади —
`packages/core/src/metadata-io.ts`, `packages/core/src/serialization.ts`,
`packages/core/src/find-references.ts`,
`packages/core/src/schemas/project-model.ts`); повний перелік повторів
перераховує
`grep -rn '"AccumulationRegister"' packages apps --include='*.ts' --include='*.tsx'`.

### 8.2 Стадії

Компілятор — чиста функція над мапою файлів «шлях → вміст»; читання диска — у
CLI. Так одна реалізація служить CLI, тестам і згодом studio (Р3). Стадії —
платформна спека §3.4; зміст П2:

1. **Файл.** Zod-валідація кожного файлу за схемою його виду.
2. **Ідентичність.** UUID присутні й унікальні; імена посилань резолвляться в
   UUID; дублікат імені в межах виду — помилка. Перейменування розпізнається за
   id при порівнянні знімків (порівняння — П3; П2 гарантує, що id є й
   стабільні).
3. **Модель.** Стандартні реквізити з виду; скоуп (колонки, успадкування,
   складені ключі); побудова фізичного знімка.
4. **Цілісність.** Посилання (ціль існує, на вид можна посилатися, `Ref` на
   `Table` — лише на одноколонковий uuid-ключ); правила скоупу (§6); регістри й
   рухи — перевірки, перенесені з `apps/web/src/hooks/use-model-validation.ts`
   і `packages/core/src/posting-compatibility.ts`; унікальність `physicalName` у
   PG-схемі; права — мінімум: словник дій кожного виду стає каталогом дій для
   майбутнього компілятора прав; кожен об'єкт має модуль-власника; ратчет
   (обидва — §8.6).
5. **Зв'язок із модулями.** Кожен ключ поведінки існує в `<Ім'я>.module.ts`
   (через згенерований тип і typecheck модуля); для кожного регістра з
   `registerMovements` є запит рухів у `<Ім'я>.sql` або конструктор; для кожного
   виду скоупу є функція множини.

Стадія 6 (план БД) — П3.

### 8.3 Вихід

**Скомпільований знімок** — детермінований (той самий вхід → побайтно той самий
знімок):

- логічна модель з резолвленими UUID;
- **фізичний знімок**: усі таблиці, колонки, типи, ключі, обмеження, індекси,
  енам-типи, коментарі — і похідні від видів, і описані в `Table`. Форма
  фізичного знімка — контракт T0, спільний для компілятора й читача каталогу
  (§9);
- SQL-одиниці: дослівні блоки `*.sql` і обгортки запитів рухів;
- каталог дій виду.

**Хеш моделі** — хеш канонічної серіалізації знімка; його звіряє П3 (платформна
спека §6.1).

### 8.4 Діагностика

Діагностика = файл + JSON-pointer + id правила + серйозність + підказка
(платформна спека §5). Тексти — у каталозі повідомлень CLI (uk/en, платформна
спека §9); проблеми Zod мапляться на діагностику з id правил. Компілятор
повертає всі діагностики прогону, а не першу. Прототипне кодування
повідомлень у рядку (`packages/core/src/validation-message.ts`) і рядкові шляхи
помилок UI зникають.

### 8.5 JSON Schema і кодоген

- **JSON Schema** на кожен вид файлу генерується з Zod (Zod 4 уміє це сам) і
  їде в пакеті; `$schema` у кожному файлі вказує на реальний файл схеми тієї ж
  версії (відносний шлях у встановлений пакет; проставляє `simetra fix`).
  Прототипні URL на неіснуючі файли зникають.
- **Кодоген** видає логічні TS-типи сутностей — для модулів
  (`defineModule<T>`) і API платформи. Фізичний тип `Database` — П3
  (платформна спека §6.5).

### 8.6 CLI, ратчет, межа модулів

- **CLI** — пакет `@simetra/cli` (платформна спека §3.2); прототипний пакет з
  тим самим ім'ям заморожено поза workspace (§11). Команди:
  - `simetra compile` — стадії 1–5, діагностика, ненульовий код при помилці,
    скомпільований знімок;
  - `simetra explain <об'єкт>` — скомпільована картина: похідні стандартні
    реквізити, скоуп і складені ключі, мапінг логічних імен на колонки, запити
    рухів;
  - `simetra fix` — механічні виправлення: відсутні UUID, `physicalName` для
    нових елементів, канонічна форма й порядок ключів, `$schema`.
- **Ратчет «поле декларації без споживача»** (платформна спека §5) у формі П2:
  кожне поле Zod-схем метамоделі читає щонайменше одна стадія компілятора чи
  побудова фізичного знімка; поле без споживача валить тест.
- **Межа модулів (Р15) — мінімум.** Кожен об'єкт має модуль-власника; за
  замовчуванням — єдиний модуль проєкту. Правило «модуль пише лише у власні
  об'єкти» стосується команд, тож його перевірка — П4, де команди з'являються.

### 8.7 Відкладено з П2

Vite-плагін — П4 (перший host-споживач); MCP-операції — П6 (ті самі операції,
що в конфігуратора). Обидва — лише інші двері до того самого компілятора.

## 9. Інтроспекція каталогу і зворотна генерація

**Читач каталогу** — ярус T2 `schema`, власна інтроспекція `pg_catalog`
(`information_schema` віддає лише видиме поточному з'єднанню). Нормалізовані
форми — з `pg_get_expr`, `pg_get_indexdef`, `pg_get_constraintdef`; ACL — через
`aclexplode` там, де потрібно (патерн —
`simplyCMS: packages/simplycms/test-harness/pg/introspect.mjs`). Результат —
фізичний знімок тієї самої форми, що в компілятора (§8.3).

**Зворотний генератор** зі знімка видає метадані `Table` (UUID призначено,
`physicalName` = поточні імена, логічні імена — перетворення фізичних за
правилом регістру §3) і енам-типи; функції, тригери, політики, в'юхи й гранти —
дослівно в `*.sql`. Клас об'єкта, якого модель не виражає, — гучна помилка
зворотної генерації, а не тиха втрата; на кожен клас, на якому інструменти
зворотної генерації вже ламалися (виразні й часткові індекси,
`NULLS NOT DISTINCT`, таблиці без PK, identity `ALWAYS`, FK на схему
провайдера), — негативний контроль.

**Критерій round-trip:** інтроспекція → зворотна генерація → компіляція →
скомпільований фізичний знімок ≡ інтроспектований знімок за таблицями,
колонками, типами, ключами, індексами, `CHECK`, FK, `DEFAULT` і коментарями.
Дослівні SQL-об'єкти проходять крізь ланцюжок текстом; їхню рівність каталогу
перевіряє каталожний гейт П3.

**Де проганяється:** на синтетичних схемах — тестами, що йдуть у CI (§10.4);
приватно — на schema-only копії схеми першого споживача, з виходами поза репо.

**Межа.** Це початок прийому (платформна спека §6.4); каталожний гейт,
планувальник, тінь і застосування — П3. Вибір інструмента **гейта** (pg-delta
чи власна інтроспекція) лишається за П0(б) і П3; тут власна інтроспекція
будує лише знімок.

## 10. Паперовий тест, синтетичний домен, середовище

### 10.1 Синтетичний домен

Живе в `examples/reference/metadata/`; референсний host П4 бере той самий
домен. Назви — українські заголовки, логічні імена — узагальнені англійські.
Проєкт оголошує два види скоупу: `org` (корінь — «Організації») і `user`
(корінь — користувач провайдера).

| Об'єкт | Вид і форма | Що доводить |
| --- | --- | --- |
| «Організації» (`Organization`) | довідник, корінь виду скоупу `org` | корінь скоупу |
| членство (`OrgMember`) | `Table` зі складеним PK і FK на `auth.users`; функція доступних id — у `*.sql` | прийнята таблиця без виду; контракт функції множини |
| «Валюти» (`Currency`) | довідник без скоупу | глобальний об'єкт; посилання скоуплене → глобальне |
| «Контрагенти» (`Counterparty`) | ієрархічний довідник, скоуп `org` | ієрархія |
| «Договори» (`Contract`) | підлеглий довідник, власник — «Контрагенти» | власник; складений FK у скоупі |
| «Налаштування користувача» (`UserSettings`) | `Table` на скоупі `user` | корінь «користувач провайдера»; явна скоуп-колонка `Table` |
| «Нарахування за послуги» (`ServiceAccrual`) | документ із двома ТЧ, рухи — запитами модуля | проведення; успадкування скоупу ТЧ |
| «Розрахунки з виконавцями» (`PerformerSettlements`) | регістр накопичення залишків із підсумками | тригерна форма; вид руху |
| «Доходи й витрати» (`IncomeExpenses`) | оборотний регістр накопичення | два регістри одного документа |
| «Ставки» (`Rates`) | періодичний регістр відомостей | період |
| перерахування й константа | по одному об'єкту | повний набір видів П2 |

Тести проганяють домен на двох тенантах (два значення `org`).

**Негативні тести компілятора** — кожен червоніє саме своїм правилом: відсутня
декларація скоупу; посилання з глобального на скоуплене; посилання між різними
видами скоупу без `crossScope`; оголошений регістр без запиту рухів; дубльований
UUID; зламане посилання за іменем.

### 10.2 Паперовий тест у П2 — що доводить

- **Структурна рівність.** Поруч із доменом лежить його «прийнята» форма —
  рукописний SQL таблиць документа, ТЧ і регістрів, яким його написав би
  застосунок без платформи (без частини стандартних реквізитів 1С). Він
  розгортається в тимчасову БД і інтроспектується (§9); скомпільований
  фізичний знімок метаданих видів 1С порівнюється з ним. Очікувана різниця —
  фікстура зі списком відсутніх стандартних реквізитів; будь-яка інша різниця
  валить тест.
- **Повнота рухів.** Для кожного регістра з `registerMovements` є запит рухів
  (стадія 5).
- **Поза П2.** Семантична рівність рухів і підсумків — проведення на тестових
  даних через згенеровану оболонку й DDL — приймальний тест П3 (§1).

### 10.3 Приватна звірка

Метадані документа першого споживача (найменший документ із рухами регістрів)
пишуться поза цим репо, у репо споживача. Їх компілюють і порівнюють з
інтроспектованою схемою локальної schema-only копії. Очікувана різниця — рівно
відсутні строгі стандартні реквізити 1С; вона ж — план міграції для П3. Виходи
звірки лишаються приватними.

### 10.4 Середовище

- **Локальний стек Simetra** — Supabase CLI (оновлений), конфігурація
  `supabase/config.toml` у репо без секретів, Postgres 17; мажорна версія
  збігається з копією схеми, з якою йде звірка. Застарілий локальний стек
  іншого проєкту власника прибирається (дозвіл власника), щоб не конфліктували
  порти.
- **CI** проганяє тести round-trip на синтетичних схемах проти сервіс-контейнера
  з образом `supabase/postgres`: у ньому є ролі й схеми провайдера, тож FK на
  `auth.users` і політики сховища перевірювані. У CI відсутність БД для таких
  тестів — червоне, а не пропуск.
- **Копія схеми першого споживача** відновлюється лише локально, в **окрему**
  БД; її файли й виходи живуть поза репо.

## 11. Порядок робіт

Кожен крок закінчується зеленими гейтами й окремим комітом; стадії компілятора
наростають разом із кроками 2–6.

0. **Середовище.** Локальний Supabase-стек і `supabase/config.toml`; сервіс
   `supabase/postgres` у CI для тестів з БД.
1. **Мінімальний П1.** Флагманський пакет `simetra` з теками ярусів і
   лінт-зонами з негативним тестом (платформна спека §3.1); `packages/core` →
   T0 `model`; прототипний рантайм видалено за платформною спекою §14;
   `apps/web`, прототипний CLI, `packages/generator-pg` і
   `packages/generator-api` заморожено поза workspace — виключено з
   `pnpm-workspace.yaml` або перенесено в теку поза ним, у git лишаються як
   референс. Кореневі гейти turbo їх не бачать.
2. **Ідентичність і файли.** UUID, логічні й фізичні імена, регістр імен,
   розкладка файлів, константи окремими об'єктами, видалення форм, посилання
   за іменем із резолвом у UUID.
3. **`Table` і типи.** Повний фізичний опис, розширена система типів.
4. **Реєстр видів** і строгі стандартні реквізити з фізичними фактами (перенос
   із генератора).
5. **Скоуп.** Види скоупу, обов'язкова декларація, успадкування, складені
   ключі, правила посилань.
6. **Документ, проведення, регістри.** Запит рухів і його обгортка,
   конструктор, контракт оболонки, регістри на тригерах.
7. **Компілятор.** Завершення стадій 1–5, діагностика з каталогом повідомлень,
   JSON Schema, кодоген логічних типів, `@simetra/cli` з `compile`/`explain`/
   `fix`; `validation-message.ts` видалено.
8. **Інтроспекція, зворотна генерація, round-trip** (§9).
9. **Синтетичний домен, паперовий тест, приватна звірка** (§10).

## 13. Поза межами П2

- **П3:** планувальник і фази, генерація DDL, RLS-шаблонів, тригерів
  (зокрема підсумків регістра й оболонки проведення) і грантів; каталожний
  гейт, тіньова БД, застосування, знімок у БД; кодоген `Database`; облік
  версій клієнтів; семантичний приймальний тест проведення.
- **П4:** команди, хости, подання, адаптери джерел, Vite-плагін, перевірка межі
  модулів для команд.
- **П6:** конфігуратор і MCP-операції.
- **Пізніше:** компілятор прав, вид «членство», вкладений скоуп, «моє», share,
  ролі, ієрархія видів скоупу, решта кандидатних видів, кастомні поля без
  деплою; доставка пакета (збірка, публікація, canary, пілот) — коли споживачу
  потрібен пакет із npm (платформна спека §12).

## 14. Відкриті питання

| Питання | Пропозиція |
| --- | --- |
| DSL конструктора: лишити граматику на регулярних виразах прототипу чи перейти на розбір в AST з позиціями помилок | розбір в AST у T0: діагностика з JSON-pointer у вираз, один розбір для перевірки й перекладу |
| Посилання в рядках конструктора (`doc.<реквізит>`, `row.<реквізит>`, ТЧ-джерело) — за логічним іменем чи за UUID | за іменем, як усі посилання в JSON; каскад перейменування покриває рядки |
| Імена тек видів (`catalogs`, `information-registers` прототипу чи літерал виду) і теки об'єкта (логічне ім'я PascalCase чи kebab-case прототипу) | тека виду — як у прототипі, тека й файли об'єкта — логічне ім'я |
| Замороженим пакетам ламається збірка проти нового core: чи мусить `generator-pg` компілюватися як референс; доля `packages/ui` (його споживачі видаляються або заморожуються) | референс для читання без компіляції; `packages/ui` заморожується разом з `apps/web` |
| Фізична форма перерахування (PG-енам, як дефолт прототипу, чи таблиця значень з UUID значення як ключем, як у 1С) і константи (своя таблиця чи спільна); у будь-якому разі вона — факт моделі, а не стратегія генератора | перерахування — PG-енам: прийнятий енам-тип тоді й є перерахуванням, без окремого оголошення, а оптимістичний патерн (§5) до нього не застосовується; константа — своя таблиця, як у 1С |
| Оборотний регістр: таблиця підсумків оборотів (платформна спека §4 читає обороти з підсумків) чи лише рухи (так трапляється в прийнятій схемі) | підсумки є — вид строгий; відсутня в прийнятій схемі таблиця підсумків — пункт плану міграції поряд зі стандартними реквізитами, і критерій М4 читається як «відсутні стандартні елементи виду» |
| Значення дискримінатора пари «тип + id» (реєстратор, поліморфний `Ref`): `physicalName` цілі, платформний енам чи UUID об'єкта — воно зберігається в даних і мусить пережити перейменування (Р5) | `physicalName` цілі: стабільний і читабельний у SQL |
