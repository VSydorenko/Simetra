# Права-2c2: адміністрування прав — дія, запобіжники, версії, журнал — план імплементації

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Статус: чернетка автора, на аудиті.
Архітектор задачі — сесія `consumer-reconciliation2`; якщо її немає — власник.

**Мета:** системні об'єкти прав («Ролі» з дельтою, «Призначення ролей») пише
лише дія адміністрування прав `administerRights`, а запобіжники §7 тримає база
й судить **результат транзакції**: приріст прав ролі чи призначення — лише в
межах прав актора на початок транзакції, кастомна роль з чинними
призначеннями не позначається на видалення, останній дієвий носій
`fullAccess` не зникає (крім видалення самого скоупу), запис без контексту
команди — лише в режимі обслуговування платформи. Користувач рядка членства й
платформні реквізити «Користувачів» дія команди не переписує. Кожна зміна прав
підвищує версію прав скоупу й лягає в журнал тією самою транзакцією. План
застосування відмовляє, коли зміна коду забирає останнього носія
`fullAccess`, і попереджає про дельти-сироти й призначення видалених
архетипів.

**Архітектура:**

- **T0** (`packages/simetra/src/model`): дія `administerRights`
  (`kinds/actions.ts`) лише на системних довідниках прав (`kinds/catalog.ts`);

  `rightsJournal`, `rightsTxActor`, `rightsTxPending`
  (`physical/snapshot.ts`).
- **T1** (`packages/simetra/src/compiler`):
  - `rights/admin-tables.ts` (новий) — платформні таблиці схеми `simetra`;
  - `rights/functions.ts` — функції даних `rights_full_access_roles`, `rights_role_grants`, функції версій;
  - `rights/guard-units.ts` (новий) — тригери знімка актора, черги, версій, журналу й відкладеної перевірки;
  - `rights/effects-units.ts` — незмінність користувача членства, самоприйняття, платформні реквізити «Користувачів».
- **T2** (`packages/simetra/src/schema`): зворотна генерація й промоція
  впізнають нові одиниці як платформні; `schema/apply/rights-sources.ts` (2d1)

- **Тести:** unit на деревах; один DB-опис у `simetra`; кейси двох сесій — у
  designer через `inTarget`.

## Global Constraints

- Усі обмеження планів Права-2a1, 2a2, 2b1, 2b2, 2d1 і 2c1 (розділи «Global Constraints») діють і тут.
- 🔴 `pnpm --filter <pkg> test <pattern>` — **без** `--` перед шаблоном.
- 🔴 Функції запобіжників, версій і журналу — `LANGUAGE plpgsql SECURITY DEFINER SET search_path = '' SET row_security = off` (як тригер ефектів, Р2b1-8), кваліфіковані відношення, `EXECUTE` — нікому; функції даних — `IMMUTABLE`, без `SECURITY DEFINER` і `EXECUTE` (Р2a1-14), крім явно названих у Р2c2-4 (`rights_role_grants` — `STABLE`) і Р2c2-11.
- 🔴 Контекст команди — лише через `simetra.command_current()` (Р2b1-2); режим обслуговування — лише через `RIGHTS_MAINTENANCE_SETTING` (T0) і `maintenanceSql(provider)` з умовою `session_user` (Р2c2-18); ідентичність транзакції — `txid_current()`; жодних інших GUC-прапорців, `pg_trigger_depth()` чи `current_user`.
- 🔴 Ефективні права ролі обчислюються **тим самим** генератором замикання, що `rights_mine` (`closurePass`, `compiler/rights/functions.ts`): друга реалізація замикання заборонена.
- 🔴 Відмова запобіжника — `RAISE EXCEPTION USING ERRCODE = '42501', MESSAGE = 'command.forbidden', DETAIL = '<код>'` з кодом із Р2c2-13, без даних рядка.
- Прийняті джерела запобіжники не охоплюють (§4.7, Р2d1-14).
- DB-тест — лише для того, що вирішує Postgres; SQL-текст — unit. Скіл `.agents/skills/writing-tests/SKILL.md` обов'язковий перед кожним кроком тестів.
- Між задачами гейти не червоні: зміна, що ламає тест, фікстуру чи згенеровану JSON Schema, і її правка — в одному коміті.
- Репо публічне: фікстури синтетичні.

| Р2c2-5 | **⊆ на COMMIT проти прав актора на початок транзакції** (архітектор, Р1). (1) **Знімок актора:** `BEFORE … FOR EACH STATEMENT` тригер на кожній таблиці системних довідників прав і довідників членства при першому записі транзакції **під контекстом команди** (немає рядка `simetra.rights_tx_actor` з `xid = txid_current()`) вставляє `rights_mine()` актора (`actor = current_user_id()`) у `simetra.rights_tx_actor` разом з ознакою «дієвий носій `fullAccess`» по рівнях (Р2c2-7) а кожен `AFTER STATEMENT` тригер, що ставить ключі (системні довідники прав і тригери `_members_*` довідників членства), ставить **усі** свої ключі **одним** оператором `INSERT … SELECT … ON CONFLICT …` разом із ключем `kind = 'actor'` (`key` — нульовий uuid; лише коли знімок цієї транзакції існує), щоб перевірка відбулася й прибрала знімок навіть у транзакції без інших ключів (зокрема лише зі змінами членства). **Прибирання:** кожна перевірка видаляє свій рядок черги, а та, після якої рядків черги цієї транзакції не лишилося, видаляє й знімок; порядок подій тоді не важливий — у `DEFERRED` (усі події на COMMIT) і в `IMMEDIATE` (події одного оператора `INSERT` — після нього, коли всі його ключі вже в черзі); наступний оператор під контекстом з іншим актором (`IS DISTINCT FROM`, актор буває `NULL`) у тій самій транзакції — `rights-context`. (2) **Черга:** негайні `AFTER … FOR EACH STATEMENT` тригери вставляють ключі зачеплених одиниць у `simetra.rights_tx_pending (xid, kind, key, scope_kind_id, scope, maintenance)` з `ON CONFLICT (xid, kind, scope_kind_id, key) DO UPDATE SET maintenance = rights_tx_pending.maintenance AND excluded.maintenance` — `kind` ∈ `actor`, `role` (кастомна роль; зміна призначення ставить і ключ `role` своєї `custom_role`, щоб `role-in-use` побачив призначення ролі, позначеної в цій чи в конкурентній транзакції), `assignment`, `holders` (скоуп, де оператор прибрав рядок форми носія, Р2c2-7). Злиття `ON CONFLICT DO UPDATE` нової події тригера не ставить, а відкладена подія бачить першу версію рядка, тож `rights_tx_check()` перечитує рядок черги за первинним ключем (`FOR UPDATE`) і з `NEW` бере лише ключ. `scope_kind_id` входить до ідентичності ключа: для `role` і `assignment` — `storage_id` таблиці рядка (вид скоупу довідника; контейнерні призначення лежать на рівні виду скоупу контейнера, `RightsLevelKey`; не `level_id` — це рівень ролі), для `holders` — вид скоупу (глобальний `holders`: і `key`, і `scope_kind_id` — нульовий uuid); глобальний рівень і `actor` — нульовий uuid, як у `rights_versions` (`storage_id` глобального рівня — `NULL`, а колонка `NOT NULL`); рядок шукається в таблиці рівня зберігання `scope_kind_id`; uuid різних рівнів і видів скоупу не мають спільної унікальності, тож без цього ключ одного виду поглинув би ключ іншого в `ON CONFLICT`. (3) **Перевірка:** `CREATE CONSTRAINT TRIGGER … AFTER INSERT ON simetra.rights_tx_pending DEFERRABLE INITIALLY DEFERRED FOR EACH ROW` — раз на ключ на COMMIT: «до» — стан на момент знімка актора: живі рядки, не змінені командою в цій транзакції, плюс перші образи «до» з журналу серед рядків `reason = 'command'` — рядок з найменшим `seq` на (`xid`, `relation`, `row_id`), Р2c2-12 (id рядків різних таблиць не мають спільної унікальності: id, що збігся з id рядка іншого системного об'єкта, не стає його образом) (записи режиму обслуговування раніше в транзакції — довірений шлях і входять у базу порівняння, як і знімок актора), «після» — живі рядки; приріст = права після − права до (Р2c2-4); кожен рядок приросту має покриватися рядком знімка актора того самого рівня з тим самим об'єктом і дією й обсягом `any` або тим самим обсягом і виміром (§4.4); рівень скоупу — `level = 'scope' AND scope = <скоуп>`; глобальний — `level = 'global'`; контейнерне призначення з контейнером C у скоупі S — рядки знімка рівня скоупу S або `level = 'container' AND container = C`. Виняток — актор був дієвим носієм `fullAccess` рівня **на початок транзакції** (знімок). `maintenance` — ⊆ пропускається. Відмова — `escalation`. Прибирання — за правилом пункту (1). Що є приростом: **роль** — права визначення ролі після мінус до (вставка — до порожньо; позначена на видалення — порожньо); **призначення** — права ролі рядка після мінус до, якщо суб'єкт і контейнер не змінилися й рядок до не був позначений, інакше — усі права ролі рядка після; видалення — порожньо; призначення кастомної ролі, позначеної на видалення, дає порожній приріст (позначена роль прав не дає, Р2a1-13; `rights_role_grants` позначки не знає, тож перевірка призначення бере її з рядка ролі). `role-in-use` дає лише перевірка ключа `role` (Р2c2-8). `SET CONSTRAINTS … IMMEDIATE` лише прискорює перевірку (на кінець оператора — строгіше), не вимикає; `ALTER TABLE … DISABLE TRIGGER` у SQL застосунку відмовляє `sql.statement-not-allowed` (Р2c1-2), а `simetra_command` не власник таблиць | §7: «перевіряється результат» — команда створює роль і її `deny`-рядки окремими операторами; знімок на початок командної частини транзакції не дає змінам, що надають права самому актору, покрити себе | спека прав §7 — «перевіряється результат транзакції проти прав актора на її початок (до першої зміни командою); перевірка — на COMMIT» (Задача 0) |

## Відомі обмеження

- Прийняті джерела: запобіжники, версії й журнал на них не діють (§4.7,
  Р2d1-14); на прийнятому членстві, на яке посилається `subject`, тригерів
  немає — його зміни не ставлять ключ `holders` у чергу.
- Через API режим обслуговування не вмикається (Р2c2-18): боргова функція з
  нелітеральним `set_config`, викликана через API, має `session_user` ролі
  входу. Лишається прямий вхід привілейованою роллю — він довірений. Серверна
  роль П4, через яку прийдуть недовірені запити, має увійти до
  `PROVIDER_LOGIN_ROLES`, коли з'явиться.
- `pg_stat_activity` локального стека показує Realtime-з'єднання під
  `supabase_admin`; це не доводить шлях конкретного користувацького запиту.
  Спільна роль включена до `PROVIDER_LOGIN_ROLES` за рішенням архітектора,
  щоб вона не давала режиму обслуговування. Задача 8 перевіряє відмову за
  цією роллю входу; перевірку повного шляху Realtime звітують окремо.
- Суперкористувач і `session_replication_role = replica` вимикають тригери —
  поза доменом довіри (як і для решти механізмів платформи).
- Недійсність користувача з боку провайдера (видалення облікового запису)
  може залишити скоуп без дієвого носія: заблокувати її неможливо, відновлення
  — команда глобального `fullAccess` (§7, П4). Те саме (`invalid` `false → true`
  без контексту) може зробити боргова `SECURITY DEFINER`-функція власника
  таблиць: відрізнити її в базі від тригера провайдера неможливо (Р2c2-10b).
- Відмова ⊆ і останнього носія приходить на COMMIT, а не на операторі; `SET CONSTRAINTS … IMMEDIATE` у застосунку переносить перевірку на кінець оператора, а знімок актора береться наново на кожному операторі (покриття — права актора перед оператором; «до» рядків, змінених раніше командою, лишається першим образом транзакції, тож чистий приріст — проти стану на початок командної частини), що строгіше; виявлення зміни актора (`rights-context`) тоді діє в межах оператора; один оператор з CTE, що пише дві таблиці прав, у цьому режимі дає хибну `escalation` (друга таблиця перевіряється вже без знімка) — fail-closed.
- SQL застосунку, що напряму пише в `simetra.rights_tx_pending`, `rights_tx_actor` чи журнал (не налаштування, а відношення), статично не перевіряється (Р2c1-6 судить налаштування): гранти на ці таблиці мають лише власник і функції платформи, тож шлях — лише боргова функція від власника схеми; кандидат на статичну перевірку відношень `simetra.*` у SQL застосунку.
- Команда прийняття запрошення — П4: справжній запрошений до прийняття прав у скоупі не має.
- `invalid` «Користувачів», змінений SQL власника поза провайдером, ключа `holders` не ставить (команда його не змінює, Р2c2-10).
- У скоупі, де дієвих носіїв уже 0 (недійсність від провайдера), будь-яка
  зміна прямого призначення з `fullAccess`, що лишає 0 носіїв, відмовляє
  `last-full-access` (Р2c2-22); відновлення — нове призначення (вставка ключа
  `holders` не ставить).
- Політики зберігання журналу немає.
- Ціну тригерів на великих операторах міряє бенчмарк 2d2.
- Перейменування функції ефектів довгої таблиці (Р2c2-20) доведено unit-тестом
  плану: двигун отримує нове ім'я; стару некеровану функцію pg-delta видаляє
  звичайним диффом, DB-тесту плану немає.

## Review Focus

1. **Самопризначення:** адміністратор прав призначає собі `OrgAdmin` чи додає `allow` до кастомної ролі, яку сам має, — `escalation` на COMMIT (покриття — знімок на початок транзакції). Тест — Задача 8 (`self-assign`, `self-held-role-delta`).
2. **Результат, а не оператор:** актор без повного архетипу створює кастомну роль «архетип мінус X» (вставка ролі, далі `deny`-рядки) однією транзакцією — проходить; без `deny` — `escalation`. Тест — Задача 8 (`create-with-deny`).
3. **Дві сесії знімають двох останніх носіїв:** рівно одна проходить, друга — `last-full-access` на COMMIT; у `REPEATABLE READ` — `40001`. Тест — Задача 8 (designer, `concurrent-last`).
4. **Видалення тенанта з `restrict`:** у режимі обслуговування — призначення, членство, далі корінь однією транзакцією — проходить. Тест — Задача 8 (`restrict-tenant-delete`).
5. **Членство й «Користувачі»:** учасник зі звичайним `update` вписує себе в чужий заповнений рядок членства — `effect`; чинний учасник «приймає» запрошений рядок — `23505` (UNIQUE членства «скоуп, користувач» відхиляє його раніше за тригер ефектів; умова «ще не учасник скоупу» лишається захистом у глибину, її тримає unit-мутація Задачі 6); дія `update` «Користувачів» змінює `invalid` — `effect`; видалення учасника без призначень командою — проходить. Тест — Задача 8 (`member-repoint`, `member-claim`, `member-delete`, `users-invalid`).
