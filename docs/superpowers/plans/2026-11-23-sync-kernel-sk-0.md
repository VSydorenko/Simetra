# План: SK-0 — шви спостереження й оракули ядра синхронізації (#357)

## 1. Заголовок

- **Статус:** чернетка на приймання; приймає архітекторка М4 (сесія
  `m4-sk-architect`). Виконує авторка плану, якщо архітекторка доручить.
- **Опори після X:** немає. Задачу 0 виконано в PR плану (коміт `cfb4eb26`):
  Додаток Б спеки ядра, правки §5.13, П4-B §12 і §13.
- **Спільні ресурси й заборони:** блок лише unit, стеків БД не потрібно. Не
  читати й не чіпати гілок призупинених робіт (`issue-115-b6-2`, D5-2). Не
  змінювати `AGENTS.md`, `CLAUDE.md`.
- **Лише CI:** повні рівні `unit`, `db`, `db-supabase`, `e2e` (усі `ci: true`
  у `.agents/kit.profile.json`). Жодна задача не закінчується повним
  локальним прогоном; локально — `run-tests unit --filter <файл>` чи
  `run-tests unit --changed`. Рівнів, яких CI не має, немає.

## 2. Мета / Архітектура / Спека

**Мета.** Кожне читання ядра даних T4 на `main` несе причину й ціль у
фізичній точці відправки; тести бачать цілі, вимоги й польоти через
діагностику, а не через поля `Subset`; оракули О1–О4 і три мутації SK-0
стоять як гейт для SK-1…SK-6. Поведінка `main` не змінюється.

**Архітектура.** Словник ядра синхронізації (причини, умови, види вимог,
види цілей, коди інвентаря) — дані у новій теці `sync/` пакета `packages/simetra/src/data/store`; SK-1 бере його без перейменувань.
Кожен шлях читання передає в `StoreSource.read` походження — причину, ціль,
код рядка Додатка Б; це поле стане польотом у SK-1. Подію `watchReads`
випускає точка, де запит дістає номер (`send` у `source.ts`). `sync()` — тимчасова проєкція стану `main` (поля `Subset`, позначки рядків, стан
служб `core.ts`, черги приймача) поруч з `inspectCore`; SK-3 замінить її
читанням `TargetState`.

**Спека.** [Спека ядра синхронізації](../specs/2026-11-23-t4-sync-kernel-design.md)
§3 (рядок SK-0), §4 (рядки `watchReads`/`sync()`, оракули), §5.2 (види
вимог), §5.3 (причини, умови, цільова таблиця), §5.13 (діагностика,
О1–О4, «Відомі прогалини `main`», мутації SK-0, правила тестів), §5.14
(рядок 1, «Було»), Додаток Б (інвентар). ADR-0098…ADR-0101. П4-B
`docs/superpowers/specs/2026-11-05-p4-b-client-data-design.md` §12 (бюджети,
модельний тест) — читати лише `doc … §12`.

## 3. Глобальні обмеження

- **Поведінка `main` не змінюється.** Жоден шлях не отримує, не втрачає й не
  відкладає читання; запити на дроті ті самі; знімки виглядів ті самі.
  Потрібна зміна поведінки — розвилка до архітекторки, а не частина SK-0.
- **Тести бюджетів не змінюються.** Множина — за тим, що тести стверджують, а
  не за назвами з П4-B §12: кожен файл `packages/simetra/src/data/**/__tests__/`,
  що рахує запити чи байти (`FakeSource.requests`, `fake.log`, `requestOf`,
  `expectBodyBudget`), крім двох модельних тестів (задача 5). Перевірка
  механічна: `git diff main -- <ці файли>` не додає, не прибирає й не змінює
  жодного рядка з `expect`; дозволено лише виклик спільного помічника
  збирача О1 і службове походження в прямих викликах `StoreSource.read`
  (Р1). Твердження О1 живуть у спільному помічнику поза цими файлами.
- **Послаблення оракула, перевірки чи допуску модельного тесту заради
  зеленого — розвилка** до архітекторки. Наявні перевірки модельних тестів
  лишаються, доки новий оракул не покриває їх строго; прибрати наявну
  перевірку — теж розвилка.
- Нова різниця інвентаря з цільовою таблицею §5.3, якої немає в §5.14, —
  рядок у списку «Різниці без рядка §5.14» Додатка Б і рядок у тілі PR
  (рішення архітекторки 2026-11-23); клітинок §5.3 не змінювати.
- Модуль `sync/` імпортує лише `epoch.ts`, `types.ts`, `defects.ts` і типи
  сесії (§5.1); проєкція стану `main` живе поза ним.
- Діагностика лише тестова: `inspectCore` не з'являється в публічних входах
  пакета (`packages/simetra/package.json` `exports`, `src/data/index.ts`).

## 4. Рішення

| # | Рішення | Вплив на спеку |
| --- | --- | --- |
| Р1 | **Походження читання.** `StoreSource.read(parts, origin)`: обов'язковий `origin` несе причину, ціль, код рядка Додатка Б і наявні `caller` та оренду запису. Читання ядра без походження не компілюється. SK-1 перетворює `origin` на `Flight` (§5.4) без зміни місць виклику. Внутрішні читання польоту (Додаток Б, «Спільне», п. 3) беруть походження з обгортки джерела, яку вже передають читачам (`tracked`, `gated` у `source.ts` і `readers.ts`). Тип `Batcher` (`batcher.ts`, нині `Omit<StoreSource, "lease">`) оголошується окремо: його `read` бере походження необов'язково, тож `batcher.test.ts` компілюється без змін; частина без походження дає подію без причини — О1 червоний. Прямі виклики `StoreSource.read` у тестах (`source.test.ts`, `withSleep` у `testing/fake-source.ts`) передають службовий код походження тестів — правка виклику, не очікувань. На затвердження | немає: §5.4 описує підпис SK-1, SK-0 — його попередник |
| Р2 | **Словник — дані.** Закриті переліки як `as const`-масиви з похідними типами в `sync/`: причини й умови §5.3, види вимог §5.2, види цілей §5.4 (вигляд, сторінка, ключі, службова частина), коди рядків Додатка Б. Неназвана причина чи код не компілюються | немає |
| Р3 | **Точка події.** `watchReads` випускає `send` у `source.ts` у мить, коли запит дістає номер (`requestOfItem`), по одній події на кожну живу частину запиту: походження + номер запиту, той самий, що поверне `requestOf`. Походження йде за слотом, а не за тотожністю частини: `dispatch` (і для вставленої частини `rights`, рядок S3) → виклик збирача → масив походжень за слотами в опціях `CoreSource.read` (`ReadOptions`, внутрішній тип `source.ts`) → `group`/`send`. Копії частин у `dispatch` (`withLiveInclude`, `rights` з `known`) і в `source.ts` `read` (адаптер без `capabilities.include` прибирає `include`) слоту не змінюють. У `CorePart`, дріт і `log` походження не потрапляє | немає |
| Р4 | **Черга пам'ятає причину.** Наступне завантаження (`trailing`, M6) і хвіст системного перечитування (`tailOptions`, R15) зберігають походження виклику, що поставив чергу; коли черга зливає кілька викликів — першого. Це лише запис для діагностики: момент і зміст читання не змінюються | немає |
| Р5 | **`sync()` на `main`.** Цілі: вигляд (і сторінка — польотом свого вигляду), рядок з позначкою свіжості, службові «знімок прав» і «версія каталогу». На ціль: вимоги (вид §5.2, епоха й бюджет — де `main` їх має), польоти (причина, вид польоту, епоха старту), черга, доказ (вигляд — `okReadEpoch`; служба — епоха відправки прийнятої відповіді), строк, умова відкладення чи причина відмови. Поля, якого `main` не має, у типі немає. Дозволено лише облік для діагностики: записати час пробудження наявного таймера (ланцюг повторів приймача, строк хвилі), не змінюючи його | §5.13 «`sync()`» — доповнено «доказ» і правило відсутнього поля (`cfb4eb26`) |
| Р6 | **О2 судить за незалежними спостереженнями, а не за прапорцями `main`.** `sync()` каже, що обіцяно; дотримання обіцянки перевіряє журнал подій і фейкове джерело. (а) У спокої (немає запитів фейкового джерела без відповіді й мікрозадач; таймери можуть чекати) кожна вимога має обіцянку чи названу умову, і обіцянку дотримано: політ — запит фейкового джерела без відповіді, подія якого називає ціль; черга — подія для цілі після осідання польоту попереду; строк — подія для цілі не пізніше строку, коли модель рухає годинник. (б) Вимога зникає лише разом з ціллю або в кроці, де осів запит, подія якого називає ціль, має вид польоту з колонки «Чим виконується» §5.2 і випущена, коли вимога вже стояла (слухач подій знімає вимоги цілі з `sync()` у мить події). Половина (б) червонить мутацію «сторінка знімає чужу вимогу». Лічильник станів спокою з ≥ 1 вимогою, які О2 справді оцінив, > 0 на кожен прогін властивості й на кожен прогін самотесту SK-0 — інакше О2 порожній | §5.13 О2 — доповнено (б) (`cfb4eb26`) |
| Р7 | **Межа кожного винятку — час моделі.** Виняток О2 з «Відомих прогалин `main`» діє, лише доки нема умови, за якої `main` сам читає: видимого тримача на видимій вкладці (рядки 3, 4, 5, 12 §5.14), рядків у сховищі для знімка прав (рядок 6); з нею читання стартує не пізніше строку того шляху (інтервал тримача плюс пауза збоїв, строк знімка). Без такої умови виняток названо станом, який його тримає (немає видимого тримача, вкладку приховано, немає інтересу), а не умовою §5.3: `target-invisible` до рядків не застосовується. Виняток О4 (рядок 1 §5.14, «Було») — лише запит з кодом рядка Додатка Б цього переліку, після спостереженої події-причини, не пізніше власної затримки шляху (0 чи пауза відкинутих) і не частіше за події. Виняток, межі якого не вдається виразити, — розвилка, а не допуск | немає: §5.13, правила тестів |
| Р8 | **Тест-страж: `Subset` у модельних тестах непрозорий.** У `model.test.ts`, `receiver-model.test.ts` і помічниках, які вони імпортують з `__tests__/`, значення типу `Subset` чи `ReaderTarget` можна лише брати ключем `Map`/`Set`/`WeakMap`, порівнювати за тотожністю й читати поля з дозвільного переліку не-свіжості; передати його у функцію, оголошену поза `__tests__` (зокрема `requirementPending`, `settleRequirement`), розширити до іншого типу (структурний псевдонім), розгорнути (`...`, `Object.entries`, `JSON.stringify`) чи прочитати індексом з нелітеральним ключем — червоне. Кожна властивість `Subset` і `ReaderTarget` стоїть або в дозвільному переліку, або в забороненому, тож нове поле червонить стража, доки його не віднесено. Самотест `inlineProgram` — на кожну форму, зокрема псевдонім і виклик помічника. Виняток зі стража — розвилка. Заборонений перелік — поля, що §5.6 відносить до стану цілі: вимоги й входи перевірки (`unconfirmedSince`, `answerRejected`, `readRevision`, `readStart`, `sectionRead`, `checkQueued`, `checkHeld`, `recheck`, `hydrated`), доказ (`okReadEpoch`), польоти (`gen`, `flight`, `flightEpoch`, `rereadEpochs`, `trailing`, `paging`, `rereadTail`, `rereadWaiters`, `rereads`), строк (`refreshedAt`, `failures`, `failedAt`), видимість (`visible`, `listeners`), ревізію (`dirty`) і `needsRefresh`. Позначки рядків у сховищі (`stale`) лишаються в оракулах правил сховища П4-B §6.2 до SK-3. На затвердження | немає: рядок SK-0 §3 називає поля `Subset` |
| Р9 | **О3 — нова фаза з межею за причиною.** Після випадкових кроків: вкладка видима, без `refresh()` і `revalidate`, плин часу моделі; кожен видимий вигляд показує правду фейкового сервера. Межу рахує модель з лімітів прогону за причиною зміни: зміна, про яку клієнт дізнається подією каналу (приєднання, сигнал), — від події, за вікном її шляху (джитер приєднання, пачка приймача) плюс паузи; лише зміна без події каналу — з інтервалом. Профіль з мутацією «хвиля приєднання не читає» бере `revalidateIntervalMs` набагато більший за `REJOIN_JITTER_MS`, щоб такт не підміняв хвилю. Наявна фаза зі збіжністю після ручного оновлення лишається | немає |
| Р10 | **Покриття інвентаря.** Збирач О1 підключено до спільних помічників ядра модельних тестів і тестів бюджетів; кожен запит їхніх прогонів має подію з кодом з переліку Р2. Окремий тест (`*.docs.test.ts`) звіряє перелік кодів у коді з колонкою «Код» Додатка Б в обидва боки | §5.13 `watchReads` — доповнено `site` (`cfb4eb26`) |
| Р11 | **`watchReads` — кілька слухачів**, виклик повертає відписку; інші `watch…` лишаються як є | немає |

| Інваріант | Тест, що червоніє | Мутація словами |

| Оракул не зеленіє порожнім | самотест кожного оракула: О1 — подію загублено (слухач пропускає одну) → червоний; О2 — вимога без обіцянки, складена в чистій функції оракула → червоний, і лічильник оцінених станів спокою з вимогою > 0 на прогін (Р6); О3 — фейковий сервер змінив рядок після останнього читання й без каналу → червоний; О4 — запит у спокої з кодом поза винятками → червоний. Порожній журнал подій при непорожньому журналі фейкового джерела — червоний | оракул, що рахує лише події й мовчить, коли їх нуль |

## 8. Задачі

Кожна задача — після попередньої. Команди: `run-tests unit --filter <файл>`
для названих файлів і `run-tests unit --changed` наприкінці задачі.

**Задача 1. Словник і походження читання.**
Файли: нова тека `store/sync/`; `source.ts` (`StoreSource`, `tracked`,
читачі), `core.ts` (`source`, `dispatch`, `startVersion`, `requestRights`,
`fireWave`, `reconcile`, `resume`, `runDue`, `runTail`, `narrow`,
`rereadBarred`, `readRequirement`, `readHydrated`), `subsets.ts` (`load`,
`loadMore`, `check`), `writer.ts` (`revalidateViews`, `singleFlight`,
`tailPass`, `revalidateHolders`, `rereadKey`), `receiver.ts` (`run`,
`startJob`, `scheduleRetry`), `readers.ts`, `window.ts`, `include.ts`,
`batcher.ts` (власний тип `Batcher`, Р1), `testing/fake-source.ts`
(`withSleep`), `__tests__/source.test.ts` (службове походження в прямих
викликах).
Готово, коли: кожен рядок Додатка Б передає своє походження (Р1); M6 і R15
