# designer-1 — `@simetra/designer`: каталог інструментів, режими CLI й MCP, адаптер двигуна схеми: план імплементації

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Мета:** перетворити `@simetra/cli` на `@simetra/designer` — один каталог
інструментів, над яким командний рядок і MCP є тонкими режимами; винести
адаптер pg-delta з рантайм-пакета `simetra`; покласти скіл споживача в пакет;
привести канон документації до спеки designer.

**Архітектура:** операції лишаються чистими функціями T1/T2 флагмана. У
`packages/designer/src/tools/` живе каталог: запис на інструмент (ім'я, опис,
T1-схема входу, ефект, руйнівність, обробник) і одна функція `invoke`, що
перевіряє вхід, дозволи й підтвердження, ставить виклик у чергу теки й пише
зміни через `writeChanges`. MCP (`src/mcp/`) і командний рядок (`src/cli/`)
лише перекладають свій транспорт у `invoke` і назад. Адаптер pg-delta й
читачі бази переїжджають у `packages/designer/src/schema-engine/`; у T2
лишаються порт, чисті факти й звірка.

**Технології:** TypeScript 7, Vitest 5, citty **0.2.2**,
`@modelcontextprotocol/server` **2.2.0**, tsx **4.23.15**, `pg` **8.23.1**,
`@supabase/pg-delta` **1.0.0-alpha.56**,
`@tanstack/intent` **0.5.0** (лише `pnpm dlx`, не залежність).

**Спека:** [спека designer](../specs/2026-10-02-simetra-designer-design.md)
(Д1–Д5, §3.1–§3.3, §4.1, §4.4, §5.1–§5.3 п.1); контекст —
[спека П2](../specs/2026-09-28-p2-metamodel-compiler-design.md) §8.6, §14;
[платформна спека](../specs/2026-09-24-simetra-platform-design.md) §3.1–§3.2,
§10, §11, §14.

**Передумова:** E2a приземлено (так і є). Перед стартом — `orient --plan`
цього файлу. Цей план іде **до E2b** (спека §5.3). `pnpm-lock.yaml`, ROADMAP і
спеку П2 §14 не править паралельно інша сесія.

**Поза планом (спека §5.3 п.2–3, §3.4):** студія, `simetra init`, симлінки

## Рішення плану

Рішення 1–7 ухвалені головним архітектором designer (сесія
`simetra-designer-spec`) 2026-10-02; рішення 8 — власником; рішення 9–13
ухвалені головним архітектором designer після рев'ю 2026-10-02.

1. **Одне ім'я інструмента на всі режими:** `compile`, `explain`, `fix`,
   `create`, `add`, `rename`, `delete`. MCP-імена `create_object` і
   `add_element` зникають без аліасів — передреліз, без шимів.
   *Чому:* каталог — єдине джерело правди; два імена одного інструмента — дві
   точки правди для скілів і агентів.
2. **Вхід мутацій у командному рядку — JSON:** позиційний аргумент,
   `--input '<json>'` або `-` (stdin), розбір **схемою входу каталогу**;
   помилка розбору — код 2 і Zod-шлях у повідомленні. `--dry-run` є в кожного
   інструмента запису, `--yes` — лише в руйнівних; обидва виводяться з ознак
   каталогу. Інструменти читання зберігають ергономічні аргументи
   (`explain <Kind>.<Name> [dir]`, `compile [dirs...]`) — це представлення
   над тим самим входом каталогу, не друга схема; тест доводить відображення.
   *Чому:* схеми вкладені (`target.element[]`, `data`) — прапорці з них
   виводяться погано, а друга схема розійшлася б із першою.
3. **`fix` — інструмент запису і в MCP** (з `dryRun`). *Чому:* кожен
   інструмент каталогу доступний у кожному режимі.
4. **Межа Д5: до designer переїжджає все, що виконує SQL над базою або
   торкається pg-delta; чиста логіка й факти лишаються в T2.** Переїжджають
   `engine/pg-delta/*` і читачі `readCensus`, `readUnmodeledProperties`,
   `readUnpopulatedViews`, `readExtensionComments` разом із типом `Queryable`
   і SQL-текстом перепису. Лишаються в T2 чисті функції перепису
   (`reconcileCensus`, `unmodeledClasses`, `censusDiagnostics`) з їхніми
   типами; увесь `desired.ts` (`compareWithDesired`, `engineScope`,
   внутрішня `outOfScopeDiagnostics`); `port.ts` з контрактом порту, уточненим
   під час виконання E2a (тризначна `transactionality`, `diagnostics` у
   статусі `loaded`, коди `engine.*`) — без копії в designer; `privileges.ts`;
   `provider/supabase.ts`. Дані поверхні пресетів додасть сюди E2b — designer-1
   цього боргу E2a не закриває. **Тести коду, що лишається в T2, лишаються в
   `packages/simetra`** — інакше зміна `desired.ts` не червоніла б у пакеті,
   де він живе; designer отримує лише тести адаптера, читачів і корпусну
   DB-звірку зі справжнім двигуном.
   Чого переміщеному коду бракує з T2 — свідомо експортується з
   `simetra/schema`, без глибоких імпортів. Інваріант із тестом: продакшн-
   вихідники `simetra` не імпортують `pg` чи `@supabase/pg-delta` навіть як
   `import type`. *Чому:* Д1 — рантайм чистий; провайдерний профіль потрібен
   звірці (`desired.ts`), тож він — факт T2.
5. **`simetra compile --all [--staged]`** — представлення командного рядка,
   не вхід каталогу (як `--out`). `--all` шукає
   `git ls-files -z -- "*metadata/project.meta.json"` (pathspec `*`
   перетинає `/`, тож знаходить і кореневу `metadata/`); поза git-репо —
   обхід ФС від cwd з пропуском `node_modules` і `.git`. `--all` разом із
   явними теками — код 2. `--staged` поза git-репо — код 2 з поясненням.
   `scripts/check-metadata.mjs` видаляється. *Чому:* споживач отримує ті самі
   двері без копіювання скрипта (спека §4.4).
6. **Гейт розміру `tools/list`:** довжина `JSON.stringify(tools)` (описи +
   `inputSchema`) не перевищує поріг = виміряний розмір у цьому плані + 20 %,
   число записується в тест константою. Інструменти запису видимі в обох
   режимах, тож список один — перевірка одна. Повідомлення падіння каже, що
   ліміт навмисний і підняти його — рішення з рев'ю. *Чому:* набір не
   розпухає непомітно (спека §3.2).
7. **Лінт-зона студії додається вже зараз:** TanStack Start заборонено в
   `packages/designer` поза `src/studio`; негативний тест поряд. *Чому:*
   правило стоїть до появи студії, а не наздоганяє її.
8. **Блок Intent в `AGENTS.md` — дослівно за документацією Intent:**
   `pnpm dlx @tanstack/intent@0.5.0 install`, блок лишається таким, як його
   пише команда. Скіли репо агенти знаходять автодискавері `.agents/skills`
   (Claude Code — через `.claude/skills`).
9. **Ефект інструмента — `"read" | "files"`.** `--allow-write` вмикає лише
   `"files"`. Дії над базою (П3) — новий ефект із власним дозволом і
   підтвердженням; `permits` розбирає ефекти вичерпним `switch`, тож новий
   ефект не стане дозволеним мовчки. Каталог designer-1 не має жодного
   інструмента, що звертається до бази.
10. **Пояснення «як увімкнути запис» — одне джерело:** `writeAccessHint()` у
    каталозі; з нього беруться і `instructions` MCP-сервера, і текст `isError`
    виклику запису в режимі лише читання. Тест доводить, що прапорець у
    фрагменті `args` — справжній прапорець команди `mcp`.
11. **Резолв шляхів через `node_modules/<пакет>`** (спека §4.2): одна функція
    `installedPackageDir(fromDir, pkg)` іде вгору від теки до
    `node_modules/<pkg>/package.json` і повертає шлях **без realpath**.
    `$schema` у `fix`/`create`/`add` будується через неї; `init` (П0 (а))
    перевикористає її. Не знайдено — помилка використання з поясненням
    (код 2 / `isError`). Щоб у цьому репо `node_modules/simetra` існував у
    корені, коренева `package.json` отримує `"simetra": "workspace:*"` у
    `devDependencies`. Закриває борг `$schema` спеки П2 §14. Тести, що пишуть
    у тимчасову копію домену, створюють її через один помічник
    `tmpProject()` із симлінком `node_modules/simetra` → `packages/simetra`;
    без нього над `os.tmpdir()` немає пакета й кожен запис став би відмовою.
12. **Тести адаптера в designer спираються на фікстури `simetra` через одну
    точку** `packages/simetra/test/support.ts` (реекспорт фікстур і
    з'єднання з тестовою базою), відносним імпортом лише з тестів designer.
    Умови: імпортувати її може лише `packages/designer/**/__tests__/**` (лінт-
    правило designer забороняє шлях у продакшн-вихідниках); `test/` не входить
    у `files`/`exports` `simetra`; `support.ts` лише реекспортує, без логіки.
    *Чому:* фікстури — спільні для звірки T2 і адаптера; копія розійшлась би.
13. **Черга викликів — на теку, у каталозі** (`queueFor(dir)`), а не в
    MCP-адаптері: студія (П6) обслуговуватиме UI й MCP в одному процесі, і
    їхні записи мусять стояти в одній черзі.

## Уточнення під час виконання

Рішення консультанта плану (сесія `simetra-designer-plan`) 2026-10-02:

- **Перегляд руйнівної зміни без підтвердження.** `invoke` відмовляє з
  `unconfirmed` лише за умови `destructive && !dryRun && !confirmed`; порядок
  перевірок не змінюється. *Чому:* dry-run нічого не пише, тож підтвердження
  там нічого не захищає, а агентові перегляд потрібен саме до `confirm`. Опис
  `delete` не змінюється. *Тести:* `invoke` — `delete` з `dryRun` без
  `confirmed` повертає `changes` і `written: false`; MCP — `delete
  {dryRun: true}` без `confirm` не `isError`, диск без змін; CLI — `delete
  --dry-run` без `--yes` — код 0, нічого не записано. Наявні тести «без
  підтвердження нічого не змінено» (без dry-run) лишаються. Умови архітектора
  (`simetra-designer-spec`): dry-run руйнівного — не помилка (`isError:
  false`, код 0), текст змін — «would delete …»; тести закріплюють обидва боки
  — dry-run без підтвердження перелічує зміни при побайтово незмінному диску,
  без dry-run і без підтвердження — `unconfirmed` (код 2 / `isError`);
  `permits` лишається першим — у режимі лише читання dry-run інструмента
  запису дає `write-disabled`.
- **Помилки використання — `UsageError`.** Один клас у
  `packages/designer/src/io/usage-error.ts`; кидають його `readMetadataDir`
  (ENOENT/ENOTDIR теки → `metadata directory not found: <dir>`),
  `writeChanges` (шлях поза текою) і `installedPackageDir` (Task 7). `invoke`
  ловить лише `UsageError` → `refusal { reason: "refused", message }`; решта
  винятків летить далі (CLI — код 2 через `main.ts`, MCP — помилка виклику
  SDK). *Чому:* баг не маскується під відмову. *Тести:* неіснуюча тека →
  `refused` з цим повідомленням; тести шляху поза текою в `writeChanges`
  перевіряють `UsageError`. Шляхи, що є лише в CLI, кидають `UsageError` і
  дають код 2 для кожної очікуваної помилки використання чи вводу-виводу:
  `--staged` поза git, `--all` разом з явними теками, відсутня батьківська
  тека для `--out`. Голий `Error` не ловиться ніде.
- `written` — `true` лише коли змін більше нуля.
- **Цілі мутацій — `z.discriminatedUnion("kind", …)`.** `elementTarget` і
  `containerTarget` у `packages/simetra/src/compiler/operations/inputs.ts`
  стають дискримінованими об'єднаннями. *Чому:* звичайний `z.union` дає Zod-шлях
  лише `target`, а Review Focus п.3 вимагає `target.kind`. Це зміна T1-схеми
  входу без зміни семантики (JSON Schema — `oneOf` замість `anyOf`); `invoke`
  нічого не розгортає. *Тести:* у `simetra` — невідомий `kind` дає шлях
  `["target","kind"]` для `renameInput` і `addElementInput`; у CLI —
  `invalid input exits 2 with the zod path` перевіряє `target.kind`. Умови
  архітектора: тест у `simetra` закріплює три шляхи — невідомий `kind` →
  `["target","kind"]`, `{kind: "Project"}` без `element` в `elementTarget` →
  `["target","element"]`, вид об'єкта без `name` → `["target","name"]`;
  окремий тест — `metadataKindSchema` не містить `"Project"` (інакше майбутній
  вид із цим ім'ям мовчки зламає дискримінатор); MCP `inputSchema` з `oneOf`
  приймають сервер SDK і in-memory клієнт `mcp.test.ts`.

## Global Constraints

- Мова: коментарі коду — українською й пояснюють **чому**; описи інструментів,
  повідомлення CLI/MCP, скіл споживача, JSDoc експортованого API — англійською.

  будь-яких трейлерів.

- Залежності — точні піни з розділу «Технології»; `pnpm install` після кожної

  документів — `python3 scripts/check-doc-anchors.py`.
- Гейти перед кожним комітом задачі: `pnpm --filter <pkg> typecheck`, `lint`,

  ```ts
  type Effect = "read" | "files"
  interface Tool<I extends z.ZodType = z.ZodType, D = unknown> {
    name: ToolName
    description: string          // англійською; MCP і `--help` беруть його звідси

    destructive: boolean

  }
  // `run` лише читає теку й викликає операцію; запис робить `invoke`.
  interface RunOutcome<D> { ok: boolean; changes: FileChange[]; diagnostics: Diagnostic[]; data?: D; refusal?: string }
  type RefusalReason = "invalid-input" | "write-disabled" | "unconfirmed" | "refused"
  interface ToolResult<D = unknown> {
    ok: boolean
    written: boolean
    changes: { path: string; deleted: boolean }[]
    diagnostics: Diagnostic[]
    data?: D
    refusal?: { reason: RefusalReason; message: string }
  }
  interface InvokeOptions { dir: string; allowWrite: boolean; dryRun: boolean; confirmed: boolean }
  function invoke<D>(tool: Tool<z.ZodType, D>, input: unknown, o: InvokeOptions): Promise<ToolResult<D>>
  function permits(tool: Tool, o: { allowWrite: boolean }): boolean   // вичерпний switch по Effect
  const TOOLS: readonly Tool[]
  function toolByName(name: string): Tool | undefined
  function queueFor(dir: string): <T>(task: () => Promise<T>) => Promise<T>   // ключ — path.resolve(dir)
  const ALLOW_WRITE_FLAG = "--allow-write"
  function writeAccessHint(launchArgs?: readonly string[]): string
    // англійською; JSON-фрагмент `"args": [...]` = справжній argv запуску сервера (без node/скрипта) + "--allow-write";
    // без launchArgs — загальна форма ["simetra", "mcp", "--allow-write"]
  function tmpProject(): Promise<{ root: string; dir: string; dispose(): Promise<void> }>
    // тестовий помічник: tmp-тека з копією examples/reference/metadata у `dir` і симлінком
    // root/node_modules/simetra → packages/simetra (рішення 11); його беруть усі тести запису
  function compileArtifacts(model: CompiledModel): FileChange[]   // snapshot.json, desired-state.sql, entities.d.ts
  ```
