**Goal:** зміна «колонка стає `NOT NULL`» на таблиці з рядками
застосовується, а не падає на кроці. Якщо в бажаної колонки є default, план
сам заповнює наявні `NULL` цим default у тій самій транзакції, перед
`SET NOT NULL`. Якщо default немає, а `NULL` є, план відмовляє заздалегідь
кодом з таблицею, колонкою й кількістю рядків. План показує, скільки рядків
заповнюється.

**Architecture:** T2 планувальник (`schema/apply/plan.ts`) знаходить кожен
крок двигуна з `AT_SetNotNull` на наявній таблиці. Він рахує `NULL` цієї
колонки в цілі. Залежно від default бажаної колонки план або вставляє крок
заповнення (`origin: "backfill"`, клас `dataStep`) безпосередньо перед цим
кроком, або відмовляє. Раннер (`execute.ts`) виконує кроки заповнення в
блоці двигуна, у порядку плану, під преамбулою двигуна. Той самий підрахунок
захищає `ADD COLUMN … NOT NULL` без default на таблиці з рядками.

**Tech Stack:** TypeScript 7, Zod, Vitest, libpg-query (дерево розбору
кроків), Postgres 17, адаптер pg-delta (`@simetrajs/designer`).

**Spec:** платформна спека §6.2 п. 4 («Межа доказу»), §6.6;
[спека промоції](../specs/2026-10-06-promotion-design.md) §7.2 («Порядок
транзакції»), §8 (класи кроків), §9.7. Правила тестів — скіл
`writing-tests`.

## Рішення

| № | Рішення | Вплив на спеку |
| --- | --- | --- |
| Р1 | **Місце кроку — новий `origin: "backfill"` у блоці двигуна.** Крок заповнення стоїть безпосередньо перед кроком двигуна, що містить `AT_SetNotNull` для цієї колонки. Раннер виконує блок двигуна як кроки `engine` і `backfill` у порядку плану, під преамбулою двигуна. Перевірка порядку походжень у раннері (`ORIGIN_ORDER`) трактує `backfill` як ранг `engine`. Альтернатива «крок у фазі intent» відкинута. Тоді крок ішов би до `SET DEFAULT` і до зміни типу колонки, і довелося б копіювати текст виразу default. Цей текст залежить від `search_path` під час видобування | промоція §7.2 «Порядок транзакції»: кроки заповнення — у блоці двигуна (задача 0) |
| Р2 | **SQL кроку — `UPDATE <схема>.<таблиця> SET <колонка> = DEFAULT WHERE <колонка> IS NULL`.** `DEFAULT` бере справжній default колонки на момент кроку. Текст виразу не копіюється, тож немає залежності від `search_path` і від deparse. Об'ємні (`now()`, `gen_random_uuid()`) рахуються по рядку, як для нового рядка. Передумова: перед кроком default колонки вже дорівнює бажаному. Тобто або живий default збігається з бажаним і жоден крок його не змінює, або раніше в плані йде крок `SET DEFAULT` цієї колонки. Інакше план відмовляє `plan.backfill-order`: це дефект порядку адаптера, а не помилка споживача. Порядок дій pg-delta (`SET DEFAULT` відносно `SET NOT NULL`) задача 1 доводить DB-тестом | платформна спека §6.6: правило заповнення (задача 0) |
| Р3 | **Клас `dataStep`; дозвіл — лише на прийнятій таблиці.** Жодне значення не втрачається: змінюються лише `NULL`. На таблиці, яку створила платформа, дозволу немає: план показує крок і кількість рядків. Така таблиця — таблиця виду в `model.physical.tables` бажаного стану, що не є одиницею промоції цього плану. На прийнятій таблиці потрібен дозвіл за id кроку: там дані споживача, і ними користуються застосунки поза платформою. Прийнята — борг `CustomTable`, таблиця SQL-модуля, таблиця одиниці промоції. Невідоме походження — прийнята. `requiredPermissions` бере такі кроки разом із `destructive` і `relaxation`. Ознака «потребує дозволу» — поле кроку під `planHash`, а не повторний висновок раннера. Зміна стандартного реквізиту платформою прийнятих таблиць не торкається, тож пункту дозволу на кожну таблицю виду не дає | §6.6: дозвіл на заповнення прийнятої таблиці; промоція §8: `dataStep` охоплює заповнення (задача 0) |
| Р4 | **Тригери: платформні ввімкнені, тригери користувача вимкнені на час кроку.** Платформні — тригери механіки: версія за `GREATEST(nextval, version + 1)` і `updated_at` (B1e), носії прав. Їх визначає перелік одиниць механіки компілятора (`compiler/mechanics-units.ts`), а не префікс імені. Решта не внутрішніх ввімкнених тригерів таблиці (підписки, тригери SQL-модулів, прийняті) вимикаються через поле кроку `triggers` з B1e. Раннер звіряє їх із живими перед вимкненням і вмикає після кроку. Внутрішні тригери FK лишаються. Причина: масове заповнення — технічна зміна схеми, а не подія предметної області. Тригери підписок дали б лавину побічних ефектів | промоція §7.2: тригери кроку заповнення (задача 0) |
| Р5 | **Підрахунок `NULL` на плані.** Для кожного кроку з `AT_SetNotNull` на таблиці, яка вже є в цілі, план читає `count(*) … WHERE <колонка> IS NULL` у rollback-транзакції reader (`dbs.reader.transaction`, як `readOwners`). Для `ADD COLUMN … NOT NULL` без `DEFAULT` на наявній таблиці план рахує `count(*)` таблиці. Таблицю, яку план створює, план не рахує. Підрахунок — під `row_security = off`, бо RLS не має ховати рядки від застосування | платформна спека §6.2 п. 4: план читає кількість порушень (задача 0) |
| Р6 | **Відмова без default.** Якщо бажана колонка без `default` (і без `identity`/`generated`), а `NULL` > 0, план відмовляє `plan.not-null-violation` з `table`, `column`, `rows`. Підказка: дати реквізиту `defaultValue` або заповнити дані до застосування. Те саме для `ADD COLUMN … NOT NULL` без default на таблиці з рядками. Якщо `NULL` = 0, крок лишається `validationScan` без заповнення | §6.6 (задача 0); промоція §9.7 — тепер це реалізація фрази «гейт рахує порушення до застосування» для `NULL` |
| Р7 | **Сторож перед `SET NOT NULL` без заповнення.** Між планом і застосуванням можуть з'явитися `NULL`. Тоді замість сирого `apply.step-failed` 23502 раннер дає `apply.not-null-violation` з тими самими параметрами. Сторож — у `step.guards`, у тому самому механізмі, що сторожі зміни типу (`type-guard.ts`). Крок із заповненням сторожа не має: заповнення в тій самій транзакції під `ACCESS EXCLUSIVE` закриває вікно | §6.6 (задача 0) |
| Р8 | **Звіт.** Артефакт плану під `planHash` несе для кожного кроку заповнення `table`, `column` і `rowsAtPlan`. Кількість залежить від даних, тож хеш плану від даних теж залежить. Це прийнятно: відбиток цілі дані не покриває, і дозвіл на план не анулюється. Фактичну кількість (`rowCount` оператора `UPDATE`) показують результат застосування й звіт репетиції (`RehearsalReport`, нове поле поруч із `data`). Вивід `plan` у CLI designer показує обидві | промоція §8 (звіт репетиції) — поле (задача 0) |
| Р9 | **Межі.** `ALTER DOMAIN … SET NOT NULL` (`SCANNING_DOMAIN_ALTERS`) лишається як є, бо домени платформа не генерує. Колонка, що в тому самому плані стає `NOT NULL` і отримує `CHECK`, який порушує default (рядок `required` з default `''` проти правила `!~ '^\s*$'`), — поза блоком. Такий крок `CHECK` падає, як і сьогодні; кандидат у борг | немає; борг — приміткою в цьому плані |

## Інтерфейси

- `PlanStep.origin` — додається `"backfill"`. `artifact.ts`: enum
  походжень, нова секція (або поле кроку) з `table`, `column`, `rowsAtPlan`.
  Форму обирає виконавець. Вимога: раннер і вивід `plan` читають одне
  джерело. `PLAN_FORMAT` 7 → 8.
- `steps.ts`: функція, що за дією двигуна і деревом розбору повертає
  колонки, які дія робить `NOT NULL` (`AT_SetNotNull` і `ColumnDef` з
  обмеженням `CONSTR_NOTNULL` у `AT_AddColumn`). Конструктор кроку
  заповнення — поруч з `intentStep`. `lockClass: accessExclusive`, бо
  `SET NOT NULL` наступним кроком однаково бере цей замок; `lockedTables` —
  таблиця кроку.
- Нумерація `s<N>` лишається наскрізною й позиційною. Крок заповнення
  отримує свій id, і id наступних кроків зсуваються. Вставка робиться до
  обчислення сторожів і лінту, щоб діагностики називали остаточні id.
  Шлях без промоції (`plan.ts`, крок 7) і шлях із промоцією (з `offset` після
  кроків наміру) використовують одну функцію.
- `execute.ts`: `block("engine")` бере кроки `engine` і `backfill` у порядку
  плану. Фаза репетиції для кроку заповнення — `engine` (окремої фази немає).
  Сторож Р7 — через наявне виконання `step.guards` у `runSteps`.
- `locks.ts`: крок заповнення входить у слід замків як крок двигуна на своїй
  таблиці.
- Крок заповнення несе `triggers` (тригери користувача, прочитані на плані)
  і ознаку дозволу (Р3).
- Нові коди: `plan.not-null-violation`, `plan.backfill-order`,
  `apply.not-null-violation`.

## Задачі

### Задача 0 — якорі й поправки спеки

### Задача 1 — доказ порядку дій двигуна

- Фікстура DB-тестів блоку — власний реквізит, що стає обов'язковим з
  `defaultValue`. Кейс `description` додається після мерджу B1d.
- DB-тест у `packages/designer/src/schema-engine/__tests__/engine-apply-port.db.test.ts`:
  колонка nullable без default → `NOT NULL` з новим default. Зафіксувати,
  що `SET DEFAULT` і `SET NOT NULL` — окремі дії, і їхній порядок.
- Якщо `SET DEFAULT` іде після `SET NOT NULL`, стоп і питання архітекторці.
  Варіанти тоді: перестановка дій у планувальнику (лише для пари однієї
  колонки) або вираз замість `DEFAULT`. Самостійно не вирішувати.
- **Готово:** тест зелений і фіксує порядок; результат — у звіті задачі.

### Задача 2 — виявлення `NOT NULL` і крок заповнення (T2, unit)

- Функція в `steps.ts`: дія → колонки, що стають `NOT NULL` (`AT_SetNotNull`,
  `AT_AddColumn` з `CONSTR_NOTNULL`). Конструктор кроку заповнення.
  `origin: "backfill"` у типі, схемі артефакту, `PLAN_FORMAT` 8.
- Вставка кроків і перевірка порядку (Р2, І4) як чиста функція від дій,
  моделей цілі й бажаного стану, і від кількостей `NULL`. Відмови Р6 — тут

- Ознака дозволу за походженням таблиці (Р3) і `requiredPermissions`.
