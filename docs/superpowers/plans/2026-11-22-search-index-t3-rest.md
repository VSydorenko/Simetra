# План: поля пошуку й тріграмний індекс (#192) і залишки T3 (#345)

## 1. Заголовок

- **Статус:** чернетка на приймання; приймає архітекторка М5 (сесія `m4-simetra-milestone`). Виконує авторка плану.
- **Опори після X:** немає. Усе спирається на `main` (9d0b0f5); #230 (пікер) бере `search` з цього блоку, а не навпаки.
- **Спільні ресурси й заборони:** стек `postgres` спільний — DB-тести лише через `run-tests db --filter`/`--changed`, стек не зупиняти, чужих об'єктів не видаляти. Не чіпати `packages/simetra/src/data/**` і пікер (#230). Жодного `CREATE EXTENSION` на спільному стеку поза тестовою базою з тегом запуску; шаблон `simetra_template` спільного стеку змінює лише `roles` (див. задачу власника).
- **Лише CI:** повні рівні `unit`, `db`, `db-supabase`, `e2e`, `packaging` (усі `ci: true`). Локально — `run-tests <рівень> --changed` чи `--filter`. CI-шарди стартують свій стек з нуля, тож нове правило `roles` вони отримують автоматично.

## 2. Мета / Архітектура / Спека

**Мета.** `contains`/`startsWith` за полями пошуку об'єкта читаються індексом. Поля пошуку — нове об'єктне `search` у T0, одне джерело для індексу й пікера (#230). Разом — залишки T3 (#345 п. 2–5).

**Архітектура.** T0 описує `search` і бере типові поля з реєстру виду. T1 виводить тріграмний індекс (новий вид похідного індексу, GIN з `extensions.gin_trgm_ops`) і вимогу розширення `pg_trgm`. T2 рендерить і застосовує; профіль вирішує, хто ставить розширення. T3 (`read-filter.ts`) не змінюється: `col ILIKE $n` уже використовує індекс.

**Спека.** ADR-0097 (`docs/adr/0097-search-fields-trigram-index.md`); П2 §5 (стандартні реквізити, реєстр виду, «Пошуковий індекс і порядок списку»); П4-B §4.1, §4.2, Рд43; профіль `postgres` §3.4–§3.5 (`docs/superpowers/specs/2026-11-08-postgres-profile-design.md`); спека прав §6.1 (дозвільний перелік вбудованих, для п. B2); ADR-0028.

## 3. Глобальні обмеження

- Без поступок сумісності; правило «кожна гілка за видом читає реєстр видів»: типові поля `search` — факт реєстру, не `switch` за назвою виду.
- Новий чи змінений T0-схема — з тестами; публічні повідомлення й діагностики — англійською.
- Наявні тести зелені; послаблення оракула — розвилка до архітекторки.

## 4. Рішення

| # | Рішення | Вплив на спеку |
| --- | --- | --- |
| Р1 | **Форма `search`.** Необов'язкове `search: { fields?: string[], mode?: "startsWith" \| "contains" }` на об'єктах видів, чий запис реєстру має факт «пошук» (довідник, документ, `CustomTable`; інші види — діагностика компілятора, якщо `search` оголошено). `fields` — логічні імена реквізитів шапки (стандартні й власні), без ТЧ і без `Ref`; дубль чи невідомий — діагностика. Відсутнє `fields` — типові з реєстру виду; `mode` типово `contains`. | П2 §5 (новий абзац «Поля пошуку») |
| Р2 | **Типові поля — поля представлення з реєстру виду.** Довідник — реквізит `mainPresentation` (найменування чи код), документ — номер; `CustomTable` — порожньо (лише оголошені). Факт — у записі реєстру видів (`packages/simetra/src/model/kinds/`), не в компіляторі. Поле, якого в об'єкта немає (довжина найменування 0), відпадає. | П2 §5 |
| Р3 | **Індекс.** Кожне поле `search` типу `String`/`Text` (не масив) — похідний індекс нового призначення `trigram` у `DerivedIndex` (`compiler/stages/model.ts`): `method: "gin"`, одна колонка з `opclass` `extensions.gin_trgm_ops`, без ключа рядка й без колонки скоупу (обмеження скоупу RLS сполучає бітова карта). Поле іншого скалярного типу — без індексу (пошук через `eq`). Тріграмний індекс ніщо не покриває й ним нічого не покривається (метод інший) — `materializeIndexes` не відкидає його й не відкидає через нього btree. Ім'я — алгоритм Postgres, як для решти похідних. | П2 §5 «Пошуковий індекс…»; П4-B Рд43 (одне речення) |
| Р4 | **Розширення як вимога моделі.** Компілятор додає до знімка вимогу `pg_trgm` у схемі `extensions`, лише коли є хоч один тріграмний індекс. Хто створює — профіль: `supabase` — план застосування ставить `CREATE EXTENSION pg_trgm WITH SCHEMA extensions` (додати в `SUPABASE_INSTALLABLE_EXTENSIONS`, `packages/simetra/src/schema/engine/provider/supabase.ts`); `postgres` — `roles` ставить розширення в цільову базу й `simetra_template`, як `plpgsql_check` (схема `extensions` належить суперкористувачу), а план лише перевіряє його наявність (`POSTGRES_EXTENSIONS` / перевірка розширень у `schema/apply/plan.ts`). Відсутнє розширення на `postgres` — названа відмова плану з порадою «запустіть `simetra roles`». | ADR-0097; профіль `postgres` §3.4–§3.5 (розширення платформи — перелік, а не лише `plpgsql_check`) |
| Р5 | **`pg_trgm` в іншій схемі.** Знімок фази читання бачить `pg_trgm` поза `extensions` — названа діагностика (наприклад `schema.extension-schema`) з виправленням `ALTER EXTENSION pg_trgm SET SCHEMA extensions`; план не створює другої копії й не йде далі. | ADR-0097; П2 §9 (інтроспекція) — одне речення |
| Р6 | **Короткий шаблон.** Сервер не відмовляє; спека фіксує межу «індекс діє від 3 символів `contains`», пікер до 3 символів шле `startsWith`. | П4-B §4.1, §4.2 |
| Р7 | **Спайк рушія — частина задачі 2.** Перш ніж будувати вивід, виконавиця доводить DB-тестом, що pg-delta планує й застосовує `CREATE INDEX … USING gin (<col> extensions.gin_trgm_ops)` і що повторний план порожній (без шуму від відбитка `schema/apply/fingerprint.ts`). Якщо ні — стоп і розвилка до архітекторки (дефект рушія виправляють, не обходять). | немає |
| Р8 | **`currval`/`lastval` (#345 п. 2).** Читання стану послідовності сесії — `currval`, `lastval` — виходить з дозвільного переліку вбудованих скрізь (тіла, вирази, голови): саме читач розкриває значення попереднього запиту з того самого з'єднання пулу. Нова властивість класу виключень у `builtin-exclusions.ts` поруч з `outlivesTransaction` (одне джерело, рішення архітекторки до Р16 T3). `nextval`/`setval` лишаються: запис послідовності — ефект даних, `DEFAULT nextval` виконується неявно. *На апрув архітекторки.* | спека прав §6.1 |
| Р9 | **Інструмент вбудованих (#345 п. 3).** `packages/simetra/scripts/builtin-functions.ts` і `packages/simetra/scripts/catalog-functions.ts` типово йдуть на стек `postgres` (профіль за замовчуванням); стек Supabase — явним `SIMETRA_TEST_DATABASE_URL`. | немає |
| Р10 | **Зарезервовані слова шляху (#345 п. 5).** `STRUCTURAL_PATH_WORDS` (`model/runtime/path.ts`) поповнюється кожним словом, з якого шлях відмови операції може починатися й яке може збігтися з ім'ям реквізиту (виконавиця збирає з `path.ts`, `operationRefusalPath` у `server/read.ts`, форм операції: `values`, `tabularSections`, `deleteIds`, `object`… — перелік у звіті з причиною для кожного). Діагностика `identity.name-structural` і суфікс прийому (`schema/reverse/names.ts`) діють на весь перелік без змін коду. Якщо наявні метадані репозиторію (`examples/`, шаблон, фікстури) вже вживають таке ім'я — стоп і розвилка. | П4-B §4.0 |
| Р11 | **Minor T3 (#345 п. 4).** DB-кейс «`SET LOCAL extra_float_digits` поза ядром між двома викликами ядра → `conflict fields`»; страж вводу-виводу верхнього рівня (`test/server-sources.test.ts`) ловить `for await` і `await using`. | немає |

## 5. Інтерфейси

**Дає #230 (пікер):** T0 `search` (`fields`, `mode`) з типовими полями з реєстру — через функцію T0, що повертає ефективні поля пошуку об'єкта (одне джерело для компілятора й клієнта; клієнтський каталог несе ефективні поля, якщо пікеру вони потрібні без метаданих — виконавиця вирішує з коду, як каталог несе `presentation`, `client-catalog.ts`). Межа «індекс від 3 символів `contains`» — у П4-B §4.1.

**Бере:** нічого з незмерджених блоків.
