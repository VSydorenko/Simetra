# П4-B3-8. Пакет читань клієнта й `known` — план імплементації

**Статус:** чернетка на приймання архітекторкою М4 (`simetra-75`). Issue #207,
віха М4. Відкладено з М3 ([ADR-0091](../../adr/0091-m3-thin-slice-scale-later.md)).

- **Анкори.** Усі анкори — на `main`; незмерджених залежностей
  план не має. B3-3, B3-6, B5a (#198) закрито.
- **Спільні ресурси.** Стек `postgres` — спільний; запускати лише
  `pnpm db:pg:start` з основного checkout, не зупиняти. DB-прогін — один за раз
  (вартовий чекає).
- **Межі серії.** `packages/simetra/src/data/**` — лише виконавець цього
  блоку. `packages/simetra/src/compiler/sql/**` не чіпати (#173). Цей блок
  компілятора не змінює.
- **Лише CI.** Повні рівні `unit`, `db`, `db-supabase` і `e2e` (профіль, `ci:
  true`) запускає CI на draft PR. Жодна задача не закінчується повним
  локальним прогоном: лише цільові форми `run-tests … --filter` / `--changed`.
  Рівнів, яких CI не має, блок не зачіпає.

## Мета, архітектура, спека

**Мета.** Звірка після гідратації, `resume()` і перечитування кількох виглядів
ідуть одним запитом `read`; ядро не тягне тіл рядків, які вже має. Готово, коли
(рядок B3-8 §13): звірка після гідратації — рівно 1 запит; системне
перечитування сторінки без змін — маркери без значень; DB-кейси `known` з
`include` під RLS цілі зелені.

**Архітектура.** Збирач пакета — обгортка `CoreSource` усередині ядра: усі
читачі й `requestVersion()` ідуть через неї, тож частини одного такту
мікрозадач стають одним викликом джерела. Джерело (`createCoreSource`) уже
ділить частини за адаптером по `READ_BATCH_MAX`, тримає обмежувач (4 запити) і
повторює `batch-aborted` / `batch-budget` — цей код лишається. Нове: частина
`version` іде тим самим запитом, що й частини об'єктів Server Function;
частини несуть `known`; маркер застосовує `ObjectStore`. На сервері `known`
дозволено разом з `include`, а `include` перша сторінка й картка просять тим
самим запитом.

**Спека.** П4-B (`docs/superpowers/specs/2026-11-05-p4-b-client-data-design.md`):
§4.1 (`known`, `include`, `known-form`), §4.2 (оператор `include`), §4.5
(конверт, пакет, бюджет пакета), §6.6 (звірка після гідратації), §6.7 (умовне
читання, пакет, `include` тим самим запитом, системне перечитування вікна,
частота), §12 (мережеві бюджети), §13 (рядки B3-8, B3-7, B5, B5c), §14.3 (дайджест
сторінки). Довідка ідей (не код): `docs/superpowers/specs/2026-11-08-t4-core-spike-report.md`;
план B3-3 до перерізу М3, задачі 5–9 (як його дістати — перший коментар
#207).

## Глобальні обмеження

- Наявні тести лишаються зеленими; правка очікуваного числа запитів у
  наявному тесті — лише там, де цей план міняє «1 + N» на «1» (задача 5).
  Послаблення будь-якого оракула, допуску чи перевірки — розвилка до
  архітекторки.
- Без шимів (принцип 5): `CoreSource.version()` і `ServerPort.version()`
  видаляються в тій самій задачі, що вводить частину `version` у пакеті.
- Швидкодія — вимога: жодного постійного спрощення; відкладення — лише з
  issue і рядком §13.
- Модельний тест ядра (`packages/simetra/src/data/store/__tests__/` з
  `defects.ts`) лишається зеленим на кожній задачі; новий дефект ядра — новий
  прапорець з власним шляхом `CAUGHT_BY`.
- Тести — за скілом `writing-tests`: unit раніше за DB, будівники фікстур,
  коди діагностик, а не текст.

Вікно збирання — одна мікрозадача, таймера немає. Збирач пропускає `run`, `refuse` і `close` без затримки; `close()` синхронний: частини в черзі отримують відмову закриття без запиту. | Р2 | **Частина — дискримінований тип за `type`.** `CoreSource.read(parts: readonly CorePart[])`, `CorePart = { type: "query"; query: RowsQuery; known?: KnownVersions } \| { type: "version" }`. `CoreReadItem` дістає варіант значення версії (`{ ok: true; type: "version"; version: VersionValue }`), варіант рядків лишається. Частини без об'єкта (рівня каталогу) джерело ставить **першими** в запит групи Server Function (§6.7 «Порядок частин») — правило за відсутністю об'єкта, не за переліком типів. `ServerPort` дістає `read(items)` для групи Server Function і втрачає `version()`; `serverFunctionAdapter` і `serverFunctionPort` (`src/data/adapter.ts`) ідуть одним `send`. Частина `version` за перевизначеного адаптера всіх об'єктів іде сама в запиті Server Function | немає (внутрішні імена) |
| Р3 | **`requestVersion()` лишає single-flight з одним хвостом**, але шле частину `version` через збирач. Тож `version` і перечитування, поставлені в одній мікрозадачі, — один запит. `serverHash(hash, versionPart)` рахує `versionPart` за наявністю частини `version` у запиті, як зараз. **Бар'єр відповіді:** значення `version` однієї відповіді ядро застосовує (липкі позначки §10) синхронно **до** видачі будь-якої частини `query` тієї самої відповіді, тож рядки об'єкта, що в цій відповіді став несумісним, відкидає фільтр `staleObjects` на мить застосування. Між окремими пакетами (понад `READ_BATCH_MAX`) порядку немає — як у М3, де `version` і перечитування — різні запити | немає |
| Р4 | **Звірка — одна внутрішня функція ядра** `reconcile({ minAgeMs? })`: `requestVersion()` і `revalidate(o, { visibleOnly: true, minAgeMs })` кожного живого об'єкта з видимими виглядами, синхронно, без `await` між об'єктами. Її кличуть `endHydration()` і `resume()`; такт інтервалу B5c (#209) кличе її ж. Перечитування на перемиканні епохи (core.ts, таймер з випадковою затримкою) лишається своїм шляхом: він на об'єкт і без `version` | немає |
| Р5 | **Правило «ключ іде в `known`»** — `knownFor` у `ObjectStore` (`store/object-store.ts`) за п'ятьма умовами §6.7: рядок показує значення (не `removed`, не прибраний `purge`, без позначки `stale.hidden`); підтверджена версія `v`; копія повна для форми за клієнтським каталогом (список — кожна колонка переліку читання; картка без ТЧ — ще кожне ліниве поле з версією проєкції `v`); рядок прочитано за поточної епохи версій (епоха останньої відповіді; нова епоха скидає право всіх рядків); ключем володіє вигляд, що читає. Форми з `known`: читання за ключами (`readKeys`, список і картка без ТЧ), системне перечитування власних сторінок вікна (`rereadPages`) і `full`, `revalidate` списку. ТЧ, `count` і цілі `include` `known` не беруть | немає |
| Р6 | **Маркер — `ObjectStore.applyMarker(scope, key, marker, readEpoch)`** тим самим шляхом, що `put`: правило версії, надгробки, епохи, позначки `stale` (маркер знімає позначку, як рядок версії `v` того самого читання). Маркер пише лише тоді, коли на мить застосування сховище тримає версію `v` з тими самими значеннями й позначки, новішої за старт читання, немає; інакше нічого не пише, а ключ іде в перечитування за ключем без `known` наступним пакетом. Частковий маркер пише копії через наявне `rowFromMarker` (часткове злиття, §6.2 правило 2). Перевірку джерела «маркер у частині без `known` — `command.internal`» лишити для частин без `known` | немає |
| Р7 | **Сервер: `known` разом з `include`.** `knownFormAllowed` (`model/runtime/read.ts`) пропускає `include`; `known` з ТЧ (`tabularSection`, `tabularSections`) і `count` лишається `known-form`. З `include` маркер — завжди об'єктна форма `{ $known, <копії>, <колонки посилань include> }`, навіть без копій носіїв (зараз `markerProjection` дає голе число, і оператор `include` id не знайде) (`model/runtime/mapping.ts`, `server/decode.ts`, `server/read.ts`: план рядків, маркер, оператор `include` бере id цілей і з маркерних рядків, і з повних; операторів — так само по одному на крок `include`). Цілі `include` `known` не беруть і приходять повністю | §4.1, §4.2 — лише прибрати історію «з B3-8 / до нього» (задача 6) |
| Р8 | **`include` тим самим запитом.** Перша сторінка вигляду й картка, чий адаптер має `capabilities.include`, просять `include` у своїй частині; рядки `included` стають першим результатом підмножини `keys` цілі тим самим `commit`, що й рядки вигляду (власник — вигляд). Наступні сторінки `include` не просять: цілі, яких ще немає в підмножині, ядро дочитує частиною `keys` наступного пакета; ціль, що вже є, не шле. Адаптер без `include` — нинішнє дочитування (`readIncluded`). **Несумісна ціль** (липка позначка §10): `include` на неї не просять, а запис `included` несумісної на мить застосування цілі відкидається без ключів (як зараз у `readIncluded`: відсутні цілі не стають `removed`) | немає (§6.7 уже так) |
| Р8а | **Системне перечитування вигляду з `include`** (`readWindowAgain`, `readFullAgain`, `revalidate` картки) — **прийнято архітекторкою 2026-11-18**. Частини вигляду йдуть без `include`; цілі, які підмножина `keys` вигляду вже тримає, перечитуються частиною `keys` з `known` **у тому самому пакеті** (їхні ключі відомі до відповіді); нові id цілей з відповіді — частиною `keys` наступного пакета. Залежний виклик `readIncluded` після відповіді лишається лише для нових id. Запитаний утримуваний ключ цілі, якого немає у відповіді (RLS, видалення), — `removed`, як зараз у `readKeys` (`missing`). Власність після `commit` — цілі живих рядків відповіді (`wanted`, як зараз): утримувана ціль поза `wanted` пише значення й звільняється (`keep=false` для `full` і картки). Застосування — в тому самому захищеному `Write`, що й рядки вигляду (ланцюжок і покоління вікна, `sameComposition` для `full`). Чому не `include` у частині перечитування: цілі `include` `known` не беруть (§4.2) і приходили б повністю на кожній звірці — бюджет «нічого не змінено ≤ 8 Б × рядків» (§12) був би порушений. Тож звірка без змін — 1 запит і маркери й для цілей; зміна посилання — +1 запит | §6.7 — правило перечитування вигляду з `include` (задача 0) |
| Р9 | **«Повернення сторінки без змін» у цьому блоці** — системне перечитування власних сторінок вікна й `full`: незмінна сторінка приходить маркерами. У `main` усі сторінки власні (тонкий зріз B3-3), знімків показу немає: їх вводить B3-7 (#206), і рядок §12 «повернення сторінки-знімка показу» міряє B3-7 тим самим шляхом читання за ключами з `known` | §13 — уточнення done-when рядків B3-8 і B3-7 (задача 0); **відхилення прийнято архітекторкою 2026-11-18** |
| Р10 | **Бюджети — unit T4 на фейковому транспорті**, що рахує запити й частини (§12: «сценарії ядра міряє unit T4 … у блоці, що вводить механізм»). Публічного лічильника `simetra/data/testing` блок не дає — це B3-10 (#210). Очікування «1 + N» — одна функція `expectedHydrationRequests` (`packages/create-simetra-app/e2e/browser.ts`) і перевірка звірки в unit рантайму: стає «1» в обох місцях | немає |
| Р11 | **Дайджест сторінки (§14.3) — лише резерв.** Форма `known` лишається `{ epoch, keys, versions }`; дайджест — пізніше необов'язковим полем частини `query` без зламу. Поля зараз немає | немає |

## Задачі

### Задача 0 — анкори й правки спеки

`orient --plan` цього плану, `doc anchors`. Правки П4-B: §6.7 — правило Р8а (системне перечитування вигляду з `include`); §13 рядок B3-8 —
done-when «системне перечитування власних сторінок і `full` без змін — маркери
без значень»; рядок B3-7 — done-when дістає бюджет «повернення сторінки-знімка
показу» §12 (Р9). Інших правок рішення не вимагають. Готово: `doc anchors && doc
lint` зелені; дельти анкорів виправлено в плані. Коміт `docs(spec): …`.
