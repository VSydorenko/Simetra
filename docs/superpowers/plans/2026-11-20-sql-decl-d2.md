## Мета, архітектура, спека

**Мета.** Definer-функція з викликачами `user` чи `command` і з `check`
компілюється, коли її тіло застосовує перевірку у формі `guardOf`; платформа
генерує функції запобіжника `simetra.rights_require` і
`simetra.rights_require_scope` з умовою, тотожною RLS і ядру команди.
Готово, коли виконано рядок Д2 таблиці §3 спеки: кожна умова — тест задачі
нижче, кожна причина `sql.declaration-check-not-applied` і
`sql.declaration-check-form` — червоний тест.

**Архітектура.** Три частини одного шляху. (1) Суддя `check` над контрактом
прав (`check-form`) — після побудови контрактів (`rightsContracts`), бо мітка
виду й UUID кастомної дії існують лише там. (2) Доказ форми `guardOf` над
портом plpgsql (`compiler/sql/plpgsql.ts`) і лексикою тексту тіла
(`compiler/sql/rewrite/lex.ts`) — замінює причину `guardUnavailable` у
`checkDeclaredCallers` (`compiler/sql/declarations.ts`). (3) Генератор функцій
запобіжника — одна гілка на пару (мітка, дія) з декларацій; умова гілки
збирається тими самими будівниками, що й політики та ядро команди
(`tenantBoundary` і межа «Користувачів» з `compiler/access-units.ts`,
`rightsCheckPredicates` з `compiler/catalog-command/rights-check.ts`,
функція множини `any` з `compiler/rights/predicates.ts`). Виняток
`sql.platform-function-call` (`checkPlatformCalls`,
`compiler/sql/function-body.ts`) дозволяє рівно виклик-запобіжник першого
оператора задекларованої функції з `check`.

**Спека.** Декларацій §5.2 (форма, причини, функції запобіжника), §5.7
(коди), §6 (безпека); платформна §6.7; спека прав §5.1 (функції множини),
§6.2 (DML дії).

## Глобальні обмеження

- Без сумісності (правило власника): причина `guardUnavailable` зникає з коду,
  повідомлення й тестів у тій самій зміні.
- Будь-яка ідентичність одиниці — лише через `compiler/sql/identity.ts`
  (#297, правило lint Р4 того плану).
- Умова гілки функції запобіжника не має власних предикатів: лише виклики
  наявних будівників. Новий будівник предиката в цьому блоці — розвилка до
  архітекторки.
- Наявні тести лишаються зеленими.

## Рішення

| # | Рішення | Вплив на спеку |
| --- | --- | --- |
| Р1 | **Місце судді.** `check-form` і доказ `guardOf` судить нова перевірка після `rightsContracts` (`compiler/pipeline.ts`), а не `checkLinks`: контракти будуються лише після гейта стадій 4–5. `checkDeclaredCallers` лишає `sql.declaration-check-missing` і `sql.declaration-anonymous-definer`, гілку `guardUnavailable` видаляє. Модель з помилками стадій 4–5 не доходить до судді — та сама межа, що й для решти правил над контрактами. Помилка `check-form` зупиняє пайплайн до побудови одиниць (ранній `return` з діагностиками, як для `projection` у `pipeline.ts`); `check-not-applied` (клас ремонту) — ні: гілка запобіжника генерується й для функції, чиє тіло ще без запобіжника виклику. | none |
| Р2 | **`sql.declaration-check-form` — не клас ремонту.** Хибна `check` — помилка автора декларації, а не стан прийнятої бази; клас ремонту (`REPAIR_CLASS`) лишається для `check-not-applied` (тіло без запобіжника виклику — стан прийому, Д4 `fix` вставляє запобіжник). **На затвердження архітекторки.** | §5.1 — одне речення про склад класу (задача 0) |
| Р3 | **Розширення порту plpgsql.** `PlpgsqlFunction` отримує структурний вид блоку автора: перший оператор зовнішнього блоку (без фіктивного `RETURN`, з урахуванням синтетичної обгортки секції `EXCEPTION` — блок автора тоді `body[0]`) і ознаку секції `EXCEPTION` блоку автора. Плаский `statements` цих фактів не несе (`walkStatement` обходить обгортку анонімно). Вузли `PLpgSQL_*` за межі порту не виходять. | none |
| Р4 | **`declareSection` — на лексиці тексту**, не на сканері libpg-query: `skipTrivia`, `readIdent` з `rewrite/lex.ts`; дозволено лише `<<`, один ідентифікатор, `>>`, далі `BEGIN` без огляду на регістр. Текст тіла — з `DefElem` `as` дерева `CREATE`. | none |
| Р5 | **Аргументи запобіжника.** Дія — рядковий літерал зі словом словника чи UUID кастомної дії (компілятор резолвить ім'я кастомної дії з `RightsContract.actions[].name`), мітка — літерал `RightsContract.kindLabel`, третій аргумент — ім'я параметра `check.row`/`check.scope` (без цілі — `NULL`). Позиційне `$n`, вираз, приведення типу — `arguments`. **Форма запиту `PERFORM`:** порт зберігає весь текст запиту (`PERFORM … WHERE false` стає `SELECT … WHERE false`, і Postgres не обчислює ціль), тож запит має розбиратися в голий `SELECT` з рівно однією ціллю — прямим `FuncCall` кваліфікованої функції запобіжника без іменованих аргументів; `FROM`, `WHERE`, `GROUP`/`HAVING`, `LIMIT`/`OFFSET`, `ORDER`, `DISTINCT`, `WITH`, операції множин, `WINDOW`, друга ціль чи обгортка (`CASE`, `COALESCE`) — `firstStatement`. | §5.2 `firstStatement` — речення про форму запиту (задача 0) |
| Р6 | **Генератор функцій запобіжника** — новий модуль у `compiler/rights/` з новим значенням `UnitGenerator` (`units.ts`) і `FIXED_BODY[<генератор>] = true`: тіло платформне (залежить від декларацій, а не від автора), тож функції входять у `platformFunctionSignatures` і в еталон платформи зворотної генерації (`hasFixedBody`, `schema/reverse/generate.ts`) і не стають дослівними одиницями застосунку. Генератор бере лише декларації, що пройшли суддю `check-form`. Функції створюються, лише коли хоч одна декларація має `check`; кожна — тільки якщо має гілку (немає цілі `scope` — немає `rights_require_scope`). ACL — `executeGrants(<підпис>, [], provider)` (`compiler/sql/execute-grants.ts`): `REVOKE` від `PUBLIC` і ролей API, без `GRANT`. Невідома пара (мітка, дія), немає права, немає рядка, `NULL` — одна відмова. | none |
| Р7 | **Умова гілки** = AND меж `RESTRICTIVE` DML дії і OR предикатів дії — тими самими будівниками. Набір меж — той самий вибір, що в політиках: для `select` — `readBoundaries(contract, visibleUsers)` (`access-units.ts`; об'єкт з `publicRead` межі тенанта на читанні не має), для `update`/`delete` — межі `scope_update`/`scope_delete`; для `rights_require_scope` — `p_scope` у `scopeSetCall` (вже експортований) і в множині `any` дії (`rowFreeGrants` у `rights/predicates.ts` — перевикористати, не дублювати). Межа «Користувачів» зараз вбудована в `buildAccessUnits`: виноситься в експортований будівник поруч із `tenantBoundary`, і політики, і функція запобіжника кличуть його. Кваліфікатор рядка `CommandRow` у `rights-check.ts` розширюється до довільного псевдоніма. Функція множини `any` експортується з `rights/predicates.ts` одним будівником (зараз приватний `scopeSet`). | none |
| Р8 | **Відмова** — `RAISE` з `SQLSTATE '42501'`, `MESSAGE 'rights.forbidden'`, `DETAIL 'no-right'`; константа поряд із `COMMAND_CORE_ERRORS` у T0 (`model/runtime/core.ts`), бо тести й клієнт читають її звідти. | none |
| Р9 | **Виняток `sql.platform-function-call`.** Окремий дозвільний набір функцій запобіжника, не `PLATFORM_READ_FUNCTIONS` (інакше голови й вирази таблиць дозволили б їх). Дозвіл — лише для першого оператора задекларованої функції з `check`, якщо він `PERFORM` функції запобіжника; будь-який інший виклик у тій самій одиниці — помилка. Правильність аргументів судить `guardOf` (Р5), тож структурний дозвіл не потребує контрактів і лишається в стадії 5. | none |
