# П2, план C1 — скоуп: план імплементації

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Мета:** метамодель і компілятор знають скоуп — межу ізоляції тенанта:
види скоупу проєкту, обов'язкова декларація об'єктів, корені, успадкування
ТЧ, скоуп-колонки з FK на корінь, складені FK між скоупленими об'єктами
одного виду й правила посилань між скоупами.

**Архітектура:** декларації — у Zod-схемах T0 (`project.meta.json` оголошує
види, об'єкт — `scope`), політику виду щодо скоупу тримає реєстр видів.
Стадія 2 резолвить декларації й корені в індекс посилань; стадія 3 додає до
фізичного знімка скоуп-колонки, `UNIQUE (scope, id)` і складені FK; стадія 4
перевіряє правила кореня й посилань. RLS, функції множини й ключі кешу —
поза C1 (П3, план D).

**Технології:** TypeScript 7, Zod 4, Vitest 5 — як у плані B.

**Спека:** [спека П2](../specs/2026-09-28-p2-metamodel-compiler-design.md) §6
(«Наслідки для моделі» — повний перелік правил скоупу), §3 (ідентичність
виду скоупу), §8.2 (стадії), §10.1 (негативні тести скоупу), §11 крок 5;
[платформна спека](../specs/2026-09-24-simetra-platform-design.md) Р10, §4
«Скоуп», §6.8.

**Серія планів П2:** A, B (виконано) → **C1** (цей) → C2 (документ,
проведення, регістри: запит рухів, AST конструктора, контракт оболонки,
ключі й підсумки регістрів, віртуальні таблиці) → D → E.

## Рішення плану (узгоджено з архітектором спеки; модельні — вже в спеці §6)

1. **Форма в файлах.** `project.meta.json`:
   `scopeKinds: [{ id?, name, physicalName?, title?, root: { object: MetadataRef } | { external: { schema, table, column } }, setFunction: { schema?, name }, onRootDelete: "restrict" | "cascade" = "restrict" }]`.
   Об'єкт: `scope?: string` — ім'я виду або `"none"`. Ref-тип: `crossScope?: true`.
   `CustomTable`: `scopeColumn?: string` (логічне ім'я власної колонки).
2. **Наявність функції множини** (стадія 5) і код `scope.set-function-missing`
   — план D разом із розбором SQL (libpg-query); у C1 `setFunction` лише
   декларується.
3. **Місце скоуп-колонки** у таблиці — одразу після колонки ключа (перед
   рештою стандартних), щоб DDL читався однаково в усіх видів.
4. **Індекс посилань** розширюється: `to.kind` приймає також `"ScopeKind"` і
   `"Column"`; нові ролі — `object.scope`, `scopeKind.root`,
   `customTable.scopeColumn`. Їх читає каскад перейменування плану D.
5. **Ключі й індекси регістрів** (ключ підсумків зі скоупом, ключ рухів із
   префіксом `recorder_type, recorder_id`) — план C2; у C1 регістр отримує
   лише скоуп-колонку з FK на корінь.

## Global Constraints

- Усі обмеження плану B чинні: чистота T0 (лише `zod`) і T1 (без Node API),
  UUID v4, імена обмежень — `chooseConstraintName`, детермінізм знімка,
  тексти діагностики англійською, коментарі українською, без шимів.
- Ім'я виду скоупу — логічне ім'я в стилі `project.naming.attributeCase`
  (воно ж логічне ім'я скоуп-колонки); `none` зарезервоване.
- `onRootDelete` діє лише на FK скоуп-колонки на корінь; складені FK між
  скоупленими об'єктами — `noAction`; ТЧ → власник — `cascade`.
- Однотенантний проєкт (немає `scopeKinds`): жодних скоуп-колонок, `scope`
  необов'язковий; будь-яке ім'я, крім `"none"`, — `scope.unknown-kind`.
- Коміти — Conventional Commits, опис українською, без трейлерів.
- Гейти після кожної задачі: `pnpm format:check && pnpm lint && pnpm typecheck && pnpm test`;
  після правки доків — `python3 scripts/check-doc-anchors.py`.

## Review Focus

1. **Скоуплений об'єкт посилається на корінь іншого виду чи на скоуплений
   об'єкт іншого виду через поліморфний `Ref`** — правило перевіряється за
   кожною ціллю `allowedTypes`, а не лише для одиночного `ref`. Тест — задача 4.
2. **Логічне ім'я виду скоупу збігається з реквізитом чи ТЧ об'єкта** (`org`
   і реквізит `org`), або `physicalName` виду — з `physicalName` реквізиту
   (`org_id`). Тести — задачі 2 і 3.
3. **Корінь, що не оголошує власний вид, чи корінь без одноколонкового
   uuid-ключа** (регістр, `CustomTable` зі складеним ключем). Тест — задача 4.
4. **Складений FK на ціль без `UNIQUE (scope, id)`** — ціль `CustomTable` чи
   глобальний довідник мусять давати звичайний FK, а не складений, інакше
   тінь плану E відкине DDL. Тест — задача 3.
5. **Однотенантний проєкт** не отримує жодної скоуп-колонки й жодного
   нового правила. Тест — задача 3.

### Task 3: Стадія 3 — фізика скоупу

**Files:**
- Modify: `packages/simetra/src/compiler/stages/model.ts`, `packages/simetra/src/model/physical/snapshot.ts` (`PhysicalColumn.origin.scopeKindId?`)
- Test: `packages/simetra/src/compiler/__tests__/stage-scope-model.test.ts`

**Interfaces:**
- Consumes: задачі 1–2 (`CompiledModel.scopeKinds`, `SourceObject.scopeKindId`).
- Produces у фізичному знімку (правила — спека §6, «Наслідки для моделі»):
  - **Корінь** (об'єкт, на який вказує `root.object` виду): скоуп-колонки
    немає.
  - **Скоуплений об'єкт виду 1С** (не корінь): колонка
    `{ name: <physicalName виду>, type: "uuid", notNull: true, origin: { scopeKindId } }`
    одразу після колонки ключа (для константи — перша); FK на ключ кореня
    (`object` — PK таблиці кореня; `external` — `schema.table(column)`) з
    `onDelete` = `onRootDelete`.
  - **Скоуплений довідник і документ:** `UNIQUE (<scope>, id)`; `codeUnique`
    → `UNIQUE (<scope>, code)` замість `UNIQUE (code)`.
  - **Рядок ТЧ скоупленого об'єкта:** скоуп-колонка (NOT NULL) і складений
    FK `(<scope>, parent_id) → власник (<scope>, id) ON DELETE cascade`
    замість одноколонкового FK на `parent_id`.
  - **Посилання** (реквізит, `parent`, `owner`, вимір регістра, колонка
    `CustomTable` не зачіпається): джерело й ціль скоуплені одним видом, ціль
    — довідник чи документ, `crossScope` немає → складений FK
    `(<scope>, <колонка>) → ціль (<scope>, id)` з `noAction`; інакше —
    звичайний FK, як у плані B (ціль глобальна, `crossScope`, ціль
    `CustomTable`, джерело — `CustomTable`).
  - **Скоуплена константа:** PK — скоуп-колонка (FK на корінь); колонки
    `singleton` немає.
  - **Регістри:** скоуп-колонка з FK на корінь; FK на документ немає.
  - **`CustomTable`:** нічого не додається.
  - Імена — `chooseConstraintName` (складений FK:
    `(<table>, "<scope>_<column>", "fkey")`, як дав би Postgres).
