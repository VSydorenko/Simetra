# П3-3a2 — тригери механіки й підписок: план імплементації

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Статус: план прийнято архітектором задачі. Правки спек (Додаток А) погоджено
архітектором задачі 16.10 — задача 1 вносить їх без зупинки.

**Мета:** таблиця виду після застосування сама тримає службову дату й
версію рядка, а підписка `EventSubscription` стає тригером:

1. кожна таблиця з колонками `updated_at` і `version` отримує тригер механіки
   `<таблиця>_simetra_touch` з однією платформною функцією `simetra.touch()`;
2. кожна підписка дає тригери `FOR EACH ROW` на кожне своє джерело, зокрема
   на таблиці провайдера; обробник не може присвоїти службові колонки;
3. промоція приймає клас `platform` для прийнятого тригера лише за справжньої
   заміни: тригер підписки з тим самим обробником, часом, рівнем, подіями й
   колонками умови, або механіка замість `moddatetime`;
4. план гучно відмовляє, коли згенерований тригер на таблиці провайдера
   зайняв би ім'я чужого живого тригера, і попереджає про нумерацію, якої
   платформа ще не генерує.

## Review Focus

1. **Клієнт записує `version` чи `updated_at` сам** (`UPDATE … SET version =
   100, updated_at = '2000-01-01'`, `UPDATE … SET version = 0`, `INSERT` з
   `version = 999` і `updated_at = '2000-01-01'`). Очікування: оновлений
   рядок має `version = OLD.version + 1`, вставлений — `version = 1`, обидва —
   `updated_at = now()`; значення клієнта не діє. Тест — задача 2.
2. **Підписка з `whenChanged` і оновлення іншої колонки.** Очікування:
   тригер не спрацьовує; оновлення змінної колонки тим самим значенням теж не
   спрацьовує; вставка спрацьовує завжди. Тест — задача 3.
3. **Чужий тригер з тим самим ім'ям на `auth.users`** на першому
   застосуванні й після останнього `apply`. Очікування: відмова
   `plan.provider-trigger-taken`, а не тиха заміна. Тест — задача 6.
4. **Прийнятий `BEFORE UPDATE OF a` (без вставки)** проти підписки
   `beforeWrite` з `whenChanged: [a]`. Очікування: відмова
   `plan.platform-replacement-missing`, бо події не рівні (підписка
   спрацювала б і на вставку). Тест — задача 5.
5. **Обробник повертає не `NEW`** (`r := NEW; r.version := 5; RETURN r;`).
   Очікування: помилка `subscription.handler-assigns-mechanics`. Тест —
   задача 4.

## Рішення плану

Розвилки вирішив архітектор задачі 2026-10-15/16 (вердикти Ф7–Ф9 і Г1–Г6).

1. **Механіка** (вплив: промоція §9.2, Додаток А.3). Одна функція
   `simetra.touch()`:

   ```sql
   CREATE FUNCTION simetra.touch() RETURNS trigger LANGUAGE plpgsql
     SECURITY INVOKER SET search_path = '' AS $$
   BEGIN
     IF TG_OP = 'INSERT' THEN
       NEW.version := 1;
     ELSE
       NEW.version := OLD.version + 1;
     END IF;
     NEW.updated_at := now();
     RETURN NEW;
   END $$;
   ```

   Імена колонок у тілі беруться з реєстру (`versionColumn().physicalName`,
   `serviceDateColumns()` з `logicalName: "updatedAt"`), а не літералами.
   `SECURITY INVOKER`: присвоєння `NEW` прав не потребує. На кожну таблицю зі
   знімка, що має обидві колонки механіки:
   `CREATE TRIGGER <makeObjectName(table, undefined, "simetra_touch")> BEFORE INSERT OR UPDATE ON <т> FOR EACH ROW EXECUTE FUNCTION simetra.touch();`.
   Вставка теж під механікою: інакше клієнт почав би рядок з довільної
   версії й дати.
   Таблиця лише з однією з двох колонок — порушення інваріанта реєстру
   (Catalog і Document дають обидві): генератор кидає
   `Error("internal: …")`, тест це фіксує. `created_at` тригером не
   захищається (спека мовчить). Функція й гранти генеруються, лише коли
   знімок має хоч одну таблицю механіки.
2. **Тригери підписки** (вплив: промоція §9.3, Додаток А.4). На кожне джерело
   контракту:
   - `beforeWrite` → `BEFORE INSERT OR UPDATE`, `onWrite` → `AFTER INSERT OR
     UPDATE`, `beforeDelete` → `BEFORE DELETE`, `onDelete` → `AFTER DELETE`;
     усі `FOR EACH ROW EXECUTE FUNCTION <handler>()`;
   - без `whenChanged` — один тригер `<name>`;
   - з `whenChanged` — `<name>` на `UPDATE` з
     `WHEN (OLD.<c1> IS DISTINCT FROM NEW.<c1> OR …)` (колонки в порядку
     контракту) і `<name>_insert` на `INSERT` без умови.

   Простір імен тригерів у Postgres — окремий для кожної таблиці, тож
   підписка з кількома джерелами дає ті самі імена на кожному. Довжину
   `<physicalName>_insert` перевіряє стадія цілісності діагностикою
   `physical.name-too-long` на `/physicalName` підписки.

   Згенеровані одиниці між собою `namespaceConflicts` не звіряє (пара без
   файлу пропускається), а граф створення перезаписав би вузол мовчки. Тож
   конвеєр після збирання згенерованих одиниць шукає однакові ідентичності
   тригерів, серед яких є одиниця `subscription`, і дає помилку
   `subscription.trigger-name-taken` (`params { name, table, holder }`,
   `holder` — `describeGenerated` іншої одиниці) на `/physicalName`
   підписки. Колізії: `audit_insert` проти `audit` з `whenChanged`, ім'я
   `<т>_simetra_touch`, ім'я тригера платформного шару на `auth.users`.

   `whenChanged` на колонці механіки (`origin.standard`, рівний
   `standardLogicalName` колонок `updatedAt` чи `version` у стилі
   `attributeCase` проєкту) — помилка `subscription.when-changed-mechanics`: умова
   `BEFORE`-тригера обчислюється з `NEW` після попередніх тригерів, тож
   спрацювання залежало б від того, чи йде механіка раніше за ім'ям. `COMMENT ON TRIGGER`
   не генерується: опис живе в метаданих, як і описи таблиць виду
   (рішення R24 П3-2b-0); коментар контракту
   `EventSubscriptionContract.title/description` переписати відповідно.
3. **Порядок `BEFORE`-тригерів.** Postgres запускає тригери таблиці в
   алфавітному порядку імен. Після заборон рішень 2 і 4 механіка не залежить
   від підписок: обробник не змінює її колонок, а `whenChanged` їх не
   читає. Обробник `BEFORE`, що читає `NEW.version` чи `NEW.updated_at`,
   бачить значення до чи після механіки залежно від імені, тож покладатися
   на них не слід. Кілька `BEFORE`-підписок однієї таблиці йдуть за іменем
   тригера, і кожна бачить `NEW` після попередніх.
4. **Обробник не присвоює службових колонок** (вплив: промоція §9.3).
   Перевірка — лише для обробника підписки з подією `beforeWrite` (результат
   `AFTER`-обробника Postgres ігнорує, а `beforeDelete` не має `NEW`; так само
   й у тексті спеки), джерело якої
   (об'єкт виду; таблиці провайдера механіки не мають) має колонки механіки
   за реєстром (`standardColumns` з `logicalName` `updatedAt`/`version`).
   Помилка `subscription.handler-assigns-mechanics`
   (`params { function, problem }`), якщо в дереві PL/pgSQL:
   - ціль оператора (`PlpgsqlStatement.target.variable`, імена через `", "`)
     — `new` або `new.<колонка механіки>` (без урахування регістру): це
     ловить `NEW.c :=`, `NEW :=`, `SELECT … INTO NEW`, `GET DIAGNOSTICS`;
   - `RETURN` повертає не `NEW` чи `NULL`. Значення, яке повертає пізніший
     `BEFORE`-тригер, і є рядком для запису: `RETURN OLD` чи запис-копія з
     обробника, що йде за іменем після `<т>_simetra_touch`, затерли б версію
     й дату механіки. Скасувати запис — `RETURN NULL`.

   Нерозбірне тіло й `EXECUTE … INTO NEW` уже зупиняє закрита оболонка
   (`subscription.handler-not-closed`: `body` чи динамічний SQL), тож
   перевірка йде лише після неї; тести це фіксують.
5. **Механіка під час кроків даних** (вплив: промоція §7.2, Додаток А.1).
   `readUserTriggers` вимикає й тригер механіки, якщо він уже є: конверсія —
   не бізнес-запис, `version` і `updated_at` не ростуть. У плані промоції
   механіка ще не існує під час запису (кроки даних — фаза 10, двигун —
   фаза 11), і сценарію, де вона вже є під час кроку даних, зараз немає.
   Код не змінюється; спека фіксує правило для майбутніх кроків даних.
6. **Форма заміни `trigger`** (вплив: промоція §8, Додаток А.2). Прийнятий
   тригер класу `platform` (дерево `CreateTrigStmt` з `clone.units`, таблиця —
   нове ім'я) замінено, якщо на тій самій таблиці бажаного стану є:
   - тригер механіки, а прийнятий — `BEFORE UPDATE … FOR EACH ROW` з
     функцією `moddatetime` (будь-яка схема) і одним аргументом — колонкою, що
     в бажаній моделі є `updated_at`. Механіка спрацьовує й на вставку, тобто
     на більше подій, ніж `moddatetime`, і це посилення, а не втрата, тож
     різниця подій заміні не заважає; або
   - тригер підписки з тією самою функцією (схема й ім'я після переписування),
     тим самим часом, рівнем і набором подій, і тією самою умовою: однаковий
     депарс `WHEN` або прийнятий `UPDATE OF <cols>` при `whenChanged` з тими
     самими колонками (множиною). Прийнятий `INSERT OR UPDATE OF <cols>`
     покривається парою `<name>` + `<name>_insert`.

   Будь-яка інша розбіжність (події, довільний `WHEN`, інша функція) —
   `plan.platform-replacement-missing`. Тригер бажаного стану на таблиці
   виду — згенерований або борг зі спільного `sql/` (як дослівні політики,
   П3-3a1). Борговий тригер тієї самої форми відтворює ту саму поведінку, тож
   нічого не губиться, а борг лишається видимим.
   Покриття `UPDATE OF` дає попередження `plan.update-of-narrowed`
   (`params { trigger, table, columns }`): тригер тепер спрацьовує лише на
   справжню зміну значення.
7. **Нумерація без лічильників** (вердикт Г1; вплив: немає). Попередження
   плану `plan.numbering-not-generated` (`params { object, table }`), одне на
   об'єкт, коли контракт `numbering` з `autonumber: true` належить таблиці,
   якої немає в живій цілі (план її створює), або таблиці-цілі промоції.
   Окремого розпізнавання нумерації немає: default нумерації заміни не має
   (форма `none`), а тригер нумерації йде загальною формою `trigger` —
   `BEFORE INSERT` відмовляє, бо події не рівні підписці запису, а
   `BEFORE INSERT OR UPDATE` з тим самим обробником, оголошеним підпискою,
   законно замінено.
   Підказка: код не заповнюватиметься, доки платформа не генерує лічильників.
8. **Колізія імені на таблиці провайдера** (вердикт Г6; вплив: промоція
   §9.2, Додаток А.3). Для кожної згенерованої одиниці класу `trigger` на
   таблиці поза схемами застосунку (`scope.schemas`) — генератори
   `subscription` і `platformLayer`: якщо жива ціль має тригер з тією самою
   ідентичністю й іншим деревом (живий `CatalogUnit.sql` — це
   `pg_get_triggerdef` без `;` і лапок, тож порівнюються `withoutLocations`
   дерев розбору, а не рядки), а в останньому застосованому стані
   (`state.marker.catalog.units`; на першому застосуванні — порожньо) його
   немає, план відмовляє `plan.provider-trigger-taken`
   (`params { trigger, table }`). Перевірка — до побудови кроків, незалежно
   від гейта дрейфу. Тригер, невидимий двигуну (функція в схемі провайдера),
   двигун вважає базовим станом провайдера й засіває в бажану тінь, тож
   згенерований `CREATE TRIGGER` падає там на «already exists»: відмова
   `engine.shadow-load-failed` (`stuck_statement`) ще до перевірки імені й
   доказу, ціль не змінюється; тест її фіксує.
9. **Зворотна генерація** (вплив: промоція §9.2, Додаток А.3). `layoutUnits`
   не пише одиниць механіки, навіть коли збереженого опису теки немає:
   функцію `simetra.touch()`, її гранти й тригер з ім'ям
   `mechanicsTriggerName(<таблиця>)`, що викликає саме `simetra.touch()`.
   Модуль користувача ними не володіє. Інший тригер, що викликає функцію
   схеми `simetra`, пишеться, як зараз: пропуск за самою схемою загубив би
   власний тригер таблиці.

## Відомі обмеження

- **Версія при зміні рядка ТЧ.** Механіка збільшує `version` лише в рядку,
  що змінюється; зміна рядка ТЧ версію шапки не чіпає. Об'єкт цілим пише
  команда (П4); до неї прямого DML на таблиці виду немає (a1).
- **Нумерація.** Якщо в першої міграції споживача є таблиця з нумерацією,
  яку заповнює база, П3-3c (лічильники) — передумова цієї міграції.
- **Прийнятий тригер лише на `UPDATE`** не має форми заміни: підписка
  `beforeWrite` спрацьовує й на вставку. Шлях — видалення з дозволом і
  обробник, що перевіряє `TG_OP`.
- **Вимкнення механіки на час кроку даних** (спека промоції §7.2) зараз не
  перевіряє жоден тест: у плані промоції механіку створює фаза двигуна після
  запису значень, а іншого кроку даних, що пише таблицю виду з уже наявною
  механікою, ще немає. Речення — правило для майбутніх кроків даних; тест
  прийде разом із першим таким кроком.
- **Чужий тригер із функцією в схемі провайдера** з ім'ям згенерованого
  дає загальне повідомлення двигуна (`engine.shadow-load-failed`, «trigger …
  already exists»), а не `plan.provider-trigger-taken` з порадою.
- **Колізія однойменних об'єктів у схемах застосунку на першому
  застосуванні без introspect** — дефект ядра, борг П3-2b §1.
- **Прийом з нуля бази, яку розгорнула Simetra.** Таблиця виду, повернута
  як `CustomTable`, втрачає механіку рядка: план знімає тригер
  `<таблиця>_simetra_touch` лише з дозволом, а повертає механіку промоція у
  вид.
- **Функція механіки після прийому з нуля.** `simetra.touch()` і її гранти
  лишаються в цілі поза межею: план їх не бачить і не знімає. Даних це не
  втрачає; прибирання — разом із відновленням видів при прийомі.

## Додаток А. Правки спек

### А.1 Спека промоції §7.2, пункт «тригери на час запису»

> не змінюються. Застарілого клієнта, який перезаписав би конвертоване, немає:
> до шляху запису (П4) жодна роль застосунку не має DML на таблиці виду

### А.2 Спека промоції §8, «Механізм-заміна», частина про тригер

Було:
> тригер — тригер, який генерує платформа з тим самим обробником, часом,
> рівнем, подіями й колонками умови, або тригер механіки замість тригера
> службової дати чи версії.

Стало:
> тригер — тригер підписки з тим самим обробником, часом, рівнем, подіями й
> колонками умови (прийнятий `UPDATE OF` покривається `whenChanged` з тими
> самими колонками, і план попереджає, що тригер звужується до справжньої
> зміни значення), або тригер механіки замість тригера службової дати
> (`moddatetime` на колонці, що стає `updated_at`; іншу функцію, що ставить
> дату, статично не довести — видалення з дозволом). Механіка спрацьовує на
> більше подій, ніж `moddatetime` (на вставку й оновлення, а не лише на
> оновлення), і це посилення, а не втрата: дата й версія стають правильними
> й на вставці. Тригер нумерації заміни не має, доки платформа не генерує
> лічильників: відмова або видалення з дозволом.

### А.4 Спека промоції §9.3, абзац «Підписка на подію — вид `EventSubscription`»

Було (речення):
> …тригер генерує П3 разом із режимом запису без поведінки (Р28). Тригер
> рендерить платформа, тож підписка спрацьовує й на запис в обхід команд…

Стало:
> …Тригер рендерить платформа (`FOR EACH ROW` на кожне джерело, ім'я —
> `physicalName` підписки): `beforeWrite` — `BEFORE INSERT OR UPDATE`,
> `onWrite` — `AFTER INSERT OR UPDATE`, `beforeDelete` і `onDelete` —
> `BEFORE` і `AFTER DELETE`. `whenChanged` — умова `WHEN (OLD.<колонка> IS
> DISTINCT FROM NEW.<колонка> OR …)` на оновлення; вставку новий рядок
> «змінює» цілком, а `OLD` в умові тригера вставки Postgres не приймає, тож
> підписка з `whenChanged` дає два тригери, `<physicalName>` на `UPDATE` з
> умовою і `<physicalName>_insert` на `INSERT`. `UPDATE OF` не годиться: він
> спрацьовує на присвоєння без зміни значення й не бачить колонок, змінених
> іншим `BEFORE`-тригером. Вставку від оновлення обробник розрізняє за
> `TG_OP` (аналог `ЭтоНовый()` 1С); окремої події «перед вставкою» немає.
> Обробник `beforeWrite` не присвоює службових колонок механіки (`NEW.updated_at`,
> `NEW.version`, ціле `NEW` присвоєнням, `SELECT … INTO NEW` чи `EXECUTE …
> INTO NEW`) і повертає `NEW` чи `NULL`, а `whenChanged` підписки не містить
> колонок механіки — інакше помилка компілятора; тож механіка від підписок не
> залежить. Обробник `BEFORE` бачить `version` і `updated_at` до чи після
> механіки залежно від порядку, тож на них не покладається; кілька
> `BEFORE`-підписок однієї таблиці Postgres викликає в алфавітному порядку
> імен тригерів, і кожна бачить `NEW` після попередніх. Режим запису без поведінки (Р28) приходить з першим
> механізмом імпорту чи патчів даних; до того кроки даних промоції вимикають
> тригери самі (§7.2). Тригер рендерить платформа, тож підписка спрацьовує й
> на запис в обхід команд… (далі без змін).

### А.5 Спека промоції §17

Рядок «**Подія «перед вставкою».**» видалити: вирішено в §9.3 (`TG_OP`, без
`beforeInsert`).

### А.6 Спека П2

Абзац «Декларативні властивості рамки». Було: `…П2 її декларує й валідує,
тригери генерує П3.` Стало: `…П2 її декларує й валідує, тригери генерує П3
(форма тригера — спека промоції §9.3).`

Перелік генерації П3. Було: `…режиму \`write_mode = 'import'\`, підписок —
вид \`EventSubscription\` (§5), засіву … і трьох ролей БД (платформна спека
§6.7, §6.12)…` Стало: `…підписок — вид \`EventSubscription\` (§5), засіву
…; режиму \`write_mode = 'import'\` — з першим механізмом імпорту чи

П3 разом із патчами даних, а ролі в П4 переносить правка А.1 плану
[П3-3a1](2026-10-15-p3-3a1-access.md).
