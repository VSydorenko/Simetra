# План #263 — приймальний e2e М4

> **Статус:** у аудиті. Приймає архітекторка М4 (сесія `m4-simetra-milestone`).
> **Якорі «після X»:** приймач сигналів і `DataRuntimeOptions.signals` — після
> B5b-3 (PR #326, `docs/superpowers/plans/2026-11-20-p4-b5b-3-signal-receiver.md`);
> транспорт `simetra/data/centrifugo` — після B5b-4
> (`docs/superpowers/plans/2026-11-20-p4-b5b-4-centrifugo-transport.md`);
> проводка клієнта шаблону й шина вкладок — після D5 частини 2
> (`docs/superpowers/plans/2026-11-20-p4-d5-signal-routes.md`, задачі 5–7);
> кеш прав клієнта, підписка на канали прав, звуження `read` і
> `RIGHTS_JITTER_MS` — після B6-2 (`docs/superpowers/plans/2026-11-20-p4-b6-2-rights-client.md`).
> На `main` уже є: маршрути токенів і власний Centrifugo прогону (D5-1,
> `packages/create-simetra-app/scripts/lib/signals-stand.mts`), канали й
> тригери сигналів прав (B6-1), знімок прав у ядрі (B5b-2).
> **Спільні ресурси:** стек `postgres` спільний; його не зупиняють. Кожен
> прогін e2e — тегова база й власний Centrifugo з мітками прогону (як зараз).
> **Лише CI:** повні рівні й job `host-template` (e2e шаблону). Локально —
> цільові `run-tests … --filter` / `--changed`; e2e — у CI.

## Мета

Наскрізний браузерний доказ критерію М4 (`docs/ROADMAP.md`): зміна в одній
вкладці з'являється в інших під RLS; відкликане командою право прибирає дані
на клієнті; вихід в одній вкладці закриває ядро іншої. Той самий засів дає
`pnpm demo` для ручного показу обох сценаріїв.

## Архітектура

Частина 1 — засів і права шаблону, без залежностей від незмерджених блоків:
дві ролі в метаданих шаблону, перше призначення адміністратора інструментом
обслуговування прав, усі інші призначення — командою прав від адміністратора;
одна функція засіву для `pnpm demo` і фікстури e2e. Частина 2 — специфікація
`e2e/acceptance.spec.ts` у Chromium на production-збірці: кілька контекстів
браузера, власний Centrifugo прогону, межі часу — з іменованих сталих
платформи, очікування — на стан інтерфейсу. Кожне «з'явилось/зникло»
доводить шлях сигналу, а не запасний інтервал.

## Глобальні обмеження

- Жодного прямого SQL для призначень ролей поза інструментом обслуговування
  прав (вимога #263); старий шлях видаляється в тій самій зміні, без обгорток.
- Жодних «магічних» пауз: `waitForTimeout` у новій специфікації немає; межа —
  іменована стала з платформи чи з цього плану з виводом у коментарі.
- Наявні e2e (`security`, `ssr`, `write`, `signals`) лишаються зеленими:
  користувачі `a` і `b` фікстури зберігають права й рядки, на які вони
  спираються.
- Поза обсягом: сценарії оракула р1–р9 (#210, М5), #328.

Згенеровані артефакти шаблону перегенеровано | П4-D §4 — одне речення про ролі шаблону (задача 0 перевіряє, де шаблон їх перелічує) |
| Р2 | **Засів через команду прав.** Перше призначення `Administrator` — дія `firstGlobalAssignment` інструмента `rights-maintenance` (`packages/designer/src/tools/rights-maintenance-tool.ts`) через CLI-підпроцес `simetra rights-maintenance --yes` з JSON `{ action, user, role }`, `SIMETRA_DATABASE_URL` = DSN мігратора (власника) і текою метаданих шаблону — так само, як `packages/create-simetra-app/template/scripts/db-setup-steps.mjs` кличе `@simetrajs/designer/bin/simetra.mjs` (`create-simetra-app` не залежить від designer, а адаптер рушія лишається поза `simetra`). Модель, застосована `db-setup`, має збігатися з компільованою — інструмент інакше відмовляє, і засів падає. Усі інші призначення (`ClientOwner`, `ClientReader`) — операція `create` над `GlobalRoleAssignments` від рантайму адміністратора (`createCommandRuntime` з його claims, як `runtimeB` у `e2e/fixtures.ts`). `assignClientOwner` (сирий SQL у режимі обслуговування, `packages/create-simetra-app/scripts/lib/app-database.mts`) видаляється | none |
| Р3 | **Одна функція засіву.** Модуль у `packages/create-simetra-app/scripts/lib/` дає один крок «користувачі, ролі, рядки» за описом складу; `createDemo` (`packages/create-simetra-app/scripts/lib/demo.mts`) і `bringUp` (`e2e/fixtures.ts`) кличуть лише його — друга копія оркестрації зникає. Рядки: `seed()` з `template/scripts/seed.mjs` і `insertOwnClients` | none |
| Р4 | **Склад користувачів.** A — `ClientOwner`, власник засіяних рядків, пише. B — лише `ClientOwner`: контроль «без права читання рядків A» (наявний користувач `b` фікстури, рядки `B…`). R — `ClientOwner` + `ClientReader`, власні рядки `R…`: ціль відкликання. Адміністратор — лише `Administrator`, без браузера. Demo: `alice` (A), `bob` (B), `rita` (R), `admin`; друкує чотири входи | none |
| Р5 | **Відкликання — команда, не SQL.** `delete` над `GlobalRoleAssignments` рядка «R — `ClientReader`» від рантайму адміністратора з `expectedVersion`, прочитаною тим самим рантаймом. У demo — скрипт `pnpm demo:rights <grant|revoke> <user> <role>` над тією самою функцією засіву (Р3); у його виводі — команда для ручного показу | none |
| Р6 | **Межі часу.** `SIGNAL_REACTION_MS` = 5 000 мс: пачкування закривається за ≤ 2 с (П4-B §8.4, Рд23) плюс одне читання; у коді e2e — статична перевірка `SIGNAL_REACTION_MS < DEFAULT_CORE_LIMITS.resumeMinIntervalMs` (15 с) і `< revalidateIntervalMs` (60 с), тож межа не досяжна запасним шляхом. Межа відкликання — `RIGHTS_JITTER_MS + SIGNAL_REACTION_MS` (B6-2 Р12) і статично `< CHANNEL_TTL` (5 хв, профіль §6.2). Межа шини — `SIGNAL_REACTION_MS`. Сталі імпортуються з публічних входів `simetra`, не копіюються. На `main` їх там немає: `DEFAULT_CORE_LIMITS` лише в `packages/simetra/src/data/store/types.ts`, `CHANNEL_TTL` — неекспортована стала `packages/simetra/src/server/signals/tokens.ts`. Тому задача 1а експортує `DEFAULT_CORE_LIMITS` з `simetra/data` (типові межі ядра — частина контракту host-а) і строки токенів (`SIGNAL_TOKEN_TTLS` з `CONNECTION_TTL`, `CHANNEL_TTL`) з `simetra/server/signals`; `RIGHTS_JITTER_MS` експортує B6-2 з `simetra/data` (інтерфейс нижче) | П4-B — рядок публічного API `simetra/data` (задача 0 знаходить §) | none |
| Р7 | **Доказ механізму, не лише результату.** Кожне «з'явилося» чи «зникло» перевіряє ще й журнал сторінки: на її WebSocket прийшов кадр публікації потрібного каналу (об'єкта — для зміни; прав користувача R чи глобальних прав — для відкликання), і читання, що принесло новий стан, надіслано після кадру. Запасний інтервал має випадкову фазу `[0, I)` (`core.ts`), тож без цієї перевірки зелене могло б прийти з інтервалу. Спостережні сторінки після старту не отримують `bringToFront`/фокусу: `resume()` не кличеться | none |
| Р8 | **«Не бачить» — не порожньо й не через відповідь.** A пише в рядок унікальний маркер прогону (`acceptance-<runTag>`). Сторінка B отримала кадр каналу об'єкта для цього рядка (П4-B §8.6, перший пункт: ключі й версії приходять) і не показує рядка ні в списку, ні в картці за прямою адресою — до й після сигналу; **і** маркера, коду чи опису рядка A немає в жодному тілі відповіді `dataFn` сторінки B (журнал задачі 3) і в HTML SSR прямого `page.goto` картки рядка A. Порожній інтерфейс сам не доводить, що вміст не прийшов і не схований клієнтом | none |
| Р9 | **«Прибирає дані», а не ховає.** На час відкликання в R відкрито дві сторінки: список і картку рядка A. У межі Р6: картка переходить у стан `purged` з причиною «Доступ змінився — дані приховано» (П4-B §6.5) — не `hidden` і не `removed` після перечитування; рядки A зникають зі списку без слотів `hidden`, власні рядки `R…` лишаються. Потім запити `dataFn` сторінки списку R блокуються (`page.route`), і перехід усередині застосунку до картки іншого рядка A не показує його значень — сховище клієнта їх не має (B6-2 Р6). Мережа до сигналу не блокується: знімок прав R приходить тим самим `dataFn` (§9.3) | none |
| Р10 | **Вихід — шина, не Дх14.** Дві сторінки A в одному контексті; вихід у першій → друга на вході в межі Р6, і між виходом і переходом друга не надіслала жодного запиту `dataFn` (журнал мережі); її сторінка рядка після цього не показує значень A | none |
| Р11 | **Порядок і стан.** Специфікація — один послідовний `describe`; відкликання — останнім, бо змінює права R до кінця прогону воркера; інші специфікації R не вживають. Повторного видавання права немає (прогін не повторюється: `retries: 0`) | none |
