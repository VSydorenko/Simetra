# П4-B6 — кеш прав клієнта й сигнали прав: план-ескіз

> **Статус:** проєкт плану, 2026-11-09; приймає архітекторка `simetra-87`.
> Блок B6 спеки П4-B (§13). Ескіз: тут рішення, інтерфейси між блоками,
> інваріанти безпеки й «готово» задач. Тест-кейси, імена й дрібні кроки
> виконавець пише сам за кодом і спекою.
>
> **Залежності.** Після B5b частин A і B (знімок прав, приймач, порт з
> `refreshTokens`, `simetra/data/centrifugo`), ПГ-4/B2 частин B і C
> (`signal_outbox`, `signal_topic_allowed`, `signal_payload_allowed`, стенд,
> `authorizeChannels`), B3-3 (публічні хуки T5) і ПГ-2 (провайдер
> `postgres`). На `main` зараз немає жодного з них, крім ядра B3-2. Якорі на
> незмерджене позначено «після X».
> **Перед стартом кожної частини:** `.agents/skills/codebase-research/scripts/orient --plan <цей файл>`.
> Розійшлося ім'я — перейменуй у плані за кодом. Розійшлася поведінка —
> до архітекторки.
> **Спільні стеки.** Виконавець ніколи не виконує `pnpm db:stop`,
> `pnpm db:start`, `pnpm db:pg:stop`, `supabase stop`. DB-тести — лише
> `pnpm --filter … test:db*` під замками стеків.

**Goal:** клієнт знає свої права дій і рахує `can(action, object, { scope?, row? })`
за контрактом прав із клієнтського каталогу; зміна прав доходить до клієнта
сигналом за секунди, а не за інтервалом свіжості чи строком токена каналу.

**Architecture:**
- **T1/T0.** Компілятор кладе контракт прав об'єкта в клієнтський каталог.
  `rights_client_snapshot()` (B5b) дістає мої id учасника й значення вимірів.
  `signal_rights` і `signal_user_rights` пишуть рядок outbox від власника;
  кличуть їх `rights_bump` і тригери членства, призначень, зв'язків і
  «Користувачів». `signal_topic_allowed` у режимі підписки відкриває канали
  прав.
- **T4.** Обчислювач `can` — загальний код над контрактом і знімком B5b.
  Знімок лишається одним сховищем (`CoreSession.rightsSnapshot()`).
  Звуження обсягу `read` на заміні знімка застосовує `can(read, row)` до
  кожного рядка сховища й до читань, що були в польоті. Приймач B5b
  підписується на канали прав і реагує за §9.3.
- **T5.** `useCan` — хук над `can` і подією заміни знімка.

**Tech Stack:** TypeScript 7, Zod, Vitest 5 (фейкові таймери, jsdom),
fast-check, `pg` 8.23.1, Postgres 17, Centrifugo v6 (стенд ПГ-4/B2),
`centrifuge` 5.8.0.

**Spec:** [П4-B](../specs/2026-11-05-p4-b-client-data-design.md) §3, §6.2
правило 4, §6.5, §8.1–§8.4, §8.6, §9, §12 (рядки «unit T1», «unit T4 (кеш
прав)», «DB `simetra`», «стенд сигналу»), §13 рядок B6, §14.3; [спека
прав](../specs/2026-10-17-rights-design.md) Рх15, §5.2, §6.3; плани
[B5b](2026-11-08-p4-b5b-signal-receiver-rights-snapshot.md) і
[ПГ-4/B2](2026-11-08-pg-4-b2-signal-transport.md). Правила тестів — скіл
`writing-tests`.

## Global Constraints

- Коментарі — українською, пояснюють «чому»; JSDoc експортованого API —
  англійською. Коміти — Conventional Commits, опис українською, без
  трейлерів. Push і PR — архітекторка.
- 🔴 Без `--` перед шаблоном vitest у `pnpm --filter`.
- Кейс «на обох стеках» — спільне тіло в `*.support.ts` і два тонкі файли
  (`*.db.test.ts`, `*.supabase.db.test.ts`), як у B5b.
- Знімок прав у T4 — **одне** сховище (B5b Р1). Обчислювач, предикати
  підписки й звуження читають `scopeSets`, рядки прав, мої id учасника й
  значення вимірів лише через `CoreSession.rightsSnapshot()`.
- Обчислювач — не захист (§9.2). База — бар'єр. Помилка обчислювача дає
  зайву чи сховану кнопку; помилка звуження не сміє показати значення, яких
  база вже не дає.
- Запис у сховище — лише `core.commit(fn, token)`; старий токен нічого не
  пише.
- Без shims: речення «До B6…» у §6.2 правило 4 і `narrowed` B5b
  замінюються в тій самій зміні.

## Рішення

| № | Рішення | Вплив на спеку |
| --- | --- | --- |
| Р1 | **Контракт прав у клієнтському каталозі** — поле `rights?` запису каталогу T0: `actions: { action, extents: ("any" \| "own" \| { dimension: uuid })[] }[]`; `ownership: { carrier, owner: "user" \| { membership: scopeKindId } }[]`; `access: { dimension, carrier, fresh: boolean, subject: "user" \| "membership" }[]`; `binding?: { container: uuid, carrier }`; `readBoundary: "tenant" \| "users" \| "none"` (з `readBoundaries`); `root?: { author?: carrier }` (корінь виду скоупу, `rootAuthor`). `carrier` — `{ attribute: <логічне ім'я> } \| { key: true }` (носій-ключ, `carrierColumn`); колонка ні серед атрибутів, ні ключем — помилка компілятора. `fresh` — зв'язок `values.relation`, чий об'єкт не `declared` у `KIND_REGISTRY`; функція виміру чи прийнята `CustomTable` — `false`. `subject` — `subjectTarget` зв'язку. Окремо — `scopeSet: "membership" \| "verbatim"` у записі каталогу скоупленого об'єкта (з `AccessContract.scope.verbatim`). `publicRead` — поле B5b Task 1, не дублюється. Граф вимог і `deny` уже розгорнуто в рядках знімка. `snapshotHash` змінюється, `kernelHash` — ні | §3, §9.2 (задача 0) |
| Р2 | **Розширення знімка B5b** (розширює, не дублює): поле §9.1 `scopes` перейменовано на `members: { scopeKind, scope, member }[]` (`rights_my_scopes()`); `dimensionValues: { dimension, values: uuid[] }[]` (`rights_dimension_values()` на кожен вимір контрактів); поле `containers` вилучено — контейнерні права є рядками `rights` з `level = 'container'` (так рахує `rights_container`). `rightsVersion` B5b Р4 не змінюється; зміну `members` і `dimensionValues` ловить `rightsVersions` | §9.1; план B5b Р3 і Task 2 (задача 0) |
| Р3 | **Гілки `can` — дзеркало `rightsPredicates`** (`compiler/rights/predicates.ts`) для дії: гілка на кожен обсяг дії × носій. Грант гілки: скоуплений об'єкт — рядок `level = 'scope'` зі `scope` рядка (як `rights_any/own/dim`); глобальні й `everyUser` рядки скоупленого не відкривають; нескоуплений — будь-який рівень, крім `container` (як `has_right`); контейнерна гілка — рядок `level = 'container'` з тим самим **внутрішнім обсягом** і `container` = носій прив'язки, плюс умова цього обсягу (як `inContainer`). Умова гілки: `own` — носій = `userId` чи ∈ моїх `member` виду; вимір — носій ∈ `dimensionValues`. **`create` кореня** — окрема гілка `rootCreatePredicates`: грант будь-якого рівня, крім контейнера, без скоупу; `own` — лише автор (`root.author`) | §9.2 (задача 0) |
| Р4 | **Тризначна композиція (логіка Кліні).** Результат = **межі ∧ (∨ гілок)**: `true ∧ unknown = unknown`, `false ∧ x = false`. Межі: тенант — скоуп ∈ `scopeSets` виду (поза ним — `false`; для `scopeSet: "verbatim"` — `unknown`, §14.3); `users` — для `read` власний рядок (`key = userId`) `true`, решта `unknown`; `publicRead` знімає межу тенанта для `read` дійсного користувача (§14.3). `unknown` у гілці: вимір з `fresh: false`; відсутній носій у рядку; знімок без `versions` — гілки, що залежать від членства (`own` з `membership`, вимір з `subject: "membership"`), і межа тенанта виду з членством. Об'єкт без контракту `rights` — `can` завжди `unknown`. Без рядка — межі ∧ (∨ гілок без умов носіїв) | §9.2, §14.3 (задача 0) |
| Р5 | **Прибирання пар лишається булевим** (рішення архітекторки). `readAllowed` пари — як у B5b: `false` → `purge`. Для дослівного виду знімок на заміні читається живим, і межа бази — той самий `scopeSetCall`; тож скоупу немає в знімку — база пари вже не дає. `unknown` дослівного виду — лише в `can`/`useCan` (кешований знімок). `hide` слабший за `purge`: не скидає чернетку, не ховає журнал, не ставить надгробка пари | §14.3 — «для `can`» (задача 0) |
| Р6 | **Звуження обсягу `read`** замінює `narrowed` B5b. На кожній заміні знімка, коли змінились рядки `read`, `members`, `dimensionValues` чи `scopeSets`, ядро в одному `commit` рахує `can(read, object, { scope, row })` кожного ключа сховища (зокрема знімки показу вікна й цілі `include`): `false` — `purge({ keys })` (стан `purged`, чернетка `card` скинута); `unknown` — нова `ObjectStore.hideKeys(keys)` / `Writer.hide(object, keys)`: `stale.seen` з новою епохою (`visibleRow` ховає значення; знімає лише читання, почате після позначки), окремий запис журналу `rights-hidden` (не `horizon-hidden`), ключі — у хвіст перечитування; `revalidate` усіх виглядів, що тримають ключ, зокрема невидимих і підмножин `include`. Рядки ТЧ ідуть за шапкою власника: схована шапка ховає `section` (B3-2), `purge` власника чистить ТЧ. `removed` після звуження скидає чернетку, як `purged` (§6.2). Збій перечитування лишає сховано. Ключ без значень рядка (частковий запис, П14) рахується з рядком без носіїв — `unknown`, ніколи формою «без рядка». **Поки ключ схований**, показаний рядок (підтверджений ⊕ живі мутації журналу) і чернетка `card` цього ключа теж сховані (не скинуті); перечитування повертає їх чи веде до `removed`/`purged`. Без змін — 0 запитів | §6.2 правило 4 (задача 0) |
| Р7 | **Епоха прав для читань у польоті.** Заміна знімка зі звуженням чи втратою пари ставить об'єкту `rightsEpoch`. `put` рядка з `readEpoch < rightsEpoch` спершу проходить `can(read, row)` за поточним знімком: `false` — рядок відкинуто, `unknown` — вставлено схованим (`stale.seen`). Інакше сторінка з польоту вставила б чужі рядки видимими, а сигналу без зміни даних немає | §6.2 правило 4 (задача 0) |
| Р8 | **`signal_rights(p_scope_kind uuid, p_scope uuid, p_version bigint)`** і **`signal_user_rights(p_user uuid, p_version bigint)`** — `SECURITY INVOKER SET search_path = ''`, `EXECUTE` нікому (`executeGrants(…, [])`). Власник обходить RLS outbox (таблиця без `FORCE`), тож `signal_payload_allowed` його не судить; **форму перевіряє сама функція** до `INSERT`: аргументи не `NULL`, версія > 0, вид і скоуп обидва нульові чи обидва ненульові, користувач ≠ `ZERO_UUID`; інакше `RAISE` з `22023`. Тіло будує канал з аргументів і `data` рівно `{ op: "rights", row_ver }`; `id` ставить штамп outbox. Режим злиття сигналів прав не гасить | §8.2 (задача 0) |
| Р9 | **Хто шле.** `rights_bump` стає `RETURNS bigint` (нова версія; виклики — `PERFORM` чи `SELECT … INTO`). Сигнал прав **скоупу** (`signal_rights`) — лише з тригерів довідників прав (ролі, дельти, призначення) і зв'язків зі скоупом; **глобальний** канал — лише з довідників прав глобального рівня (адміністративна зміна, що стосується всіх). Сигнал **користувача** (`signal_user_rights`, версія — `max` версій скоупів цього користувача в операторі): тригер членства — `userColumn` старих і нових рядків `WHERE IS NOT NULL` (запрошення без користувача й самоприйняття легальні); призначення рівня скоупу — `subject` → користувач через довідник членства; глобальні — `subject`; зв'язок без колонки скоупу — його `subject` (користувач чи через членство); «Користувачі» на `invalid`/`user_kind` — сам рядок. Зв'язок без скоупу й «Користувачі» глобального каналу **не** чіпають. Тригер сигналу членства стоїть на кожному довіднику членства виду скоупу в проєкті з довідниками прав, зокрема виду без довідника прав рівня скоупу (там він сам кличе `rights_bump` пари). Для `UPDATE` і `DELETE` кожного тригера — старі й нові рядки: переміщення призначення чи зв'язку між скоупами дає сигнали обом скоупам і обом користувачам. `DISTINCT` у межах оператора. Прийняті джерела тригерів не мають — свіжість за інтервалом (§8.6) | §8.2, спека прав Рх15 (задача 0) |
| Р10 | **Режим підписки `signal_topic_allowed`** для каналів прав — у кожній гілці спершу `current_user_id() IS NOT NULL`; `simetra-rights:<вид>:<скоуп>` — вид є видом скоупу моделі й скоуп ∈ `scopeSetCall(вид)`; `simetra-rights:<нуль>:<нуль>` — дійсний користувач; змішані нулі — `false`; `simetra-user:<id>` — `id = current_user_id()`. Режим відправки обох префіксів лишається `false`, `signal_payload_allowed` з `op: "rights"` — `false` (B2) | §8.3 (задача 0) |
| Р11 | **Підписки приймача на канали прав** — лише коли знімок має `versions`. Канали: `simetra-rights:` кожного `scopeSets`, глобальний і `simetra-user:<userId>`. `canSubscribeRights(snapshot, channel)` — дзеркало Р10; перерахунок дельтою разом із каналами змін (B5b Р7) | §8.4 (задача 0) |
| Р12 | **Реакція** (§9.3). Канал прав скоупу чи глобальний з `row_ver` > кешованої версії пари (`BigInt`; пари немає — як більша) → `requestRights()` після джитера `random() × RIGHTS_JITTER_MS` (2000), сигнали в межах вікна злито; ≤ — ігнор. Сигнал каналу користувача → `requestRights()` і `refreshTokens()`: обидва перший раз — одразу, далі не частіше `REFRESH_MIN_MS` (5000) з одним хвостом. Нерозібране повідомлення каналу прав — як сигнал без версії. Відмова `auth`: канал прав скоупу — `purge({ scope })` кожного об'єкта виду й `requestRights()`; глобальний чи канал користувача — `requestVersion()` і `requestRights()` | §8.4 (задача 0) |
| Р13 | `useCan(action, object, opts?) : boolean \| "unknown"` у T5 поруч із хуками B3-3: `useSyncExternalStore` над `onRightsChange` (B5b) і `runtime.can`. Хост показує `unknown` доступним (§9.2). Функціональних опцій хук не рахує (П4-E) | немає |

## Інваріанти безпеки й тести, що червоніють на дефекті

Кожен рядок — тест виконавця й навмисна мутація на закоміченому дереві
(мутацію відкочує після червоного прогону). Кожен бар'єр судиться окремо,
щоб другий бар'єр не маскував мутацію першого. Мутація без червоного тесту
— дефект плану, до архітекторки.

| Інваріант | Тест (рівень) | Мутація, що мусить червоніти |
| --- | --- | --- |
| І1. Підробити сигнал прав може лише власник | DB обох стеків: `has_function_privilege(<роль>, 'simetra.signal_rights(uuid,uuid,bigint)', 'EXECUTE')` і так само `signal_user_rights` — `false` для `simetra_command`, `simetra_signals` і кожної ролі API профілю; `signal_topic_allowed('simetra-rights:…', true)` і `('simetra-user:…', true)` під `simetra_command` — `false` | `GRANT EXECUTE … TO simetra_command`; режим відправки повертає `true` для каналу прав |
| І2. Форма рядка від власника — у функції | DB: кожен недійсний аргумент Р8 — `22023` і 0 рядків outbox; дійсний — `data` рівно `{ id, op, row_ver }` | прибрати кожну перевірку Р8 окремо |
| І3. Зміна прав дає сигнал у правильний канал | DB: під `simetra_command` — зміна ролі скоупу → канал прав скоупу; переміщення призначення й зв'язку між скоупами → обидва скоупи й обидва користувачі; членство, призначення, деактивація → канал користувача; запрошення без користувача й самоприйняття — успіх; запис у зв'язок без скоупу — 0 рядків глобального каналу; `ROLLBACK` — 0 рядків | `rights_bump` без `signal_rights`; тригер членства без `signal_user_rights` чи без `IS NOT NULL`; зв'язок шле в глобальний |
| І4. Канал прав відкривається лише своєму | DB обох стеків, Р10: свій скоуп так, чужий ні, дослівна функція, що відсікає скоуп, ні, деактивований користувач (зокрема з дослівною функцією, що включає скоуп) ні, глобальний — лише дійсний, канал користувача — лише свій, змішані нулі ні; `authorizeChannels` відсіює чужі | гілка користувача без `= current_user_id()`; гілка скоупу без `scopeSetCall`; гілка без перевірки дійсного користувача |
| І5. Предикат T4 каналів прав ≡ база | DB-еквівалентність (розширення B5b Task 6): `canSubscribeRights` = `signal_topic_allowed(c, false)` на кожній парі «користувач, канал прав» | `canSubscribeRights` пропускає скоуп поза `scopeSets` |
| І6. Обчислювач ≡ ядро на фікстурах | DB обох стеків (§12 «DB `simetra`»): дії запису — `true`/`false` ≡ успіх/`no-right` ядра в транзакції з `ROLLBACK`; `read` — видимість `SELECT` під claims; без рядка — існування фікстурного рядка з успіхом. Фікстури: `any`, `own` (користувач і членство), вимір з оголошеним зв'язком, контейнерна роль з `any` і з `own`, `deny`, `fullAccess`, глобальна роль і `everyUser` на скоупленому й нескоупленому, `publicRead`, `create` кореня, дія з переходом, носій-ключ, дослівна функція, що відсікає скоуп із грантом рівня скоупу, «Користувачі» поза моїми скоупами. `unknown` еквівалентністю не судиться, але для `fresh: true` і знімка з `versions` не з'являється | `can` рахує глобальний рядок на скоупленому; контейнер без внутрішнього обсягу; межа як гілка `∨`, а не `∧` |
| І7. Втрата `read` ховає дані негайно | unit T4: звуження → `false` — `purge` ключа в усіх сховищах і чернетці `card`; `unknown` — значення сховано в тому самому `commit`, `revalidate` усіх виглядів ключа, збій перечитування лишає сховано, читання, почате до позначки, не відкриває; `unknown` → перечитування дало `removed` → чернетку скинуто; сторінка в польоті під час звуження (`any` → `own`) не вставляє чужих рядків видимими (Р7); частковий запис після звуження схований; поки ключ схований — показаний рядок з мутацією журналу й чернетка `card` без значень | `unknown` без `hide`; `hide` знімає читання, почате до позначки; `put` з польоту без `can`; частковий запис через форму «без рядка»; чернетка видима під `hide` |
| І8. Втрата пари — `purge`, зокрема для дослівного виду | unit T4: скоуп зник зі `scopeSets` (вид із членством і дослівний) — `purge` пари разом із чернеткою `card` і рядками журналу, надгробок пари відкидає читання в польоті; `can` для дослівного виду поза `scopeSets` — `unknown` | `readAllowed` повертає `unknown` замість `false` |

| І11. Старе покоління нічого не робить | unit T4 і модельний тест: сигнал прав і відповідь `rights` після `dispose()`/`session-changed` — 0 записів; таймери джитера й хвости `requestRights`/`refreshTokens` старого покоління — 0 викликів транспорту, 0 змін підписок | заміна знімка без перевірки токена; таймер без перевірки покоління |

## Review Focus

1. **Відкликане членство при живій підписці** — без сигналу межа 5 хв токена
   (§8.6), з сигналом — секунди. Стенд вимірює час до закриття каналу й
   прибирання; число — у §8.6 (задача 7).
2. **Видалення учасника разом із призначеннями одним оператором** —
   користувача призначення вже не знайти через членство; сигнал дає тригер
   членства. DB-кейс каскаду — задача 3.
3. **Масове створення членства** (провізія тенанта, імпорт) — один сигнал
   на користувача й один на скоуп. DB-кейс з 1 000 рядків одним оператором —
   задача 3.
4. **Кількість каналів прав** = |`scopeSets`| + 2. Межа `authorizeChannels`
   (256 каналів на виклик, B2) — виконавець звіряє, що транспорт B5b ділить
   запит токенів; якщо ні — до архітекторки.
5. **Шторм сигналів прав** — один оператор, що підвищує багато скоупів чи
   зачіпає багатьох користувачів, не дає кожному клієнту більше одного
   `requestRights()` на вікно джитера (Р12). Тест — задача 7.
