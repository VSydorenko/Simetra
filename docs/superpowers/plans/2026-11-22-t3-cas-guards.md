# План: T3 — CAS за полями й гарди сервера (#228, #175, #174, #191)

## 1. Заголовок

- **Статус:** чернетка на приймання; приймає архітекторка М5 (сесія
  `m4-simetra-milestone`). Виконує авторка плану (правило власника).
- **Опори після X:** частина C (правила тіла функцій, #174 п. 1) — лише після
  мерджу PR #335 (#271 Д5): він переписує `compiler/sql/function-body.ts`,
  `messages.ts`, `diagnostics.ts`. Частини A і B від #335 не залежать.
- **Спільні ресурси й заборони:** стек `postgres` спільний — DB-тести лише
  через `run-tests db --filter`/`--changed` (guard чекає черги); стек не
  зупиняти. Не чіпати `packages/simetra/src/data/**` (B5b-3 #326, B5b-4 #337
  у роботі), #192, #208. Клієнтська половина (`baseValues` у
  `DataWriter.update`, UI конфлікту) — #338 / #227, не тут.
- **Лише CI:** повні рівні `unit`, `db`, `db-supabase`, `e2e` і `packaging`
  (усі `ci: true` у `.agents/kit.profile.json`). Жодна задача не закінчується
  повним локальним прогоном; локально — лише `run-tests <рівень> --changed`
  чи `--filter`. Рівнів, яких CI не має, немає.

## 2. Мета / Архітектура / Спека

**Мета.** Сервер закриває вікно гонки «чужий запис між перевіркою клієнта й
нашою транзакцією» (#227, правило 3): `update` несе очікувані значення
змінених полів, ядро звіряє їх під тим самим замком рядка й відмовляє
`command.conflict` `reason: "fields"`. Разом — мапінг відмов T3 (#175), гарди
сесії пулу й джерел `src/server` (#174), розрізнювач і шлях відмов форми
передачі (#191).

**Архітектура.** Одна перевірка — одне місце: порівняння полів живе лише в
SQL-ядрі `<t>_save` (T1 генерує), під замком `FOR NO KEY UPDATE`, після
перевірки права над станом «до». T0 дає форму операції й причини відмов,
T3 лише передає параметр і вирішує придатність об'єкта (модуль з
`beforeWrite` → версія). Клієнт (T4) нічого не вирішує: шле і версію, і
значення; сервер обирає перевірку.

**Спека.** П4 рантайм `docs/superpowers/specs/2026-10-26-p4-runtime-design.md`
§5 (Рт2, Рт4), §6.4 (операція), §6.5 (перевірка до транзакції), §6.6
(`<t>_save`, порядок), §6.9 (хуки), §6.10 (помилки), §7.2–§7.3; П4-B
`docs/superpowers/specs/2026-11-05-p4-b-client-data-design.md` §7.1
(«Конфлікт»), §14.1 (рядок «CAS за полями»); платформна спека Р24; звіт
спайку ядра T4 §9 (`docs/superpowers/specs/2026-11-08-t4-core-spike-report.md`);
спека прав `docs/superpowers/specs/2026-10-17-rights-design.md` (дозвільний
перелік тіла функції) — для частини C.

## 3. Глобальні обмеження

- Без поступок сумісності (правило власника): підпис ядра змінюється без
  `DEFAULT` і без старої перегрузки; старий двоаргументний `save` зникає.
- Порядок усередині ядра (§6.6) лишається, CAS вбудовується в нього, не
  поруч.
- `COMMAND_CORE_ERRORS` (`packages/simetra/src/model/runtime/core.ts`) — єдине
  джерело причин ядра для T1 і T3; нова причина — лише там.
- Наявні тести лишаються зеленими; послаблення будь-якої перевірки чи
  оракула заради зеленого — розвилка до архітекторки.

## 4. Рішення

| # | Рішення | Вплив на спеку |
| --- | --- | --- |
| Р1 | **Форма.** `update` отримує необов'язкове `expectedValues` — ті самі логічні реквізити, що й `values`, з базовими значеннями. Набір ключів `expectedValues` дорівнює набору ключів `values`, непорожній; з `tabularSections` чи `deleteIds` — `command.invalid` (Zod T0, до бази). `expectedVersion` лишається обов'язковим: перемикач створення/зміни й перевірка для непридатних об'єктів. | П4 §6.4, §6.5 (правило операції) |
| Р2 | **Підпис ядра** — `<t>_save(p_item jsonb, p_expected_version bigint, p_expected_values jsonb)`. `p_expected_values IS NULL` — перевірка версії, як зараз; інакше — перевірка полів **замість** версії. `mark_deletion`, `delete`, `<корінь>_create_root` не змінюються. Нове ADR (наступний вільний номер на мить коміту; зараз 0096) «CAS за полями в ядрі», ADR-0067 отримує посилання. | П4 Рт2, §6.6; ADR-0067; нове ADR |
| Р3 | **Місце й порядок.** Гілка зміни: контекст → замок ієрархії → `SELECT … FOR NO KEY UPDATE` (`NOT FOUND` — `no-right`) → версія (лише коли `p_expected_values IS NULL`) → право над «до» → **поля** (лише коли задано) → решта як зараз. Поля — після права: розбіжність значень не стає оракулом змісту для того, кому дія над рядком не дозволена. | П4 §6.6 «Порядок усередині функції» |
| Р4 | **Порівняння.** Значення входу приводиться до типу колонки (`jsonb_populate_record(NULL::<t>, p_expected_values)`, той самий шлях, що й `p_item`) і порівнюється з рядком «до» в **тій самій закодованій формі, у якій ядро віддає колонку в результаті** (вираз кодування колонки `rowJson` у `catalog-command/units.ts`), через `IS DISTINCT FROM` над `jsonb`. Так рівність працює й для типів без оператора `=` (`json`, `xml`, `point` прийнятих таблиць), а typmod приводить обидва боки однаково. `NULL` очікуваний — очікується `NULL`. | П4 §6.6 |
| Р5 | **Вхід `p_expected_values`** проходить ту саму перевірку, що й `p_item` (`inputLines`): об'єкт, ключі лише з колонок зміни (`updateKeys`, без ключа таблиці й без `tabular`), приведення до типу. Додатково ядро відмовляє, коли набір ключів `p_expected_values` (без ключа таблиці) не дорівнює набору ключів зміни в `p_item` чи `p_item` має `tabular`. Відмова — `22023` з `DETAIL 'p_expected_values'` (нова причина `COMMAND_CORE_ERRORS.invalid.expectedValues`). Захист у глибину: «сліпе» поле без бази неможливе й при ваді T3. | П4 §6.6 |
| Р6 | **Відмова** — `P0001` `command.conflict`, `DETAIL 'fields'` (нова `COMMAND_CORE_ERRORS.conflict.fields`), `HINT` — поточна версія. Переліку полів і поточних значень відмова не несе: клієнт звіряє `baseValues` з перечитаним рядком (#227, правило 4), а `DETAIL`/`HINT` за §6.10 несуть лише значення з переліку й безпечне ціле. | П4 §6.10; спайк §9 — відхилення (без значень у відповіді) |
| Р7 | **Межа з обробником, що читає інші поля** (рішення, яке просить #228). Обробник підписки (`EventSubscription`, тригер бази) і `onWrite` виконуються під замком рядка над поточним рядком — CAS за полями для них коректний: похідне поле рахується з актуального рядка. Хук `beforeWrite` модуля об'єкта виконується **до** замка й може читати застарілий стан (`ctx.read`) чи дописати в чернетку поле без бази. Тому для об'єкта, чий модуль має `beforeWrite`, T3 передає `p_expected_values = NULL`: перевіряється версія, відмова — `reason: "version"`. Це суворіше, не слабше: тихого перезапису немає, лише більше конфліктів. Факт — з `objectModules` рантайму; каталог його не несе, клієнт його не знає й не потребує. | П4 §6.9 (новий абзац «Хуки й CAS за полями»), П4-B §7.1 «Конфлікт» |
| Р8 | **ТЧ — лише версія.** Масив ТЧ — повна заміна рядків, тож CAS за полями шапки разом із ТЧ тихо стер би паралельну правку інших рядків (Р1 це забороняє). Правило 6 #227 (правка рядків ТЧ) на сервері тримає версія власника — без тихого перезапису; польова перевірка рядків ТЧ — пізніше окремим рішенням разом із дельтами рядків (#338/#208). | П4-B §7.1 (дельта рядка); #227 — примітка |
| Р9 | **`kernelHash` не змінюється**: він хешує `operations` каталогу (імена функцій і дію контексту), а каталог не змінюється. Підпис ядра — факт версії платформи (lockstep), не контракту об'єкта. | П4 §6.3 — одне речення |
| Р10 | **`23503` на `delete`** (#175 п. 1): фаза `write` з `operation: "delete"` і `TABLE` помилки ≠ таблиці об'єкта фази → `command.invalid` `reason: "referenced"`, `object` — об'єкт фази, без `path`. Чужий об'єкт і його реквізит назовні не йдуть. *На апрув архітекторки* (альтернатива — `command.constraint` без реквізитів). | П4 §6.10, рядок `command.invalid` |
| Р11 | **Помилка без SQLSTATE** (#175 п. 2). Класифікує порт, бо лише він знає драйвер: `connectionLost` = SQLSTATE `08*`/`57P01..03`, мережевий код Node (`ECONNRESET`, `ETIMEDOUT`, `EPIPE`, `ECONNREFUSED`, `ECONNABORTED`, `EHOSTUNREACH`, `ENETUNREACH`, `ENOTFOUND`, `EAI_AGAIN`), відмова `pool.connect()` чи подія `error`/`end` клієнта до відмови запиту. Решта без SQLSTATE (`TypeError` драйвера, вада T3) — `command.internal` з журналом; з'єднання знищується в обох гілках (довіри до нього немає). Порядок подій `pg` (чи `end` приходить до відмови запиту) виконавець звіряє з опублікованим кодом закріпленої версії `pg` (`pkg-src`) і цитує файл/символ у коментарі. | П4 §6.5 «Утрата з'єднання», §6.10 (`unavailable`, `internal`) |
| Р12 | **CHECK правила рядка** (#175 п. 4): каталог рантайму несе для CHECK правила рядка колонки, які читає правило, у порядку колонок таблиці (`facts.checkColumns` стає багатозначним; джерело — розбір правила, `compiler/sql/row-rule.ts`). Тоді `23514` дає `command.constraint` `kind: "check"` з реквізитами правила — нової форми помилки немає. CHECK без колонок лишається `command.internal`. | П4 §6.10, рядок `command.constraint` |
| Р13 | **Функції сесії в T3** (#174 п. 2): `set_config`, `current_setting`, `pg_has_role` у SQL-тексті `src/server` — лише `pg_catalog.<функція>`; страж — тест джерел. | П4 §6.5 — одне речення в «Правила» |
| Р14 | **Тест джерел `src/server`** (#174 п. 3–4): правило «плоска тека» застаріло — `src/server/signals/` уже є. Замість лінту плоскої теки тест джерел обходить `src/server/**` рекурсивно (без `__tests__`), і всі його перевірки (провайдер, `process.env`, нова — I/O на верхньому рівні модуля: виклик на верхньому рівні, `fetch`, таймери, `new` I/O-об'єктів) діють на всі файли. | немає (спека правила плоскої теки не має) |
| Р15 | **Розрізнювач і шлях форми передачі** (#191): `leavesOf` (`server/read.ts`) відкидає гілку об'єднання за **явно названим** дискримінатором (ключ із самої схеми об'єднання — `discriminator`/літерали гілок), а не за «`invalid_value` на першому сегменті»; `operationRefusalPath` зберігає сегмент ТЧ так, що не-UUID ключ рядка ТЧ дає шлях `<ТЧ>.<індекс>.<ключ>`, а не шлях шапки. | П4-B §4.0 — немає (форма та сама, виправлення вади) |
| Р16 | **Сесія пулу** (#174 п. 1, частина C): у тілі функції чи процедури будь-якого файлу, борг включно, `SET`/`RESET` — лише `SET LOCAL` (`RESET` — заборонено: він сесійний), `set_config` — лише з третім аргументом-літералом `true`; тимчасова таблиця тіла не може мати ім'я типу `pg_catalog` (затінення типу через `pg_temp` до кінця транзакції). Перелік імен типів — стала T1 поруч із `builtin-functions.ts`; DB-тест звіряє її з `pg_type` схеми `pg_catalog` закріпленої версії. Відмова — помилка компілятора (коди — за класом правила тіла; один код на клас). Без винятку для боргу (правило власника: одне повне правило). | спека прав — дозвільний перелік тіла; П4 §7.3 — кейс пулера |

## 5. Інтерфейси

**Дає частина A іншим блокам (#338, #227 — клієнт):**

- T0 логічна форма: `{ action: "update", object, id, expectedVersion, values, expectedValues }`
  (`packages/simetra/src/model/runtime/operation.ts`,
  `updateOperationObjectSchema`); правила Р1.
- Форма передачі: `expectedValues` — за фізичними колонками, значення
  кодуються тим самим `encodeRow`, що й `values`
  (`model/runtime/wire.ts`, `mapping.ts`, конверт `envelope.ts`); звірка
  сумісності (`server/compatibility.ts`) перевіряє колонки `expectedValues`
  так само, як колонки `values`.
- Відмова: `CommandError` `{ code: "command.conflict", reason: "fields", currentVersion }`;
  для об'єкта з `beforeWrite` — `reason: "version"` (Р7). Клієнт обробляє
  обидві як конфлікт поля й перечитує рядок.
- Відображення для T4: `DataWriter.update` (#338) кладе `baseValues` змінених
  полів у `expectedValues`; локальна перевірка #227 лишається ранньою
  відмовою без `run`.

**Бере:** нічого з незмерджених блоків для A і B; C — після #335.
