# `@simetra/designer` — інструменти розробника

Рішення й причини — [спека designer](../superpowers/specs/2026-10-02-simetra-designer-design.md);
дослідження — [постачання інструментів, 2026-10](../research/tooling/toolset-delivery-2026-10.md).
Тут — як це працює в коді й з позиції двох проєктів: репо платформи й проєкту
споживача.

## 1. Один каталог, кілька режимів

```
                ┌──────────── @simetra/designer ────────────┐
CLI  simetra …  │  src/cli ─┐                               │
MCP  simetra mcp│  src/mcp ─┼─► src/tools: каталог + invoke ─┼─► T1 операції (simetra/compiler)
студія (П6)     │  src/studio ┘     │                        │
                │                   └─► src/io: читання теки, writeChanges
                └───────────────────────────────────────────┘
```

- **Каталог** (`src/tools/catalog.ts`) — один запис на інструмент: ім'я,
  опис, схема входу, дві осі доступу (`files`: `read`/`write`; `database`:
  `none`/`read`/`write`), ознака руйнівності, обробник. Обробник лише читає
  теку (і, з віссю бази, підключення) й викликає операцію.
- **`invoke`** (`src/tools/invoke.ts`) — єдине місце рішень: розбір входу,
  дозвіл режиму (`permits`, вичерпно по обох осях), наявність підключення для
  інструмента бази, підтвердження руйнівного, черга теки, запис лише при `ok`
  і без dry-run. Тексти підказок відмов — `src/tools/hints.ts`. Очікувані відмови (`UsageError`) стають відповіддю, решта
  винятків — ні, щоб баг не маскувався під відмову.
- **Черга теки** (`src/tools/queue.ts`) впорядковує записи в одну теку, тож
  паралельні виклики (MCP, згодом студія) не гублять зміни.
- **Режими** лише перекладають свій транспорт у `invoke`: CLI (`src/cli/`)
  виводить підкоманди з каталогу, MCP (`src/mcp/`) реєструє ті самі записи як
  інструменти. Імена однакові в обох режимах; перелік — у каталозі.
- **Інструменти бази** (`src/tools/database-tools.ts`) — `introspect`
  (`files: "write"`, `database: "read"`) і `diff` (`files: "read"`,
  `database: "read"`) складають двигун (`src/schema-engine`, вантажиться
  лише їхнім викликом), порт T2 (`compareWithDesired`, `engineScope`) і
  зворотний генератор (`reverseGenerate`). Підключення — ресурс запуску
  (`src/io/database.ts`: `databaseResource` з імен змінних, зафіксованих
  прапорцями `--database-url-env` / `--shadow-url-env`); пули відкриває
  адаптер двигуна на виклик і закриває в `finally`: кожне читання цілі — у
  транзакції `READ ONLY` (`src/schema-engine/read-only.ts`), без сесійного
  стану на цілі; тінь — окремий пул, що пише.
  Будь-який виняток підключення чи запиту класифікує одна межа
  (`withDatabase`): відмова підключення (недосяжна база, автентифікація,
  немає бази чи права, хибна адреса, тінь без `CREATEDB` чи іншої мажорної
  версії) стає відмовою виклику (код 2), збій самої роботи з базою —
  діагностикою `database.failed` (код 1). Текст в обох — стабільні фрази,
  `host:port/db` того сервера, що збійнув, і код помилки, тож рядок
  підключення, користувач і пароль не потрапляють у жоден канал виводу.
- **План і застосування** (`src/tools/apply-tools.ts`) — `plan`
  (`files: "write"`, `database: "read"`) будує план порту T2 (`buildPlan`) і
  пише артефакт у `plans/` поруч із текою метаданих — єдиний запис поза
  текою (спека designer §3.1, §3.2); `apply` (`files: "read"`,
  `database: "write"`, руйнівний) читає артефакт лише звідти й виконує його
  раннером T2 (`executePlan`). Порт виконання `ApplyDatabase` реалізує
  `src/schema-engine/apply-database.ts`: одне з'єднання й одна транзакція на
  виклик; пул, що може писати в ціль, `apply` відкриває лише після всіх
  перевірок, що не потребують бази.

## 2. Правила безпеки

| Правило | CLI | MCP |
| --- | --- | --- |
| Запис файлів | дозволений (прапорця `--read-only` немає: виклик мутації людиною — уже явна дія) | дозволений; з `simetra mcp --read-only` інструменти запису видимі, але виклик повертає пояснення, як увімкнути запис |
| Перегляд без запису | `--dry-run` (лише в інструментів, що пишуть файли; деінде — відмова); `apply` замість нього має `--rehearse` | `dryRun: true`; `apply` — `rehearse: true` |
| Руйнівний інструмент | `--yes` | `confirm: true`; перегляд підтвердження не потребує |
| Підключення до бази | лише із середовища запуску (типово `SIMETRA_DATABASE_URL`, інша — `--database-url-env`), ніколи з входу; без нього інструмент бази відмовляє з назвою змінної | те саме (`simetra mcp --database-url-env`) |
| Читання бази | ціль читається лише в транзакціях `READ ONLY`, без сесійного стану; тінь — поруч із ціллю або на сервері `--shadow-url-env` тієї самої мажорної версії | те саме |
| Запис у базу | лише `apply` з `--yes --plan-hash <hex>` показаного плану | лише з прапорцем запуску `simetra mcp --allow-database-write`, і виклик несе `confirm: true` та `planHash` |
| Запис узагалі | лише якщо результат компілюється без помилок | те саме |

Коди виходу CLI: `0` — успіх, `1` — у результаті є помилки діагностики (для
`diff` — ще й відмінності бази від метаданих; для інструментів бази — збій
роботи з базою, `database.failed`), `2` — відмова самого виклику
(вхід не за схемою, немає `--yes`, немає підключення, база недосяжна, помилка
використання чи вводу-виводу).

## 3. Єдині двері

`simetra compile --all` знаходить кожну теку метаданих (за
`*metadata/project.meta.json`) у піддереві поточної теки; `--staged` компілює
вміст індексу Git. У цьому репо це `pnpm metadata:check` (pre-commit — з
`--staged`, CI — без); у проєкті споживача — той самий режим.

## 4. Два проєкти

### Репо платформи (тут)

- `@simetra/designer` розробляється як пакет workspace; запуск — з
  вихідників (`packages/designer/bin/simetra.mjs` через tsx).
- Скіл споживача лежить у пакеті як частина продукту й **невидимий** агентам
  платформи: його немає в `.agents/skills` і `.claude/skills`, designer не є
  кореневою залежністю, його не індексують пошук документації й граф коду.
  Агенти платформи користуються лише скілами розробки.
- Якість скіла тримає тест прикладів: кожен приклад входу розбирається реальною
  схемою інструмента, кожна команда існує. Скіл змінюється в тому ж коміті, що
  й інструмент.

### Проєкт споживача

Цільовий сценарій (спека designer §4):

```bash
pnpm add simetra
pnpm add -D @simetra/designer
pnpm exec simetra init --agents claude,codex
```

- `init` кладе відносні симлінки `.claude/skills/<скіл>` і
  `.agents/skills/<скіл>` → `node_modules/@simetra/designer/skills/<скіл>` і
  пише MCP-конфіг без прапорців (запис увімкнено) і друкує, що є
  `--read-only`; `AGENTS.md` і `CLAUDE.md` споживача не
  змінює. Агент споживача знаходить скіл автодискавері, і той завжди тієї ж
  версії, що й встановлені інструменти й рантайм.
- Агент працює через MCP-інструменти (або CLI) за правилами скіла: перегляд
  `dryRun`, без `id` у вході, перейменування — інструментом з каскадом.
- Оновлення платформи — `pnpm up simetra @simetra/designer`; симлінки
  підхоплюють новий скіл самі, `init --check` у CI ловить розбіжності.

**Стан:** каталог (з `introspect`, `diff`, `plan` і `apply`), режими CLI і MCP,
`compile --all`, скіл у пакеті й тест прикладів — у коді. `simetra init`, збірка й публікація пакета, пілот із
tarball — разом із доставкою пакета (П0 (а), [ROADMAP](../ROADMAP.md)); до
того сценарій споживача відтворюється лише вручну.
