# ADR-0022: Рушій колекцій T4 — TanStack DB за фасадом і адаптерами

Status: superseded by ADR-0079
Decided by: owner
Spec: [платформна спека](../superpowers/specs/2026-09-24-simetra-platform-design.md) §2 (Р16), §8.1; [карта перевикористання](../research/stack/reuse-map-2026-09.md)

## Context

Рантайму даних потрібні колекції з оптимістичними мутаціями, вікнами, живими
запитами й синхронізацією. Будувати такий рушій з нуля дорого, а готова
бібліотека в сімействі TanStack вже використовується в стеку. Платформа
водночас не може звʼязати згенерований код з API конкретної бібліотеки.

## Decision

Рушій колекцій T4 — TanStack DB (колекції запитів у режимі on-demand) за
фасадом T4: фабрика колекцій, оптимістичні мутації, write-back, вікна,
relation-view, синхронізація резидентних колекцій. Рушій не знає джерела даних,
версія бібліотеки закріплена точно (ADR-0021), а згенерований код звертається до
контрактів Simetra, не до API бібліотеки (Р16, ADR-0010). Черга мутацій —
`offline-transactions` TanStack DB; налаштування перегляду й чернетки —
вбудовані `localStorage`- і `local-only`-колекції. Генератор списків сортує з
`limit` лише за збереженими колонками.

## Why

- Бібліотека дає готові колекції запитів у режимі on-demand з
  `loadSubsetOptions`, тож не потрібно писати рушій колекцій із нуля (карта
  перевикористання 2026-09).
- Фасад T4 й адаптери джерел ізолюють платформу від бібліотеки: заміна рушія
  не зачіпає згенерований код і UI (Р16).

## Rejected

- Інші кандидати й причини їх відхилення — у карті перевикористання; у спеці
  для цього рядка окремого переліку немає.

## Consequences

Фасад T4 зберіг межу, але бібліотека в статусі RC виявилась такою, що
відкладене застосування синхронних записів давало тіньовий стан фасаду, і
значна частина механізмів планів була обходами. Тому рішення замінено ADR-0079:
рушій T4 — власне ядро даних. Публічний контракт фасаду T4 (Р16) при цьому не
змінився.
