# ADR-0092: Декларація функції — JSON-файл поруч із SQL, схема Zod у T0

Status: proposed
Decided by: architect
Spec: [декларації функцій](../superpowers/specs/2026-11-18-sql-function-declarations-design.md) §5.1; [платформна спека](../superpowers/specs/2026-09-24-simetra-platform-design.md) §6.7

## Context

Платформна спека §6.7 обіцяла «TS-декларацію сигнатури поруч із SQL» для
`EXECUTE` функцій застосунку й названої перевірки `SECURITY DEFINER`-функції.
Механізму в коді немає. Компілятор — чиста функція `files → знімок`, і TS
застосунку він не виконує: `*.module.ts` читається як текст (стадія 5 —
typecheck), а вибір завантажувача TS (jiti чи type stripping Node) —
відкрите питання §13 до спайку на першому host. Єдине джерело типів
метаданих — схеми Zod у T0, і T0 не має залежностей, крім `zod`. Наявні
посилання метаданих на функції SQL (`setFunction` виду скоупу, `handler`
підписки) — JSON-поле `{ schema?, name }`.

## Decision

- Декларації функцій одного файлу `<основа>.sql` лежать у файлі
  `<основа>.functions.json` поруч із ним; схема файлу — Zod у T0.
- SQL лишається єдиним джерелом форми функції: підпис, мова, волатильність,
  `SECURITY DEFINER`, `SET search_path`. Декларація тримає лише те, чого SQL
  не виражає мовою платформи: викликачів (з них виводиться `EXECUTE`) і
  названу перевірку.

## Why

- Компілятор лишається чистою функцією над текстом: JSON розбирається тим
  самим шляхом, що й `.meta.json`, без виконання коду застосунку й без
  завантажувача TS. Питання §13 стосується лише модулів поведінки й не
  блокує #271.
- Тип декларації — `z.infer` схеми T0, як для решти метаданих; TS-форма
  дала б другий опис того самого типу.
- JSON diff/merge-friendly й редагується інструментами designer і агентами
  через ті самі мутації, що й `.meta.json`.
- Файл поруч із SQL тримає декларацію там, де її шукає читач функції, і
  працює однаково для модуля об'єкта, спільного `sql/` і боргу `CustomTable`.
- Форма функції в декларації повторювала б SQL: два місця одного факту
  розходяться, а `pg_get_functiondef` у зворотній генерації однаково дає її
  в тексті `CREATE`.

## Rejected

- TS-файл декларації — потребує завантажувача TS у компіляторі (спайк §13),
  виконання коду застосунку під час компіляції й другого опису типу поза Zod.
- Поле в `.meta.json` об'єкта — спільні файли `sql/` і борг не мають
  об'єкта-власника, тож декларації жили б у двох місцях.
- Один файл проєкту (як `sql-debt.json`) — далеко від SQL і спільна точка
  конфліктів злиття для незалежних змін.
- `SECURITY DEFINER` і `search_path` у декларації — дублює `CREATE`.

## Consequences

- designer читає новий суфікс `.functions.json`; зворотна генерація пише
  його поруч із `.sql`.
- Формулювання «TS-декларація» зникає зі спек; термін — «декларація функції»
  (`docs/GLOSSARY.md`).
- Кодоген підписів функцій бере підпис із розбору SQL, а доступність — із
  декларації; окремого TS-файлу для кодогену немає.
