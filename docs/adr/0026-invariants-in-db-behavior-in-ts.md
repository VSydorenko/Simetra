# ADR-0026: Інваріанти даних — у базі, поведінка команд — у TS у тій самій транзакції

Status: accepted 2026-10-01
Decided by: owner
Spec: [платформа в Postgres](../superpowers/specs/2026-10-01-platform-in-postgres-design.md) §2 (Р23), §3; [платформна спека](../superpowers/specs/2026-09-24-simetra-platform-design.md) §2 (Р23), §6.12

## Context

Принцип BRD «правила, які неможливо обійти» треба довести до рівня даних: кожен механізм, що мусить триматися для будь-якого автора запису, не може залежати від серверних функцій застосунку. JavaScript у базі на цільових провайдерах недоступний. Імпорт, міграції й `psql` теж пишуть дані й не проходять через команду.

## Decision

Критерій «для будь-якого автора запису». Усе, що мусить триматися для будь-якого автора (обов'язковість, незмінність проведеного, закриті періоди, цілісність посилань, підсумки, нумерація, версія), — обмеження, тригери, згенеровані функції й RLS. Обчислення, валідація понад декларативну й умовні правила команди — TS-хуки всередині `runCommand` у тій самій транзакції. Запити над даними (рухи, вибірки для правил) — SQL-модуль об'єкта. Імпорт і міграції пишуть у режимі `SET LOCAL simetra.write_mode = 'import'`: тригери платформи читають цей транзакційний параметр і вимикають лише поведінку, а не інваріанти; роль мігратора перевіряється.

## Why

- «Усе в SQL» означало б писати прикладну логіку на PL/pgSQL — регрес відносно 1С для TS-команд, бо JavaScript у базі в цільових провайдерів недоступний ([спека](../superpowers/specs/2026-10-01-platform-in-postgres-design.md) §2, Р23).
- «Усе в TS» не тримається для імпорту, міграцій і `psql`.
- Межа за критерієм «для будь-якого автора» відтворює модель 1С, де `ОбменДанными.Загрузка` — режим без поведінки.
- Критерій успіху №1: жоден інваріант даних не залежить від того, через які двері прийшов запис — команда T3, MCP, імпорт, міграція, `psql` (§1).

## Rejected

- `session_replication_role` як режим імпорту — вимикає й FK та потребує суперкористувача.
- Усе в SQL — прикладна логіка на PL/pgSQL замість TS.
- Усе в TS — не тримає інваріанти для імпорту, міграцій і `psql`.

## Consequences

Легше: одне правило, куди класти нову перевірку, і можливість імпорту без обходу інваріантів. Важче: кожен новий механізм платформи мусить мати форму обмеження чи тригера, а тригери поведінки читають `write_mode`. Не «виправляти»: `session_replication_role` не вводити як режим імпорту; режим `import` не повинен вимикати інваріанти.
