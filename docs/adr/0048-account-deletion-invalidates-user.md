# ADR-0048: Видалення облікового запису робить користувача `invalid`; FK на таблицю провайдера немає

Status: accepted 2026-10-07
Decided by: owner
Spec: [системна схема й користувачі](../superpowers/specs/2026-10-07-system-schema-users-design.md) §2 (С4, С8), §6, §7.1

## Context

Провайдер видаляє облікові записи (фізично чи м'яко) без блокування, а сліди роботи користувача (авторство, виконавці) живуть далі. Зрілі метадані-платформи не видаляють користувача, а роблять його недійсним. У 1С це реквізит `Недействителен`.

## Decision

Видалення облікового запису в провайдера (фізичне чи м'яке, або вебхук IdP) видаляє рядок `identities` і ставить `invalid` у «Користувачі»; сам рядок користувача не видаляється, посилання авторства й виконавця лишаються. Застосунок блокує людину платформною командою, що ставить `invalid`, не чіпаючи облікового запису в провайдера. Знеособлення — явна платформна команда для реквізитів з новою властивістю `personalData`: очищає найменування й такі реквізити, рядок не видаляє (id лишається як «знеособлений користувач»). Фізичне видалення — лише платформна команда очистки, коли на рядок ніщо не посилається (FK це гарантує). FK на таблицю провайдера немає, зокрема на Supabase немає FK з «Користувачі» на `auth.users`; інваріант адаптера Supabase: `id` рядка «Користувачі» дорівнює `auth.users.id`.

## Why

- Провайдер видаляє свій рядок без блокування лише тоді, коли FK на нього немає; сліди роботи живуть ([спека](../superpowers/specs/2026-10-07-system-schema-users-design.md) §2, С4; §6).
- Перевірено, що FK з «Користувачі» на `auth.users` змушує видалення облікового запису в Auth падати, а з `CASCADE` — знищує користувача разом зі слідами роботи (§7.1, С8).
- Рівність `id` дає `current_user_id()` = `auth.uid()` для дійсного користувача, а наявні дані, що посилаються на обліковий запис, переходять на «Користувачі» заміною FK без переписування значень.

## Rejected

- FK «Користувачі» → таблиця провайдера — блокує видалення облікового запису або каскадом знищує сліди.
- Видалення рядка користувача разом з обліковим записом — ламає авторство й посилання.
- Знеособлення видаленням рядка — id має лишитися як «знеособлений користувач».

## Consequences

Легше: провайдер видаляє облікові записи вільно, історія роботи не рветься. Важче: знеособлення — окрема явна команда, а властивість `personalData` мусить бути оголошена на реквізитах. Не «виправляти»: не додавати FK на таблицю провайдера й не видаляти рядки користувачів, на які посилаються дані.
