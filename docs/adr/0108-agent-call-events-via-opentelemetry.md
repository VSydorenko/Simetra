# ADR-0108: журнал викликів агента — подія з формою платформи, вихід через OpenTelemetry, у базі не зберігається

Status: accepted 2026-11-24
Decided by: owner
Spec: [П4-F](../superpowers/specs/2026-11-24-p4-f-agents-design.md) §5.4

## Context

Журнал прав бачить лише зміни прав, а журнал змін даних належить історії версій. Що агент читав, не видно ніде. Рядок на кожен виклик агента швидко росте; з часом журнал аналізують у спеціальній системі логів. Рішення про спостережуваність у платформі досі немає, тож це рішення — перше й задає зразок.

## Decision

- Платформа фіксує форму події виклику агента: час, тривалість, інструмент, хеш входу, статус, код помилки, кількість рядків, `sub`, `act.sub`, тенант закріплення. Значень даних і тексту входу подія не несе.
- Адаптер MCP-входу видає подію через порт host-а; платформа подію в базі не зберігає.
- Шаблон host-а без налаштувань пише подію JSON-рядком у стандартний вивід за моделлю даних логів OpenTelemetry; з налаштованим експортером OpenTelemetry — шле її туди.
- Ротація й строк зберігання — справа системи логів.

## Why

- Основна база не навантажується журналом, що росте з кожним викликом.
- Перехід на спеціальну систему логів (Grafana Loki, ClickHouse, OpenSearch тощо) — налаштування host-а, а не код платформи.
- Регламентних завдань для ротації таблиці в платформі ще немає (платформна спека §13).

## Rejected

- Таблиця в базі з поділом за місяцями — навантажує базу, потребує регламентного завдання, переїзд у систему логів — новий код.
- Таблиця й OpenTelemetry разом — два механізми зберігання.
- Без журналу — читання агентом не простежити.

## Consequences

Без системи логів журнал живе лише у виводі сервера; історії викликів у застосунку немає. Остання активність підключення на екрані підключених клієнтів береться з таблиць Better Auth (видача й оновлення токенів), а не з журналу. Залежність OpenTelemetry — у шаблоні host-а, а не в пакеті `simetra`.
