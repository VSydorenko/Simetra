# ADR-0020: Нове перерахування — `text` + `CHECK` з мітками; прийнятий Postgres-енум стає `Enumeration` з наявними мітками

Status: accepted 2026-09-28
Decided by: owner
Spec: [спека П2](../superpowers/specs/2026-09-28-p2-metamodel-compiler-design.md) §2 (М15), §4; [спека промоції](../superpowers/specs/2026-10-06-promotion-design.md) §3 (Пр9), §9

## Context

Перерахування мусить бути читабельним у даних і змінюватися без простою:
додавання й видалення значень — звичайна зміна схеми. Енам-тип Postgres не
видаляє значення без переписування таблиці. Прийняті бази вже можуть містити
енам-типи, які не можна просто замінити.

## Decision

- Нове перерахування фізично — колонка `text` + `CHECK (… IN …)`. Значення має
  UUID, логічне ім'я й фізичну мітку, призначену раз; порядок значень — у
  метаданих (М15).
- Перейменування значення — лише метадані; додавання й видалення значення —
  «розширити → звузити» `CHECK` (ADR-0005).
- Це шаблон лише для нових перерахувань: прийняті енам-типи Postgres
  виражаються як є в `CustomTable`.
- При промоції прийнятий енам-тип конвертується у вид `Enumeration`; фізичні
  мітки значень дорівнюють наявним міткам енаму, тож `UPDATE` даних і
  переписування літералів не потрібні (Пр9).

## Why

- Дані читабельні; додавання й видалення без простою (енам-тип Postgres не
  видаляє значення без переписування таблиці); мітка робить перейменування
  безкоштовним (М15).
- Мітки, призначені раз, не вимагають зміни даних при промоції (Пр9).

## Rejected

- Таблиця значень з UUID — нечитабельні дані, засів значень у кожну БД і жодного
  виграшу, коли ім'я не відрізняється від мітки.
- Енам-тип Postgres для нових перерахувань — видалення значення потребує
  переписування таблиці.

## Consequences

Легше: зміна набору значень без простою, читабельні дані. Важче: цілісність
значень тримає `CHECK`, а не тип. Не «виправляти»: прийняті енам-типи лишаються
енамами в `CustomTable` до промоції; мітка значення літерал у `CHECK` і в даних,
тому дві однакові мітки в одному перерахуванні — помилка.
