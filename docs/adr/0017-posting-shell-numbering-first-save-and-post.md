# ADR-0017: Проведення — оболонка платформи й рухи SQL-запитом модуля; номер першим записом; `saveAndPost` в одній транзакції

Status: accepted 2026-09-28
Decided by: owner
Spec: [спека П2](../superpowers/specs/2026-09-28-p2-metamodel-compiler-design.md) §2 (М5, М21, М22), §5, §7; [спека «Платформа в Postgres»](../superpowers/specs/2026-10-01-platform-in-postgres-design.md) §2 (Р25), §5

## Context

Рухи реальних документів виходять за межі будь-якого декларативного опису, а
механіка навколо них (блокування, статус, права, підсумки) однакова для всіх
документів. Потрібен розподіл: що дає платформа, а що пише модуль. Окремо
треба визначити, коли документ отримує номер і як змінюється проведений
документ.

## Decision

- Проведення = оболонка платформи + рухи SQL-запитом модуля; декларативний
  конструктор рухів — лише для простих випадків (М5).
- Контракт оболонки: функції `<doc>_save(p_document jsonb, p_expected_version
  bigint)`, `<doc>_post(p_id uuid)`, `<doc>_unpost(p_id uuid)`; команда
  `saveAndPost` композує їх в одній транзакції T3: `unpost` → `save` → `post`
  (М22, Р25).
- Номер документа й код довідника призначаються першим записом із лічильника в
  тій самій транзакції; період номера — генерована колонка в поясі проєкту;
  унікальність `(носій скоупу, період, номер)` (М21, Р25).
- Проведений документ незмінний: прямий `UPDATE`/`DELETE` документа й його ТЧ
  блокує тригер, що пропускає лише оболонку за транзакційним прапорцем.

## Why

- Реальні рухи виходять за межі будь-якого DSL; механіка однакова для всіх
  документів (М5).
- Виміряно на платформі 1С: номер — першим записом у режимі «Запись», а
  проведений документ змінюється повторним записом у режимі «Проведение»
  атомарно ([спека «Платформа в Postgres»](../superpowers/specs/2026-10-01-platform-in-postgres-design.md) §2, Р25).
- Користувач бачить номер чернетки; редагування проведеного — одна дія, а не
  дві транзакції з гардом від дубля.

## Rejected

- Повний posting DSL — не покриває реальні рухи.
- Послідовність (`sequence`) для номера — дає пропуски.
- Прямий `UPDATE` проведеного документа — обходить оболонку й підсумки.

## Consequences

Легше: однакова механіка проведення для всіх документів, а модуль пише лише
запит рухів. Важче: пропуски номерів від видалених чернеток прийнятні й не
виправляються. Не «виправляти»: `saveAndPost` — одна транзакція, а не два
виклики з клієнта.
