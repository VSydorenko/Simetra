# Дослідження: Повна карта метаданих 1С:Підприємство 8.3

> **Мета:** Глибокий аналіз системи метаданих платформи 1С:Підприємство 8.3 як основа для BRD open-source візуального конфігуратора бізнес-метаданих.  
> **Дата:** 2026-03-22  
> **Формат:** Структурований технічний документ

---

## 1. Повний перелік типів об'єктів метаданих

Дерево метаданих конфігурації 1С:Підприємство 8.3 складається з кількох великих груп. Нижче наведено повний перелік, згрупований за функціональним призначенням.

### 1.1. Загальні об'єкти (General)

| Тип об'єкта | Опис | Призначення |
|---|---|---|
| **Підсистеми** (Subsystems) | Логічне групування функціональності | Визначає командний інтерфейс, розділи програми |
| **Загальні модулі** (CommonModules) | Модулі з повторно використовуваним кодом | Серверні, клієнтські, зовнішнього з'єднання |
| **Параметри сеансу** (SessionParameters) | Значення, що зберігаються у пам'яті сеансу | Поточний користувач, поточна організація тощо |
| **Ролі** (Roles) | Набори прав доступу | RLS, права на об'єкти метаданих |
| **Загальні реквізити** (CommonAttributes) | Реквізити, спільні для багатьох об'єктів | Організація, Відповідальний тощо |
| **Плани обміну** (ExchangePlans) | Налаштування обміну даними | Розподілені бази, обмін між конфігураціями |
| **Критерії відбору** (FilterCriteria) | Параметризовані відбори | Пошук пов'язаних об'єктів |
| **Підписки на події** (EventSubscriptions) | Обробники подій об'єктів | Підписка на ПередЗаписом, ПриЗаписі тощо |
| **Регламентні завдання** (ScheduledJobs) | Завдання, що виконуються за розкладом | Фонові/планові операції |
| **Функціональні опції** (FunctionalOptions) | Перемикачі функціональності | Увімкнення/вимкнення блоків конфігурації |
| **Параметри функціональних опцій** (FunctionalOptionsParameters) | Параметри, що визначають значення опцій | Зв'язок опцій з даними |
| **Визначені типи** (DefinedTypes) | Іменовані складені типи | Централізоване управління типами |
| **Сховища налаштувань** (SettingsStorages) | Сховища для збереження налаштувань користувачів | Варіанти звітів, налаштування форм |
| **Загальні форми** (CommonForms) | Форми, не прив'язані до об'єктів | Діалоги вибору, налаштувань |
| **Загальні команди** (CommonCommands) | Команди, доступні глобально | Дії в командному інтерфейсі |
| **Групи команд** (CommandGroups) | Групування команд | Організація меню |
| **Загальні макети** (CommonTemplates) | Шаблони друкованих форм, макетів | Табличний документ, Active Document, HTML |
| **XDTO-пакети** (XDTOPackages) | Опис XML-типів | Для web-сервісів та обміну |
| **Web-сервіси** (WebServices) | SOAP web-сервіси | Публікація API |
| **HTTP-сервіси** (HTTPServices) | RESTful HTTP-сервіси | REST API |
| **WS-посилання** (WSReferences) | Посилання на зовнішні web-сервіси | Споживання зовнішніх SOAP-API |
| **Стилі** (Styles) | Візуальне оформлення | Кольори, шрифти елементів інтерфейсу |
| **Мови** (Languages) | Мовні налаштування | Мультимовність конфігурації |

### 1.2. Прикладні об'єкти — Довідкова інформація

| Тип об'єкта | Опис |
|---|---|
| **Константи** (Constants) | Одиничні значення (назва організації, ставка НДС) |
| **Довідники** (Catalogs) | Списки умовно-постійної інформації (контрагенти, номенклатура) |
| **Перелічення** (Enums) | Фіксовані набори значень (стать, статус замовлення) |
| **Плани видів характеристик** (ChartsOfCharacteristicTypes) | Динамічно розширювана аналітика (додаткові реквізити) |
| **Плани рахунків** (ChartsOfAccounts) | Плани бухгалтерських рахунків |
| **Плани видів розрахунку** (ChartsOfCalculationTypes) | Види нарахувань/утримань для розрахунку зарплати |

### 1.3. Прикладні об'єкти — Документи і рух

| Тип об'єкта | Опис |
|---|---|
| **Документи** (Documents) | Реєстрація подій господарської діяльності |
| **Журнали документів** (DocumentJournals) | Об'єднання документів різних типів у спільний перелік |
| **Послідовності** (Sequences) | Контроль хронологічного порядку проведення документів |
| **Нумератори** (DocumentNumerators) | Наскрізна нумерація документів різних типів |

### 1.4. Прикладні об'єкти — Регістри

| Тип об'єкта | Опис |
|---|---|
| **Регістри відомостей** (InformationRegisters) | Зберігання структурованої інформації «ключ → значення» з можливою періодичністю |
| **Регістри накопичення** (AccumulationRegisters) | Накопичення числових даних: остатки та/або обороти |
| **Регістри бухгалтерії** (AccountingRegisters) | Бухгалтерські проводки (дебет-кредит) у розрізі плану рахунків |
| **Регістри розрахунку** (CalculationRegisters) | Розрахунок зарплати з механізмами витіснення та залежності |

### 1.5. Прикладні об'єкти — Бізнес-процеси

| Тип об'єкта | Опис |
|---|---|
| **Бізнес-процеси** (BusinessProcesses) | Опис маршрутів виконання завдань (карта маршруту) |
| **Задачі** (Tasks) | Елементи виконання, породжені бізнес-процесами |

### 1.6. Прикладні об'єкти — Звітність і обробка

| Тип об'єкта | Опис |
|---|---|
| **Звіти** (Reports) | Формування звітності (зазвичай на базі СКД) |
| **Обробки** (DataProcessors) | Утилітарні операції, що не мають власних даних у БД |

### 1.7. Прикладні об'єкти — Зовнішні джерела

| Тип об'єкта | Опис |
|---|---|
| **Зовнішні джерела даних** (ExternalDataSources) | Доступ до зовнішніх SQL-баз без ETL |

### 1.8. Підлеглі об'єкти (Sub-objects)

Ці об'єкти існують лише в контексті батьківського:

- **Реквізити** (Attributes) — поля об'єктів
- **Табличні частини** (TabularSections) та їх реквізити
- **Форми** (Forms) — керовані форми (managed forms)
- **Макети** (Templates) — табличні документи, HTML, Active Document
- **Команди** (Commands) — дії об'єкта
- **Виміри** (Dimensions) — для регістрів
- **Ресурси** (Resources) — для регістрів
- **Графи** (ExtDimensionAccountingFlags) — субконто для плану рахунків
- **Ознаки обліку** (AccountingFlags) — прапорці обліку для рахунків
- **Предефіновані елементи** (PredefinedData) — для довідників, ПВХ, планів рахунків

## 2. Детальний опис прикладних типів метаданих

### 2.1. Константи (Constants)

**Стандартні реквізити:** Відсутні у звичному розумінні. Кожна константа — це єдине значення визначеного типу.

**Налаштування типу:**
- Тип значення (будь-який примітивний або посилальний)
- Режим запису (Допустимо / Заборонено при записі транзакції)

**Підоб'єкти:** Форма константи, форма набору констант, менеджер значення.

**Особливості:** Константи не мають реквізитів або табличних частин. Зберігаються в одній системній таблиці. Набір констант може бути записаний атомарно в одній транзакції.

---

### 2.2. Довідники (Catalogs)

**Стандартні реквізити:**

| Реквізит | Тип | Опис |
|---|---|---|
| Посилання (Ref) | СправочникСсылка.<Ім'я> | Унікальний ідентифікатор елемента |
| Код (Code) | Рядок / Число | Код елемента (автонумерація) |
| Найменування (Description) | Рядок | Найменування елемента |
| ПозначенняВидалення (DeletionMark) | Булево | Позначка на видалення |
| Батько (Parent) | СправочникСсылка.<Ім'я> | Посилання на батьківську групу (ієрархія) |
| ЦеГрупа (IsFolder) | Булево | Прапорець: елемент чи група |
| Власник (Owner) | СправочникСсылка.<ІмʼяВласника> | Посилання на власника (підпорядкований довідник) |
| Предефінований (Predefined) | Булево | Чи є елемент предефінованим |
| ІмʼяПредефінованого (PredefinedDataName) | Рядок | Програмне ім'я предефінованого елемента |

**Налаштування типу:**
- Довжина коду та тип коду (Рядок / Число)
- Довжина найменування
- Ієрархія: Ні / Ієрархія груп та елементів / Ієрархія елементів
- Обмеження кількості рівнів ієрархії
- Власники (список довідників-власників, тип підпорядкування)
- Автонумерація (увесь довідник / у межах підпорядкування)
- Контроль унікальності коду
- Серія коду
- Основне представлення (Код / Найменування)
- Характеристики введення на основі
- Привілейований режим отримання даних

**Підоб'єкти:** Реквізити, Табличні частини (та їх реквізити), Форми, Макети, Команди.

**Особливості:**
- Підтримка ієрархії (групи + елементи або тільки елементи)
- Підпорядкування іншим довідникам (один до багатьох)
- Предефіновані елементи (фіксовані в конфігурації)
- Автонумерація з контролем унікальності

---

### 2.3. Документи (Documents)

**Стандартні реквізити:**

| Реквізит | Тип | Опис |
|---|---|---|
| Посилання (Ref) | ДокументСсылка.<Ім'я> | Унікальний ідентифікатор |
| Номер (Number) | Рядок / Число | Номер документа |
| Дата (Date) | Дата | Дата та час документа |
| ПозначенняВидалення (DeletionMark) | Булево | Позначка на видалення |
| Проведений (Posted) | Булево | Прапорець проведення |

**Налаштування типу:**
- Довжина номера, тип номера (Рядок / Число)
- Нумератор (свій або спільний DocumentNumerator)
- Періодичність нумерації (Рік / Квартал / Місяць / День / Невизначена)
- Автонумерація
- Проведення: Заборонити / Дозволити
- Оперативне проведення (Дозволити / Заборонити)
- Привілейований режим при проведенні
- Послідовності, в які входить документ
- Введення на основі / на підставі
- Рухи по регістрах (перелік регістрів, по яких документ здійснює рухи)

**Підоб'єкти:** Реквізити, Табличні частини, Форми, Макети, Команди.

**Особливості:**
- Проведення (posting) — центральний механізм реєстрації рухів
- Кожен документ має момент часу (ДатаЧас + Посилання) для однозначного впорядкування
- Рухи по регістрах задаються на вкладці «Рухи» конструктора
- Підтримка скасування проведення
- Журнали документів для об'єднаного відображення

---

### 2.4. Перелічення (Enums)

**Стандартні реквізити:**

| Реквізит | Тип | Опис |
|---|---|---|
| Посилання (Ref) | ПеречислениеСсылка.<Ім'я> | Посилання на значення переліченння |
| Порядок (Order) | Число | Порядковий номер |

**Налаштування типу:** Тільки список значень (задається на етапі конфігурування).

**Підоб'єкти:** Значення переліченння (EnumValues), Форми, Команди.

**Особливості:**
- Значення фіксовані, користувач не може їх змінювати
- Не мають коду, найменування, реквізитів або табличних частин
- Синонім кожного значення — це його "найменування" для користувача
- В БД зберігаються як порядковий номер або внутрішній ідентифікатор

---

### 2.5. Регістри відомостей (InformationRegisters)

**Стандартні реквізити:**

| Реквізит | Тип | Опис |
|---|---|---|
| Період (Period) | Дата | Період запису (для періодичних регістрів) |
| Реєстратор (Recorder) | ДокументСсылка.* | Документ-реєстратор (для підпорядкованих) |
| НомерРядка (LineNumber) | Число | Порядковий номер запису у наборі |
| Активність (Active) | Булево | Чи активний запис |

**Налаштування типу:**
- Періодичність: Непер. / У межах секунди / У межах дня / У межах місяця / У межах кварталу / У межах року
- Режим запису: Незалежний / Підпорядкований реєстратору
- Основний відбірний період
- Дозволити підсумки зрізу останніх

**Структура даних (підоб'єкти):**
- **Виміри** (Dimensions) — ключ запису, визначають розрізи зберігання
- **Ресурси** (Resources) — збережувана інформація
- **Реквізити** (Attributes) — додаткова інформація
- Форми, Макети, Команди

**Особливості:**
- Два режими запису: незалежний (редагується вручну) та підпорядкований реєстратору (записи пишуться через документи)
- Зріз останніх / зріз перших — віртуальні таблиці для отримання актуальних значень на дату
- Ключ унікальності = Період + Виміри (+ Реєстратор + НомерРядка для підпорядкованих)

---

### 2.6. Регістри накопичення (AccumulationRegisters)

**Стандартні реквізити:**

| Реквізит | Тип | Опис |
|---|---|---|
| Період (Period) | Дата | Дата руху |
| Реєстратор (Recorder) | ДокументСсылка.* | Документ-реєстратор |
| НомерРядка (LineNumber) | Число | Порядковий номер |
| Активність (Active) | Булево | Чи активний запис |
| ВидРуху (RecordType) | ВидДвиженияНакопления | Прихід (+) або Розхід (−) — тільки для залишкових |

**Налаштування типу:**
- Вид регістру: **Залишки** (Balance) або **Обороти** (Turnovers)
- Дозволити розділення підсумків (для паралельності запису)
- Регістратори (перелік типів документів)

**Структура даних:**
- **Виміри** (Dimensions) — аналітичні розрізи (Номенклатура, Склад, тощо)
- **Ресурси** (Resources) — числові значення, що накопичуються (Кількість, Сума)
- **Реквізити** (Attributes) — додаткова інформація (не бере участі в агрегації)
- Форми, Макети, Команди

**Особливості:**
- Для залишкових — підтримується таблиця підсумків (залишки на кінець місяця) + оперативні підсумки
- Для оборотних — тільки обороти (без знаку приходу/розходу)
- Ресурси — тільки числовий тип
- Віртуальні таблиці: Залишки, Обороти, ЗалишкиТаОбороти (для залишкових); Обороти (для оборотних)
- Всі записи обов'язково підпорядковані документу-реєстратору

---

### 2.7. Регістри бухгалтерії (AccountingRegisters)

**Стандартні реквізити:**

| Реквізит | Тип | Опис |
|---|---|---|
| Період (Period) | Дата | Дата проводки |
| Реєстратор (Recorder) | ДокументСсылка.* | Документ-реєстратор |
| НомерРядка (LineNumber) | Число | Порядковий номер |
| Активність (Active) | Булево | Активність запису |
| РахунокДт (AccountDr) | ПланСчетовСсылка.* | Рахунок дебету |
| РахунокКт (AccountCr) | ПланСчетовСсылка.* | Рахунок кредиту |
| СубконтоДт[N] | Характеристика | Субконто дебету N-го виду |
| СубконтоКт[N] | Характеристика | Субконто кредиту N-го виду |

**Налаштування типу:**
- План рахунків, з яким пов'язаний регістр
- Кореспонденція (Так / Ні) — чи зберігаються проводки з дебетом і кредитом одночасно
- Максимальна кількість субконто
- Регістратори

**Структура даних:** Виміри, Ресурси, Реквізити.

**Особливості:**
- Тісно пов'язаний з Планом рахунків та Планом видів характеристик (субконто)
- Ресурси можуть бути "балансовими" (ведуться за дебетом і кредитом окремо)
- Віртуальні таблиці: Залишки, Обороти, ОборотиДтКт, ЗалишкиТаОбороти, РухиЗСубконто

---

### 2.8. Регістри розрахунку (CalculationRegisters)

**Стандартні реквізити:**

| Реквізит | Тип | Опис |
|---|---|---|
| Період (Period) | Дата | Період реєстрації |
| Реєстратор (Recorder) | ДокументСсылка.* | Документ-реєстратор |
| НомерРядка (LineNumber) | Число | Порядковий номер |
| Активність (Active) | Булево | Активність |
| ВидРозрахунку (CalculationType) | ПланВидовРозрахункуСсылка.* | Вид нарахування/утримання |

| ПеріодДіїКінець (ActionPeriodEnd) | Дата | Кінець періоду дії |
| БазовийПеріодПочаток (BasePeriodStart) | Дата | Початок базового періоду |
| БазовийПеріодКінець (BasePeriodEnd) | Дата | Кінець базового періоду |
| Сторно (Storno) | Булево | Сторнування |

**Налаштування типу:**
- План видів розрахунку, з яким пов'язаний
- Періодичність (Місяць / Квартал / Рік / День)

**Структура:** Виміри, Ресурси, Реквізити.

**Особливості:**
- Механізми витіснення (displacement) за періодом дії
- Залежність за базовим періодом
- Найскладніший прикладний об'єкт платформи, використовується переважно для розрахунку зарплати

## 3. Система типів даних 1С

### 3.1. Примітивні типи

| Тип | Опис | Аналог у SQL/C# |
|---|---|---|
| **Число** (Number) | Довільна довжина та точність (задається: Довжина, ДробоваЧастина, Невід'ємне) | decimal / numeric |
| **Рядок** (String) | Фіксована / Змінна довжина / Необмежений | varchar / text |
| **Дата** (Date) | Дата / Час / Дата+Час | datetime / date |
| **Булево** (Boolean) | Істина / Хибність | bool |
| **СховищеЗначення** (ValueStorage) | Бінарний контейнер для будь-яких даних (файли, зображення) | bytea / varbinary |
| **УнікальнийІдентифікатор** (UUID) | 16-байтний GUID | uuid |
| **Null** | Відсутність значення в БД | NULL |
| **Невизначено** (Undefined) | Невизначене значення (в коді, не в БД) | null (runtime) |

### 3.2. Посилальні типи (Reference Types)

Кожен прикладний об'єкт (Довідник, Документ, Перелічення, ПВХ, План рахунків, ПВР, Бізнес-процес, Задача) має відповідний посилальний тип:

- `СправочникСсылка.<Ім'я>` — посилання на конкретний довідник
- `ДокументСсылка.<Ім'я>` — посилання на конкретний тип документа
- `ПеречислениеСсылка.<Ім'я>` — посилання на значення переліченння
- та інші аналогічно

### 3.3. Складений тип (Composite Type)

Реквізит може мати **складений тип** — комбінацію кількох примітивних та/або посилальних типів. Наприклад: `СправочникСсылка.Контрагенти + СправочникСсылка.ФізичніОсоби + Рядок`.

У БД для складеного типу створюється набір полів:
- `_Type` — дискримінатор (байт, що вказує на конкретний тип)
- `_RTRef` — код таблиці (якщо посилальний тип)
- `_RRRef` — посилання (binary(16))
- `_S` — рядкове значення
- `_N` — числове значення
- `_T` — значення дати
- `_L` — булеве значення

### 3.4. Колекції значень (Runtime, не для зберігання)

| Тип | Опис | Аналог |
|---|---|---|
| **Масив** (Array) | Індексована колекція | List<T> |
| **Структура** (Structure) | Колекція ключ-значення (ключі — ідентифікатори) | Dictionary<string, object> |
| **Відповідність** (Map) | Колекція ключ-значення (ключі — будь-які) | Dictionary<object, object> |
| **СписокЗначень** (ValueList) | Список з презентацією, позначками вибору | — |
| **ТаблицяЗначень** (ValueTable) | In-memory таблиця з типізованими колонками | DataTable |
| **ДеревоЗначень** (ValueTree) | Ієрархічна таблиця значень | — |

## 4. Технічне зберігання метаданих

### 4.1. Бінарні формати файлів

| Формат | Розширення | Опис |
|---|---|---|
| Файл конфігурації | `.cf` | Повний бінарний файл конфігурації (стислий контейнер) |
| Файл оновлення | `.cfu` | Файл оновлення конфігурації від постачальника |
| Вивантаження інформаційної бази | `.dt` | Повний дамп: конфігурація + дані (для backup/restore) |

Формат `.cf` — це compound-файл (подібний до OLE structured storage), що містить серіалізовані метадані та код модулів у внутрішньому бінарному форматі 1С. Цей формат непрозорий і не призначений для ручного редагування.

### 4.2. Вивантаження в XML (формат Конфігуратора)

Платформа підтримує команду «Конфігурація → Вивантажити конфігурацію у файли», яка створює структуру каталогів з XML-файлами.

**Структура каталогів:**
```
Configuration/
├── Configuration.xml          — кореневий файл з описом конфігурації
├── ConfigDumpInfo.xml         — інформація про стан вивантаження
├── Catalogs/
│   ├── Контрагенти.xml        — метаопис довідника
│   ├── Контрагенти/
│   │   ├── Forms/             — форми
│   │   ├── Templates/         — макети
│   │   └── Ext/               — модуль об'єкта, модуль менеджера
├── Documents/
│   ├── ПрихіднаНакладна.xml
│   └── ПрихіднаНакладна/
│       └── ...
├── AccumulationRegisters/
├── InformationRegisters/
├── CommonModules/
├── Roles/
├── Subsystems/
└── ...
```

**Ключовий файл ConfigDumpInfo.xml** — містить хеші об'єктів, що дозволяє інкрементальну вивантаження/завантаження (тільки змінені об'єкти).

**Проблеми формату XML Конфігуратора:**
- Формат змінюється між версіями платформи (сумісність не гарантована)
- Великі XML-файли для складних форм (погано для Git diff)
- Деякі об'єкти серіалізуються нестабільно (різний порядок елементів при повторному вивантаженні)

### 4.3. Формат 1C:EDT (Enterprise Development Tools)

EDT використовує **власний формат**, відмінний від XML вивантаження Конфігуратора. Конвертація між форматами виконується утилітою `ring`.

**Відмінності від XML Конфігуратора:**
- Більш гранулярне розбиття на файли (кожен модуль, форма, макет — окремий файл)
- Формати адаптовані для Git (менші diff'и)
- Підтримка Eclipse workspace structure
- Модулі зберігаються як `.bsl` файли
- Форми — як XML, але в іншому форматі

**Структура каталогу EDT-проекту:**
```
src/
├── Configuration/
│   ├── Configuration.mdo      — головний файл конфігурації
│   └── ...
├── Catalogs/
│   └── Контрагенти/
│       ├── Контрагенти.mdo    — метаопис (XML)
│       ├── ObjectModule.bsl   — модуль об'єкта
│       ├── ManagerModule.bsl  — модуль менеджера
│       ├── Forms/
│       │   └── ФормаЕлемента/
│       │       ├── Form.form  — описание форми (XML)
│       │       └── Module.bsl — модуль форми
│       └── Templates/
├── Documents/
├── AccumulationRegisters/
└── ...
```

### 4.4. Формат BSL (мова 1С) — використання метаданих у коді

У коді на мові 1С (BSL — Built-in Scripting Language) метадані доступні через глобальний об'єкт `Метаданные` (`Metadata`):

```bsl
// Отримання метаданих об'єкта
МетаДовідник = Метаданные.Справочники.Номенклатура;
МетаДовідник.Реквізити  // колекція реквізитів
МетаДовідник.ТабличніЧастини  // колекція табличних частин
МетаДовідник.СтандартніРеквізити  // стандартні реквізити

// Перевірка типу
Якщо ТипЗнч(Об'єкт) = Тип("СправочникСсылка.Номенклатура") Тоді
    // ...
КінецьЯкщо;

// Динамічний доступ
Для Кожного Реквізит З Метаданные.Справочники.Номенклатура.Реквізити Цикл
    Ім'я = Реквізит.Ім'я;
    Тип = Реквізит.Тип;
КінецьЦиклу;
```

## 5. Стандартні реквізити vs Реквізити

### 5.1. Концептуальна різниця

| Критерій | Стандартні реквізити | Користувацькі реквізити |
|---|---|---|
| Хто створює | Платформа автоматично | Розробник у конфігураторі |
| Видалення | **Неможливе** | Можливе |
| Перейменування | **Неможливе** (тільки синонім) | Можливе |
| Зміна типу | **Неможлива** (тип фіксований) | Можлива |
| Присутність у БД | Завжди (стовпець в таблиці) | Тільки якщо створений |
| Приклади | Код, Найменування, Дата, Номер, ПозначенняВидалення | Контрагент, Сума, Коментар |

### 5.2. Що можна налаштувати для стандартних реквізитів

Через кнопку "Стандартні реквізити" у конфігураторі доступні обмежені налаштування:

- **Синонім** — відображуване ім'я (але програмне ім'я незмінне)
- **Підказка** — текст підказки
- **Заповнення** — контроль заповнення (Не контролювати / Видавати попередження / Видавати помилку)
- **Перевірка заповнення** — для керованих форм
- **Індексування** — Індексувати / Не індексувати / Індексувати з додатковим впорядкуванням
- **Повнотекстовий пошук** — Використовувати / Не використовувати
- **Зміна** та **Формат редагування** — для відображення на формах

### 5.3. Вплив на генерацію таблиць у БД

Кожен прикладний об'єкт генерує одну або кілька таблиць у БД. Стандартні реквізити завжди присутні як стовпці:

**Таблиця довідника (наприклад `_Reference42`):**
```
_IDRRef           -- binary(16), ідентифікатор = Посилання
_Version          -- binary(8), версія запису
_Marked           -- binary(1), ПозначенняВидалення
_IsMetadata       -- binary(1), Предефінований
_Code             -- nvarchar(N), Код
_Description      -- nvarchar(N), Найменування
_Folder           -- binary(1), ЦеГрупа
_ParentIDRRef     -- binary(16), Батько
_OwnerIDRRef      -- binary(16), Власник (якщо є підпорядкування)
_Fld123           -- ..., користувацький реквізит 1
_Fld124           -- ..., користувацький реквізит 2
...
```

Імена стовпців у БД — це згенеровані ідентифікатори (`_Fld` + число), а не людиночитабельні імена. Mapping зберігається у внутрішніх системних таблицях (`Config`, `ConfigSave`, `Params`).

## 6. Предефіновані елементи

### 6.1. Що таке предефіновані елементи

Предефіновані елементи — це елементи довідників, ПВХ, планів рахунків та ПВР, які:
- Створюються розробником у конфігураторі (на етапі проєктування)
- Мають програмне ім'я (PredefinedDataName), за яким до них звертаються з коду
- Не можуть бути видалені користувачем
- Можуть бути перейменовані користувачем (змінюється Найменування, але не програмне ім'я)

### 6.2. Зберігання

**У конфігурації (.cf / XML / EDT):** предефіновані елементи зберігаються як частина метаопису об'єкта — перелік із програмним ім'ям та реквізитами за замовчуванням.

**У БД:** предефіновані елементи — це звичайні записи в тій самій таблиці, що й решта елементів. Відмінність — заповнене поле `_PredefinedID` (binary(16)), яке містить зв'язок із метаданими. Поле `_IsMetadata` = Істина для предефінованих.

### 6.3. Механізм роботи

При першому запуску інформаційної бази або при оновленні конфігурації платформа автоматично:
1. Порівнює перелік предефінованих у конфігурації з наявними в БД
2. Створює відсутні предефіновані елементи
3. Видаляє зайві (якщо розробник видалив із конфігурації)

Доступ з коду:
```bsl
// Отримання предефінованого елемента
Валюта = Справочники.Валюти.Долар;  // за програмним ім'ям
// або
Валюта = ПредефінованеЗначення("Справочник.Валюти.Долар");
```

### 6.4. Типові проблеми

- **Дублювання:** при некоректному оновленні бази може створитися кілька записів з одним PredefinedDataName — це призводить до помилки «Предефінований елемент не є унікальним»
- **Порожні посилання:** якщо предефіноване значення видалили з конфігурації, але воно використовується в документах — отримуємо "бите" посилання
- **Швидкодія:** метод `ПредефінованеЗначення()` кешується, але масове використання може впливати на старт сеансу
- **Оновлення:** зміна складу предефінованих при оновленні типової конфігурації може конфліктувати з користувацькими даними

## 7. Механізм рухів документів (Проведення)

### 7.1. Що таке «проведення» технічно

**Проведення** (Posting) — це процес, при якому документ реєструє **рухи** (записи) у підпорядкованих регістрах. Технічно це:

1. Встановлення прапорця `Проведений = Істина` у записі документа
2. Виконання коду модуля об'єкта документа, процедура `ОбробкаПроведення(Відмова, РежимПроведення)`
3. Формування наборів записів для кожного регістру, по якому документ здійснює рухи
4. Запис наборів записів у таблиці регістрів

### 7.2. Конфігурування зв'язку «Документ → Регістр»

На вкладці **«Рухи»** конструктора документа розробник:
1. Відзначає галочками регістри, по яких документ здійснює рухи
2. Може використати **Конструктор рухів** для автоматичної генерації коду

Після цього:
- У метаданих документа з'являється властивість `Рухи` (колекція регістрів)
- У метаданих кожного відміченого регістру документ з'являється як `Реєстратор`
- Платформа автоматично створює об'єкти `Рухи.<ІмʼяРегістру>` (наборізаписів), доступні в модулі об'єкта

### 7.3. Типова процедура проведення

```bsl
Процедура ОбробкаПроведення(Відмова, РежимПроведення)

    // 1. Очищення старих рухів (автоматичне, якщо увімкнено)
    // Рухи.ОстаткіТоварів.Записувати = Істина;

    // 2. Формування нових рухів
    Для Кожного РядокТЧ З Товари Цикл
        Рух = Рухи.ОстаткіТоварів.Додати();
        Рух.ВидРуху = ВидДвиженняНакопичення.Прихід;
        Рух.Період = Дата;
        Рух.Номенклатура = РядокТЧ.Номенклатура;
        Рух.Склад = Склад;
        Рух.Кількість = РядокТЧ.Кількість;
        Рух.Сума = РядокТЧ.Сума;
    КінецьЦиклу;

    // 3. Запис рухів (виконується автоматично після завершення процедури)

КінецьПроцедури
```

### 7.4. Режими проведення

| Режим | Опис |
|---|---|
| **Оперативне** | Проведення «в реальному часі», контроль залишків на момент проведення |
| **Неоперативне** | Проведення заднім числом, без контролю оперативних залишків |

### 7.5. Скасування проведення

При скасуванні проведення (UnPosting):
1. Виконується процедура `ОбробкаСкасуванняПроведення(Відмова)`
2. Всі набори записів (рухи) документа очищуються
3. Прапорець `Проведений` встановлюється в `Хибність`

### 7.6. Зв'язок із Послідовностями

Якщо документ входить у послідовність, при проведенні:
- Перевіряється «межа послідовності» — чи не порушує документ хронологічний порядок
- Якщо дата документа раніше за межу — потрібне перепроведення (відновлення послідовності)
- Це забезпечує цілісність залежних від порядку розрахунків (наприклад, собівартість за FIFO)

### 7.7. Таблиці рухів у БД

Кожен регістр зберігає рухи в окремій таблиці. Для регістру накопичення залишків створюється дві таблиці:

- **Таблиця рухів** (`_AccumRg<N>`) — всі записи з полями: Період, Реєстратор, НомерРядка, Активність, ВидРуху, Виміри, Ресурси, Реквізити
- **Таблиця підсумків** (`_AccumRgT<N>`) — агреговані залишки по місяцях: Період, Виміри, Ресурси

Оперативні підсумки (на «безкінечну» дату 3999-11-01) дозволяють миттєво отримати поточні залишки без розрахунку.

## Додаток B: Ключові висновки для проєктування метамоделі

### B.1. Що варто перенести в наш продукт

1. **Розділення об'єктів за бізнес-семантикою** — не просто «таблиці», а «довідники», «документи», «регістри» з різною поведінкою
2. **Стандартні реквізити** — кожен тип об'єкта автоматично отримує фіксований набір полів
3. **Складені типи** — реквізит може посилатися на об'єкти різних типів
4. **Регістри з вимірами/ресурсами/реквізитами** — потужна модель для аналітичного обліку
5. **Проведення документів** — декларативний зв'язок «документ → регістри → рухи»
6. **Предефіновані елементи** — фіксовані записи, задані на етапі конфігурування
7. **Плани видів характеристик** — механізм для динамічного розширення аналітики

### B.2. Що варто зробити інакше

1. **Людиночитабельні імена в БД** — замість `_Fld123` використовувати `snake_case` імена
2. **Відкритий формат метаданих** — JSON або YAML замість бінарного `.cf`
3. **Git-first** — формат файлів, оптимізований для diff/merge
4. **Відмова від compound-файлів** — кожен об'єкт = окремий файл
5. **Типізація реквізитів регістрів** — ресурси не обмежувати тільки числовим типом (для регістрів відомостей)
6. **Спрощення регістрів розрахунку** — виключити з MVP, це рідкісний випадок
7. **REST API першим класом** — автоматична генерація API з метаданих (як Frappe)
8. **Code-gen для міграцій** — замість магії платформи, явні SQL-міграції

### B.3. Рекомендований порядок реалізації для MVP

1. Довідники (з ієрархією та підпорядкуванням)
2. Перелічення
3. Документи (з табличними частинами)
4. Регістри відомостей
5. Регістри накопичення (залишки та обороти)
6. Константи
7. Плани видів характеристик (фаза 2)
8. Регістри бухгалтерії та Плани рахунків (фаза 3)
9. Бізнес-процеси та Задачі (фаза 4)
10. Регістри розрахунку та ПВР (фаза 5)
