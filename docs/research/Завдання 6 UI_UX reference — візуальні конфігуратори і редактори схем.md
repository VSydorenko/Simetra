# UI/UX патерни для візуального конфігуратора бізнес-метаданих

**Висновок:** Сучасний конфігуратор метаданих має поєднати перевірену часом архітектуру 1С — ієрархічне дерево, табличний редактор, палітру властивостей — із UX-рішеннями SaaS-інструментів: staged operations з diff view (Supabase), іконки типів полів (NocoDB/Airtable), drag-and-drop зв'язки на canvas (DrawDB). Стек **react-arborist + @tanstack/react-table + react-resizable-panels + Zustand + zundo** покриває всі ключові потреби і нативно інтегрується з shadcn/ui. Нижче — детальний аналіз кожного інструменту та конкретні рекомендації для BRD.

---

## A. Конфігуратор 1С:Підприємство 8.3 — перевірена архітектура з застарілим UX

### Структура інтерфейсу

Конфігуратор 1С побудований на класичному **3-панельному layout**: ліворуч — дерево метаданих (панель "Конфигурация"), по центру — робоча область з вкладками редакторів, праворуч — палітра властивостей. Верхня панель містить меню та тулбар із кнопками основних дій. Дерево метаданих та палітра властивостей — **dock-панелі з режимом auto-hide** (кнопка-шпилька у верхньому куті): при відкріпленні згортаються в кнопку на краю вікна. Палітра властивостей **автоматично оновлюється** при зміні виділення — виберіть об'єкт у дереві, і праворуч з'являться його властивості. Цей патерн "selection → properties" є фундаментальним і повинен бути збережений.

### Дерево метаданих

Дерево має **фіксовані кореневі гілки**, визначені платформою — їх не можна видалити чи перейменувати:

- **Загальні** (Підсистеми, Загальні модулі, Ролі, Загальні реквізити, Плани обміну, Регламентні завдання тощо)
- **Константи**
- **Довідники** → окремі довідники → Реквізити, Табличні частини, Форми, Макети
- **Документи** → аналогічна структура
- **Журнали документів**
- **Перерахування**
- **Звіти, Обробки**
- **Плани видів характеристик, Плани рахунків, Плани видів розрахунку**
- **Регістри відомостей, Регістри накопичення, Регістри бухгалтерії, Регістри розрахунку**
- **Бізнес-процеси, Задачі**

**Контекстне меню** на вузлах дерева включає: Додати (зелене "+"), Копіювати, Видалити (з перевіркою посилальної цілісності), Перемістити вверх/вниз, Властивості (Alt+Enter), Пошук посилань на об'єкт, Сортування (за ім'ям, синонімом, коментарем), Фільтр за підсистемами. **Drag-and-drop** підтримується повністю — об'єкти переносяться між сумісними гілками з автоматичним копіюванням підлеглих елементів.

**Інкрементний пошук** — набір літер миттєво позиціонує курсор на відповідному об'єкті. Глобальний пошук (Ctrl+Shift+F) шукає по всіх модулях конфігурації.

### Редагування об'єкта — система вкладок

Подвійний клік на об'єкті (наприклад, Довідник) відкриває **спеціалізований редактор із вкладками**. Для довідника це: **Основні** (ім'я, синонім, коментар, довжина коду, довжина найменування, належність до підсистем), **Ієрархія** (налаштування груп та елементів), **Власники**, **Дані** (найважливіша вкладка — таблиця реквізитів та табличних частин), **Нумерація**, **Форми** (основна форма елемента, форма списку, форма вибору), **Макети**, **Права** (матриця прав за ролями), **Команди**. Для документів вкладки відрізняються: з'являються **Рухи** (реєстрація в регістрах), а замість Ієрархії — Нумерація.

Такий послідовний потік редагування (Основні → Дані → Форми → Права) є **інтуїтивним і добре структурованим** — цей патерн варто зберегти.

### Реквізити та типи

На вкладці **Дані** відображається таблиця реквізитів із колонками Ім'я та Тип. Додавання нового реквізиту — кнопка "+" → створюється рядок із типом за замовчуванням (Рядок) → палітра властивостей показує всі властивості реквізиту. Призначення типу — кнопка "…" біля властивості Тип → відкривається **модальний діалог вибору типу** з деревовидним списком: примітивні типи (Рядок, Число, Дата, Булево) та посилальні (ДовідникПосилання.XXX, ДокументПосилання.XXX тощо). Підтримуються **складені типи** (кілька типів одночасно).

### Стандартні vs користувацькі реквізити

**Стандартні реквізити** (Посилання, Код, Найменування, ПозначкаВидалення тощо) **винесені за окрему кнопку** "Стандартні реквізити" на вкладці Дані — вони не з'являються в основній таблиці реквізитів. Це чітко відокремлює системні поля від користувацьких. У стандартних реквізитів обмежений набір властивостей, що редагуються — тип та ім'я змінити не можна. У редакторі форм **основний реквізит виділяється жирним шрифтом**.

### Що незручно — відомі проблеми UX

Спільнота 1С сформулювала низку системних проблем конфігуратора:

- **Застаріле ядро** — розробники характеризують конфігуратор як "застаріле середовище розробки з таким legacy, що дешевше було все перебудувати на Eclipse"
- **Відсутність темної теми** — лише часткова кастомізація кольорів для модулів коду; дерево, палітра, діалоги залишаються світлими
- **Обмеження одного сеансу** — лише один Конфігуратор на базу одночасно, що критично для командної роботи
- **Примітивний контроль версій** — "Сховище конфігурацій" використовує блокування на рівні об'єктів; лише один розробник може редагувати модуль одночасно
- **Відсутність рефакторингу** — немає rename-with-references, extract method, обмежений autocomplete
- **Повільність на великих конфігураціях** — відкриття, оновлення, порівняння конфігурацій може тривати десятки хвилин
- **Втрата контексту між сеансами** — при закритті конфігуратора всі відкриті вкладки губляться
- **Обмеження diff/merge** — при порівнянні конфігурацій немає гранулярного контролю над окремими елементами форм
- **Проблеми з HiDPI** — дрібні шрифти в дереві та палітрі на сучасних моніторах

### Що зручно — патерни для збереження

**Дерево метаданих як центральна навігація** з фіксованою структурою за типами створює зрозумілу ментальну модель. **Табовані редактори з послідовним потоком** (Основні → Дані → Форми → Права) роблять складні об'єкти керованими. **Палітра властивостей як універсальний інспектор** із auto-update при зміні виділення — потужний інструмент для швидкого перегляду. **Повна клавіатурна доступність** — практично кожна дія має хоткей. **Фільтрація дерева за підсистемами** дозволяє працювати лише зі своєю частиною конфігурації.

## B. 1C:EDT — Eclipse-based еволюція з проблемами продуктивності

1C:EDT побудований на **Eclipse** і встановлюється як окремий додаток. Інтерфейс використовує Eclipse-конвенції: **перспективи** (1С:Enterprise, Git, Debug), **Navigator** (ліворуч — аналог дерева метаданих), **Editor area** (центр — вкладки відкритих об'єктів), **Properties panel** (аналог палітри властивостей із додатковим **пошуком по рядку** — суттєве покращення), **Problems panel** (реальний час — помилки видно одразу), **Outline** (структура поточного редактора).

**Ключові покращення порівняно з класичним конфігуратором**: нативна **Git-інтеграція** (замість об'єктних блокувань — гілки, паралельна робота), **реальна валідація коду в реальному часі** з виводом типів, **кращий diff/merge** ("все в одному місці — конфігурація, форми"), **кілька проектів в одному workspace**, **кросплатформність** (Windows, macOS, Linux), **збереження контексту сесії** (всі вкладки відновлюються при перезапуску).

**Проблеми EDT, що стримують впровадження**: критично **низька продуктивність** ("запускає проекти жахливо повільно порівняно з конфігуратором"), **високі вимоги до обладнання** (мінімум 16 ГБ RAM, SSD, Core i7), **залежність від конфігуратора під капотом** (EDT конвертує формат у XML і відправляє команди до Configurator-агента), **не всі функції портовані** (створення дистрибутивів, адміністрування, звичайні форми), **складність встановлення** Java/Eclipse. Спільнота характеризує ситуацію так: "на одному стільці — покинутий конфігуратор, на іншому — недоношений EDT".

**Висновок для BRD**: EDT демонструє правильний напрямок (Git, real-time validation, multi-project), але його реалізація на Eclipse показує, що **нативний веб-стек з React дасть кращий developer experience**, ніж надбудова над legacy-платформою.

## C. Supabase Studio — еталон сучасного SaaS-редактора схем

Supabase Studio побудований на **React/Next.js** із власною дизайн-системою **на базі shadcn/ui** — це безпосередньо релевантний для нашого стеку приклад. Ключові UI-рішення:

**Створення таблиці**: кнопка "New Table" → модальне вікно з ім'ям таблиці → колонка `id` створюється автоматично. Додавання колонок — кнопка "+" у правому краю заголовків grid → **бічна панель (slide-over)** з конфігурацією: ім'я, тип (dropdown), default value, toggle для Primary Key, Nullable, Unique, Array. Supabase свідомо обмежує набір типів у UI до підмножини PostgreSQL — розширені типи потребують SQL Editor.

**Staged operations з Diff View** (запроваджено у 2026) — користувач ставить зміни в чергу (insert, edit, delete), переглядає diff, підтверджує атомарно через `Cmd+S`. **Це важливий патерн для редактора метаданих**, де помилки коштують дорого.

**Foreign keys**: окрема кнопка "Add foreign key relation" у панелі колонки → каскадний вибір Schema → Table → Column → On Delete/Update actions. **Schema Visualizer** (побудований на **React Flow**) показує інтерактивну ER-діаграму з таблицями як картками та зв'язками як лініями.

**Загальний стиль**: темна тема за замовчуванням, **Command Palette** (`Cmd+K`) для швидкої навігації, **табований інтерфейс** (як VS Code) для кількох таблиць одночасно, **Monaco Editor** для SQL. Естетика — "професійна IDE зустрічає SaaS-дашборд".

## D. NocoDB, Baserow, Airtable — патерни для редактора реквізитів

### Концепція "Field Type" з іконками

Всі три інструменти використовують **візуальні іконки в заголовках колонок** для позначення типу поля. NocoDB має **30+ типів**, категоризованих у групи: Text-based (Single line, Long text, Email, URL), Numerical (Number, Currency, Percentage), Date & Time, Select-based (Single/Multi select з кольоровими тегами), Link-based (Links, Lookup, Rollup), Custom (Attachment, Barcode, JSON, Rating). Кожен тип має свою іконку. Airtable додає кольорові pills для опцій Select-полів — **високо-візуальний патерн**, який варто запозичити.

### Редагування полів

**NocoDB** виділяється **Multi-field Editor** — панель, де ліворуч відображається список усіх полів, праворуч — конфігурація вибраного поля. Підтримується batch-редагування з єдиним "Save changes". Це **найкращий патерн для масового визначення реквізитів бізнес-об'єкта**.

**Baserow** демонструє чіткий **поділ view-specific (сортування, фільтрація, приховування) та глобальних змін** (перейменування, зміна типу, видалення). Baserow також має **Undo/Redo для змін схеми** (Ctrl+Z) — критичну "сітку безпеки". Поле створюється через dropdown-popover біля заголовка з ім'ям, типом та type-specific налаштуваннями.

**Airtable** як gold standard no-code UX: найбільш відполірований grid, **кольорові опції для Select**, автогенерація Form View із полів таблиці, розширений record expansion modal.

### Що запозичити для BRD

- **Multi-field Editor** (NocoDB): список полів + детальна конфігурація вибраного = ідеально для реквізитів бізнес-об'єкта
- **Іконки типів у заголовках** (всі три): миттєва візуальна ідентифікація типу поля
- **Side panel замість модального вікна** (Supabase, NocoDB): grid залишається видимим під час редагування
- **Staged operations** (Supabase): чергування змін, diff, атомарний commit
- **Undo/Redo** (Baserow): обов'язково для MVP
- **Display Value vs Primary Key** (NocoDB): розділення технічного ID та "представлення" об'єкта — пряма аналогія з 1С

## E. Frappe DocType Editor — metadata-driven підхід

Frappe має **два режими редагування DocType**: legacy (таблиця полів як child table grid) та **Form Builder** (з Frappe v15) — візуальний WYSIWYG-редактор із **3-панельним layout**: ліворуч — палітра типів полів для drag-and-drop, по центру — canvas із відображенням форми як її побачить кінцевий користувач (Tab → Section → Column → Field), праворуч — панель властивостей виділеного елемента.

**Drag-and-drop** працює повноцінно: перетягування типу поля з палітри на форму, переміщення полів між секціями та вкладками, переупорядкування секцій. Зміни відображаються в реальному часі.

**Аналогії з 1С**: Normal DocType ≈ Довідник, Submittable DocType ≈ Документ (з workflow Draft→Submitted→Cancelled), Child Table ≈ Таблична частина, Single DocType ≈ Константа/Налаштування, Tree DocType ≈ Ієрархічний довідник. **Цей маппінг підтверджує, що патерн "тип бізнес-об'єкта визначає набір поведінок" є універсальним** і повинен бути закладений в архітектуру BRD.

**Ключова цінність Frappe**: зміна DocType-визначення автоматично оновлює і схему БД, і UI — справжній model-driven підхід. **Слабкість**: немає візуалізації зв'язків між DocType (кожен редагується ізольовано), немає canvas із просторовим розташуванням.

## F. DrawDB та dbdiagram.io — canvas-based та dual-mode патерни

### DrawDB — SVG canvas з React

DrawDB — React SPA з **SVG-based canvas**: таблиці рендеряться як `<foreignObject>` всередині SVG (повний HTML/CSS), зв'язки — як SVG `<path>` з bezier-кривими. Стек: **React + Semi UI + Dexie.js (IndexedDB) + Monaco Editor**. State management побудований на **React Context + custom hooks** (`useTables`, `useRelationships`, `useAreas`).

**Створення зв'язків**: клік на **синю точку** біля поля → перетягування до цільового поля іншої таблиці → зв'язок створюється візуально. Sidebar містить вкладки Tables, Relationships, Subject Areas, Notes, Types, Enums — кожна дозволяє детальне редагування.

**Редагування полів**: клік на таблицю на canvas → sidebar відкриває детальний редактор із ім'ям, типом (dropdown), NOT NULL/PK/Unique toggles, Default value, Check constraint, Comment. Зміни миттєво відображаються на canvas-картці.

### dbdiagram.io — dual code+visual

dbdiagram.io використовує **split-pane layout**: ліворуч — Monaco Editor з DBML (Database Markup Language), праворуч — авто-генерована ER-діаграма. Підхід **code-first**: зміни робляться лише в тексті, діаграма оновлюється в реальному часі. **Ctrl+Click** на імені таблиці в коді фокусує її на діаграмі. Зв'язки визначаються текстово: `Ref: posts.user_id > users.id`.

### Рекомендації для BRD

Для MVP рекомендується **form-based підхід** (як Frappe/1C) із можливістю додати **canvas-режим** у наступних версіях. Якщо canvas потрібен раніше — патерн DrawDB (SVG + foreignObject) перевірений і працює з React. Бібліотека **React Flow** (яку використовує Supabase для Schema Visualizer) — найкращий варіант для canvas зі зв'язками.

## G. Конкретні рекомендації для React-стеку BRD

### Дерево метаданих — ліва панель

**Рекомендована бібліотека: react-arborist** (~3 400 GitHub stars, ~115K weekly downloads npm). Ключові переваги: вбудована віртуалізація для 10K+ вузлів, drag-and-drop, inline rename, повна кастомізація node-рендерера — кожен вузол можна оформити shadcn/ui-компонентами з lucide-react іконками. Альтернатива — **headless-tree** (наступник react-complex-tree, ~790 stars): повністю headless, кращий accessibility (W3C ARIA), composable feature plugins, ~9.5kB; але все ще в beta.

**Контекстне меню**: shadcn/ui має вбудований компонент **Context Menu** (`@radix-ui/react-context-menu`). Патерн — обгортати кожен node дерева `<ContextMenu>`, показуючи різні дії залежно від типу вузла:

- На кореневій гілці "Довідники": Додати довідник
- На конкретному довіднику: Редагувати, Копіювати, Видалити, Пошук посилань
- На гілці "Реквізити": Додати реквізит, Додати табличну частину

**Іконки для типів об'єктів** (lucide-react — вже залежність shadcn/ui):

| Тип об'єкта | Іконка | Код |
|---|---|---|
| Довідник | Database / FolderTree | `<Database />` |
| Документ | FileText | `<FileText />` |
| Регістр | Table2 / ScrollText | `<Table2 />` |
| Перерахування | List | `<List />` |
| Поле (String) | Type | `<Type />` |
| Поле (Number) | Hash | `<Hash />` |
| Поле (Date) | Calendar | `<Calendar />` |
| Поле (Boolean) | ToggleLeft | `<ToggleLeft />` |
| Поле (Reference) | Link | `<Link />` |

**Пошук по дереву**: react-arborist підтримує фільтрацію через `searchTerm` prop. Рекомендується shadcn/ui Input із debounce зверху дерева — аналог інкрементного пошуку 1С, але потужніший (substring match замість prefix-only).

**Drag-and-drop у MVP**: рекомендую **ні для переміщення об'єктів між гілками** (надто складна валідація сумісності), але **так для переупорядкування реквізитів** всередині об'єкта — це низько-ризикова і високо-корисна фіча. react-arborist підтримує це з коробки.

### Редактор полів — центральна панель

**Рекомендована бібліотека: @tanstack/react-table** — headless, мільйони npm downloads, **shadcn/ui має офіційний Data Table рецепт**. Для inline editing використовується документований патерн `table.options.meta?.updateData()` із custom cell-рендерерами, що перемикаються між display/edit режимами.

**Таблиця vs Список vs Cards**: рекомендую **таблицю як основний режим** (як у 1С та NocoDB) — вона найефективніша для перегляду багатьох реквізитів з їх типами та властивостями. Колонки таблиці: Іконка типу, Ім'я, Тип (з badge), Обов'язковість, Коментар. Для детального редагування — бічна панель (як у Supabase/NocoDB).

**Відображення типу поля з іконкою**: кожен тип має іконку + колір + мітку. Reference-поля відображаються окремим стилем — shadcn/ui `<Badge variant="outline">` із іконкою Link та назвою цільової сутності (наприклад, `🔗 Контрагент`). Приклад маппінгу:

```tsx
const fieldTypeConfig = {
  String:    { icon: Type,       color: "text-blue-500",   label: "Рядок" },
  Number:    { icon: Hash,       color: "text-green-500",  label: "Число" },
  Date:      { icon: Calendar,   color: "text-orange-500", label: "Дата" },
  Boolean:   { icon: ToggleLeft, color: "text-purple-500", label: "Булево" },
  Reference: { icon: Link,       color: "text-red-500",    label: "Посилання" },
  Enum:      { icon: List,       color: "text-yellow-500", label: "Перерахування" },
};
```

**Inline editing vs окрема форма**: гібридний підхід — **ім'я та тип редагуються inline** у таблиці (як у NocoDB), **детальні властивості — у бічній панелі** (як у Supabase). Клік на реквізит у таблиці відкриває його властивості у правій панелі.

### Панель властивостей — права панель

**Реалізація**: кастомний компонент на shadcn/ui-примітивах — немає готової бібліотеки "property grid" для React, що була б достатньо якісною. Використовувати `<Accordion>` або `<Collapsible>` для згрупованих секцій.

**Context-sensitive контент**: панель перемикає вміст залежно від типу виділеного об'єкта. Для entity (Довідник, Документ) — загальні властивості (ім'я, синонім, належність до підсистем, налаштування ієрархії). Для field (реквізит) — тип, обов'язковість, значення за замовчуванням, індексування, перевірка заповнення. Перемикання через простий `switch(selectedObject.kind)`.

**Групування властивостей** (рекомендовані секції):

- "Основні" — Ім'я, Код, Синонім, Коментар
- "Налаштування типу" — type-specific опції (довжина рядка, точність числа, цільова сутність для посилання)
- "Валідація" — Обов'язковість, Min/Max, Шаблон
- "Представлення" — Підказка, Порядок, Видимість

**Стандартні реквізити**: відображаються у тій же панелі, але з `text-muted-foreground` стилем, `<Lock>` іконкою та disabled-контролами. Патерн 1С (окрема кнопка "Стандартні реквізити") можна замінити на **розділ у таблиці** із візуальним відділенням — сірий фон, іконка замка, підпис "Системні". Це зручніше, ніж окрема кнопка, бо всі реквізити видно одразу.

### Загальний layout і тулбар

**Resizable panels: react-resizable-panels** від Brian Vaughn (React core contributor) — **вбудований у shadcn/ui** (`npx shadcn add resizable`). ~5 100 GitHub stars, ~4M weekly downloads. Рекомендована конфігурація:

```tsx
<ResizablePanelGroup direction="horizontal">
  <ResizablePanel defaultSize={20} minSize={15} maxSize={30}>
    {/* Дерево метаданих */}
  </ResizablePanel>
  <ResizableHandle withHandle />
  <ResizablePanel defaultSize={50} minSize={30}>
    {/* Редактор полів */}
  </ResizablePanel>
  <ResizableHandle withHandle />
  <ResizablePanel defaultSize={30} minSize={20} collapsible>
    {/* Панель властивостей */}
  </ResizablePanel>
</ResizablePanelGroup>
```

**Command Palette**: shadcn/ui має вбудований **Command** компонент (на базі cmdk від Paco Coursey, ~3kB). Використовується для швидкої навігації по об'єктах, створення нових об'єктів, виконання дій — `Cmd+K`.

**Keyboard shortcuts: react-hotkeys-hook** — сучасний hooks API, scoped хоткеї, автоматичне ігнорування при введенні тексту. Рекомендовані хоткеї:

- `Ctrl+K` — Command Palette
- `Ctrl+Z` / `Ctrl+Shift+Z` — Undo/Redo
- `Ctrl+S` — Зберегти зміни
- `Delete` — Видалити виділений елемент
- `F2` — Перейменувати
- `Ctrl+N` — Новий об'єкт
- `Alt+Enter` — Відкрити властивості (як у 1С)
- `Ctrl+F` — Пошук по дереву

### State management та undo/redo

**Рекомендація: Zustand + immer middleware + zundo** (~3kB Zustand + <700B zundo). Zustand ідеально підходить для "document model" метаданих — централізований store із slice-патерном для модульності. `zundo` надає battle-tested undo/redo через `temporal` middleware. `immer` дозволяє інтуїтивні мутації вкладеного стану.

```tsx
export const useMetadataStore = create<MetadataState>()(
  temporal(
    immer((set) => ({
      objects: {},
      selectedId: null,
      updateField: (objectId, fieldId, updates) => set((state) => {
        const field = state.objects[objectId]?.fields?.find(f => f.id === fieldId);
        if (field) Object.assign(field, updates);
      }),
    })),
    { partialize: (state) => ({ objects: state.objects }) }
  )
);
```

**Валідація**: **Zod + react-hook-form** — shadcn/ui має first-class підтримку через компонент Form (`npx shadcn add form`).

## Висновки та пріоритети для MVP

Архітектура BRD повинна будуватися на трьох перевірених патернах: **ієрархічне дерево як навігація** (1С), **таблиця реквізитів із бічною панеллю властивостей** (NocoDB + Supabase), **staged operations із diff** (Supabase). Стек shadcn/ui вже включає три ключові бібліотеки (resizable panels, command palette, form validation), що скорочує час інтеграції.

Для MVP першого релізу рекомендується сфокусуватися на: 3-panel layout із деревом, таблицею реквізитів та панеллю властивостей; inline editing імені та типу у таблиці; context-sensitive правою панеллю; Command Palette для навігації; Undo/Redo через zundo. Canvas-візуалізацію зв'язків (React Flow) та drag-and-drop між гілками дерева варто відкласти на другу ітерацію — вони додають значну складність при обмеженій цінності на ранніх етапах.

Найважливіший урок з аналізу 1С: **не повторювати помилку "legacy lock-in"**. Метадані повинні серіалізуватися у відкритий текстовий формат (JSON/YAML) із git-friendly структурою файлів — один файл на об'єкт. Це забезпечить версіонування, командну роботу та інтеграцію з CI/CD без жодного з обмежень, що роками критикує спільнота 1С.
