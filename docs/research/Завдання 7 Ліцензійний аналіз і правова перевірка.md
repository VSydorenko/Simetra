# Ліцензійний аналіз для open-source конфігуратора бізнес-метаданих

**Рекомендація: обирайте Apache 2.0 з DCO замість CLA.** Серед 18 перевірених проєктів лише 7 мають ліцензії, повністю сумісні з вашим проєктом для прямого копіювання коду. Решта — copyleft або source-available ліцензії, з яких можна лише вивчати ідеї та архітектурні підходи. Термінологія 1С (довідник, документ, регістр) є загальновживаною і не захищена авторським правом, але назву «1С» використовувати в назві продукту не можна. Проєкти-аналоги (OneScript, bsl-language-server) роками працюють без жодних юридичних претензій від компанії 1С, що створює позитивний прецедент.

## Проєкти з повною сумісністю: звідки безпечно брати код

З 18 перевірених проєктів **код можна вільно копіювати** лише з 10 (з дотриманням attribution):

- **Apache 2.0**: supabase/pg-meta, supabase/supabase, drizzle-team/drizzle-orm, prisma/prisma, prisma/prisma-engines, holistics/dbml, amplication/amplication (тільки `packages/`, не `ee/`)
- **MIT**: frappe/frappe, saltcorn/saltcorn, DbUp/DbUp, drizzle-kit

Для Apache 2.0 проєктів при копіюванні коду необхідно: зберегти оригінальний copyright notice, включити копію ліцензії Apache 2.0, зберегти NOTICE-файл (якщо існує), зазначити змінені файли. Для MIT проєктів достатньо зберегти copyright notice та текст ліцензії.

Решта **8 проєктів** мають copyleft або пропрієтарні ліцензії. З них можна лише **вивчати архітектурні ідеї, алгоритми та підходи** — але писати власну реалізацію «з нуля» (clean-room implementation). Особливо це стосується ERPNext (GPL v3), Odoo (LGPL v3), DrawDB (AGPL-3.0), pgModeler (GPL v3) та Budibase (GPL v3). NocoDB та Directus слід **повністю уникати** — їхні ліцензії (Sustainable Use License та BSL 1.1) є найбільш рестриктивними та несумісними з будь-якою open-source моделлю.

## B. Термінологія 1С: що можна, а що — ні

### Товарні знаки «1С» та «1C:Enterprise»

**«1С» є зареєстрованим загальновідомим товарним знаком у Росії** (свідоцтво №106, дата визнання — 1 січня 2006 року). За рішенням Роспатенту, знак отримав безстрокову правову охорону, що поширюється навіть за межі зареєстрованого класу товарів. Соціологічне опитування показало, що **92% респондентів** правильно ідентифікували торговельну марку «1С».

Щодо реєстрації в Україні: пряме підтвердження реєстрації в базі УКРНОІВІ не знайдено, однак компанія 1С активно працювала на українському ринку. З огляду на поточну геополітичну ситуацію (війна Росії проти України), **примусовість виконання прав на товарний знак російської компанії в Україні є невизначеною** і потенційно обмеженою санкціями. Рекомендується перевірити актуальний статус через базу даних УКРНОІВІ або за допомогою українського патентного повіреного.

### Функціональна термінологія: безпечно для використання

Терміни «довідник», «документ», «регістр накопичення», «регістр відомостей», «табличні частини», «проведення» є **загальними функціонально-описовими термінами** бухгалтерського та бізнес-домену. Вони не підлягають захисту авторським правом або товарним знаком з таких причин:

**Доктрина scènes à faire** захищає елементи, що є стандартними або продиктованими предметною областю. Бухгалтерські та ERP-терміни існували задовго до 1С:Підприємство. **Рішення Суду ЄС у справі SAS Institute v. World Programming Ltd** прямо підтвердило: функціональність програмного забезпечення не може бути монополізована через авторське право. Тест «Abstraction-Filtration-Comparison» зі справи **Computer Associates v. Altai** фільтрує такі елементи як незахищені. Жодних судових справ, де 1С стверджувала б права інтелектуальної власності на цю термінологію, не знайдено.

**Висновок: інший програмний продукт може вільно використовувати ту саму термінологію.**

### Формулювання «натхненний 1С» та «аналог 1С»

| Формулювання | Рівень ризику | Коментар |
|---|---|---|
| «натхненний 1С:Підприємство» | **Низький** | Захищено доктриною nominative fair use — чітко розрізняє ваш продукт від 1С |
| «аналог конфігуратора 1С» | **Середній** | Можна інтерпретувати як заяву про функціональну еквівалентність; краще «альтернатива» |
| «сумісний з 1С:Підприємство» | **Низький** (якщо правда) | Захищено як compatibility claim, але має бути фактично правдою |
| Використання «1С» у **назві продукту** | **Високий** | Категорично не рекомендується — ймовірне порушення товарного знаку |
| Використання логотипу або фірмового стилю 1С | **Високий** | Категорично заборонено |

### Як подібні проєкти обходять ці питання

**OneScript** (EvilBeaver) описує себе як «незалежна крос-платформна реалізація віртуальної машини, що виконує скрипти мовою 1С:Enterprise». Ключовий підхід: підкреслює **незалежність** від 1С та відсутність використання коду 1С. Працює з ~2014 року без жодних юридичних претензій.

**bsl-language-server** (1c-syntax) прямо вказує «Language Server Protocol implementation for 1C (BSL) — 1C:Enterprise 8». Організація навіть називається «1c-syntax». Активно підтримується роками без юридичних проблем.

Обидва проєкти: вільно використовують назву «1С:Enterprise» в описах; не включають «1С» у назву самого продукту; не використовують логотипи 1С; підкреслюють незалежність. **Компанія 1С де-факто толерує екосистемні проєкти** і навіть має власну GitHub-організацію (github.com/1C-Company).

**Рекомендований дисклеймер** для README та сайту:

> «Цей проєкт не пов'язаний, не схвалений і не асоційований з компанією 1С або її продуктами. «1С» та «1С:Підприємство» є зареєстрованими товарними знаками компанії 1С. Цей проєкт є незалежним open-source інструментом, натхненним концепціями конфігуратора 1С:Підприємство.»

## C. MIT проти Apache 2.0: конкретна рекомендація

### Порівняння для вашого випадку

| Критерій | MIT | Apache 2.0 | Переможець |
|---|---|---|---|
| **Патентний захист** | Немає явного патентного гранту; юридична невизначеність | Явний патентний грант + retaliation clause (автоматичне припинення ліцензії при патентних позовах) | **Apache 2.0** |
| **Простота для контриб'юторів** | ~170 слів; максимально простий | ~10 500 слів; формальніший, але зрозумілий | **MIT** |
| **Сумісність з GPL v2** | ✅ Сумісний | ❌ Несумісний (через патентний clause) | **MIT** |
| **Сумісність з GPL v3** | ✅ Сумісний | ✅ Сумісний | Нічия |
| **Корпоративне прийняття** | Добре | Відмінне — юристам легше перевіряти явні умови | **Apache 2.0** |
| **Що обирають аналоги** | Saltcorn, DbUp, Frappe | Prisma, Drizzle ORM, Supabase, Amplication, DBML | **Apache 2.0** |

### Рекомендація: Apache 2.0

**Обирайте Apache 2.0** з таких причин:

**Індустріальний стандарт.** Серед безпосередньо порівнянних проєктів (Prisma, Drizzle ORM, Supabase, Amplication, DBML) Apache 2.0 є домінуючою ліцензією. Це позиціонує проєкт в рамках усталеної екосистемної норми для інструментів роботи з базами даних та метаданими.

**Патентний захист критичний для бізнес-інструменту.** Для продукту, орієнтованого на бізнес-метадані та конфігурацію баз даних, явний патентний грант надає реальний захист. Корпоративні користувачі оцінять юридичну визначеність. Retaliation clause Apache 2.0 відлякує патентних тролів.

**Несумісність з GPL v2 — не проблема.** Для візуального конфігуратора метаданих інтеграція з GPL v2-only кодовими базами (як ядро Linux) практично нереальна. GPL v3 сумісність забезпечена.

**Мінімальний overhead.** Вимоги Apache 2.0 (NOTICE-файл, attribution) є добре задокументованими та автоматизованими.

**Альтернативний варіант:** подвійне ліцензування MIT OR Apache 2.0 (як в екосистемі Rust) надає користувачам вибір і максимальну сумісність, зберігаючи патентний захист для тих, хто обирає Apache 2.0.

## D. CLA та DCO: що обрати

### Рекомендація: DCO (Developer Certificate of Origin), без CLA

**CLA (Contributor License Agreement)** — юридична угода, яку контриб'ютори підписують перед прийняттям внесків. Надає проєкту широкі права, включно з можливістю перелцензування. Основна проблема: створює бар'єр для контриб'юторів і потребує адміністративної інфраструктури.

**DCO (Developer Certificate of Origin)** — легковагова альтернатива, створена Linux Foundation у 2004 році. Контриб'ютор додає `Signed-off-by: Name <email>` до кожного комміту, підтверджуючи право на внесок коду.

| Аспект | CLA | DCO |
|---|---|---|
| Юридична природа | Обов'язковий контракт | Атестація при коміті |
| Бар'єр для контриб'юторів | **Високий** | **Мінімальний** |
| Адміністративне навантаження | Висока (трекінг, зберігання) | Мінімальне (записується в git) |
| Патентне покриття | Часто включає | Покладається на ліцензію проєкту |
| Можливість перелцензування | Так (контроверсійно) | Ні |

**Хто використовує CLA:** Google, Microsoft, Apache Software Foundation, NocoDB (використав CLA саме для зміни ліцензії — це підірвало довіру спільноти).

**Хто використовує DCO:** Linux kernel, Docker, Git, GitLab (мігрував з CLA на DCO у 2017), Chef (мігрував у 2016), OpenInfra Foundation (мігрував у 2025), Keycloak.

**Хто не використовує ні CLA, ні DCO:** Prisma, Supabase, Drizzle ORM, Saltcorn, Amplication — більшість порівнянних проєктів не мають формального процесу.

**Чому DCO, а не CLA для вашого проєкту:**

Поєднання **Apache 2.0 + DCO** покриває обидва ключові ризики: Apache 2.0 забезпечує патентний грант від контриб'юторів (секція 3 та 5), а DCO забезпечує атестацію права на внесок. CLA створює зайву фрикцію для нового проєкту і асоціюється з «bait-and-switch» стратегіями (NocoDB — яскравий негативний приклад). Індустріальний тренд однозначно рухається від CLA до DCO.

**Імплементація:** додайте опис DCO в `CONTRIBUTING.md` та встановіть GitHub App [DCO Bot](https://github.com/apps/dco) для автоматичної перевірки `Signed-off-by` у pull requests.

## E. Практичні рекомендації

### Що робити при запозиченні коду

Для **Apache 2.0 проєктів** (Supabase, Prisma, Drizzle, DBML, Amplication CE): створіть файл `THIRD-PARTY-NOTICES` або `NOTICE` у корені проєкту. Для кожного запозиченого фрагменту вкажіть: назву проєкту-джерела, оригінальний copyright, текст або посилання на ліцензію. Зберігайте оригінальні заголовки файлів з copyright. Позначайте модифіковані файли.

Для **MIT проєктів** (Frappe, Saltcorn, DbUp): збережіть copyright notice та текст MIT ліцензії у файлах або в `THIRD-PARTY-NOTICES`.

### Чого не робити

Не копіюйте код із GPL v3 проєктів (ERPNext, pgModeler, Budibase, DrawDB) — навіть невеликі фрагменти «заражають» весь проєкт copyleft-обов'язками. Не копіюйте код з NocoDB (Sustainable Use License) або Directus (BSL 1.1) — ці ліцензії несумісні з open-source. З LGPL-3.0 (Odoo, bsl-language-server) та MPL-2.0 (OneScript) допускається лінкування як бібліотеки, але не пряме копіювання та перелцензування.

### Пріоритетні джерела для вивчення та запозичення

- **Архітектура метаданих:** Prisma schema engine (Apache 2.0), holistics/dbml (Apache 2.0), Drizzle ORM (Apache 2.0)
- **UI конфігуратора:** Supabase Studio (Apache 2.0), Amplication CE (Apache 2.0)
- **Бізнес-логіка ERP:** Frappe Framework (MIT) — найбільш пермісивний ERP-фреймворк
- **Міграції БД:** DbUp (MIT), Prisma migrate (Apache 2.0)
- **Концепції 1С:** OneScript (MPL-2.0, вивчати ідеї), bsl-language-server (LGPL-3.0, вивчати ідеї)
