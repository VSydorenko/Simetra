## Завдання 1: Повна карта метаданих 1С:Підприємство 8.3

```
Мені потрібне глибоке дослідження системи метаданих платформи 1С:Підприємство 8.3. Це дослідження буде використано як основа для BRD open-source продукту — візуального конфігуратора бізнес-метаданих, натхненного 1С, але для сучасних стеків (.NET, PostgreSQL, React).

Результат має бути українською мовою у вигляді структурованого документа.

Що потрібно дослідити:

1. **Повний перелік типів об'єктів метаданих 1С:Підприємство 8.3** — не тільки основні (довідники, документи, регістри), а ВСІ: константи, перелічення, плани видів характеристик, плани рахунків, плани видів розрахунку, бізнес-процеси, задачі, журнали документів, послідовності, критерії відбору, зовнішні джерела даних, регламентні завдання, HTTP-сервіси, Web-сервіси, загальні модулі, ролі, підсистеми тощо.

2. **Для кожного прикладного типу метаданих** (довідники, документи, регістри відомостей, регістри накопичення, регістри бухгалтерії, регістри розрахунку, перелічення, плани видів характеристик, плани рахунків, плани видів розрахунку, бізнес-процеси, задачі, константи, послідовності, журнали документів, критерії відбору) надай:
   - Стандартні реквізити (які задані платформою і не видаляються користувачем). Наприклад, для довідника: Код, Найменування, ПозначенняВидалення, Батько, ЦеГрупа, Власник, Предефінований.
   - Налаштування типу (що конфігурується для цього типу в конфігураторі). Наприклад, для довідника: довжина коду, тип коду, тип ієрархії, кількість рівнів ієрархії.
   - Дозволені підоб'єкти (табличні частини, виміри, ресурси, реквізити, рухи, графи, форми, макети тощо).
   - Особливості поведінки (нумерація, проведення, підпорядкування, періодичність тощо).

3. **Система типів даних 1С** — примітивні типи (Число, Рядок, Дата, Булево, СховищеЗначення, УнікальнийІдентифікатор, Null, Невизначено), складений тип, посилальні типи, колекції значень (Масив, Структура, Відповідність, СписокЗначень, ТаблицяЗначень).

4. **Як 1С зберігає метадані технічно:**
   - Внутрішній формат конфігурації (файл .cf, .cfu, .dt)
   - Формат вивантаження у файли XML (ConfigDumpInfo.xml, структура каталогів)
   - Формат 1C:EDT (Enterprise Development Tools) — як метадані представлені для роботи з Git
   - Формат BSL (мова 1С) — як метадані використовуються в коді

5. **Концепція "стандартних реквізитів" vs "реквізитів" в 1С:**
   - Чим стандартні реквізити відрізняються від звичайних
   - Чи можна їх перейменувати, приховати, змінити тип
   - Як вони впливають на генерацію таблиць у БД

6. **Предефіновані елементи:**
   - Як працюють предефіновані елементи довідників та планів видів характеристик
   - Як вони зберігаються в конфігурації і в БД
   - Які проблеми з ними виникають на практиці

7. **Механізм рухів документів:**
   - Як документи реєструють рухи по регістрах
   - Що таке "проведення" технічно
   - Як конфігурується зв'язок "документ → регістр"

Формат результату: структурований документ з чіткими заголовками, таблицями стандартних реквізитів для кожного типу, і прикладами де доречно. Документ має бути достатньо детальним, щоб на його основі можна було спроектувати метамодель нового продукту.
```

## Завдання 2: Існуючі open-source проєкти — аналоги та суміжні рішення

```
Мені потрібне дослідження існуючих open-source проєктів, які реалізують metadata-driven підхід до бізнес-додатків або інструменти для роботи з метаданими 1С. Це дослідження для BRD open-source візуального конфігуратора бізнес-метаданих (аналог конфігуратора 1С для сучасних стеків).

Результат має бути українською мовою.

Що потрібно дослідити:

### A. Проєкти з екосистеми 1С на GitHub

Знайди і проаналізуй:

1. **BSL Language Server** (1c-syntax/bsl-language-server) — як він парсить і працює з метаданими 1С. Яка модель метаданих використовується всередині.

2. **OneScript** (EvilBeaver/OneScript) — альтернативний рантайм для мови 1С. Чи є у нього робота з метаданими конфігурацій.

3. **1C:EDT-related tools** — будь-які open-source інструменти для роботи з форматом метаданих EDT.

4. **v8unpack, gconn, та інші утиліти** для розпакування/парсингу конфігурацій 1С. Як вони представляють метадані.

5. **Vanessa Automation, Vanessa ADD** — тестові фреймворки для 1С, чи мають вони моделі метаданих.

6. Будь-які інші проєкти на GitHub з тегами "1c-enterprise", "1c-metadata", "1c-configurator".

Для кожного проєкту: URL репозиторію, ліцензія, мова, кількість зірок, останній коміт, і головне — яку частину метаданих 1С вони моделюють і як.

### B. Metadata-driven business platforms (не-1С)

1. **Frappe Framework / ERPNext** — їхня система DocType. Як описуються сутності, стандартні поля, child tables, наслідування. Ліцензія.

2. **Odoo** — система моделей (ir.model). Як визначаються поля, зв'язки, наслідування. Концепція computed fields. Ліцензія.

3. **Saltcorn** — open-source no-code platform. Як вони описують таблиці і зв'язки. Ліцензія.

4. **Budibase** — їхня внутрішня модель даних. Ліцензія.

5. **NocoDB** — як вони маплять візуальну модель на SQL-схему. Концепція virtual columns. Ліцензія.

6. **Directus** — schema introspection і автоматичний API. Ліцензія.

7. **Amplication** — генерація бекенду з метаданих. Ліцензія.

Для кожного: чим схожий на конфігуратор 1С, чим відрізняється, що можна запозичити (ідеї або код з урахуванням ліцензії).

### C. Інструменти візуального моделювання схем БД

1. **dbdiagram.io / DBML** — формат DBML, open-source парсер. Ліцензія.
2. **pgModeler** — моделер для PostgreSQL. Як представляє схему. Ліцензія.
3. **DrawDB** (drawdb-io/drawdb) — open-source database diagram editor. Ліцензія.
4. **Prisma** — schema language і migrate. Ліцензія.
5. **Drizzle** — schema as code і drizzle-kit. Ліцензія.

Для кожного: чи є бізнес-семантика (документи, довідники), чи тільки таблиці/колонки.

### D. Зведена таблиця

- Назва
```

## Завдання 4: Schema introspection і DDL generation — технічний аналіз

```
Мені потрібен технічний аналіз того, як існуючі open-source інструменти реалізують читання схеми PostgreSQL (schema introspection) і генерацію DDL (CREATE/ALTER TABLE). Це дослідження для BRD open-source візуального конфігуратора бізнес-метаданих.

Результат має бути українською мовою.

Що дослідити:

### A. supabase/pg_meta (Apache 2.0)
Репозиторій: https://github.com/supabase/pg-meta

1. Загальна архітектура — як організований код, які модулі.
2. Як вони читають schema з PostgreSQL — які системні таблиці і views використовуються (information_schema, pg_catalog, pg_class, pg_attribute тощо).
3. Як вони генерують SQL для CREATE TABLE, ALTER TABLE, ADD/DROP COLUMN.
4. Як обробляють foreign keys, indices, constraints.
5. Як працюють з RLS-політиками, тригерами, функціями.
6. Внутрішня модель даних — як вони представляють таблицю, колонку, зв'язок у TypeScript.
7. Що з цього можна перенести на .NET / C#.

### B. Drizzle Kit (Apache 2.0)
Репозиторій: https://github.com/drizzle-team/drizzle-orm (пакет drizzle-kit)

1. Як працює schema diff — алгоритм порівняння двох станів схеми.
2. Як генеруються міграції (SQL-файли).
3. Як вони обробляють rename vs drop+create (відома проблема schema diff).
4. Формат snapshot schema.
5. Що корисного для нашого генератора міграцій.

### C. Prisma Migrate (Apache 2.0)
Репозиторій: https://github.com/prisma/prisma-engines (Rust)

1. Як Prisma schema перетворюється в SQL.
2. Їхній schema diff engine — загальна архітектура.
3. Як вони обробляють destructive changes (drop column, drop table).
4. Shadow database концепція.
5. Що корисного і які обмеження.

### D. EF Core Migrations (.NET)
1. Як EF Core робить schema diff (ModelDiffer).
2. Як генеруються міграції — формат C# класів міграцій.
3. Як працює MigrationsSqlGenerator для PostgreSQL (Npgsql.EntityFrameworkCore.PostgreSQL).
4. Як можна програмно створити Model і згенерувати міграцію без реальних entity-класів (через ModelBuilder API).
5. Обмеження і відомі проблеми.

### E. PostgreSQL DDL generation patterns
1. Які SQL-запити потрібні для повного schema introspection PostgreSQL.
2. Best practices для генерації CREATE TABLE з правильним порядком constraints.
3. Як генерувати ALTER TABLE з мінімальними breaking changes.
4. Як працювати з PostgreSQL enum types, arrays, JSONB у контексті schema generation.
5. Як генерувати індекси, unique constraints, check constraints.

### F. Зведена таблиця
Порівняння підходів: pg_meta vs Drizzle Kit vs Prisma vs EF Core за критеріями:
- Schema introspection (як читають)
- Schema diff (як порівнюють)
- DDL generation (як генерують)
- Migration format
- Обробка destructive changes
- Ліцензія
- Що запозичити

Формат: технічний документ з прикладами коду/SQL, діаграмами потоків, і конкретними рекомендаціями.
```

## Завдання 5: Формати опису метаданих і схем — порівняльний аналіз

```
Мені потрібне дослідження форматів, які різні інструменти використовують для серіалізації/опису метаданих і схем баз даних. Це дослідження для BRD open-source візуального конфігуратора бізнес-метаданих — нам потрібно обрати правильний формат зберігання метамоделі.

Результат має бути українською мовою.

Ключове питання: наш продукт зберігає метадані бізнес-об'єктів (довідники, документи, регістри з вимірами/ресурсами тощо). Як це серіалізувати — JSON, YAML, власний DSL, TypeScript, XML? Кожен варіант має trade-offs.

Що дослідити:

### A. Prisma Schema Language (.prisma)
1. Синтаксис і приклади — як виглядає реальна .prisma схема.
2. Чому вони зробили власний DSL замість JSON/YAML/TypeScript.
3. Як вони прийшли до цього рішення (історія, blog posts, RFC).
4. Tooling: syntax highlighting, LSP, formatter, parser.
5. Плюси і мінуси за відгуками спільноти.
6. Як вони версіонують формат.

### B. DBML (Database Markup Language)
Репозиторій: https://github.com/holistics/dbml
1. Синтаксис і приклади.
2. Парсер і генератори (dbml-to-sql, sql-to-dbml).
3. Ліцензія.
4. Обмеження — чи може він описати бізнес-семантику (не тільки таблиці).

### C. Drizzle — schema as TypeScript
1. Як виглядає схема в Drizzle (TypeScript код).
2. Переваги: type safety, IDE autocomplete, imports.
3. Недоліки: прив'язка до TypeScript runtime.
4. Як вони серіалізують snapshot для diff.

### D. JSON Schema і OpenAPI
1. Як JSON Schema використовується для опису моделей даних.
2. Версіонування формату (draft-04, draft-07, 2020-12).
3. Чи підходить JSON Schema для опису бізнес-метаданих з кастомними розширеннями.

### E. 1С EDT XML формат
1. Як 1С:EDT серіалізує метадані для Git.
2. Структура каталогів і файлів.
3. Приклад: як виглядає довідник в EDT-форматі.
4. Плюси і мінуси цього підходу.

### F. Frappe DocType JSON
1. Як Frappe серіалізує DocType в JSON.
2. Приклад реального файлу.
3. Як це працює з Git.

### G. Порівняльний аналіз

Зведена таблиця за критеріями:
- Людиночитабельність
- Git-friendliness (мінімальний diff при змінах)
- Парсинг (складність імплементації парсера)
- Extensibility (як додати нові поля/типи)
- Tooling (syntax highlighting, validation, LSP)
- Придатність для опису бізнес-об'єктів (довідники, регістри, документи з табличними частинами)

### H. Рекомендація

На основі аналізу — яку стратегію серіалізації обрати для нашого продукту:
- Чи варто робити власний DSL?
- Чи достатньо JSON з JSON Schema валідацією?
- Чи потрібен подвійний формат (JSON для машин + DSL для людей)?
- Як забезпечити стабільний, детерміністичний вивід для Git.

Формат: аналітичний документ з прикладами кожного формату, таблицею порівняння, і аргументованою рекомендацією.
```

```
Мені потрібне дослідження UI/UX патернів у візуальних конфігураторах метаданих і редакторах схем баз даних. Це дослідження для BRD open-source візуального конфігуратора бізнес-метаданих (аналог конфігуратора 1С для сучасних стеків).

Результат має бути українською мовою.

Ми будуємо десктопний/веб-додаток (Tauri + Vite + React + shadcn/ui), де користувач моделює бізнес-об'єкти: довідники, документи, регістри. Нам потрібні конкретні UI-рішення.

Що дослідити:

### A. Конфігуратор 1С:Підприємство 8.3

4. Як редагуються реквізити — таблиця реквізитів, панель властивостей.
5. Як візуально відрізняються стандартні реквізити від користувацьких.
6. Що незручно — відомі проблеми UX конфігуратора, скарги спільноти.
7. Що зручно — патерни, які варто зберегти.

### B. 1C:EDT (Enterprise Development Tools)
1. Як виглядає інтерфейс EDT — чи він покращив UX конфігуратора.

### C. Supabase Studio — Table Editor

3. UX для додавання зв'язків між таблицями.

### G. Загальні UI-патерни для нашого продукту

На основі аналізу — рекомендації для конкретних UI-рішень:

1. **Дерево метаданих (ліва панель):**
   - Які бібліотеки React використовувати (react-arborist, @tanstack/react-virtual, тощо)
   - Контекстне меню — які дії на кожному рівні
   - Drag-and-drop — чи потрібен у MVP
   - Іконки для типів об'єктів
   - Пошук/фільтрація по дереву

2. **Редактор полів (центральна панель):**
   - Таблиця vs список vs cards
   - Inline editing vs окрема форма
   - Як показувати тип поля з іконкою
   - Як показувати reference-поля

3. **Панель властивостей (права панель):**
   - Context-sensitive — різний контент для entity vs field
   - Grouped properties vs flat list
   - Як показувати стандартні реквізити (readonly, інший стиль)

4. **Загальний layout:**
   - 3-panel resizable layout — які бібліотеки (react-resizable-panels тощо)
   - Top toolbar — які дії
   - Keyboard shortcuts

Формат: аналітичний документ з описом UI-патернів, конкретними рекомендаціями бібліотек для React, і порівняльними коментарями "як у конфігураторі 1С → як зробити краще".
```

## Завдання 8: PostgREST як runtime API layer для metadata-driven системи

```
Мені потрібне окреме технічне дослідження PostgREST як open-source REST layer над PostgreSQL. Це дослідження буде використано для Phase 3 runtime-архітектури open-source візуального конфігуратора бізнес-метаданих.

Результат має бути українською мовою у вигляді структурованого документа.

Що потрібно дослідити:

1. **Що таке PostgREST технічно**:
   - чи є це частиною PostgreSQL чи окремим сервером
   - як він експонує таблиці, views і SQL-функції як REST API
   - які HTTP-патерни підтримує (CRUD, filtering, ordering, pagination, RPC)

2. **Open-source статус і екосистема**:
   - офіційний репозиторій, ліцензія, документація, Docker image
   - хто використовує PostgREST у production
   - як він пов'язаний із Supabase

3. **Deployment моделі**:
   - standalone PostgreSQL + PostgREST
   - self-hosted варіант
   - Supabase як managed deployment target
   - що саме потрібно для запуску automatic REST над plain PostgreSQL

4. **Безпека і доступ**:
   - роль PostgreSQL grants
   - JWT support
   - Row Level Security
   - які межі між application auth і database auth

5. **Наскільки PostgREST підходить для runtime Simetra**:
   - як мапляться операції DataProvider (`list`, `get`, `create`, `update`, `delete`, `searchRef`, `postDocument`, `getConstants`)
   - чи підходить він для CRUD по довідниках і документах
   - чи підходить для RPC викликів posting/unposting
   - які є обмеження для polymorphic refs, складних join-сценаріїв і constants strategy

6. **Порівняння PostgREST vs Supabase як deployment target**:
   - що дає чистий PostgREST
   - що додатково дає Supabase
   - коли для продукту достатньо PostgreSQL + PostgREST, а коли потрібен ширший стек

7. **Рекомендації для BRD і архітектури runtime**:
   - чи варто використовувати PostgREST як перший runtime adapter
   - чому transport layer має бути абстрактним (`DataProvider`), а не жорстко прив'язаним до SDK
   - який MVP scope є реалістичним

Формат результату: короткий, але технічно насичений документ з таблицями, практичними висновками і окремою секцією "Що це дає Simetra".
```
