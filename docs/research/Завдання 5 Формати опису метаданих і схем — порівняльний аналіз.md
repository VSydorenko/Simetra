# Серіалізація метаданих бізнес-об'єктів: вибір формату для BRD

**JSON з JSON Schema валідацією — оптимальний базовий формат для BRD.** Він забезпечує найкращий баланс між людиночитабельністю, Git-friendliness, розширюваністю та доступністю тулінгу, не вимагаючи створення власного парсера. Аналіз шести альтернативних підходів — Prisma DSL, DBML, Drizzle TypeScript, JSON Schema, 1С:EDT XML та Frappe DocType JSON — показує, що кожен формат має специфічні trade-offs, але для open-source візуального конфігуратора бізнес-метаданих зі стеком .NET 8+/PostgreSQL/React найбільш раціональна стратегія — **JSON з кастомною JSON Schema метасхемою**, з можливістю додавання DSL-представлення в майбутньому. Нижче — детальний аналіз кожного формату з прикладами і порівнянням.

---

## A. Prisma Schema Language — власний DSL для опису моделей

Prisma створила один з найуспішніших прикладів спеціалізованого DSL для метаданих. Формат `.prisma` — декларативний, блочний синтаксис, натхненний GraphQL SDL, але адаптований для реляційних баз:

```prisma
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String?
  role      Role     @default(USER)
  posts     Post[]
}

model Post {
  id        Int      @id @default(autoincrement())
  title     String   @db.VarChar(255)
  published Boolean  @default(false)
  author    User     @relation(fields: [authorId], references: [id])
  authorId  Int
}

enum Role {
  USER
  ADMIN
}
```

### Чому Prisma обрала власний DSL

Команда Prisma пояснює рішення трьома ключовими аргументами. По-перше, **мовна незалежність**: `.prisma` файл використовується клієнтами на JavaScript, TypeScript, Rust, Python і Go — один source of truth для всіх рантаймів. По-друге, **декларативність**: на відміну від TypeScript-коду, `.prisma` файл можна статично аналізувати без виконання — це критично для міграцій (`prisma migrate`) та інтроспекції бази. По-третє, **доступність для нетехнічних членів команди**: продакт-менеджери і аналітики можуть читати і розуміти схему.

Еволюція формату показова: **Prisma 1** (2017–2019) використовувала GraphQL SDL, **Prisma 2** (2020) перейшла на власний PSL, а **Prisma Next** (анонсований 2025) додає TypeScript як альтернативний формат визначення схеми — визнаючи, що спільнота роками вимагала цього (GitHub Issue #1805).

### Тулінг і парсер

Парсер написаний на **Rust з використанням PEG-граматики (pest)** і компілюється у WebAssembly для VSCode-розширення. Екосистема включає LSP-сервер (автодоповнення, jump-to-definition, діагностика), опціонований форматер `prisma format` (аналог `gofmt` — без конфігурації), і DMMF (Data Model Meta Format) — JSON-представлення для генераторів. Існують також сторонні парсери: `@loancrate/prisma-schema-parser` (TypeScript, порт PEG.js), `prisma-ast` (JavaScript AST), `tree-sitter-prisma-io`.

### Критика спільноти

Головна претензія — **відсутність розширюваності**: PSL не підтримує користувацькі атрибути, типізовані JSON-поля чи soft delete. Проєкт ZenStack створив надмножину PSL саме для цього. Код-генерація (`prisma generate`) сповільнює цикл розробки порівняно з Drizzle. Формат **не має власної версії** окремо від версії ORM — нові можливості додаються через `previewFeatures` флаги.

**Ключовий висновок для BRD**: Prisma довела, що власний DSL може бути успішним, але потребує **значних інвестицій** — парсер на Rust, LSP-сервер, VSCode-розширення, форматер, WASM-збірка. Для стартапу це нереалістичний обсяг роботи на старті.

## B. DBML — легковагий DSL для діаграм баз даних

DBML (Database Markup Language) — open-source DSL від Holistics (ліцензія **Apache-2.0**), створений як формалізація синтаксису dbdiagram.io. GitHub: **~3,500 зірок**, npm-завантажень `@dbml/core`: **~128,000/тиждень**.

```dbml
Project ecommerce {
  database_type: 'PostgreSQL'
  Note: 'E-commerce platform database'
}

enum order_status {
  pending [note: 'Awaiting payment']
  processing
  shipped
  delivered
}

Table customers {
  id int [pk, increment]
  email varchar(255) [unique, not null]
  name varchar(255) [not null]
  created_at timestamp [default: `now()`]
}

Table orders {
  id int [pk, increment]
  customer_id int [not null]
  status order_status [not null, default: 'pending']
  total decimal(10,2) [not null]
  indexes {
    (customer_id, status)
  }
}

Ref: orders.customer_id > customers.id [delete: cascade]
```

DBML підтримує `TablePartial` (повторно використовувані набори полів), вбудовані приклади даних (`records`), check-обмеження, та конвертацію в/з SQL для PostgreSQL, MySQL, MSSQL, Oracle. Парсер побудований на **ANTLR + PEG.js**, є сторонні парсери на Python, Go, PHP, Java і **C# (Ivy.Dbml.Parser)**.

### Критичне обмеження для BRD

DBML **не може описати бізнес-семантику**. Він оперує виключно фізичними таблицями: немає концепцій «довідник», «документ», «регістр», «вимір/ресурс». Система атрибутів `[...]` має **фіксований набір ключів** (pk, not null, unique, default, increment, note, ref) — додати кастомні неможливо. Пропозиція загальної системи анотацій (Issue #49, 2019) була закрита без повної реалізації. Єдиний механізм довільних метаданих — поле `note` (один рядок тексту). DBML також не підтримує views, stored procedures, computed fields.

**Висновок**: DBML ідеально підходить для візуалізації DB-схем, але **непридатний як формат зберігання бізнес-метамоделі** через відсутність розширюваності.

## C. Drizzle — схема як TypeScript-код

Drizzle ORM визначає схему безпосередньо в TypeScript, використовуючи builder-функції:

```typescript
import { pgTable, serial, text, integer, boolean, 
         timestamp, varchar, pgEnum } from 'drizzle-orm/pg-core';
import { relations } from 'drizzle-orm';

export const roleEnum = pgEnum('role', ['user', 'admin']);

export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  email: varchar('email', { length: 255 }).notNull().unique(),
  name: text('name'),
  role: roleEnum('role').default('user').notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull(),
});

export const posts = pgTable('posts', {
  id: serial('id').primaryKey(),
  title: varchar('title', { length: 200 }).notNull(),
  content: text('content'),
  published: boolean('published').default(false),
  authorId: integer('author_id').references(() => users.id),
});

// Reusable patterns via spread
const timestamps = {
  updatedAt: timestamp('updated_at'),
  createdAt: timestamp('created_at').defaultNow().notNull(),
};
```

### Переваги TypeScript-підходу

**Type safety без кодогенерації** — типи виводяться автоматично через `$inferSelect` та `$inferInsert`. IDE-автодоповнення працює з коробки. Можливість використовувати imports, spread-оператори, умови і цикли дає **безмежну композабельність** — наприклад, шаблон `timestamps` вище.

### Серіалізація снапшотів для міграцій

Drizzle Kit виконує TypeScript-файли, викликає `getTableConfig()` для кожної таблиці, і серіалізує результат у **JSON-снапшот** (валідується Zod-схемою). Кожна міграція зберігається як пара `snapshot.json` + `migration.sql`. Для порівняння снапшотів використовується бібліотека `json-diff` з «зплющенням» складних структур у рядки-ключі.

### Критичний недолік для BRD

Схема — це **імперативний код**, який неможливо проаналізувати без виконання TypeScript-рантайму. Spread-оператори, динамічні імпорти, умовні конструкції означають, що фінальна форма схеми відома тільки в рантаймі. Для BRD, де метадані мають читатися з .NET бекенду, парситися в React-фронтенді та зберігатися у Git — залежність від TypeScript-рантайму є **неприйнятною**. Сам Drizzle визнає цю проблему — саме тому вони серіалізують у JSON для diff.

**Висновок**: TypeScript-as-schema працює чудово всередині TS-екосистеми, але **неприйнятний для кросплатформного продукту** з .NET бекендом.

## D. JSON Schema — стандарт з найширшою екосистемою

JSON Schema — найпоширеніший формат опису структур даних. Поточні рекомендовані версії: **draft-07** (2018, центр тяжіння екосистеми) та **2020-12** (сумісний з OpenAPI 3.1).

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "Customer",
  "type": "object",
  "x-entity-type": "catalog",
  "x-icon": "users",
  "x-table-name": "customers",
  "properties": {
    "id": {
      "type": "integer",
      "x-primary-key": true,
      "x-auto-increment": true,
      "readOnly": true
    },
    "email": {
      "type": "string",
      "format": "email",
      "title": "Email Address",
      "x-unique": true,
      "x-searchable": true,
      "x-display-order": 2
    },
    "status": {
      "type": "string",
      "enum": ["active", "inactive"],
      "default": "active",
      "x-ui-widget": "select"
    }
  },
  "required": ["email"]
}
```

### Механізм розширень

JSON Schema **офіційно підтримує** кастомні анотації через префікс `x-`. Ключові слова з `x-` є неявно визначеними анотаціями — їх значення збираються, але не впливають на валідацію. Це той самий патерн, який OpenAPI використовує для Specification Extensions. Починаючи з версії 2019-09, система **Vocabularies** (`$vocabulary`) дозволяє формально оголошувати набори кастомних ключових слів з URI-ідентифікатором.

Стандартні метадані вже доступні: `title` (відображуване ім'я), `description`, `examples`, `default`, `readOnly`/`writeOnly`, `deprecated`, `$comment`. Для бізнес-семантики — `x-entity-type`, `x-dimensions`, `x-resources` тощо.

### Сильні і слабкі сторони

Екосистема **масштабна**: валідатори (Ajv, NJsonSchema для .NET), генератори коду (quicktype, json-schema-to-typescript), генератори форм (react-jsonschema-form), `$ref` для композиції схем. Використовується OpenAPI, AsyncAPI, OpenMetadata, Backstage.

Головний недолік — **багатослівність**. Простий об'єкт з 10 полями займає 80+ рядків JSON. Відсутність коментарів у стандартному JSON (хоча `$comment` є з draft-07). **Немає нативного моделювання зв'язків** — foreign keys потребують кастомних розширень.

## E. 1С:EDT — XML-серіалізація як приклад для бізнес-метаданих

1С:EDT зберігає метадані у файлах `.mdo` (Metadata Object) з XML-серіалізацією у просторі імен `http://g5.1c.ru/v8/dt/metadata/mdclass`. Це **найближчий аналог** того, що потрібно BRD — формат описує саме бізнес-об'єкти з вимірами, ресурсами, табличними частинами.

### Структура каталогів

```
src/
├── Configuration/Configuration.mdo     # Кореневий файл конфігурації
├── Catalogs/
│   └── Products/
│       ├── Products.mdo                # Метадані довідника (XML)
│       ├── ObjectModule.bsl            # Модуль об'єкта (код)
│       └── Forms/ItemForm/Form.form    # Форма (XML)
├── Documents/
│   └── SalesOrder/SalesOrder.mdo
├── InformationRegisters/
│   └── ExchangeRates/ExchangeRates.mdo
└── AccumulationRegisters/
    └── InventoryBalance/InventoryBalance.mdo
```

### Приклад: регістр відомостей у форматі EDT

```xml
<?xml version="1.0" encoding="UTF-8"?>
<mdclass:InformationRegister xmlns:mdclass="http://g5.1c.ru/v8/dt/metadata/mdclass"
                              uuid="aabbccdd-1122-3344-5566-778899aabbcc">
  <name>ExchangeRates</name>
  <synonym><key>ru</key><value>Курсы валют</value></synonym>
  <informationRegisterPeriodicity>Day</informationRegisterPeriodicity>
  
  <!-- Виміри -->
  <dimensions uuid="dim11111-2222-3333-4444-555555555555">
    <name>Currency</name>
    <synonym><key>ru</key><value>Валюта</value></synonym>
    <type><types>CatalogRef.Currencies</types></type>
    <master>true</master>
  </dimensions>

  <!-- Ресурси -->
  <resources uuid="res11111-2222-3333-4444-555555555555">
    <name>Rate</name>
    <synonym><key>ru</key><value>Курс</value></synonym>
    <type>
      <types>Number</types>
      <numberQualifiers>
        <precision>15</precision><scale>4</scale>
      </numberQualifiers>
    </type>
  </resources>
</mdclass:InformationRegister>
```

### Проблеми підходу 1С:EDT

XML — **надмірно багатослівний**: конфігурація 200 МБ у `.cf` розгортається до ~1.2 ГБ XML-файлів. Форми (`.form`) генерують величезні дифи навіть при мінімальних змінах. Кореневий `Configuration.mdo` — постійне джерело merge-конфліктів, бо кожне додавання об'єкта змінює цей файл. **Формат нестабільний між версіями EDT** — оновлення EDT 2025.2.0 змінило формат, створюючи масовані фантомні дифи. Платформа 1С не може читати `.mdo` напряму — потрібна конвертація через `ring` або `1cedtcli`.

Спільнота розділена: частина розробників перейшла на EDT, частина залишається на Конфігураторі з `DumpConfigToFiles`. Багато команд використовують **гібридний підхід** — Конфігуратор для розробки, 1C:GitConverter для автоматичного експорту в Git.

**Урок для BRD**: структура каталогів 1С (один файл на об'єкт, код окремо від метаданих) — це правильний патерн. Але XML як формат серіалізації — **поганий вибір** через багатослівність і складність дифів.

## F. Frappe DocType — JSON як єдине джерело істини

Frappe Framework (основа ERPNext) серіалізує кожен DocType у JSON-файл, який містить повну метамодель: поля, дозволи, layout, поведінку:

```json
{
  "doctype": "DocType",
  "name": "Customer",
  "module": "Selling",
  "naming_rule": "By fieldname",
  "autoname": "field:customer_name",
  "is_submittable": 0,
  "is_tree": 0,
  "search_fields": "customer_name,customer_group",
  "title_field": "customer_name",
  "field_order": ["customer_name", "customer_group", "territory", "items"],
  "fields": [
    {
      "fieldname": "customer_name",
      "fieldtype": "Data",
      "label": "Customer Name",
      "reqd": 1,
      "in_list_view": 1,
      "unique": 1
    },
    {
      "fieldname": "customer_group",
      "fieldtype": "Link",
      "label": "Customer Group",
      "options": "Customer Group",
      "reqd": 1
    },
    {
      "fieldname": "items",
      "fieldtype": "Table",
      "label": "Items",
      "options": "Customer Item"
    }
  ],
  "permissions": [
    {"role": "Sales Manager", "read": 1, "write": 1, "create": 1}
  ]
}
```

### Як це працює з Git

У **developer mode** збереження DocType через UI автоматично оновлює JSON-файл на диску. `bench migrate` синхронізує JSON → DB. З версії Frappe 14 використовується **MD5-хеш** для визначення змін (замість ненадійного `modified` timestamp).

### Проблеми Frappe-підходу

**Merge-конфлікти** — головний біль спільноти. Поле `modified` (timestamp), масив `field_order`, значення `idx` змінюються при кожному збереженні, генеруючи шум у дифах. `custom_field.json` — особливо проблематичний файл. Layout-елементи (`Section Break`, `Column Break`) зберігаються як «поля» разом з даними, роздуваючи файл. Складні DocType (Sales Invoice зі 100+ полями) генерують файли на тисячі рядків.

Позитивна сторона — **архітектура розширень**: Custom Fields і Property Setters дозволяють кастомізацію без зміни оригінальних файлів. Це елегантний патерн розділення стандартних і користувацьких метаданих.

**Урок для BRD**: підхід Frappe (один JSON-файл = один об'єкт, повна метамодель) — правильний напрямок. Але потрібно уникнути помилок: **не зберігати timestamps і volatile дані** у файлі, використовувати детерміністичну серіалізацію з відсортованими ключами.

## H. Рекомендована стратегія серіалізації для BRD

### Чому не власний DSL

Створення власного DSL за прикладом Prisma вимагає: PEG/ANTLR-граматики, парсера, LSP-сервера, VSCode-розширення, форматера, WASM-збірки для веб-редактора. Prisma витратила роки на цю інфраструктуру, маючи десятки мільйонів доларів фінансування. Для open-source проєкту на старті це **нераціональна інвестиція**. DSL виправданий тільки коли формат стабілізується і з'явиться достатня спільнота — це рішення для версії 2.0+.

### Чому JSON, а не YAML чи XML

**XML** (шлях 1С) — надмірно багатослівний, погані дифи, важке ручне редагування. **YAML** — проблеми з типізацією (`no` → `false`, `1.0` → число), залежність від відступів створює merge-конфлікти. **JSON** — детерміністичний вивід з `sorted_keys`, універсальні парсери в усіх мовах (.NET `System.Text.Json`, JS `JSON.parse`, Python `json`), підтримка JSON Schema валідації, відсутність проблем з implicit typing.

### Як забезпечити стабільний, детерміністичний вивід для Git

Проблеми Frappe (volatile `modified` timestamps, мінливий `field_order`) та 1С (фантомні зміни `commandInterface`) мають чіткі рішення:

- **Серіалізація з `sorted_keys`** і фіксованим відступом (2 пробіли) — `JsonSerializerOptions { WriteIndented = true, PropertyNamingPolicy = CamelCase }` у .NET, з кастомним `JsonConverter` для стабільного порядку масивів
- **Ніяких volatile даних** у файлі: жодних timestamps, автоінкрементних idx, чексум. Тільки семантичні дані
- **Canonical JSON**: масиви атрибутів сортувати за `name` — гарантований однаковий вихід при тому самому наборі полів
- **Trailing newline** в кінці файлу (Git-конвенція)
- **Окремий файл на об'єкт** — зміна довідника «Товари» не торкається файлу документа «Замовлення»
- **JSON Schema валідація** у CI/CD — `$schema` поле у кожному файлі вказує на метасхему, що валідує структуру

### Чи потрібен подвійний формат

На старті — **ні**. JSON є і машинним, і людиночитабельним форматом. Якщо в майбутньому з'явиться потреба у DSL-представленні (наприклад, для швидкого скаффолдингу через CLI), можна додати **BRD Schema Language** як sugar-синтаксис, що компілюється у той самий JSON. Це підхід Prisma (PSL → DMMF JSON) і Drizzle (TypeScript → JSON snapshot). JSON залишається canonical format, DSL — зручний вхід.

Пріоритетний порядок інвестицій:

- **Фаза 1**: JSON + JSON Schema метасхеми + детерміністична серіалізація + валідація в CI
- **Фаза 2**: React-візуальний редактор, що генерує JSON (основний UX продукту)
- **Фаза 3** (за потреби): Легковагий DSL для CLI/text editing, що компілюється в JSON

### Чому саме JSON, а не інші варіанти — підсумок

JSON забезпечує **найнижчий поріг входу** для контриб'юторів (не треба вивчати DSL), **найширший тулінг** (.NET, TypeScript, Python парсери з коробки, JSON Schema валідація, react-jsonschema-form для прототипів UI), **найкращу кросплатформність** (Tauri 2.0 на Rust, .NET 8 бекенд, React фронтенд — усі нативно працюють з JSON), і **достатню людиночитабельність** при правильному форматуванні. Це рішення, яке можна прийняти зараз і масштабувати потім — на відміну від DSL, який вимагає значних початкових інвестицій і складно змінювати після того, як спільнота почне його використовувати.
