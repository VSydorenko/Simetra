# Карта перевикористання: що беремо готовим, що копіюємо, що будуємо самі

- **Дата.** 2026-09-30.
- **Метод.** Реконі за ярусами й адверсарні верифікатори за першоджерелами, плюс вибіркові перевірки через npm і GitHub.

- **Статус.** Затверджено власником 30.09.2026. Пункти розділу 12 розв'язано за рекомендаціями документа; єдине лишається відкритим питанням до П3 — UUID v7 для id рядків.

Позначки в колонці «Рішення»:

- **залежність** — ставимо як пакет або інструмент
- **копіюємо код** — з атрибуцією, лише MIT / Apache / BSD / ISC
- **ідеї** — читаємо, переносимо принцип, код не копіюємо
- **будуємо самі** — диференціатор або немає придатного рішення
- **відхилено**

## 1. Головне

- **Рушій схеми не пишемо.** Каталожний diff, план, доказ і застосування дає `@supabase/pg-delta` (TypeScript; ліцензія — у рядку таблиці нижче; той самий рушій, що стоїть за `supabase db diff` у нових проєктах). Він закріплюється точною alpha-версією і ховається за нашим портом `SchemaEngine`. Ціна: рушій ніколи не розбирає SQL, тож план потребує тіньової бази. Це змінює стадію 6 компілятора.
- **Типи `Database` генеруємо без бази.** Supabase виніс генератор у `@supabase/postgrest-typegen` (MIT): він приймає чисті дані, а не з'єднання, тож компілятор будує його вхід зі знімка метаданих. Форма типу гарантовано збігається з тією, яку чекає supabase-js.
- **Цільова база Postgres 17.** Supabase збирає лише образи 15 і 17 (первинне джерело: конфіг збірки образів). Можливості Postgres 18 (uuidv7, temporal-ключі) не можуть бути умовою для типового адаптера.
- **Один форм-движок, одна бібліотека примітивів, одна DnD.** TanStack Form, shadcn на Base UI (Radix сповільнився, shadcn офіційно має варіант на Base UI), pragmatic-drag-and-drop. Дублікати відхилено.
- **Диференціатор будуємо самі, і він невеликий.** Реєстр видів і стадії компілятора, планувальник намірів (UUID, фази, патчі), рендерер бажаного стану, оболонка проведення, підсумки й віртуальні таблиці регістрів, RLS-шаблони скоупу, нумерація, контракти CardShell і ListShell з деривацією екранів із метаданих. Усе інше збирається.
- **Вбудоване замість мікрозалежностей.** Node 24 має `util.styleText` і `crypto.randomUUID`; топологічне сортування, серіалізатор з порядком ключів і JSON Pointer коштують по кілька десятків рядків.
- **Ліцензійна межа тепер жорстка й задокументована.** Код лише з MIT, Apache-2.0, BSD, ISC, PostgreSQL License; копілефт і source-available лише ідеями; NocoBase не читаємо взагалі (його ліцензія прямо забороняє будувати на ньому low-code платформи).

## 2. Правила перевикористання

- **Закріплення версій.** Усе, що в статусі alpha, beta або 0.x (pg-delta, postgrest-typegen, TanStack DB, react-data-grid, citty, tsdown), закріплюється точною версією без каретки. Оновлення проходить через контрактні тести Simetra на корпусі наших згенерованих схем, а не через оновлення lock-файлу.
- **Порт над кожною нестабільною залежністю.** Згенерований код і яруси звертаються до контрактів Simetra (`SchemaEngine`, адаптер джерела, `GridAdapter`, форм-фасад), а не до внутрішнього API бібліотеки. Заміна бібліотеки не торкається метаданих і екранів.
- **Копіювання коду.** Лише з репозиторію, де є файл LICENSE із перелічених ліцензій; файл `THIRD_PARTY_NOTICES` у корені з рядком copyright кожного джерела; заголовок у кожному скопійованому файлі з джерелом і ліцензією; модифіковані копії позначаються. Для GPL, LGPL, AGPL, BSL, FSL, PolyForm і власних ліцензій діє clean-room: читаємо документацію й поведінку, не переписуємо структуру коду.
- **Ліцензійні розбіжності перевіряються по файлу LICENSE, а не по npm.** Приклади з дослідження: postgres-meta (LICENSE Apache-2.0, npm MIT), drizzle-kit (корінь Apache-2.0, пакет MIT), GitHub API повертає «не визначено» для monorepo без кореневого LICENSE (pg-toolbelt, Supabase CLI).

> **Архітектурний наслідок.** Стадії 1–5 компілятора лишаються чистою функцією без бази. Стадія 6 (план) потребує доступної тіньової бази: CLI, MCP і Vite-плагін планують лише за наявності локального стеку. Альтернатива, яку обрала Prisma Next (повністю офлайн-diff за знімками контракту на диску без тіньової бази), вимагає власної повної моделі DDL, тобто саме того, чого ми уникаємо. Свідомий вибір: онлайн-план ціною локального Postgres.

## 9. Що будуємо самі

Це і є платформа. Список короткий, і кожен пункт спирається на готові блоки з таблиць вище.

1. **Реєстр видів і стадії компілятора**: Zod-схеми видів, стандартні реквізити з налаштувань виду, фізичний знімок, резолв посилань за UUID, каскад перейменування, діагностика з кодами, канонічний форматер файлів, JSON Schema на кожен вид.
2. **Рендерер бажаного стану**: з фізичного знімка в декларативний CREATE-DDL, RLS-шаблони скоупу й прав у некорельованій формі, явні гранти, оболонка проведення, тригери підсумків, віртуальні таблиці регістрів, нумерація, обгортки запитів рухів.
3. **Планувальник намірів над `SchemaEngine`**: перейменування як нуль DDL, класифікація змін (expand, contract, destructive, data), фази, патчі даних pre/post, лінт деструктивних змін, marker і ledger у базі, оркестрація тіні.
4. **Генерація тестів**: pgTAP-набори з метаданих (політики за ролями й скоупом, гранти, рухи, узгодженість підсумків) і тонкий Vitest-раннер.
5. **Фасад рантайму даних**: контракт адаптера джерела, PostgREST-адаптер з embed і keyset, мапінг логічних імен, ключі скоупу, відновлення після розриву, команди над RPC з версією рядка, схеми Zod для рядків, форм і URL з метаданих.
6. **Контракти CardShell і ListShell** з деривацією «метадані → екран», слот-системою, RefPicker, `GridAdapter` для табличних частин, shell з навігацією з метаданих, збереженими видами.
7. **Студія і MCP** як тонкі поверхні над тим самим API компілятора.

## 11. Рішення на розсуд архітектора

Власник делегував решту рішень. Ось що я ухвалюю, кожне з однією причиною.

1. **pg-delta як єдиний рушій за портом, точний pin alpha, перейменування вимкнено.** Єдиний TS-рушій із повним покриттям RLS, функцій, тригерів і ACL; ризик alpha ізолюється портом і контрактними тестами.
2. **Стадія 6 компілятора онлайн.** План потребує тіньової бази: co-located у проді, локальний Supabase у dev і CI. Офлайн-diff означав би власну модель DDL.
3. **PG17 як цільова версія, PG18 як опційна гілка генератора.** Supabase збирає лише 15 і 17.
4. **Realtime лише як сигнал.** Один broadcast на команду з ключами; дані перечитуються через API.
5. **Типи `Database` через postgrest-typegen, логічні типи власним емітером.** Форма типів збігається з очікуваннями supabase-js без бази.
6. **TanStack Form як єдиний форм-движок; shadcn на Base UI; RAC лише для дат.** Одна бібліотека на роль.
7. **TanStack Table для списків, react-data-grid за GridAdapter для табличних частин.** Редагування з клавіатурою в 1С-стилі готове, а ризик beta закритий адаптером і точним pin.
8. **pragmatic-drag-and-drop, headless-tree, cmdk, xyflow + dagre, Monaco ліниво.** Стабільні, пермісивні, без дублювання.
9. **Canary через pkg.pr.new, реліз на merge, без changesets.** Збігається з моделлю доставки спеки §11.
10. **Вбудоване замість мікрозалежностей.** styleText, randomUUID, власні toposort, серіалізатор і pointer.
11. **Політика копіювання** з розділу 2 стає правилом репо: THIRD_PARTY_NOTICES, заголовок у файлі, перелік дозволених ліцензій, clean-room для решти.

## 12. Що лишається за власником

- **Залежність у статусі alpha в ядрі.** Я вважаю ризик прийнятним за умов пункту 1 вище; якщо ні, запасний шлях — власна інтроспекція лише для класів об'єктів, які генерує Simetra, і pgschema як рушій. Це помітно дорожче.
- **Імпорт із 1С через mdclasses (LGPL) як зовнішній процес.** Юридична оцінка запуску LGPL-інструмента без копіювання коду; не для першої віхи.
- **UUID v7 для id рядків.** Спека не вимагає; v7 дає локальність індексу, v4 є вбудованим. Пропоную v4 для метаданих і відкрите питання для рядків до П3.
- **Де живе політика копіювання.** AGENTS.md (правило для агентів) чи CONTRIBUTING (правило для людей). Пропоную обидва: коротке правило в AGENTS.md з посиланням на CONTRIBUTING.
