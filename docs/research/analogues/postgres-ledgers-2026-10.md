# Регістри й облікові журнали на Postgres: прецеденти

## Про цей документ

- **Питання.** Як відкриті проєкти й інженерні команди ведуть залишки, обороти й проводки нативно в Postgres — що з їхніх форм годиться для згенерованих регістрів Simetra, що відкинути і що можна копіювати за ліцензією.
- **Дата.** 2026-10-01.
- **Метод.** Читання вихідного коду й документації проєктів (локальні клони в тимчасовій теці, у репо не потрапляють), інженерних публікацій за першоджерелами; ліцензії — з файлів `LICENSE` у репозиторіях (`CONTRIBUTING.md` § «Copying code from other projects»).
- **Джерела.** Названо в тексті з URL.
- **Куди лягли рішення.** [Спека «Платформа в Postgres»](../../superpowers/specs/2026-10-01-platform-in-postgres-design.md) (Р26 — форма підсумків, тригер, межа моменту); платформна спека §15.
- **Статус.** Контекст рішень, не правила.

## 1. Головні висновки

1. **Обороти за період замість накопичених залишків** — спільна форма 1С (помісячні підсумки) і `pg_accumulator`: проведення заднім числом зачіпає один період, а залишок на дату читається з обмеженої кількості рядків. Накопичений залишок у кожному рядку руху (`pgledger`, Formance) дешевий у читанні «зараз», але ламається каскадом при записі в минуле.
2. **Тригер на рівні оператора з таблицями переходів**, що агрегує дельти за ключем і робить upsert у відсортованому порядку, — правильна форма ведення підсумків: один запис на ключ за оператор, без взаємних блокувань.
3. **Контроль балансу й режим дельт — взаємовиключні** (Modern Treasury): синхронна перевірка потребує блокування рядка підсумку; гарячий ключ лікують лише асинхронним згортанням, і тоді перевірки «на льоту» немає.
4. **`pg_ivm` для підсумків не годиться**: ексклюзивне блокування всього подання після кожної зміни базової таблиці, без секціонування.
5. **Код копіювати не варто, форми — так.** Жоден прецедент не ставиться на цільових провайдерів як є (`pg_accumulator` — C і фоновий воркер) або не має потрібної ліцензії (гісти без ліцензії, LedgerSMB — GPL). Генератор Simetra пише SQL за власними шаблонами, запозичуючи форму з атрибуцією ідей у цьому документі.

## 2. `pg_accumulator`

Репозиторій: https://github.com/Treedo/pg_accumulator (ліцензія PostgreSQL; один автор, кілька місяців історії, версія 1.2 на дату перевірки; pgTAP-тести).

**Що правильне й збігається з 1С і Simetra:**

- рухи — лише додаванням; `UPDATE` рухів заборонено тригером; розпроведення — видалення за реєстратором, перепроведення — видалення й вставка в одній транзакції;
- підсумки — обороти за день, місяць і рік плюс окремий кеш поточного залишку; залишок на дату = роки до + місяці року + дні місяця + рухи дня;
- тригери `AFTER … FOR EACH STATEMENT REFERENCING NEW TABLE / OLD TABLE`, агрегат за ключем і один upsert на ключ;
- `register_verify` зі статусами розбіжностей і функції перебудови;
- похідні таблиці захищені від прямого запису тригером.

**Вади реалізації, через які це джерело форми, а не залежність:**

| Вада | Доказ у коді | Наслідок |
| --- | --- | --- |
| ключ підсумків — 64-бітний хеш рядкової конкатенації вимірів з роздільником | функція хешу `hashtextextended(dim1::text \|\| '\|' \|\| dim2::text …)` | колізія конструктивна, не лише ймовірнісна: виміри `('a\|b','c')` і `('a','b\|c')` дають один ключ |
| бакет періоду без часового поясу | `date_trunc('month', period)`, `period::date` | сеанси з різним `TimeZone` кладуть рухи в різні місяці |
| порядок upsert не зафіксований | `INSERT … SELECT … GROUP BY … ON CONFLICT` без `ORDER BY` | можливі взаємні блокування при паралельному проведенні (не відтворювалось) |
| порожніх вимірів немає | `register_post`: «dimension is required» | головна семантична потреба 1С не розв'язана |
| нульові рядки не видаляються | тригер видалення лише віднімає | підсумки розростаються |
| DDL у рантаймі | `register_create` будує таблиці через `EXECUTE format` | суперечить Р6 Simetra: бажаний стан рендерить компілятор |
| C-частина, `superuser = true`, фоновий воркер через `shared_preload_libraries` | `pg_accumulator.control`, `src/bgworker` | не ставиться на цільових провайдерів |
| `repost` описано як «лише чиста дельта» | реалізація — `unpost` + `post` цілком | — |

**Що взято в Simetra (форма, не код):** структура «обороти за місяць + поточні залишки» (без рівнів «день» і «рік»), тригер на таблицях переходів із відсортованим upsert і видаленням нульових рядків, алгоритм залишку на дату й оборотів за діапазон, `verify`/`rebuild` як контракт виду, тестові сценарії (заднім числом, перепроведення, узгодженість). Що змінено: ключ — справжні виміри з носієм скоупу першим і `UNIQUE NULLS NOT DISTINCT`; бакет — у поясі проєкту; результат віртуальних таблиць — рядки з групуванням, а не один `jsonb`; межа «момент + реєстратор».

## 3. Інші проєкти

- **`pgledger`** (MIT, https://github.com/pgr0ss/pgledger) — баланс у рядку рахунку з версією; переказ блокує рахунки `FOR UPDATE` у відсортованому порядку (без взаємних блокувань); перевірка «від'ємний баланс заборонено» після оновлення з відкатом. Заявлені автором заміри на локальному PG 17: порядок кількох тисяч переказів за секунду, падіння близько 30% на гарячих рахунках (https://pgrs.net/2025/05/16/pgledger-in-postgresql-is-fast/). Взято: стабільний порядок блокування ключів.
- **Formance Ledger** (MIT, https://github.com/formancehq/ledger) — append-only рухи з накопиченими обсягами в рядку, `fillfactor` для таблиць, що часто оновлюються. Взято: нижчий `fillfactor` для таблиць підсумків як перший крок проти гарячих рядків.
- **`pg_ivm`** (PostgreSQL, https://github.com/sraoss/pg_ivm) — інкрементальні матеріалізовані подання: у READ COMMITTED бере `ExclusiveLock` на подання після зміни базової таблиці, базові таблиці не можуть бути секціонованими. Відхилено для підсумків.
- **Гісти «double-entry in Postgres»** (без ліцензії — лише ідеї): оригінал NYKevin (https://gist.github.com/NYKevin/9433376) — баланси в матеріалізованому поданні з повним `REFRESH` на кожен оператор, антипатерн (коментатори: секунди на сотні тисяч рядків); варіант sundbry (https://gist.github.com/sundbry/80edb76658f72b7386cca13dd116d235) — відкладений тригер обмеження, що в момент коміту перевіряє «дебет = кредит» журналу, і «запечатаний журнал» (проводки лише в транзакції створення). Взято: відкладена перевірка в момент коміту як форма контролю інваріантів набору рядків.
- **LedgerSMB** (GPL — лише ідеї): уся логіка в збережених процедурах; зміна сигнатури вимагає `DROP`, тож генерація функцій має вестися детерміновано разом зі зміною сигнатур; API приймає всі входи операції атомарно; тести — pgTAP.

## 4. Інженерні публікації

- **Modern Treasury** (https://docs.moderntreasury.com/docs/handling-concurrency, https://moderntreasury.com/journal/behind-the-scenes-how-we-built-ledgers-for-high-throughput): три кеші балансу (поточний, на кінець дня, після кожного запису); синхронний запис з умовою на баланс бере блокування рядка, гарячі рахунки — лише асинхронно через чергу; версійне й балансове блокування розрізнено. Взято: `balanceControl` і режим дельт — взаємовиключні.
- **Square Books** (https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/): баланс у рядку книги — єдина змінна таблиця. **Stripe** (https://stripe.dev/blog/ledger-stripe-system-for-tracking-and-validating-money-movement): незмінний журнал, баланс відтворюється програванням, коректність — клірингові рахунки. **Uber LedgerStore** (https://www.uber.com/en-IE/blog/how-ledgerstore-supports-trillions-of-indexes): повнота перевіряється контрольними сумами за вікнами. Взято: `verify` як регулярна перевірка, не лише ручна.
- **Shopify inventory** (https://shopify.engineering/scaling-inventory-reservations): рядок на одиницю плюс `SKIP LOCKED` для резервувань — окремий механізм, не підсумки.
- **Нумерація без пропусків** (https://www.cybertec-postgresql.com/en/postgresql-sequences-vs-invoice-numbers/; `nextval` не відкочується — postgresql.org/docs/17/functions-sequence.html): таблиця-лічильник, оновлювана в транзакції, серіалізує транзакції одного лічильника — свідома ціна, та сама, що в 1С.
