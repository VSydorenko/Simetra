# Мультимовні дані: форми зберігання, прецеденти, механізми Simetra

> **Про цей документ.** Контекст рішень ADR-0111…ADR-0114, не правила. Правила —
> [спека мультимовних даних](../../superpowers/specs/2026-11-24-multilingual-data-design.md).
> Дата перевірки — 2026-11-24, код `main` 014a48e8.

## Питання

Як універсальна платформа бізнес-застосунків зберігає значення текстових
реквізитів кількома мовами даних, якщо набір мов — дані, а всі механізми
платформи (обмеження, сортування, пошук, права, синхронізація, представлення
посилань) уже побудовані на колонці шапки.

## Форми зберігання

| Форма | Суть |
| --- | --- |
| A | основна мова в колонці шапки + таблиця перекладів для інших мов |
| B | усі мови, разом з основною, у таблиці перекладів; шапка без тексту |
| C | `jsonb` на реквізит `{код: значення}` у шапці |
| D | одна загальна таблиця (сутність, поле, мова, значення) — EAV |
| E | колонки на мову (`name_lang1`, `name_lang2`) |

## Прецеденти

- **Odoo 16** перейшов з EAV `ir.translation` на `jsonb` у таблиці моделі; кожне непорожнє значення мусить мати ключ `en_US` — fallback для інших мов. Причини — швидше читання й тріграмний пошук будь-якою мовою; ціна — повільніший імпорт перекладів (https://mergebot.odoo.com/odoo/odoo/pull/97692).
- **Business Central** — форма A: `Item.Description` у базовій таблиці, `Item Translation` з ключем товар + варіант + мова (https://microsoft.github.io/BCApps/reference/base-application/Table/Microsoft.Inventory.Item.Item-Translation.html).
- **SAP** — текстові таблиці з ключем мови (`MAKT`, `SPRAS`), ближче до B; fallback — «додаткова мова» (вторинні джерела: https://leanx.eu/en/sap/table/makt).
- **Dataverse** — загального перекладу даних немає: локалізовні лише кілька атрибутів продуктів (https://learn.microsoft.com/en-us/dynamics365/sales/developer/localize-product-property-values). **Frappe** — переклад лише рядків інтерфейсу.
- **1С БСП «Мультиязычность»** — додаткові реквізити `НаименованиеЯзык1/2` (форма E); деталі з ITS не підтверджено.
- **Фреймворки:** Rails Mobility пропонує табличний, key-value, колонковий і `jsonb` бекенди й називає ціну табличного — JOIN на мову (https://github.com/shioyama/mobility/wiki/Table-Backend); django-parler і Directus — таблиця перекладів з ключем (батько, мова).
- **Попереднє дослідження e-commerce проєкту** (2026-10, PG17, 50k рядків × 5 мов): аналітики радили A (≈60/40), обрано B за критеріями симетрії мов і «одна колонка на поле»; B повільніша на сирих читаннях, перехід A↔B на 50k рядків — секунди; три класи дефектів A без правил ядра — текст мови у двох місцях, неявна мова запису, зміна мови джерела переносить текст; колізію адреси сторінки через fallback не ловила жодна форма.

## Сортування мовою L з fallback

`coalesce(переклад, джерело)` охоплює дві таблиці, тож індексу для нього немає; під RLS `CoalesceExpr` не leak-safe (postgres `REL_17_STABLE`, `optimizer/util/clauses.c`). Leakproof у 17.12: `texteq`, `text_lt/le/gt/ge`, `bttextcmp`, `starts_with`, `uuid_*`; не leakproof: `lower`, `left`, `textlike`. Розглянуто: щільні рядки з видимим значенням (обрано, ADR-0112), розріджені рядки з переглядом скоупу, гібрид, окрема колонка `<col>_effective`.

## Відкрите на момент дослідження

- Чи діє складений індекс `(language_id, префікс)` під політикою членства з підзапитом — доводить блок B1 спеки.
- Вбудовування view у PostgREST не перевірено; читання мовою L у адаптері PostgREST іде через Server Function.
