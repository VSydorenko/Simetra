# Модель мережевого навантаження клієнтських даних T4

## Про цей документ

- **Питання:** скільки запитів, байтів і операторів бази дають типові
  сценарії клієнта T4 за редакцією 3 спеки П4-B і що з цього прибирають
  умовне перечитування, пакет читань, стиснення й обмеження частоти.
- **Дата:** 2026-11-08.
- **Метод:** аналітична модель над виміряними числами. Розмір рядка й
  стиснення — синтетичний рядок довідника (15 колонок: два UUID, версія,
  код, назва, контакти, `Numeric`, `DateTime`, ознаки), JSON форми передачі,
  Node 24 `zlib` (gzip рівень 6, brotli якість 4). Робота бази — Postgres 17
  в окремому одноразовому контейнері, таблиця на 1 млн рядків у п'яти
  скоупах, політика RLS за множиною скоупів користувача, `EXPLAIN (ANALYZE,
  BUFFERS)` під роллю читача. Кількість операторів читання — з коду T3
  (`packages/simetra/src/server/runtime.ts`, `readRows`). Затримки — зі звітів
  спайків ([realtime](../../superpowers/specs/2026-11-08-t4-realtime-spike-report.md),
  [UI й SSR](../../superpowers/specs/2026-11-08-t4-ux-spike-report.md),
  [вікно](../../superpowers/specs/2026-11-08-t4-window-spike-report.md)).
- **Куди лягли рішення:** [спека П4-B](../../superpowers/specs/2026-11-05-p4-b-client-data-design.md)
  Рд39–Рд45, §4.1, §4.5, §6.7, §12, §13; [платформна
  спека](../../superpowers/specs/2026-09-24-simetra-platform-design.md) Р42.
- **Статус:** вхід поправки «швидкодія й мінімальне мережеве навантаження».
  Числа — порядок величини для синтетичного рядка, а не бюджет. Бюджети
  задає спека як відношення до корисних байтів (§12 П4-B).

## 1. Виміряні величини

| Величина | Значення | Джерело |
| --- | --- | --- |
| рядок списочної форми в JSON передачі | 471 Б | синтетичний рядок, 15 колонок |
| сторінка 100 рядків (`{ ok, value: { rows }, serverHash }`) | 47,7 КБ; gzip 9,8 КБ; brotli 8,7 КБ | `zlib` |
| та сама сторінка стовпцями (`columns` + масиви) | 31,9 КБ; gzip 9,4 КБ; brotli 8,7 КБ | `zlib` |
| відповідь «усі 100 рядків не змінено» — індекси | 0,4 КБ | `zlib` |
| відповідь «усі 100 рядків не змінено» — UUID ключів | 4,0 КБ | `zlib` |
| запит `known` на 100 ключів (ключі й версії) | 4,6 КБ; браузер тіло запиту не стискає | `zlib` |
| оператори Postgres на одне читання | 6 + 1 на кожну ціль `include` (`BEGIN`, `statement_timeout`, claims, `SET LOCAL ROLE`, `SELECT`, `COMMIT`) | `readRows` |
| keyset-сторінка за неіндексованим полем, 1 млн рядків, RLS | 2 373 мс, 403 тис. буферів (повне сканування видимих і top-N) | `EXPLAIN` |
| те саме з індексом `(скоуп, поле, ключ)` і фільтром скоупу | 1,0 мс, 106 буферів | `EXPLAIN` |
| без фільтра скоупу (список двох скоупів) з тим самим індексом | 131 мс (сортування 200 тис.) | `EXPLAIN` |
| без фільтра скоупу з індексом `(поле, ключ)` | 1,8 мс | `EXPLAIN` |
| 200 ключів, рядок цілком (`to_jsonb`) | 6–7 мс | `EXPLAIN`, теплий кеш |
| 200 ключів, списочна проєкція | 2,6–3,3 мс | `EXPLAIN` |
| 200 ключів умовно, усі не змінені | 1,5–3,0 мс | `EXPLAIN` |
| `run` → відповідь | ≈ RTT | спайк realtime |
| `run` → сигнал → пачка → перечитування | ≈ 2×RTT + 50 мс | спайк realtime |

Висновки вимірів:

- **Стиснення** зменшує сторінку вп'ятеро. Стовпцеве кодування дає −33 %
  без стиснення, а зі стисненням — нічого: брати його не варто.
- **Умовна відповідь** на незмінну сторінку в 100 разів менша за повну.
  Тепер основна вага — у запиті (`known`), бо браузер не стискає тіла
  запиту.
- **Робота бази** від умовного читання падає лише вдвічі: RLS і вибірку
  рядка за ключем база робить однаково. Економія — серіалізація й мережа, а
  не пошук. Тому окремий індекс `(id, version)` не потрібен: під RLS
  потрібен доступ до рядка за колонками політики, а не лише за індексом.
- **Порядок без індексу** на великій таблиці — повне сканування видимої
  множини на кожну сторінку (секунди). Індекс повинен містити скоуп першим
  для списку одного скоупу й не містити його для списку кількох скоупів.

## 2. Сценарії: редакція 3 проти поправки

Позначення: `V` — видимі вигляди списку вкладки; вікно тримає власними
видимі сторінки ± 2, тобто ≈ 5 сторінок по 100 рядків. Байти — нестиснені
JSON форми передачі; оператори — оператори Postgres. Після поправки читання
коштує `BEGIN`, один оператор налаштування, по оператору на частину й
`COMMIT` (§4.5 П4-B).

| Сценарій | Редакція 3: запити / байти / оператори | Після поправки: запити / байти / оператори |
| --- | --- | --- |
| SSR-вхід зі списком: після гідратації | 2 (`version`, з B5 `rights`) / < 2 КБ / 6 (`version` бази не питає) | 1 (пакет `version` + `rights`) / < 2 КБ / 4 |
| відкриття списку без SSR, 2 `include`, `count` | 4 (сторінка, потім цілі двох об'єктів, `count`) і 2 RTT / 48 КБ + цілі / 24 | 1 і 1 RTT / ті самі корисні байти / 7 |
| прокрутка на нову сторінку | 1 / 47,7 КБ / 6 | 1 / 47,7 КБ / 4 |
| повернення до сторінки-знімка показу | 1 / 47,7 КБ / 6 | 1 / запит 4,6 КБ, відповідь 0,4 КБ / 4 |
| картка з 2 ТЧ (по 20 рядків) і 2 `include` | 5 і 2 RTT / ≈ 15 КБ / 30 | 1 і 1 RTT / ≈ 15 КБ / 8 |
| повторне відкриття тієї самої картки, нічого не змінено | 5 / ≈ 15 КБ / 30 | 1 / < 1 КБ / 8 |
| правка поля, `await` | 1 `run` / рядок результату | без змін |
| власне відлуння сигналу | 0 | 0 |
| чужий сигнал: пачка ключів двох об'єктів | 2 / змінені рядки / 12 | 1 / змінені рядки / 5 |
| системне перечитування вікна (`revalidate`) | ≈ 8 (за ключами + keyset кожної сторінки) / ≈ 480 КБ / 48 | 1 / запит 23 КБ, відповідь 2 КБ / 8 |
| системне перечитування `full` на 5 000 рядків | 25 послідовних keyset-сторінок / 2,4 МБ / 150 | 2 пакети / запит 230 КБ, відповідь 40 КБ / 31 |
| фокус вкладки (`resume()`), на кожен фокус | як `revalidate` × `V` | ≤ 1 запит не частіше за 15 с |
| інтервал `revalidateIntervalMs` (60 с), видима вкладка | `revalidate` × `V` щохвилини | 1 пакет щохвилини на рантайм |
| прихована вкладка | 0 | 0 |
| повторне приєднання без `recovered` | `revalidate` × `V` + 2 | 1 пакет |

**Масштаб.** 1 000 активних користувачів, у кожного видимий один список з
вікном:

| | Редакція 3 | Після поправки |
| --- | --- | --- |
| запитів на сервер від інтервалу | ≈ 133 за секунду | ≈ 17 за секунду |
| операторів Postgres від інтервалу | ≈ 800 за секунду | ≈ 133 за секунду |
| вихідний трафік від інтервалу (нестиснений) | ≈ 8 МБ/с | ≈ 0,03 МБ/с (вхідний ≈ 0,4 МБ/с) |
| трафік клієнта за годину видимого списку | ≈ 28 МБ | ≈ 1,5 МБ |

Фокус вкладки в редакції 3 коштує стільки ж, скільки інтервал, на кожне
перемикання вікна: користувач, що перемикається між поштою й застосунком
двадцять разів за годину, тягне ще ≈ 10 МБ.

## 3. Розглянуті механізми

| Механізм | Висновок |
| --- | --- |
| умовне читання `known` (ключ → версія) | брати: відповідь незмінного рядка — індекс замість тіла |
| дайджест сторінки (хеш послідовності `(ключ, версія)`) | відкласти: зменшив би запит `full` з 230 КБ до одиниць КБ, але потребує другого обміну на розбіжності; додається необов'язковим полем запиту без зламу, коли бюджет `full` цього вимагатиме |
| пакет читань в одній транзакції `REPEATABLE READ READ ONLY` | брати: один виклик функції, одне з'єднання пулу, один знімок бази для всіх частин екрана |
| `include` у тому самому запиті, що й сторінка | брати: прибирає залежний другий RTT на відкритті списку |
| стовпцеве кодування рядків | не брати: зі стисненням виграшу немає |
| стиснення відповідей на краю host-а | брати: brotli чи gzip від 1 КБ; T3 не стискає |
| HTTP/2 | уже дає мультиплексування й стиснення заголовків; роботи сервера на запит не зменшує, тож пакет потрібен |
| індекс `(id, version)` | не брати: під RLS виграшу немає |
| індекс під кожен порядок списку з вікном | брати для оголошених порядків; DB-тест плану |
| мінімальний інтервал перечитування на фокус | брати: 15 с |
| лідер вкладки | лишається за потребою (§6.3 П4-B): приховані вкладки вже не перечитують |
